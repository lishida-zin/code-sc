# Level 9: チーム開発・プロジェクト管理

> **目標**: チームで高品質なソフトウェアを継続的に届けられるエンジニアになる
> **関連資格**: IPAプロジェクトマネージャ試験、PMP、認定スクラムマスター(CSM)

## なぜチーム開発を学ぶのか？

```
「優れたエンジニア」と「優れたチームプレイヤー」は違う

❌ 一人で完璧なコードを書ける → チームで成果が出ない
⭕ チームの生産性を最大化できる → 組織全体の品質が向上
```

**シニアエンジニアの視点**:
- 技術力だけではシニアになれない
- AI時代こそ「人間ならでは」のスキルが差別化要因
- チームの成果 > 個人の成果

## Level 9 完了時の到達目標

### コードレビュー（及びプロセスレビュー）で指摘できること

1. **プロセスの問題**
   - アジャイルの形骸化（レトロが形だけ、ベロシティのノルマ化）
   - PR運用の問題（巨大PR、レビュー遅延、形式的レビュー）
   - 振り返りの不足

2. **コミュニケーションの問題**
   - 意思決定の不透明さ（ADR/RFCの欠如）
   - 知識の属人化
   - ドキュメント不足/陳腐化

3. **運用の問題**
   - SLI/SLOの未定義
   - インシデント対応の属人化
   - オブザーバビリティの不足

4. **組織の問題**
   - 技術的負債の放置
   - 育成・メンタリングの不足
   - バーンアウトの兆候

### 実務で活かせるスキル

| スキル | 活用場面 |
|--------|---------|
| アジャイル推進力 | チームのプロセス改善 |
| レビュー設計力 | コードレビュー文化の構築 |
| コミュニケーション設計力 | チームの情報共有最適化 |
| プロジェクト管理力 | リスク管理、スケジュール管理 |
| SRE実践力 | 本番サービスの信頼性向上 |

## よくある現場の間違い（レビューで見抜くポイント）

```
# ❌ よくある間違い1: ベロシティをノルマにする
「今スプリントのベロシティは30だから、次も30以上出してね」
→ チームが見積もりを膨らませる、品質低下

# ⭕ 正しいベロシティの使い方
「過去5スプリントの平均ベロシティは28。
次スプリントも同じくらいの計画にしよう」
→ 予測ツールとして使用
```

```
# ❌ よくある間違い2: ブレームフルなPost-mortem
「この障害はAさんがデプロイしたから起きた。
次からAさんは本番デプロイ禁止」
→ 報告を恐れる文化、問題の隠蔽

# ⭕ ブレームレスPost-mortem
「デプロイ時にカナリアリリースがなかった。
カナリアリリースを導入し、自動ロールバックを設定する」
→ システムの改善、心理的安全性
```

```
# ❌ よくある間違い3: 監視 = オブザーバビリティ
「CPUとメモリのアラート設定したから、監視はOK」
→ 「何が起きているか」がわからない

# ⭕ オブザーバビリティの実践
「ログ（何が起きた）、メトリクス（どの程度か）、
トレース（どの経路で起きた）の3本柱で
予測できなかった問題も調査できる」
→ 未知の問題にも対応可能
```
