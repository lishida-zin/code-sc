テストピラミッド

テストには「ピラミッド」という考え方があります。 建物と同じで、土台がしっかりしていれば安定するのです。

なぜ「ピラミッド」と呼ぶ？

ピラミッド = 底辺が広く、頂上が狭い

  • 底辺（ユニットテスト）：たくさん書く。速い。安定。
  • 中間（統合テスト）：適度に書く。やや遅い。
  • 頂上（E2Eテスト）：少なく書く。遅い。不安定になりやすい。

エジプトのピラミッドを想像してください。

底辺が狭くて頂上が広いと、倒れますよね？

テストも同じです。E2Eばかりだと不安定になります。

テストピラミッド（図解）

3種類のテストを比較

種類 テスト対象 実行速度 安定性 比率
ユニットテスト 関数、クラス単体 ミリ秒 高い 70-80%
統合テスト API + DB連携 秒 中 15-25%
E2Eテスト 画面操作（Playwright等） 数十秒 低い 5-10%

レビューで指摘すべきポイント

  • E2E過多：「テストピラミッドが逆転している。ユニットテストを増やすべき」
  • ユニットテストがゼロ：「ビジネスロジックにユニットテストを追加すべき」
  • E2Eだけで全てをカバー：「実行時間が長くなりCIが遅くなる」

逆ピラミッド（アンチパターン）

E2Eテスト: 50件（80%）
統合テスト: 10件（15%）
ユニット: 3件（5%）
// CI実行時間: 30分
// 頻繁にFlakyテスト発生

正しいピラミッド

E2Eテスト: 5件（5%）
統合テスト: 20件（20%）
ユニット: 75件（75%）
// CI実行時間: 3分
// 安定してパス

Vitest基礎

Vitestは、2026年のNode.jsテストの標準ツールです。 Jestより高速で、ESMにネイティブ対応しています。

Vitestとは？

Vitest = Vite + Test

Vite（ヴィート）の高速さをテストにも活かしたツールです。

  • 高速：Jestの約1.5-2倍速い
  • ESMネイティブ：import/exportがそのまま使える
  • Jest互換：既存のJestテストがほぼそのまま動く
  • 設定不要：ゼロコンフィグで始められる

基本構文：describe / it / expect

3つの基本構文を覚えましょう。

構文 意味 由来
describe テストをグループ化 「説明する」
it / test 1つのテストケース 「それは〜する」
expect 期待する結果を検証 「期待する」
基本的なテストの書き方
import { describe, it, expect } from 'vitest';
import { add, multiply } from './math';

// describeでグループ化
describe('math関数', () => {
  // itで1つのテスト
  it('addは2つの数を足す', () => {
    // expectで結果を検証
    expect(add(1, 2)).toBe(3);
    expect(add(-1, 1)).toBe(0);
  });

  it('multiplyは2つの数を掛ける', () => {
    expect(multiply(2, 3)).toBe(6);
    expect(multiply(0, 5)).toBe(0);
  });
});

よく使うマッチャー

マッチャー = 「どう比較するか」を指定するメソッド

マッチャーの例
// 等価比較
expect(value).toBe(3);              // 厳密等価 (===)
expect(obj).toEqual({ a: 1 });      // オブジェクト比較

// 真偽値
expect(value).toBeTruthy();         // truthyな値
expect(value).toBeFalsy();          // falsyな値
expect(value).toBeNull();           // null
expect(value).toBeUndefined();      // undefined

// 数値
expect(value).toBeGreaterThan(3);   // > 3
expect(value).toBeLessThan(10);     // < 10
expect(value).toBeCloseTo(0.3, 5);  // 浮動小数点

// 文字列
expect(str).toContain('hello');     // 含む
expect(str).toMatch(/regex/);       // 正規表現

// 配列
expect(arr).toContain(item);        // 含む
expect(arr).toHaveLength(3);        // 長さ

// 例外
expect(() => fn()).toThrow();       // エラーを投げる
expect(() => fn()).toThrow('msg');  // 特定のエラー

セットアップ：beforeEach / afterEach

テストの前後で処理を実行できます。

セットアップとクリーンアップ

    userService = new UserService();
  });

  // 各テストの後に実行

    userService.cleanup();
  });

  it('ユーザーを作成できる', () => {
    const user = userService.create({ name: 'Alice' });
    expect(user.name).toBe('Alice');
  });
});

Vitestで「各テストの前に実行する処理」を定義するのは？

モックとスタブ

モックとスタブは、テストで「偽物」を使う技術です。 外部依存（API、DB）を切り離してテストできます。

モックとスタブの違い

たとえ話：映画の撮影を想像してください。

  • スタブ = 背景セット。見た目だけ用意する。
  • モック = スタントマン。動きを真似して、どう使われたか記録する。
種類 役割 検証できること
スタブ 決まった値を返す 戻り値のみ
モック 呼び出しを記録 呼び出し回数、引数、順序

vi.fn() - モック関数

vi.fn()は、呼び出しを記録する「偽の関数」を作ります。

vi.fn()の使い方
import { vi, describe, it, expect } from 'vitest';

describe('vi.fn()', () => {
  it('呼び出しを記録する', () => {
    // モック関数を作成
    const mockFn = vi.fn();

    // 呼び出す
    mockFn('hello', 123);

    // 検証：呼ばれたか？
    expect(mockFn).toHaveBeenCalled();

    // 検証：何回呼ばれた？
    expect(mockFn).toHaveBeenCalledTimes(1);

    // 検証：どんな引数で呼ばれた？
    expect(mockFn).toHaveBeenCalledWith('hello', 123);
  });

  it('戻り値を指定する', () => {
    const mockFn = vi.fn().mockReturnValue(42);
    expect(mockFn()).toBe(42);
  });

  it('非同期の戻り値を指定する', async () => {
    const mockFn = vi.fn().mockResolvedValue({ id: 1 });
    const result = await mockFn();
    expect(result).toEqual({ id: 1 });
  });
});

vi.mock() - モジュール全体をモック

vi.mock()は、モジュール全体を偽物に置き換えます。

vi.mock()の使い方
import { vi, describe, it, expect } from 'vitest';
import { sendEmail } from './emailService';
import { createUser } from './userService';

// モジュール全体をモック
vi.mock('./emailService', () => ({
  sendEmail: vi.fn().mockResolvedValue({ success: true }),
}));

describe('UserService', () => {
  it('ユーザー作成後にメールを送信する', async () => {
    await createUser({ email: 'test@example.com' });

    // sendEmailが呼ばれたことを検証
    expect(sendEmail).toHaveBeenCalledWith(
      expect.objectContaining({ to: 'test@example.com' })
    );
  });
});

vi.spyOn() - 既存関数を監視

vi.spyOn()は、既存の関数を「監視」します。

元の動作を保ちつつ、呼び出しを記録できます。

vi.spyOn()の使い方
import { vi, describe, it, expect } from 'vitest';

describe('vi.spyOn()', () => {
  it('console.logを監視する', () => {
    // console.logを監視
    const spy = vi.spyOn(console, 'log');

    console.log('hello');

    expect(spy).toHaveBeenCalledWith('hello');

    // 監視を解除
    spy.mockRestore();
  });

  it('戻り値を上書きする', () => {
    const obj = {
      getValue: () => 'original',
    };

    // spyOnで上書き
    vi.spyOn(obj, 'getValue').mockReturnValue('mocked');

    expect(obj.getValue()).toBe('mocked');
  });
});

モックの使い分け

方法 用途 例
vi.fn() コールバック関数をモック onClick, onSubmit
vi.mock() モジュール全体を置換 API呼び出し、DB操作
vi.spyOn() 既存関数を監視 console.log, Date.now

過剰モック

// 全部モックしている

モック漏れ：外部依存をモックしていない

モック漏れ

// 実際のAPIを叩いている
it('should fetch user', async () => {
  const user = await fetchUser(1);
  // テストが外部APIに依存
});

正しいモック

vi.mock('./api');

it('should fetch user', async () => {
  vi.mocked(fetchUser).mockResolvedValue({
    id: 1, name: 'Test'
  });

  expect(user.name).toBe('Test');
});

APIテスト

APIテストは、HTTPエンドポイントをテストします。 Supertestを使って、リクエスト/レスポンスを検証しましょう。

Supertestとは？

Supertest = HTTPリクエストをシミュレートするライブラリ

  • サーバーを起動せずにテスト可能
  • GET/POST/PUT/DELETEをシミュレート
  • ステータスコード、レスポンスボディを検証
インストール
npm install -D supertest @types/supertest

基本的な使い方

GETリクエストのテスト
import { describe, it, expect } from 'vitest';
import request from 'supertest';
import app from '../app';  // Expressアプリ

describe('GET /users', () => {
  it('ユーザー一覧を取得できる', async () => {
    const response = await request(app)
      .get('/users')
      .expect(200)                          // ステータスコード
      .expect('Content-Type', /json/);      // ヘッダー

    // レスポンスボディを検証
    expect(response.body).toBeInstanceOf(Array);
    expect(response.body.length).toBeGreaterThan(0);
  });

  it('存在しないエンドポイントは404', async () => {
    await request(app)
      .get('/unknown')
      .expect(404);
  });
});

POST/PUT/DELETEのテスト

POSTリクエストのテスト
describe('POST /users', () => {
  it('ユーザーを作成できる', async () => {
    const newUser = { name: 'Alice', email: 'alice@example.com' };

    const response = await request(app)
      .post('/users')
      .send(newUser)                        // リクエストボディ
      .set('Content-Type', 'application/json')
      .expect(201);

    expect(response.body).toMatchObject({
      name: 'Alice',
      email: 'alice@example.com',
    });
    expect(response.body.id).toBeDefined();
  });

  it('不正なデータは400エラー', async () => {
    const response = await request(app)
      .post('/users')
      .send({ name: '' })                   // 不正なデータ
      .expect(400);

    expect(response.body.error).toBeDefined();
  });
});
認証が必要なAPIのテスト
describe('認証が必要なAPI', () => {
  let authToken: string;

  // テスト前にログインしてトークン取得
  beforeAll(async () => {
    const res = await request(app)
      .post('/auth/login')
      .send({ email: 'test@example.com', password: 'password' });

DBテスト

データベースのテストは本番DBを使わないのが鉄則です。 テスト用DBとトランザクションを活用しましょう。

絶対NG：本番DBでテスト

本番DBでテストすると...

  • テストデータが本番に混入
  • 本番データが削除される可能性
  • 顧客情報の漏洩リスク
  • テストの並列実行で競合

絶対NG

// .envの本番DB接続情報をそのまま使う
const db = new Pool({
  connectionString: process.env.DATABASE_URL
  // 本番DBに接続してしまう！
});

正しい方法

// テスト用の環境変数を使う
const db = new Pool({
  connectionString: process.env.TEST_DATABASE_URL
  // テスト専用DBに接続
});

トランザクションでロールバック

パターン：テストごとにロールバック

テスト開始時にトランザクション開始、終了時にロールバック。

データが残らないので、テストが独立する。

トランザクションを使ったテスト
import { describe, it, expect, beforeEach, afterEach } from 'vitest';
import { db } from '../db';

describe('UserRepository', () => {
  let trx: Transaction;

  // 各テスト前にトランザクション開始
  beforeEach(async () => {
    trx = await db.transaction();
  });

  // 各テスト後にロールバック
  afterEach(async () => {
    await trx.rollback();
  });

  it('ユーザーを作成できる', async () => {
    const user = await createUser(trx, { name: 'Alice' });
    expect(user.name).toBe('Alice');
    // ロールバックされるのでDBに残らない
  });
});

Prismaでのテスト

Prismaのセットアップ

import { PrismaClient } from '@prisma/client';
import { beforeAll, afterAll, beforeEach } from 'vitest';

export const prisma = new PrismaClient();

beforeAll(async () => {

afterAll(async () => {
  await prisma.$disconnect();

// 各テスト後にデータをクリーンアップ

正常系のみテストの問題

正常系のみ

異常系も含む

describe('divide', () => {
  it('10 / 2 = 5', () => {
    expect(divide(10, 2)).toBe(5);
  });

  it('0で割るとエラー', () => {
    expect(() => divide(10, 0)).toThrow();
  });

  it('負の数も計算できる', () => {
    expect(divide(-10, 2)).toBe(-5);
  });

境界値テスト

境界値 = 条件の境目にある値

バグは境界付近で発生しやすい。

境界値テストの例
// 関数: 1-100の範囲チェック
function isValidScore(score: number): boolean {
  return score >= 1 && score <= 100;
}

describe('isValidScore - 境界値', () => {
  // 有効な境界値
  it('1は有効（下限）', () => {
    expect(isValidScore(1)).toBe(true);
  });

  it('100は有効（上限）', () => {
    expect(isValidScore(100)).toBe(true);
  });

  // 無効な境界値
  it('0は無効（下限-1）', () => {
    expect(isValidScore(0)).toBe(false);
  });

  it('101は無効（上限+1）', () => {
    expect(isValidScore(101)).toBe(false);
  });

  // 中間値
  it('50は有効（中間）', () => {
    expect(isValidScore(50)).toBe(true);
  });
});

エッジケース（特殊な入力）

エッジケース = 極端な状況、特殊な入力

データ型 テストすべきエッジケース
文字列 空文字 ""、空白のみ " "、非常に長い文字列
配列 空配列 []、1要素、大量の要素
数値 0、負数、NaN、Infinity
オブジェクト null、undefined、空オブジェクト {}
エッジケースのテスト例
describe('getUserName', () => {
  it('正常なユーザー', () => {
    expect(getUserName({ name: 'Alice' })).toBe('Alice');
  });

  // エッジケース
  it('nullを渡した場合', () => {
    expect(getUserName(null)).toBe('Unknown');
  });

  it('undefinedを渡した場合', () => {
    expect(getUserName(undefined)).toBe('Unknown');
  });

  it('空オブジェクトを渡した場合', () => {
    expect(getUserName({})).toBe('Unknown');
  });

  it('nameが空文字の場合', () => {
    expect(getUserName({ name: '' })).toBe('Unknown');
  });
});

例外のテスト
describe('parseJSON', () => {

テストカバレッジ

カバレッジは「コードの何%がテストされているか」を示す指標です。 ただし、数値だけを追うのはNGです。

カバレッジとは？

たとえ話：テスト = 健康診断

  • カバレッジ100% = 全身を検査した
  • でも「検査した」と「異常を見つけた」は別
  • カバレッジが高くても、テストの質が低いと意味がない

カバレッジの種類

種類 意味
行カバレッジ 何行が実行されたか
分岐カバレッジ if/elseの両方が実行されたか

c8でカバレッジを計測

c8 = Node.js V8エンジン組み込みのカバレッジツール

Vitestでは設定するだけで使えます。

vitest.config.ts
import { defineConfig } from 'vitest/config';

export default defineConfig({
  test: {
    coverage: {
      provider: 'v8',           // c8を使う
      reporter: ['text', 'html'], // レポート形式
      exclude: [
        'node_modules',
        'tests',
        '**/*.d.ts',
      ],
      // カバレッジ閾値
      thresholds: {
        lines: 80,
        functions: 80,
        branches: 80,
        statements: 80,
      },
    },
  },
});

カバレッジ目標の目安

レベル 目標 説明
最低ライン 60% 主要なロジックはカバー
推奨 80% バランスが良い目標
高品質 90%+ 重要なライブラリ、金融系

注意：100%を目指さない

  • 100%達成のコストが高すぎる
  • テストのためだけの無意味なコードが増える
  • 80%で十分なケースが多い

レビューで指摘すべきポイント

数値だけを追う

// カバレッジ100%だが意味がない
it('adds numbers', () => {
  add(1, 2);  // 戻り値を検証していない
});
// 行は実行されるがバグを見つけられない

質を重視

it('adds numbers correctly', () => {
  expect(add(1, 2)).toBe(3);
  expect(add(-1, 1)).toBe(0);
  expect(add(0, 0)).toBe(0);
});
// 結果を検証しているので意味がある

指摘例

  • 「カバレッジは高いがexpectがない」
  • 「重要なビジネスロジックがカバーされていない」
  • 「分岐カバレッジが低い（elseが通っていない）」

CI/CD統合

テストは自動で実行されるべきです。 GitHub ActionsでCI/CDパイプラインを構築しましょう。

CI/CDとは？

CI（Continuous Integration） = 継続的インテグレーション

  • コードの変更を頻繁にマージ
  • 自動テストで品質を担保

CD（Continuous Delivery/Deployment） = 継続的デリバリー/デプロイ

  • いつでもリリースできる状態を維持
  • 自動デプロイ

たとえ話：工場の品質管理

  • 手動検査 = 人がいないと検査できない
  • 自動検査 = 24時間機械が検査してくれる

GitHub Actionsの基本

GitHub Actions = GitHubに組み込まれたCI/CDツール

.github/workflows/test.yml
name: Test

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest

    steps:
      # リポジトリをチェックアウト
      - uses: actions/checkout@v4

      # Node.jsをセットアップ
      - uses: actions/setup-node@v4
        with:
          node-version: '22'
          cache: 'npm'

      # 依存関係インストール
      - run: npm ci

      # リント
      - run: npm run lint

      # 型チェック
      - run: npm run typecheck

      # テスト実行
      - run: npm run test

      # カバレッジ（オプション）
      - run: npm run test:coverage

DBテストを含むCI設定

PostgreSQLを使うCI設定
name: Test with DB

on: [push, pull_request]

jobs:
  test:
    runs-on: ubuntu-latest

    services:
      postgres:
        image: postgres:16
        env:
          POSTGRES_USER: test
          POSTGRES_PASSWORD: test
          POSTGRES_DB: myapp_test
        ports:
          - 5432:5432
        options: >-
          --health-cmd pg_isready
          --health-interval 10s
          --health-timeout 5s
          --health-retries 5

    env:
      DATABASE_URL: postgresql://test:test@localhost:5432/myapp_test

    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '22'
          cache: 'npm'

      - run: npm ci

      # マイグレーション実行
      - run: npx prisma migrate deploy

      # テスト実行
      - run: npm run test

ブランチ保護ルール

mainブランチを保護してテストを必須にしましょう。

設定方法：

  1. GitHub リポジトリ → Settings → Branches
  2. Add branch protection rule
  3. Branch name pattern: main
  4. 「Require status checks to pass before merging」にチェック
  5. 必須のチェックに「test」を追加

効果：

  • テストが通らないとマージできない
  • 壊れたコードがmainに入らない

レビューで指摘すべきポイント

  • CIがない：「GitHub Actionsでテストを自動化すべき」
  • 手動実行のみ：「PRにCI必須を設定すべき」
  • テストがスキップされている：「skip/onlyを削除すべき」

手動実行のみ

# ローカルでしかテストしない
npm run test
# PRをマージ
# テストが壊れていることに後で気づく

CI必須

# PRを作成
# → 自動でCIが実行
# → テスト失敗でマージブロック
# → 修正してからマージ
