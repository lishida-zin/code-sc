認証 vs 認可

認証（Authentication）と認可（Authorization）は、 セキュリティの基本です。この2つを混同すると、重大な脆弱性を生みます。

たとえ話で理解する

認証 = 身分証明書の確認

  • 「あなたは誰ですか？」を確認
  • 例：パスポートで本人確認
  • 英語：Authentication（オーセンティケーション）
  • 語源：authentic（本物の）

認可 = 入館許可証の確認

  • 「あなたは何ができますか？」を確認
  • 例：社員証で入れるフロアが決まる
  • 英語：Authorization（オーソライゼーション）
  • 語源：authorize（権限を与える）
建物に入るとき：
1. 認証：受付で身分証を見せる（本人確認）
2. 認可：入館証をもらう（どこに行けるか決まる）

Webアプリでも同じ流れ：
1. 認証：ログインする（ユーザーを特定）
2. 認可：権限をチェック（何ができるか判定）

技術的な違い

項目 認証（Authentication） 認可（Authorization）
目的 「誰か」を確認 「何ができるか」を判定
質問 Who are you? What can you do?
手段 ID/PW、生体認証、Passkey ロール、権限、ACL
タイミング 最初に実行 認証後に実行
略称 AuthN AuthZ

コードで見る認証と認可

認証：ログイン処理
// 認証：ユーザーが誰かを確認
async function login(email: string, password: string) {
  // 1. ユーザーを検索
  const user = await db.user.findUnique({ where: { email } });

  // 2. パスワードを検証（認証の本体）
  const isValid = await bcrypt.compare(password, user.passwordHash);

  if (!isValid) {
    throw new Error('認証失敗');  // 本人ではない
  }

  // 3. 認証成功 → トークン発行
  return generateToken(user.id);
}
認可：権限チェック
// 認可：何ができるかを判定
async function deleteUser(requesterId: string, targetUserId: string) {
  // 1. リクエスト者の情報を取得
  const requester = await db.user.findUnique({
    where: { id: requesterId }
  });

  // 2. 権限をチェック（認可の本体）
  if (requester.role !== 'admin') {
    throw new Error('権限がありません');  // 認可失敗
  }

  // 3. 認可成功 → 処理を実行
  await db.user.delete({ where: { id: targetUserId } });
}

レビューで見抜くべき問題

NG: 認可チェックなし

// 認証だけで認可を忘れている
app.delete('/users/:id', authMiddleware, async (req, res) => {
  // 誰でも他人を削除できてしまう！
  await db.user.delete({ where: { id: req.params.id } });
  res.json({ success: true });
});

OK: 認可チェックあり

// 認証 + 認可の両方をチェック
app.delete('/users/:id', authMiddleware, async (req, res) => {
  // 自分自身 or 管理者のみ削除可能
  if (req.user.id !== req.params.id && req.user.role !== 'admin') {
    return res.status(403).json({ error: 'Forbidden' });
  }
  await db.user.delete({ where: { id: req.params.id } });
  res.json({ success: true });
});

指摘例：

  • 「認証は通っていますが、認可チェックがありません」
  • 「ログインユーザーなら誰でもアクセスできる状態です」
  • 「IDOR（Insecure Direct Object Reference）脆弱性があります」

パスワード管理

パスワードを平文で保存するのは最悪のセキュリティ違反です。 bcryptでハッシュ化し、安全に保存しましょう。

なぜハッシュ化が必要か？

DBが流出した場合：

  • 平文保存 → 全ユーザーのパスワードが漏洩
  • ハッシュ保存 → パスワード自体は漏洩しない
// 平文保存（絶対NG）
| id | email          | password    |
|----|----------------|-------------|
| 1  | alice@mail.com | password123 |  ← 丸見え！

// ハッシュ保存（OK）
| id | email          | password_hash                          |
|----|----------------|----------------------------------------|
| 1  | alice@mail.com | $2b$10$X7z... (元に戻せない)          |

ハッシュ vs 暗号化

項目 ハッシュ 暗号化
復元 不可能（一方向） 可能（双方向）
用途 パスワード保存 データ保護（復元が必要）
例 bcrypt, Argon2 AES, RSA

なぜパスワードにはハッシュ？

→ 検証時に「元のパスワード」を知る必要がないから

ログイン時：
1. 入力されたパスワードをハッシュ化
2. DBに保存されたハッシュと比較
3. 一致すれば認証成功

→ 元のパスワードを復元する必要がない！

bcryptの仕組み

bcryptは、パスワードハッシュに特化したアルゴリズムです。

3つの重要な特徴：

  1. ソルト（Salt）：ランダムな文字列を追加
  2. ストレッチング：計算を意図的に遅くする
  3. コストファクター：計算回数を調整可能
bcryptの使い方
import bcrypt from 'bcrypt';

// パスワードのハッシュ化（登録時）
const saltRounds = 10;  // コストファクター
const passwordHash = await bcrypt.hash('password123', saltRounds);
// → '$2b$10$X7z...' のような文字列

// パスワードの検証（ログイン時）
const isValid = await bcrypt.compare('password123', passwordHash);
// → true または false

ソルト（Salt）とは？

たとえ話：料理の「塩」のように、味を変えるもの

問題：同じパスワードは同じハッシュになる

// ソルトなしの場合
"password" → "5f4dcc3b5aa..."  // 常に同じ
"password" → "5f4dcc3b5aa..."  // 常に同じ

→ レインボーテーブル攻撃で解読される！

解決：ソルトを追加すると、毎回異なるハッシュに

// ソルトありの場合
"password" + "abc123" → "7f9e2a1b..."  // ソルトごとに異なる
"password" + "xyz789" → "3d8c4e5f..."  // ソルトごとに異なる

→ レインボーテーブルが使えない！

bcryptのメリット：ソルトを自動生成・保存してくれる

レビューで見抜くべき問題

NG: 平文保存

// 絶対にやってはいけない
await db.user.create({
  data: {
    email,
    password: password  // 平文！
  }
});

OK: ハッシュ保存

// bcryptでハッシュ化してから保存
const passwordHash = await bcrypt.hash(password, 10);
await db.user.create({
  data: {
    email,
    passwordHash  // ハッシュ
  }
});

NG: MD5/SHA1を使用

// 古い・高速すぎる
import crypto from 'crypto';
const hash = crypto.createHash('md5')
  .update(password).digest('hex');

OK: bcryptを使用

// パスワード専用アルゴリズム
import bcrypt from 'bcrypt';
const hash = await bcrypt.hash(password, 10);

指摘例：

  • 「パスワードが平文で保存されています」
  • 「MD5は高速すぎてブルートフォースに弱いです」
  • 「bcryptまたはArgon2を使用してください」

JWT基礎

JWT（JSON Web Token）は、認証情報を安全にやり取りするための標準規格です。 読み方は「ジョット」です。

JWTとは？

たとえ話：JWTは「改ざん検知機能付きの名札」

  • 名前や役職が書いてある（情報を持つ）
  • 会社の印鑑が押してある（署名で改ざん検知）
  • 有効期限がある（期限切れ無効）

語源：

  • JSON：データ形式
  • Web：Web用途
  • Token：認証トークン

JWTの構造（3つのパート）

JWTは3つの部分をドット（.）で繋いだ文字列です。

eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJ1c2VySWQiOiIxMjMiLCJleHAiOjE3MDk0NTM2MDB9.X7z4Q...
|___________________________________|.___________________________________|._______|
           ヘッダー                              ペイロード                  署名
パート 内容 Base64デコード後
ヘッダー アルゴリズム、トークン種別 {"alg":"HS256","typ":"JWT"}
ペイロード ユーザー情報、有効期限 {"userId":"123","exp":1709453600}
署名 改ざん検知用のハッシュ （デコード不可）

重要：ペイロードはBase64でエンコードされているだけ

→ 誰でも読める！機密情報を入れてはいけない

署名と検証の仕組み

JWTの生成（署名）
import jwt from 'jsonwebtoken';

// JWTを生成（署名する）
const token = jwt.sign(
  { userId: '123' },           // ペイロード
  process.env.JWT_SECRET,      // 秘密鍵
  { expiresIn: '1h' }          // 有効期限
);
// → eyJhbGciOiJIUzI1NiIs...
JWTの検証
// JWTを検証（署名を確認）
try {
  const decoded = jwt.verify(token, process.env.JWT_SECRET);
  console.log(decoded.userId);  // "123"
} catch (error) {
  // 署名が不正 or 期限切れ
  console.log('無効なトークン');
}

検証の流れ：

  1. ヘッダーとペイロードを取り出す
  2. 秘密鍵で署名を再計算
  3. トークンの署名と一致するか確認
  4. 有効期限を確認

レビューで見抜くべき問題

NG: decodeで検証したつもり

// decodeは署名を検証しない！
const decoded = jwt.decode(token);
// 改ざんされたトークンでも読めてしまう
const userId = decoded.userId;  // 危険！

OK: verifyで検証

// verifyは署名を検証する
const decoded = jwt.verify(token, process.env.JWT_SECRET);
// 改ざんされていれば例外が発生
const userId = decoded.userId;  // 安全

NG: ペイロードに機密情報

jwt.sign({
  userId: '123',
  password: 'secret123',  // NG！
  creditCard: '4111...'   // NG！
}, secret);

OK: 最小限の情報のみ

jwt.sign({
  userId: '123',  // IDのみ
  role: 'user'    // 必要最小限
}, secret);

指摘例：

  • 「jwt.decode()は署名を検証しません。jwt.verify()を使ってください」
  • 「JWTペイロードに機密情報が含まれています」
  • 「秘密鍵がハードコードされています」

JWTベストプラクティス

JWTの使い方を間違えると、セキュリティホールになります。 有効期限、保存場所、Refresh Tokenの設計が重要です。

有効期限の設計

トークン種別 推奨期限 用途
Access Token 15分〜1時間 API認証
Refresh Token 7日〜30日 Access Token再発行

なぜAccess Tokenを短くするか？

  • 漏洩時の被害を最小化
  • 権限変更を素早く反映
  • Refresh Tokenで再発行すれば不便なし

トークンの保存場所

保存場所 XSS CSRF 推奨
localStorage 脆弱 安全 非推奨
sessionStorage 脆弱 安全 非推奨
HttpOnly Cookie 安全 対策必要 推奨

NG: localStorageに保存

// XSSで盗まれる可能性がある
localStorage.setItem('token', token);

// JavaScriptから読み取り可能
const token = localStorage.getItem('token');

OK: HttpOnly Cookieに保存

// サーバー側でCookieを設定
res.cookie('token', token, {
  httpOnly: true,   // JSからアクセス不可
  secure: true,     // HTTPS必須
  sameSite: 'strict' // CSRF対策
});

// ブラウザが自動でCookieを送信

Refresh Token フロー

1. ログイン
   Client → Server: メール＋パスワード
   Server → Client: Access Token + Refresh Token

2. API呼び出し
   Client → Server: Access Token（Authorizationヘッダー）
   Server → Client: データ

3. Access Token期限切れ
   Client → Server: Access Token（期限切れ）
   Server → Client: 401 Unauthorized

4. トークン更新
   Client → Server: Refresh Token
   Server → Client: 新しいAccess Token

5. 再度API呼び出し
   Client → Server: 新しいAccess Token
   Server → Client: データ
トークン更新の実装
// トークン更新エンドポイント
app.post('/auth/refresh', async (req, res) => {
  const refreshToken = req.cookies.refreshToken;

  try {
    // Refresh Tokenを検証
    const decoded = jwt.verify(refreshToken, process.env.REFRESH_SECRET);

    // 新しいAccess Tokenを発行
    const newAccessToken = jwt.sign(
      { userId: decoded.userId },
      process.env.JWT_SECRET,
      { expiresIn: '15m' }
    );

    res.json({ accessToken: newAccessToken });
  } catch {
    res.status(401).json({ error: 'Invalid refresh token' });
  }
});

署名アルゴリズムの選択

アルゴリズム 種類 推奨
none なし 絶対禁止
HS256 対称鍵 小規模向け
RS256 非対称鍵 推奨（特にマイクロサービス）

RS256の利点：

  • 秘密鍵は発行サーバーのみが持つ
  • 公開鍵で誰でも検証できる
  • 秘密鍵の共有が不要

OAuth2/OIDC

OAuth2は認可の標準規格、OIDCは認証の標準規格です。 「Googleでログイン」はこれらを使っています。

OAuth2とは？

たとえ話：「代理人への権限委譲」

あなたが家（Googleアカウント）を持っている
→ 清掃業者（サードパーティアプリ）に掃除を頼みたい
→ 合鍵（アクセストークン）を渡す
→ 清掃業者は掃除だけできる（限定的な権限）
→ 金庫は開けられない（パスワードは渡さない）

メリット：

  • パスワードを第三者に渡さない
  • 必要な権限だけ委譲できる
  • いつでも権限を取り消せる

認可コードフロー（最も安全）

1. ユーザーが「Googleでログイン」をクリック
   アプリ → Google: 「認可をください」

2. Googleがログイン画面を表示
   ユーザー → Google: 「ログインします」

3. 同意画面
   Google → ユーザー: 「このアプリに許可しますか？」
   ユーザー → Google: 「許可します」

4. 認可コードを発行
   Google → アプリ: 認可コード（一時的な引換券）

5. アクセストークンと交換
   アプリ（バックエンド） → Google: 認可コード + クライアントシークレット
   Google → アプリ: アクセストークン + IDトークン

6. ユーザー情報を取得
   アプリ → Google: アクセストークン
   Google → アプリ: ユーザー情報

なぜバックエンドで交換するか？

  • クライアントシークレットを隠すため
  • フロントエンドに秘密鍵を置いてはいけない

OIDC（OpenID Connect）とは？

項目 OAuth2 OIDC
目的 認可（Authorization） 認証（Authentication）
得られるもの アクセストークン IDトークン（JWT）
わかること 何ができるか 誰であるか

OIDCはOAuth2の拡張

OAuth2 + ユーザー認証機能 = OIDC

Passkey概要

Passkeyは「パスワードなし認証」の新しい標準です。 指紋や顔認証でログインでき、フィッシングに強い設計です。

Passkeyとは？

たとえ話：「デジタルな鍵と錠前」

  • 秘密鍵（鍵）：デバイスに安全に保存
  • 公開鍵（錠前）：サーバーに登録
  • 生体認証で秘密鍵を使用
  • パスワードを覚える必要なし

Passkeyの利点：

項目 パスワード Passkey
フィッシング 脆弱 耐性あり
使い回し よくある 不可能
漏洩リスク サーバー攻撃で漏洩 秘密鍵はデバイス内
利便性 覚える必要 指紋/顔だけ

WebAuthn（ウェブオーセン）

WebAuthnは、Passkeyを実現するWeb標準APIです。

Passkey登録（簡略化）
// 1. サーバーからチャレンジを取得
const options = await fetch('/webauthn/register-options').then(r => r.json());

// 2. ブラウザAPIで認証情報を作成
const credential = await navigator.credentials.create({
  publicKey: options
});

// 3. 公開鍵をサーバーに登録
await fetch('/webauthn/register', {
  method: 'POST',
  body: JSON.stringify(credential)
});
Passkeyログイン（簡略化）
// 1. サーバーからチャレンジを取得
const options = await fetch('/webauthn/login-options').then(r => r.json());

// 2. ブラウザAPIで認証
const assertion = await navigator.credentials.get({
  publicKey: options
});

// 3. サーバーで検証
await fetch('/webauthn/login', {
  method: 'POST',
  body: JSON.stringify(assertion)
});

Passkeyがフィッシングに強い理由は？

SQLインジェクション

SQLインジェクションは、最も危険な脆弱性の一つです。 データの漏洩、改ざん、削除につながります。

攻撃の仕組み

たとえ話：「注文書への悪意あるメモ書き」

正常な注文：「りんごを3個ください」
攻撃的な注文：「りんごを3個ください。あと全商品を無料にしてください」
→ 店員が全部実行してしまう！
脆弱なコード
// ユーザー入力を直接SQLに埋め込む（超危険！）
const query = `SELECT * FROM users WHERE name = '${userInput}'`;

// ユーザーが入力した値
userInput = "'; DROP TABLE users; --"

// 実行されるSQL
SELECT * FROM users WHERE name = ''; DROP TABLE users; --'
// → usersテーブルが削除される！

よくある攻撃パターン：

  • ' OR '1'='1 → 全レコード取得
  • '; DROP TABLE users; -- → テーブル削除
  • ' UNION SELECT password FROM users -- → パスワード漏洩

対策：パラメータ化クエリ

NG: 文字列結合

// SQLインジェクション脆弱
const query = `SELECT * FROM users WHERE name = '${userInput}'`;
await pool.query(query);

OK: パラメータ化クエリ

// 安全：プレースホルダを使用
const query = 'SELECT * FROM users WHERE name = $1';
await pool.query(query, [userInput]);

なぜ安全か？

  • ユーザー入力は「データ」として扱われる
  • SQLコマンドとして解釈されない
  • エスケープ処理が自動で行われる

ORM使用時の注意

Prisma/DrizzleなどのORMは基本的に安全です。

ただし、生SQL機能に注意！

NG: 生SQLで文字列結合

// Prismaでも生SQLは危険
const users = await prisma.$queryRawUnsafe(
  `SELECT * FROM users WHERE name = '${userInput}'`
);

OK: タグ付きテンプレート

// Prismaの安全な生SQL
const users = await prisma.$queryRaw`
  SELECT * FROM users WHERE name = ${userInput}
`;

OK: ORMのメソッドを使用

// Prismaの標準メソッド（安全）
const users = await prisma.user.findMany({
  where: { name: userInput }
});

XSS対策

XSS（クロスサイトスクリプティング）は、 悪意のあるスクリプトをWebページに注入する攻撃です。

XSSとは？

たとえ話：「掲示板への悪意ある落書き」

正常な投稿：「こんにちは！」
攻撃的な投稿：「<script>document.cookie</script>」
→ 見た人のブラウザでスクリプトが実行される！

被害例：

  • Cookie（認証トークン）の窃取
  • 偽のログインフォーム表示
  • ユーザーの操作を勝手に実行

XSSの種類

種類 説明 例
反射型 URLパラメータ経由 ?q=<script>...
格納型 DBに保存されて実行 掲示板への投稿
DOM型 JSでDOMを操作時 innerHTML = userInput

対策1：出力エスケープ

NG: innerHTML直接代入

// スクリプトが実行される！
element.innerHTML = userInput;

// Reactでも同様に危険
<div dangerouslySetInnerHTML={{ __html: userInput }} />

OK: textContentを使用

// テキストとして扱われる（安全）
element.textContent = userInput;

// Reactはデフォルトでエスケープ
<div>{userInput}</div>  // 安全

エスケープとは？

入力: <script>alert('XSS')</script>
↓ エスケープ
出力: &lt;script&gt;alert('XSS')&lt;/script&gt;
→ HTMLタグとして解釈されず、文字として表示される

対策2：CSP（Content Security Policy）

CSPは、許可されたスクリプトのみ実行を許可するヘッダーです。

CSPヘッダーの設定
// Expressでの設定
app.use((req, res, next) => {
  res.setHeader(
    'Content-Security-Policy',
    "default-src 'self'; script-src 'self'"
  );
  next();
});

// または helmet を使用（推奨）
import helmet from 'helmet';
app.use(helmet());

CSPの効果：

  • インラインスクリプトを禁止
  • 外部スクリプトの読み込みを制限
  • eval()の実行を禁止

レビューで見抜くべきポイント

危険なパターン：

  • innerHTML = ...
  • document.write(...)
  • dangerouslySetInnerHTML
  • eval(userInput)

指摘例：

  • 「innerHTMLの使用はXSS脆弱性を生みます」
  • 「textContentを使用してください」
  • 「CSPヘッダーの設定を検討してください」

CSRF対策

CSRF（クロスサイトリクエストフォージェリ）は、 ユーザーの意図しない操作を実行させる攻撃です。

CSRFとは？

たとえ話：「偽の申込書への署名」

1. 被害者がネットバンクにログイン中
2. 攻撃者が悪意あるサイトへ誘導
3. 悪意あるサイトにこんなフォームが：
   <form action="https://bank.com/transfer" method="POST">
     <input name="to" value="attacker" />
     <input name="amount" value="1000000" />
   </form>
   <script>document.forms[0].submit();</script>
4. 被害者のブラウザが自動的にリクエスト送信
5. Cookieも一緒に送られ、銀行は正規のリクエストと判断
6. 100万円が攻撃者に送金される！

ポイント：

  • 被害者は悪意あるサイトを見ただけ
  • 認証Cookieが自動送信される
  • サーバーは正規リクエストと区別できない

対策1：CSRFトークン

サーバーが発行した秘密のトークンをフォームに埋め込みます。

CSRFトークンの仕組み
// サーバー側：トークン生成
import crypto from 'crypto';

app.get('/form', (req, res) => {
  const csrfToken = crypto.randomBytes(32).toString('hex');
  req.session.csrfToken = csrfToken;

  res.send(`
    <form action="/transfer" method="POST">
      <input type="hidden" name="_csrf" value="${csrfToken}" />
      <input name="amount" />
      <button>送金</button>
    </form>
  `);
});

// サーバー側：トークン検証
app.post('/transfer', (req, res) => {
  if (req.body._csrf !== req.session.csrfToken) {
    return res.status(403).json({ error: 'Invalid CSRF token' });
  }
  // 処理を続行
});

なぜ効果的か？

  • 攻撃者はトークンを知らない
  • トークンなしのリクエストは拒否される

対策2：SameSite Cookie

SameSite属性は、Cookieを同一サイトからのみ送信する設定です。

SameSite Cookieの設定
res.cookie('sessionId', sessionId, {
  httpOnly: true,
  secure: true,
  sameSite: 'strict'  // または 'lax'
});
値 動作 推奨
strict 同一サイトからのみ送信 最も安全
lax トップレベルナビ時は送信 バランス良い（デフォルト）
none 常に送信 非推奨（CSRF脆弱）

レビューで見抜くべきポイント

危険なパターン：

  • フォームにCSRFトークンがない
  • SameSite属性が未設定
  • 重要な操作にGETを使用

NG: GETで重要操作

// GETでデータ変更（CSRF脆弱）
app.get('/delete-account', (req, res) => {
  deleteAccount(req.user.id);
});

OK: POSTで重要操作

// POSTでデータ変更 + CSRFトークン
app.post('/delete-account', csrfProtection, (req, res) => {
  deleteAccount(req.user.id);
});

セキュリティヘッダー

HTTPヘッダーでセキュリティを強化できます。 helmetライブラリで簡単に設定しましょう。

helmet（ヘルメット）

helmetは、セキュリティヘッダーを一括設定するExpressミドルウェアです。

helmetの使い方
import express from 'express';
import helmet from 'helmet';

const app = express();

// 1行で複数のセキュリティヘッダーを設定
app.use(helmet());

// カスタマイズも可能
app.use(helmet({
  contentSecurityPolicy: {
    directives: {
      defaultSrc: ["'self'"],
      scriptSrc: ["'self'", "trusted-cdn.com"],
    }
  }
}));

主要なセキュリティヘッダー

ヘッダー 効果
Content-Security-Policy XSS対策、許可するリソースを制限
X-Content-Type-Options MIMEタイプのスニッフィング防止
X-Frame-Options クリックジャッキング防止
Strict-Transport-Security HTTPS強制
X-XSS-Protection ブラウザのXSSフィルター有効化

CORS（Cross-Origin Resource Sharing）

CORSは、異なるオリジンからのリクエストを制御する仕組みです。

CORSの設定
import cors from 'cors';

// 特定のオリジンのみ許可（推奨）
app.use(cors({
  origin: 'https://myapp.com',
  credentials: true  // Cookieを含める場合
}));

// すべてのオリジンを許可（開発用、本番は非推奨）
app.use(cors({
  origin: '*'
}));

NG: 本番で全オリジン許可

// 誰でもAPIを叩ける
app.use(cors({ origin: '*' }));

OK: 特定オリジンのみ

// 自社サイトからのみ
app.use(cors({
  origin: ['https://myapp.com', 'https://admin.myapp.com']
}));

HTTPS必須化

本番環境では必ずHTTPSを使用してください。

HTTPSの効果：

  • 通信の暗号化
  • 改ざん検知
  • サーバー認証
HTTPSリダイレクト
// HTTPをHTTPSにリダイレクト
app.use((req, res, next) => {
  if (req.header('x-forwarded-proto') !== 'https') {
    return res.redirect(`https://${req.header('host')}${req.url}`);
  }
  next();
});

チェックリスト：

  • CORSが適切に設定されているか（origin: '*' は危険）
  • 本番でHTTPSが強制されているか
  • Cookieにsecure/httpOnly/sameSiteがあるか

NG: セキュリティヘッダーなし

const app = express();
