RESTとは

REST（Representational State Transfer）は、Web APIの設計スタイルです。

2000年にRoy Fieldingが提唱しました。
「Web」が成功した設計原則をAPI設計に応用したものです。

💡 語源

Representational = 表現
State = 状態
Transfer = 転送
→ 「リソースの状態を表現として転送する」という意味です。

リソース指向

RESTの最も重要な考え方がリソース指向です。

リソース = 名詞で表せる「もの」
例: ユーザー、投稿、商品、注文

❌ 動詞ベース（古い設計）

GET /getUserById?id=1
POST /createUser
POST /updateUserName
DELETE /removeUser

「何をするか」を動詞で表現

⭕ リソース指向（RESTful）

GET /users/1
POST /users
PATCH /users/1
DELETE /users/1

「何に対して」を名詞で表現

🍽️ たとえ話

レストランのメニューに例えると:
動詞ベース: 「ステーキを焼いて」「サラダを作って」「ドリンクを注いで」
リソース指向: 「ステーキ1つ」「サラダ1つ」「ドリンク1つ」
→ リソース（料理）を指定するだけで十分！

HTTPメソッド

リソースに対する操作はHTTPメソッドで表現します。

HTTPメソッドとCRUD対応
メソッド 操作 例 冪等性
GET 取得（Read） GET /users/1 ⭕
POST 作成（Create） POST /users ❌
PUT 全体更新（Replace） PUT /users/1 ⭕
PATCH 部分更新（Modify） PATCH /users/1 ⭕
DELETE 削除（Delete） DELETE /users/1 ⭕
📝 冪等性（べきとうせい）とは

「何度実行しても結果が同じ」という性質です。
GET: 何度取得しても同じデータ（冪等）
DELETE: 2回削除しても「削除された状態」は同じ（冪等）
POST: 2回実行すると2つ作成される（非冪等）

ステートレス

RESTではサーバーは状態を持たないことが原則です。

ステートレス = 各リクエストは独立している
→ 前のリクエストの情報をサーバーが覚えていない

❌ ステートフル

// サーバーがセッションを持つ
POST /login  // ログイン状態を保持
GET /my-data // サーバーが「誰か」を覚えている

サーバーがユーザーを記憶

⭕ ステートレス

// 毎回認証情報を送る
GET /users/1
Authorization: Bearer <token>

毎回「自分が誰か」を伝える

利点:

  • スケーラビリティ: どのサーバーでも処理可能
  • シンプル: セッション管理が不要
  • キャッシュ: レスポンスをキャッシュしやすい

見抜くべき問題

🔴 コードレビューで指摘すべきポイント
  • 動詞エンドポイント: /getUser, /createPost など
  • GETで副作用: GET /deleteUser?id=1
  • POSTで取得: POST /searchUsers
  • PUTで部分更新: 一部フィールドだけ送ってPUT

命名規則

URLの命名には一貫したルールが必要です。

推奨される命名規則
  • 小文字のみ: /users（/Users ではない）
  • 複数形: /users, /posts, /orders
  • ケバブケース: /user-profiles（/userProfiles ではない）
  • 名詞のみ: /users（/getUsers ではない）

❌ 悪い例

/User             // 大文字
/user             // 単数形
/userProfiles     // キャメルケース
/user_profiles    // スネークケース
/getUsers         // 動詞

⭕ 良い例

/users            // 小文字・複数形
/user-profiles    // ケバブケース
/order-items      // ケバブケース
💡 ケバブケースとは

単語をハイフン（-）で繋ぐ命名法。
串刺し（kebab）のように見えるから「ケバブケース」。
URLでは最も読みやすく、推奨されています。

階層構造

リソース間の関係はURLの階層で表現します。

階層構造の例
// ユーザーの投稿一覧
GET /users/1/posts

// 投稿のコメント一覧
GET /posts/1/comments

// ユーザー1の投稿2のコメント一覧
GET /users/1/posts/2/comments

原則: 深くなりすぎない（3階層程度まで）

❌ 深すぎる

GET /companies/1/departments/2/teams/3/members/4/tasks/5

深すぎて分かりにくい

⭕ 適切な深さ

GET /teams/3/members
GET /members/4/tasks

必要な関係だけを表現

クエリパラメータ

リソースの特定以外にはクエリパラメータを使います。

クエリパラメータの用途
用途 例
フィルタリング GET /users?status=active
ソート GET /users?sort=created_at&order=desc
ページネーション GET /users?page=2&limit=20
検索 GET /users?q=tanaka
フィールド選択 GET /users?fields=id,name,email

パスパラメータ vs クエリパラメータ

使い分けの基準
- パスパラメータ クエリパラメータ
用途 リソースの特定 オプション・条件
必須か 必須 省略可能
例 /users/123 /users?status=active

見抜くべき問題

🔴 コードレビューで指摘すべきポイント
  • 命名の不一致: /users と /User が混在
  • キャメルケース: /userProfiles
  • 単数形: /user/1（/users/1 が正しい）
  • 動詞の使用: /getUsers, /deletePost
  • 深すぎる階層: 4階層以上

📚 このページで学ぶこと
  • ステータスコードの分類（2xx/3xx/4xx/5xx）
  • よく使うステータスコード
  • 適切な使い分け

ステータスコードとは

ステータスコードは、HTTPレスポンスの結果を表す3桁の数字です。

ステータスコードの分類
範囲 分類 意味
2xx 成功 リクエストが正常に処理された
3xx リダイレクト 別のURLに移動が必要
4xx クライアントエラー リクエストに問題がある
5xx サーバーエラー サーバー側に問題がある

2xx: 成功

コード 名前 使う場面
200 OK GET成功、更新成功
201 Created POST成功（新規作成）
204 No Content DELETE成功（返すデータなし）

4xx: クライアントエラー

コード 名前 使う場面
400 Bad Request リクエストの形式が不正
401 Unauthorized 認証が必要/認証失敗
403 Forbidden 認証済みだが権限がない
404 Not Found リソースが見つからない
409 Conflict 既に存在する（重複登録）
422 Unprocessable Entity バリデーションエラー
429 Too Many Requests レート制限に達した
💡 401 vs 403 の違い

401 Unauthorized: 「あなた誰？」（認証されていない）
403 Forbidden: 「あなたは知ってるけど、権限がない」（認可されていない）
→ 401は再ログインで解決、403は権限付与が必要

5xx: サーバーエラー

コード 名前 使う場面
500 Internal Server Error サーバー内部エラー
502 Bad Gateway 上流サーバーからの応答が不正
503 Service Unavailable メンテナンス中/過負荷
504 Gateway Timeout 上流サーバーがタイムアウト

見抜くべき問題: 全部200返却

🔴 最もよくある問題 
// ❌ エラーでも200を返す
app.post('/users', (req, res) => {
  if (!req.body.email) {
    // 200で返している（間違い！）
    res.status(200).json({
      success: false,
      error: 'Email is required'
    });
    return;
  }
  // ...
});

// ⭕ 適切なステータスコードを返す
app.post('/users', (req, res) => {
  if (!req.body.email) {
    res.status(400).json({  // 400 Bad Request
      error: 'Email is required'
    });
    return;
  }
  // ...
});

全部200の問題点:

  • クライアントがエラー判定しにくい
  • 監視ツールがエラーを検知できない
  • キャッシュの制御が困難
  • REST原則から外れる

JSON構造の基本

APIのリクエスト/レスポンスはJSON形式が標準です。

基本的なレスポンス構造
// 単一リソース
{
  "id": "123",
  "name": "田中太郎",
  "email": "tanaka@example.com",
  "createdAt": "2026-01-15T10:30:00Z"
}

// リソースのコレクション
{
  "data": [
    { "id": "1", "name": "田中" },
    { "id": "2", "name": "佐藤" }
  ],
  "meta": {
    "total": 100,
    "page": 1,
    "limit": 20
  }
}

命名規則

フィールド名の命名
ケース 例 採用
キャメルケース createdAt, firstName 推奨（JavaScript親和性）
スネークケース created_at, first_name 許容（Ruby/Python系）

重要: どちらでもいいが、プロジェクト内で統一すること

ページネーション

大量のデータを取得する場合はページネーションが必須です。

主な方式
方式 例 特徴
Offset ?page=2&limit=20 シンプル、大量データで遅い
Cursor ?cursor=abc123&limit=20 高速、リアルタイム向け
Offset方式のレスポンス
GET /users?page=2&limit=20

{
  "data": [...],
  "pagination": {
    "page": 2,
    "limit": 20,
    "total": 150,
    "totalPages": 8
  }
}
Cursor方式のレスポンス
GET /posts?cursor=eyJpZCI6MTAwfQ&limit=20

{
  "data": [...],
  "pagination": {
    "nextCursor": "eyJpZCI6MTIwfQ",
    "hasMore": true
  }
}

エラーレスポンス

エラーレスポンスも統一された形式にします。

✓ 推奨: 統一されたエラー形式 
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "入力内容に問題があります",
    "details": [
      {
        "field": "email",
        "message": "メールアドレスの形式が不正です"
      },
      {
        "field": "password",
        "message": "8文字以上必要です"
      }
    ]
  }
}
❌ 悪い例: 形式がバラバラ 
// エンドポイントAの場合
{ "error": "Invalid email" }

// エンドポイントBの場合
{ "message": "Error", "errors": ["Invalid"] }

// エンドポイントCの場合
{ "success": false, "msg": "Failed" }

見抜くべき問題

🔴 コードレビューで指摘すべきポイント
  • 命名の不統一: createdAt と created_at が混在
  • ページネーションなし: 全件返却
  • エラー形式がバラバラ: APIごとに違う
  • 日付形式の不統一: ISO 8601以外の形式
  • ネストが深すぎる: 5階層以上のJSON

APIバージョニング

📚 このページで学ぶこと

  • 破壊的変更とは

なぜバージョニングが必要か

APIは変更されるものです。
しかし、既存のクライアントを壊さずに変更したい。

🏢 たとえ話

建物の入口を変えるとき:
バージョニングなし: 突然入口を変える → 来訪者が迷子
バージョニングあり: 新しい入口を作り、古い入口も残す → 徐々に移行

3つの方式

1. URLバージョニング（最も一般的）
GET /v1/users
GET /v2/users

利点: 直感的、キャッシュしやすい
欠点: URLが変わる

2. ヘッダーバージョニング
GET /users
Accept: application/vnd.myapi.v1+json

GET /users
Accept: application/vnd.myapi.v2+json

利点: URLがきれい
欠点: ブラウザでテストしにくい

3. クエリパラメータバージョニング
GET /users?version=1
GET /users?version=2

利点: 実装が簡単
欠点: オプション扱いになりがち

✓ 2026年の推奨

URLバージョニングが最も一般的で推奨。
シンプルで分かりやすく、多くのAPIで採用されています。

破壊的変更（Breaking Changes）

破壊的変更とは、既存のクライアントが動かなくなる変更です。

❌ 破壊的変更の例
  • フィールドの削除（name → 削除）
  • フィールド名の変更（name → fullName）
  • フィールドの型変更（id: "123" → id: 123）
  • 必須フィールドの追加
  • エンドポイントの削除
  • レスポンス構造の変更
✓ 非破壊的変更（後方互換）
  • オプショナルなフィールドの追加
  • 新しいエンドポイントの追加
  • 新しいHTTPメソッドの追加

バージョン移行戦略

移行のベストプラクティス
  1. 新バージョンをリリース（v2）
  2. 旧バージョンを非推奨に（deprecation notice）
  3. 移行期間を設ける（6ヶ月〜1年）
  4. 旧バージョンを廃止
非推奨を伝える方法
// レスポンスヘッダーで通知
Deprecation: true
Sunset: Sat, 31 Dec 2026 23:59:59 GMT
Link: </v2/users>; rel="successor-version"

// レスポンスボディで通知
{
  "data": [...],
  "warning": "This API version is deprecated. Please migrate to v2 by 2026-12-31."
}

見抜くべき問題

🔴 コードレビューで指摘すべきポイント
  • バージョニングなし: 本番APIにバージョンがない
  • 破壊的変更: 既存フィールドの削除/変更
  • 非推奨通知なし: 突然のAPI廃止
  • 複数方式の混在: v1とversionパラメータが混在

OpenAPIとは

OpenAPIは、REST APIの仕様を記述するための標準フォーマットです。

Swaggerは元々の名前。現在はOpenAPI Specification（OAS）が正式名称です。

💡 歴史

Swagger: 2011年に登場、API仕様記述ツール
OpenAPI: 2015年にLinux Foundationへ寄贈され標準化
→ 仕様は「OpenAPI」、ツール群は「Swagger」と呼ばれることが多い

OpenAPI仕様書の基本

基本構造（YAML形式）
openapi: 3.1.0
info:
  title: ユーザー管理API
  version: 1.0.0
  description: ユーザーのCRUD操作を提供します

servers:
  - url: https://api.example.com/v1
    description: 本番環境

paths:
  /users:
    get:
      summary: ユーザー一覧を取得
      responses:
        '200':
          description: 成功
          content:
            application/json:
              schema:
                type: array
                items:
                  $ref: '#/components/schemas/User'

components:
  schemas:
    User:
      type: object
      properties:
        id:
          type: string
        name:
          type: string
        email:
          type: string
          format: email
      required:
        - id
        - name
        - email

主要なセクション

セクション 役割
info APIの基本情報（タイトル、バージョン）
servers APIサーバーのURL
paths エンドポイントの定義
components 再利用可能なスキーマ
security 認証方式の定義

Swagger UI

Swagger UIは、OpenAPI仕様書から自動生成されるドキュメントUIです。

Swagger UIの機能
  • インタラクティブ: ブラウザからAPIを試せる
  • 自動生成: 仕様書から自動でUI生成
  • リクエスト例: サンプルリクエストを表示
  • 認証対応: 認証トークンを入力可能

コード生成

OpenAPI仕様書からクライアントコードやサーバースタブを生成できます。

主なコード生成ツール
ツール 特徴
openapi-typescript TypeScript型定義を生成
openapi-generator 40以上の言語に対応
orval React Query/SWR統合

見抜くべき問題

🔴 コードレビューで指摘すべきポイント
  • ドキュメントなし: 仕様書がない/古い
  • 実装との乖離: 仕様書と実装が一致していない
  • 型定義の不足: スキーマが不完全
  • サンプルなし: リクエスト/レスポンス例がない

GraphQLとは

GraphQLは、Facebookが開発したAPIクエリ言語です。

特徴: クライアントが必要なデータだけを指定して取得できる

🍽️ たとえ話

レストランで例えると:
REST: セットメニュー（決まった内容が来る）
GraphQL: アラカルト（欲しいものだけ注文）

Query（データ取得）

RESTの場合
// ユーザーと投稿を別々に取得
GET /users/1
GET /users/1/posts

// 2回のリクエストが必要
GraphQLの場合
query {
  user(id: "1") {
    name
    email
    posts {
      title
      createdAt
    }
  }
}

// 1回のリクエストで必要なデータだけ取得

Mutation（データ変更）

Mutationは、データの作成・更新・削除を行います。 

mutation {
  createUser(input: {
    name: "田中"
    email: "tanaka@example.com"
  }) {
    id
    name
    email
  }
}

Subscription（リアルタイム）

Subscriptionは、データの変更をリアルタイムで受け取ります。 

subscription {
  messageAdded(roomId: "123") {
    id
    content
    sender {
      name
    }
  }
}

// WebSocketで接続し、新しいメッセージをリアルタイム受信

REST vs GraphQL

観点 REST GraphQL
データ取得 エンドポイントごとに固定 クライアントが指定
Over-fetching 発生しやすい 発生しない
Under-fetching 複数リクエスト必要 1リクエストで完結
キャッシュ HTTPキャッシュ活用 専用キャッシュ必要
学習曲線 低い 高い
📝 Over-fetching / Under-fetching

Over-fetching: 必要以上のデータを取得してしまう
Under-fetching: 必要なデータが足りず、追加リクエストが必要

N+1問題

GraphQLで最も注意すべき問題がN+1問題です。

🔴 N+1問題の例 
query {
  users {        # 1回のクエリで全ユーザー取得
    name
    posts {      # 各ユーザーごとに投稿を取得（N回）
      title
    }
  }
}

// ユーザー10人 → 1 + 10 = 11回のDBクエリ
// ユーザー1000人 → 1 + 1000 = 1001回のDBクエリ
✓ 解決策: DataLoader 
// DataLoaderでバッチ処理
const postLoader = new DataLoader(async (userIds) => {
  // 1回のクエリで全ユーザーの投稿を取得
  const posts = await db.posts.findMany({
    where: { userId: { in: userIds } }
  });
  // ユーザーIDごとにグループ化して返す
  return userIds.map(id =>
    posts.filter(post => post.userId === id)
  );
});

tRPCとは

tRPCは、型安全なRPC（Remote Procedure Call）ライブラリです。

特徴: サーバーとクライアントで型を共有できる

💡 RPC（Remote Procedure Call）とは

「遠隔手続き呼び出し」の意味。
サーバーの関数を、ローカルの関数のように呼び出す仕組みです。

tRPCの基本

サーバー側（router定義）
// server/router.ts
import { initTRPC } from '@trpc/server';
import { z } from 'zod';

const t = initTRPC.create();

export const appRouter = t.router({
  // ユーザー取得
  getUser: t.procedure
    .input(z.object({ id: z.string() }))
    .query(async ({ input }) => {
      const user = await db.user.findUnique({
        where: { id: input.id }
      });
      return user;
    }),

  // ユーザー作成
  createUser: t.procedure
    .input(z.object({
      name: z.string(),
      email: z.string().email()
    }))
    .mutation(async ({ input }) => {
      return await db.user.create({ data: input });
    })
});

export type AppRouter = typeof appRouter;
クライアント側（型安全な呼び出し）
// client/api.ts
import { createTRPCClient } from '@trpc/client';
import type { AppRouter } from '../server/router';

const trpc = createTRPCClient<AppRouter>({
  url: 'http://localhost:3000/trpc',
});

// 型が自動で付く！
const user = await trpc.getUser.query({ id: '1' });
// user.name, user.email に補完が効く

// 型エラーを検出！
await trpc.createUser.mutation({
  name: '田中',
  email: 'invalid'  // ❌ emailの形式エラー
});

tRPCの強み

✓ tRPCのメリット
  • 完全な型安全: 入力/出力の型がサーバーとクライアントで共有
  • 自動補完: IDEで補完が効く
  • スキーマ不要: OpenAPI/GraphQLスキーマを書く必要がない
  • 開発体験（DX）が最高: 型エラーを即座に検出

REST / GraphQL / tRPC の比較

観点 REST GraphQL tRPC
型安全 手動で型定義 コード生成で型 自動で共有
学習曲線 低い 高い 中程度
公開API 最適 適 不向き
内部API 可 可 最適
言語 任意 任意 TypeScript限定

tRPCの適切なユースケース

✓ tRPCが最適な場面
  • フルスタックTypeScript: Next.js, T3 Stackなど
  • Monorepo: サーバーとクライアントが同じリポジトリ
  • 内部API: 自社サービス内での通信
  • 小〜中規模プロジェクト: MVPやスタートアップ
❌ tRPCが不向きな場面
  • 公開API: 外部開発者が使うAPI
  • 非TypeScript環境: モバイルアプリ（Swift/Kotlin）との通信
  • マルチリポジトリ: 別チームが管理するサービス間

見抜くべき問題

🔴 コードレビューで指摘すべきポイント
  • 用途の誤解: 公開APIにtRPCを使おうとしている
  • バリデーション不足: zodスキーマが不完全
  • エラーハンドリング: TRPCErrorを適切に使っていない
  • 認証/認可: middlewareで権限チェックしていない
