RDBとは何か

RDBは「Relational Database」の略です。

日本語では「関係データベース」と呼びます。

📚 たとえ話：図書館

RDBは「図書館の本棚」に似ています。

  • テーブル = 本棚（ジャンル別に分類）
  • 行（レコード） = 1冊の本
  • 列（カラム） = 本の情報（タイトル、著者、ISBN）

テーブル、行、列

RDBはデータを「表形式」で管理します。

📊 usersテーブルの例
id name email age
1 田中太郎 tanaka@example.com 25
2 山田花子 yamada@example.com 30
3 佐藤次郎 sato@example.com 22

行（Row/Record）: 横方向。1人分のデータ。
列（Column/Field）: 縦方向。データの種類。

主キー（Primary Key）

主キーは「各行を一意に識別する」列です。

🔑 主キーのルール
  • 一意: 重複しない
  • NOT NULL: 空にできない
  • 変更しない: 一度決めたら変えない

例: ユーザーID、注文番号、商品コード 

-- 主キーの定義
CREATE TABLE users (
  id SERIAL PRIMARY KEY,  -- 主キー（自動採番）
  name VARCHAR(100) NOT NULL,
  email VARCHAR(255) UNIQUE NOT NULL
);

外部キー（Foreign Key）

外部キーは「他のテーブルを参照する」列です。

🔗 テーブル間の関係

「投稿」は「ユーザー」に属する関係を表現します。 

-- postsテーブル
CREATE TABLE posts (
  id SERIAL PRIMARY KEY,
  title VARCHAR(255) NOT NULL,
  user_id INT REFERENCES users(id),  -- 外部キー
  created_at TIMESTAMP DEFAULT NOW()
);

user_idはusers.idを参照しています。

見抜くべき問題

🔍 コードレビューの観点
❌ 外部キー制約なし
-- 参照整合性が保証されない
CREATE TABLE posts (
  id SERIAL PRIMARY KEY,
  user_id INT  -- REFERENCESがない！
);

存在しないユーザーを参照できてしまう

⭕ 外部キー制約あり
-- 参照整合性が保証される
CREATE TABLE posts (
  id SERIAL PRIMARY KEY,
  user_id INT REFERENCES users(id)
    ON DELETE CASCADE
);

存在しないユーザーは参照できない

SQL基礎

📚 このページで学ぶこと
  • CRUD操作（SELECT/INSERT/UPDATE/DELETE）
  • JOIN（テーブル結合）
  • よくある間違いと対策

SQLとは

SQLは「Structured Query Language」の略です。

データベースに「問い合わせ」をする言語です。

💬 SQLの語源

「Query（クエリ）」は「質問」という意味です。
データベースに質問して、答えをもらうイメージです。

CRUD操作

データ操作の基本は「CRUD」です。

📝 CRUD = 4つの基本操作
操作 SQL 意味
Create INSERT 作成
Read SELECT 読み取り
Update UPDATE 更新
Delete DELETE 削除

SELECT（読み取り）

-- 全件取得
SELECT * FROM users;

-- 列を指定
SELECT name, email FROM users;

-- 条件を指定
SELECT * FROM users WHERE age >= 20;

-- 並び替え
SELECT * FROM users ORDER BY created_at DESC;

-- 件数制限
SELECT * FROM users LIMIT 10;

INSERT（作成）

-- 1件挿入
INSERT INTO users (name, email, age)
VALUES ('田中太郎', 'tanaka@example.com', 25);

-- 複数件挿入
INSERT INTO users (name, email, age) VALUES
  ('山田花子', 'yamada@example.com', 30),
  ('佐藤次郎', 'sato@example.com', 22);

UPDATE（更新）

-- 条件に合う行を更新
UPDATE users
SET email = 'new@example.com'
WHERE id = 1;
🔥 WHERE忘れは致命的！ 
-- ❌ WHEREがないと全行が更新される！
UPDATE users SET email = 'oops@example.com';
-- 全ユーザーのメールが書き換わる

DELETE（削除）

-- 条件に合う行を削除
DELETE FROM users WHERE id = 1;
🔥 WHERE忘れは致命的！ 
-- ❌ WHEREがないと全行が削除される！
DELETE FROM users;
-- 全ユーザーが消える

JOIN（テーブル結合）

複数のテーブルを「結合」してデータを取得します。 

-- INNER JOIN: 両方に存在するデータのみ
SELECT users.name, posts.title
FROM users
INNER JOIN posts ON users.id = posts.user_id;

-- LEFT JOIN: 左テーブルは全て、右は一致するもの
SELECT users.name, posts.title
FROM users
LEFT JOIN posts ON users.id = posts.user_id;
💡 JOINの種類
  • INNER JOIN: 両方に存在するものだけ
  • LEFT JOIN: 左は全部、右は一致のみ
  • RIGHT JOIN: 右は全部、左は一致のみ
  • FULL OUTER JOIN: 両方全部

見抜くべき問題

🔍 コードレビューの観点
❌ SELECT * の乱用
-- 不要なカラムまで取得
SELECT * FROM users;

パフォーマンス低下、機密情報漏洩リスク

⭕ 必要なカラムのみ
-- 必要なカラムだけ指定
SELECT id, name FROM users;

効率的、安全

正規化（1NF）

📚 このページで学ぶこと
  • 正規化とは何か
  • 第1正規形（1NF）のルール
  • 原子値と繰り返しグループ

正規化とは

正規化は、データの重複や矛盾を減らすための設計技法です。

🏠 たとえ話：整理整頓

正規化は「部屋の整理整頓」に似ています。
同じものを複数の場所に置かない。
物の置き場所を決めて、探しやすくする。

なぜ正規化が必要？

⚠️ 正規化しないと起きる問題
  • 更新異常: 1箇所を直し忘れてデータ不整合
  • 挿入異常: 不要なデータも一緒に入れる必要
  • 削除異常: 意図しないデータも消える

第1正規形（1NF）のルール

1NFは最も基本的な正規形です。

✓ 1NFの条件
  1. 原子値: 1つのセルに1つの値
  2. 繰り返しグループなし: 同じ種類の列を複数持たない

原子値の違反例

🔥 ❌ 1NF違反：カンマ区切り
order_id products
1 りんご, バナナ, オレンジ
2 みかん, ぶどう

1つのセルに複数の値が入っている！
「りんごだけ検索」が難しくなる。

✓ ⭕ 1NF準拠：中間テーブル

ordersテーブル:

order_id customer_id
1 101
2 102

order_itemsテーブル（中間テーブル）:

order_id product_id
1 1 (りんご)
1 2 (バナナ)
1 3 (オレンジ)

繰り返しグループの違反例

🔥 ❌ 1NF違反：繰り返しカラム
id phone1 phone2 phone3
1 090-xxxx 080-xxxx NULL

phone1, phone2, phone3... と増やすのは設計ミス。
4つ目の電話番号が必要になったら？

✓ ⭕ 1NF準拠：別テーブル 
-- 電話番号を別テーブルに
CREATE TABLE user_phones (
  id SERIAL PRIMARY KEY,
  user_id INT REFERENCES users(id),
  phone VARCHAR(20) NOT NULL
);

-- 何件でも登録可能
INSERT INTO user_phones (user_id, phone) VALUES
  (1, '090-xxxx-xxxx'),
  (1, '080-xxxx-xxxx');

見抜くべき問題

🔍 コードレビューの観点
  • カンマ区切り（CSV形式）でデータを格納していないか
  • phone1, phone2, phone3 のような連番カラムがないか
  • JSONカラムに配列を無計画に入れていないか

正規化（2NF/3NF）

📚 このページで学ぶこと
  • 第2正規形（2NF）：部分関数従属の排除
  • 第3正規形（3NF）：推移的関数従属の排除
  • 実務でよく見る違反パターン

第2正規形（2NF）

2NFは「部分関数従属」を排除します。

📖 部分関数従属とは

複合主キー（2つ以上の列）の一部だけに
依存しているカラムがある状態です。

2NF違反の例

🔥 ❌ 2NF違反

複合主キー: (order_id, product_id)

order_id product_id quantity product_name
1 101 2 りんご
2 101 3 りんご

product_nameはproduct_idだけで決まる。
複合キー全体に依存していない = 部分関数従属

✓ ⭕ 2NF準拠 
-- 注文明細テーブル
CREATE TABLE order_items (
  order_id INT REFERENCES orders(id),
  product_id INT REFERENCES products(id),
  quantity INT NOT NULL,
  PRIMARY KEY (order_id, product_id)
);

-- 商品テーブル（別に分離）
CREATE TABLE products (
  id SERIAL PRIMARY KEY,
  name VARCHAR(100) NOT NULL
);

第3正規形（3NF）

3NFは「推移的関数従属」を排除します。

📖 推移的関数従属とは

A → B → C という「間接的な依存」がある状態です。
主キーに直接依存していないカラムがある。

3NF違反の例

🔥 ❌ 3NF違反
user_id name dept_id dept_name
1 田中 10 営業部
2 山田 10 営業部

user_id → dept_id → dept_name
dept_nameはdept_idに依存（推移的関数従属）

✓ ⭕ 3NF準拠 
-- ユーザーテーブル
CREATE TABLE users (
  id SERIAL PRIMARY KEY,
  name VARCHAR(100) NOT NULL,
  dept_id INT REFERENCES departments(id)
);

-- 部門テーブル（別に分離）
CREATE TABLE departments (
  id SERIAL PRIMARY KEY,
  name VARCHAR(100) NOT NULL
);

正規形のまとめ

📊 正規化の段階
正規形 ルール 違反例
1NF 原子値のみ "a,b,c" カンマ区切り
2NF 部分関数従属なし 複合キーの一部に依存
3NF 推移的関数従属なし A→B→C 間接依存
💡 実務でのポイント

通常は3NFまで正規化すれば十分です。
ただしパフォーマンスのため、意図的に非正規化することもあります。
「なぜ非正規化したか」をコメントで残しましょう。

インデックス基礎

📚 このページで学ぶこと
  • インデックスとは何か
  • B-treeインデックスの仕組み
  • EXPLAINでクエリを分析

インデックスとは

インデックスは「索引」という意味です。

📚 たとえ話：本の索引

分厚い本で「JavaScript」という単語を探すとき、
1ページ目から順に探すのは大変ですよね。
索引（インデックス）があれば、すぐにページ番号がわかります。

データベースのインデックスも同じです。
データを素早く見つけるための「目印」です。

B-treeインデックス

PostgreSQLで最も一般的なインデックスはB-treeです。

🌳 B-treeの仕組み

B-tree = Balanced Tree（平衡木）

  • データがソートされた状態で保存される
  • 検索がO(log n)で高速
  • =, <, >, BETWEEN に有効

インデックスの作成と削除

-- インデックスの作成
CREATE INDEX idx_users_email ON users(email);

-- ユニークインデックス（重複禁止）
CREATE UNIQUE INDEX idx_users_email_unique ON users(email);

-- インデックスの削除
DROP INDEX idx_users_email;

インデックスが有効な場面

✓ インデックスを作るべきカラム
  • WHERE句で頻繁に使うカラム
  • JOINの結合条件に使うカラム
  • ORDER BYでソートするカラム
  • 外部キー（必須！）

EXPLAIN（実行計画）

EXPLAINでクエリの実行計画を確認できます。 

-- 実行計画を確認
EXPLAIN SELECT * FROM users WHERE email = 'test@example.com';

-- より詳細な情報（実際に実行）
EXPLAIN ANALYZE SELECT * FROM users WHERE email = 'test@example.com';
📊 EXPLAINの読み方 
-- インデックスがない場合
Seq Scan on users  (cost=0.00..25.00 rows=1000)
↑ 全件スキャン（遅い）

-- インデックスがある場合
Index Scan using idx_users_email on users  (cost=0.00..8.27 rows=1)
↑ インデックススキャン（速い）

Seq Scan（Sequential Scan）が出たら要注意！
インデックスを追加すべきか検討しましょう。

見抜くべき問題

🔍 コードレビューの観点
❌ 外部キーにインデックスなし
-- 外部キーを追加
ALTER TABLE posts
ADD COLUMN user_id INT REFERENCES users(id);
-- インデックスがない！JOINが遅くなる
⭕ 外部キーにインデックスあり
-- 外部キーを追加
ALTER TABLE posts
ADD COLUMN user_id INT REFERENCES users(id);

-- インデックスも追加
CREATE INDEX idx_posts_user_id ON posts(user_id);

インデックス戦略

📚 このページで学ぶこと
  • 複合インデックス（Composite Index）
  • 部分インデックス（Partial Index）
  • GINインデックス（全文検索、配列）

複合インデックス

複合インデックスは、複数のカラムを組み合わせたインデックスです。 

-- 複合インデックスの作成
CREATE INDEX idx_orders_user_status
ON orders(user_id, status);

-- このクエリで有効
SELECT * FROM orders
WHERE user_id = 1 AND status = 'pending';
⚠️ カラムの順序が重要！

複合インデックスは左から順に使われます。 

-- インデックス: (user_id, status, created_at)

-- ⭕ user_id のみ → 使われる
WHERE user_id = 1

-- ⭕ user_id + status → 使われる
WHERE user_id = 1 AND status = 'pending'

-- ❌ status のみ → 使われない！
WHERE status = 'pending'

-- ❌ created_at のみ → 使われない！
WHERE created_at > '2024-01-01'

部分インデックス

部分インデックスは、条件に合う行だけにインデックスを作ります。 

-- アクティブユーザーだけにインデックス
CREATE INDEX idx_users_active_email
ON users(email)
WHERE is_active = true;

-- 未完了の注文だけにインデックス
CREATE INDEX idx_orders_pending
ON orders(created_at)
WHERE status = 'pending';
✓ 部分インデックスのメリット
  • インデックスサイズが小さくなる
  • 更新時のオーバーヘッドが減る
  • 特定のクエリパターンに最適化できる

GINインデックス

GIN（Generalized Inverted Index）は特殊なインデックスです。

📖 GINが有効な場面
  • 配列の検索
  • 全文検索
  • JSONBの検索
-- 配列カラムへのGINインデックス
CREATE INDEX idx_posts_tags ON posts USING GIN(tags);

-- 配列の検索
SELECT * FROM posts WHERE tags @> ARRAY['javascript'];

-- JSONBへのGINインデックス
CREATE INDEX idx_users_metadata ON users USING GIN(metadata);

-- JSONBの検索
SELECT * FROM users WHERE metadata @> '{"role": "admin"}';

インデックスの注意点

⚠️ 過剰なインデックスは逆効果
  • INSERT/UPDATE/DELETEが遅くなる
  • ストレージを消費する
  • メンテナンスのコストが増える

「念のため」で作りすぎないこと！

見抜くべき問題

🔍 コードレビューの観点
❌ 全カラムにインデックス
-- やりすぎ！
CREATE INDEX idx1 ON users(name);
CREATE INDEX idx2 ON users(email);
CREATE INDEX idx3 ON users(age);
CREATE INDEX idx4 ON users(created_at);
-- 全部作るのはNG
⭕ 必要なものだけ
-- クエリパターンに基づいて選択
CREATE INDEX idx_users_email ON users(email);
-- emailはログインで使うから必要

-- 複合インデックスで対応
CREATE INDEX idx_orders_user_status
ON orders(user_id, status);

トランザクション

📚 このページで学ぶこと
  • トランザクションとACID特性
  • 分離レベル
  • デッドロックと対策

トランザクションとは

トランザクションは「一連の処理をまとめる」仕組みです。

💰 たとえ話：銀行振込

AさんからBさんに1万円を振り込む場合：
1. Aさんの口座から1万円を引く
2. Bさんの口座に1万円を足す

この2つの処理は両方成功するか、両方失敗するべき。
途中で止まると、お金が消えてしまいます。

ACID特性

トランザクションが満たすべき4つの特性です。

📊 ACID
特性 意味
Atomicity（原子性） 全て成功 or 全て失敗
Consistency（一貫性） 整合性を保つ
Isolation（分離性） 他の処理から独立
Durability（永続性） 確定したら消えない

トランザクションの基本操作

-- トランザクション開始
BEGIN;

-- 処理を実行
UPDATE accounts SET balance = balance - 10000 WHERE id = 1;
UPDATE accounts SET balance = balance + 10000 WHERE id = 2;

-- 成功したらコミット
COMMIT;

-- 失敗したらロールバック
ROLLBACK;

分離レベル

分離レベルは、トランザクション間の「見え方」を決めます。

📊 分離レベル一覧
レベル 特徴
READ UNCOMMITTED 他の未コミットを読める（危険）
READ COMMITTED コミット済みだけ読める（PostgreSQL標準）
REPEATABLE READ 同じクエリで同じ結果
SERIALIZABLE 完全分離（最も安全、最も遅い）

デッドロック

デッドロックは「お互いにロックを待ち合う」状態です。

🔥 デッドロックの例 
トランザクションA:
  1. テーブル1をロック
  2. テーブル2をロックしようとする → 待ち

トランザクションB:
  1. テーブル2をロック
  2. テーブル1をロックしようとする → 待ち

→ 永遠に終わらない！
✓ デッドロックの対策
  • ロックの順序を統一する（常にテーブル1→2の順）
  • トランザクションを短くする
  • タイムアウトを設定する

見抜くべき問題

🔍 コードレビューの観点
❌ トランザクションなし
// 途中で失敗するとデータ不整合
await db.execute('UPDATE accounts SET ...');
await db.execute('UPDATE accounts SET ...');
// 2つ目が失敗しても1つ目は戻らない
⭕ トランザクションあり
await db.transaction(async (tx) => {
  await tx.execute('UPDATE accounts SET ...');
  await tx.execute('UPDATE accounts SET ...');
  // どちらか失敗したら両方ロールバック
});

ORMとは

ORMは「Object-Relational Mapping」の略です。

🔗 ORMの役割

データベースのテーブルと
プログラムのオブジェクトを対応させます。
SQLを直接書かなくても、データを操作できます。 

// ORMなし（生SQL）
const result = await db.query(
  'SELECT * FROM users WHERE id = $1',
  [userId]
);

// ORMあり（Prisma）
const user = await prisma.user.findUnique({
  where: { id: userId }
});

Prisma vs Drizzle（2026年版）

📊 比較表
項目 Prisma Drizzle

  • チームにSQLが苦手な人がいる

Prismaスキーマ

Prismaではschema.prismaファイルでモデルを定義します。 

// prisma/schema.prisma

generator client {
  provider = "prisma-client-js"
}

datasource db {
  provider = "postgresql"
  url      = env("DATABASE_URL")
}

model User {
  id        Int      @id @default(autoincrement())
  email     String   @unique
  name      String?
  posts     Post[]   // リレーション
  createdAt DateTime @default(now())
}

model Post {
  id        Int      @id @default(autoincrement())
  title     String
  content   String?
  published Boolean  @default(false)
  author    User     @relation(fields: [authorId], references: [id])
  authorId  Int
}

N+1問題と対策

🔥 ❌ N+1問題 
// ユーザー一覧を取得（1クエリ）
const users = await prisma.user.findMany();

// 各ユーザーの投稿を取得（Nクエリ）
for (const user of users) {
  const posts = await prisma.post.findMany({
    where: { authorId: user.id }
  });
  // ユーザーが100人いたら100回クエリが走る！
}
✓ ⭕ Eager Loading（includeで解決） 
// 1クエリで全て取得
const users = await prisma.user.findMany({
  include: {
    posts: true  // リレーションを一緒に取得
  }
});

// users[0].posts でアクセス可能

selectで必要なカラムのみ取得

// ❌ 全カラム取得
const users = await prisma.user.findMany();

// ⭕ 必要なカラムのみ
const users = await prisma.user.findMany({
  select: {
    id: true,
    name: true
    // emailは不要なので取得しない
  }
});

クエリ最適化の基本

✓ 最適化のチェックリスト
  • 必要なカラムだけSELECT（SELECT * を避ける）
  • WHERE句で絞り込む
  • 適切なインデックスを作成
  • EXPLAINで実行計画を確認
  • N+1問題を解消

スロークエリの発見

-- PostgreSQL: 実行時間が長いクエリを記録
-- postgresql.conf で設定
log_min_duration_statement = 1000  -- 1秒以上のクエリをログ

-- 実行計画で確認
EXPLAIN ANALYZE
SELECT * FROM orders
WHERE user_id = 1 AND status = 'pending';

コネクションプール

コネクションプールは、DB接続を再利用する仕組みです。

🏊 たとえ話：プール

毎回新しいプールを作るのではなく、
既存のプールを共有して使い回すイメージです。
接続の作成コストを削減できます。 

// Prismaのコネクションプール設定
// schema.prisma
datasource db {
  provider = "postgresql"
  url      = env("DATABASE_URL")
  // ?connection_limit=10 をURLに追加
}

// Node.js pg-pool
import { Pool } from 'pg';

const pool = new Pool({
  connectionString: process.env.DATABASE_URL,
  max: 10,  // 最大接続数
  idleTimeoutMillis: 30000  // アイドルタイムアウト
});

見抜くべき問題

🔍 コードレビューの観点
❌ 毎回接続を作成
async function getUser(id: number) {
  // 毎回新しい接続を作成
  const prisma = new PrismaClient();
  const user = await prisma.user.findUnique({
    where: { id }
  });
  await prisma.$disconnect();
  return user;
}
⭕ シングルトンで再利用
// グローバルで1つのインスタンス
const prisma = new PrismaClient();

async function getUser(id: number) {
  return prisma.user.findUnique({
    where: { id }
  });
}
