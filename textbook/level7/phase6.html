機能要件 vs 非機能要件

システムの要件は2種類に分類されます。

機能要件（FR）

「何ができるか」

  • ユーザー登録ができる
  • 商品を検索できる
  • 注文を確定できる

What（システムが行う機能）

非機能要件（NFR）

「どのように動くか」

  • 3秒以内に応答する
  • 99.9%の可用性
  • 同時1万ユーザーを処理

How（品質・制約）

🏠 たとえ話：家の要件

機能要件：3LDK、キッチン、風呂がある
非機能要件：耐震等級3、断熱性能UA値0.46以下、30年保証

機能だけでは住めない。安全性・耐久性も必要。
システムも同じで、非機能要件なしでは実用にならない。

ISO 25010 品質モデル

ISO/IEC 25010は、ソフトウェア品質の国際標準です。
8つの品質特性を定義しています。

📊 ISO 25010 品質特性ツリー

8つの品質特性の概要

品質特性 意味 例
機能適合性 機能がニーズを満たす度合い 全機能が仕様通り動作
性能効率性 使用リソースに対する性能 レスポンス3秒以内
互換性 他システムとの連携能力 API互換、データ形式
使用性 使いやすさ、学習しやすさ 直感的UI、ヘルプ充実
信頼性 障害なく動作し続ける能力 99.9%可用性、自動復旧
セキュリティ 情報・システムの保護 認証、暗号化、監査ログ
保守性 修正・改善のしやすさ モジュール化、テスト容易
移植性 別環境への移行しやすさ コンテナ化、クラウド移行

なぜ非機能要件が重要か

⚠️ 非機能要件を軽視した結果
  • 性能問題：リリース後に「遅すぎて使えない」
  • スケール問題：ユーザー増加でシステムダウン
  • セキュリティ事故：情報漏洩で信用失墜
  • 運用地獄：障害対応で開発が止まる

非機能要件は「後から追加」が極めて困難です。
設計段階から考慮する必要があります。

性能要件の定義方法

📚 このページで学ぶこと
  • 性能要件の3つの観点（レイテンシ、スループット、容量）
  • パーセンタイルによる定義方法
  • 性能要件の書き方

性能要件の3つの観点

観点 意味 例
レイテンシ 1リクエストの応答時間 API応答200ms以内
スループット 単位時間あたりの処理量 1000 req/sec
容量 扱えるデータ量・接続数 同時接続10万、DB100TB
🏠 たとえ話：高速道路

レイテンシ：東京→大阪まで何時間か（1台の移動時間）
スループット：1時間に何台通れるか（処理能力）
容量：同時に何台走れるか（キャパシティ）

パーセンタイルで定義する

「平均200ms」は意味がない指標です。
なぜなら、一部のリクエストが極端に遅くても平均は良く見えるから。

悪い定義
// 平均は騙される
平均レスポンス: 200ms

// 実態
- 90%は50ms
- 10%は1500ms
- 平均 = 195ms ← 良く見える！

10人に1人は1.5秒待たされる

良い定義
// パーセンタイルで定義
p50: 100ms以内  // 半分のリクエスト
p95: 300ms以内  // 95%のリクエスト
p99: 500ms以内  // 99%のリクエスト

// これなら「ほぼ全員」の体験を保証
📝 パーセンタイルの意味
  • p50（中央値）：半分のリクエストがこの時間以内
  • p95：95%のリクエストがこの時間以内（100回中95回）
  • p99：99%のリクエストがこの時間以内（100回中99回）
  • p99.9：99.9%がこの時間以内（1000回中999回）

SLAでよく使われるのはp95やp99です。

性能要件の書き方

【性能要件ドキュメント例】

■ API性能要件
| エンドポイント | p50 | p95 | p99 | スループット |
|---------------|-----|-----|-----|-------------|
| GET /users    | 50ms | 100ms | 200ms | 500 req/s |
| POST /orders  | 100ms | 300ms | 500ms | 100 req/s |
| GET /search   | 200ms | 500ms | 1s | 200 req/s |

■ 容量要件
- 同時接続ユーザー: 10,000人
- データ保持期間: 5年
- 1日あたりデータ増加量: 100GB

■ 測定条件
- 負荷条件: 通常負荷の2倍
- ネットワーク: 同一リージョン内
- データ量: 本番相当
🔍 コードレビューの観点

曖昧な性能要件を見つけたら指摘：

  • 「高速であること」→ 数値で定義されていない
  • 「平均200ms」→ パーセンタイルで定義すべき
  • 「十分なスループット」→ 具体的な数値がない
  • 測定条件が未定義 → 同じ条件で測れない

信頼性・可用性の定量化

📚 このページで学ぶこと
  • 可用性の計算方法（ナイン）

可用性とナイン

可用性 = システムが使える時間の割合

可用性 通称 年間ダウンタイム 月間ダウンタイム
99% 2ナイン 3.65日 7.3時間
99.9% 3ナイン 8.76時間 43.8分
99.95% 3.5ナイン 4.38時間 21.9分
99.99% 4ナイン 52.6分 4.4分
99.999% 5ナイン 5.26分 26秒
⚠️ ナインを1つ増やすコスト

99.9% → 99.99%（3ナイン→4ナイン）は
コストが10倍以上かかることも珍しくない。

  • 冗長化構成の複雑化
  • 監視・運用体制の強化
  • 自動復旧の高度化

ビジネス要件に見合った可用性を選ぶことが重要。

MTBF / MTTR / MTTA

指標 正式名称 意味 計算
MTBF Mean Time Between Failures 障害間の平均時間 稼働時間 / 障害回数
MTTR Mean Time To Repair 平均復旧時間 総復旧時間 / 障害回数
MTTA Mean Time To Acknowledge 平均認知時間 検知から対応開始まで
📝 可用性の計算式 
可用性 = MTBF / (MTBF + MTTR)

例：
- MTBF = 720時間（30日に1回障害）
- MTTR = 0.5時間（30分で復旧）

可用性 = 720 / (720 + 0.5) = 99.93%

MTTRを短くすることが可用性向上の鍵。

信頼性を高める設計

アプローチ 説明 例
冗長化 コンポーネントを複数用意 マルチAZ、レプリカDB
フェイルオーバー 障害時に自動で切り替え アクティブ-スタンバイ
グレースフルデグラデーション 一部機能を落として継続 推薦機能停止で基本検索のみ
サーキットブレーカー 障害の連鎖を防ぐ 外部API障害時に即座にエラー返却

SLA / SLO / SLI の違いと設計

📚 このページで学ぶこと
  • SLA、SLO、SLIの違い
  • エラーバジェットの考え方

SLA / SLO / SLI とは

📊 SLA / SLO / SLI の関係
用語 正式名称 意味 対象
SLI Service Level Indicator 測定可能な品質指標 エンジニア
SLO Service Level Objective SLIの目標値（内部目標） 開発チーム
SLA Service Level Agreement 顧客との契約（ペナルティ付き） 顧客・ビジネス
🏠 たとえ話：宅配便

SLI：「今日の配送で98%が翌日到着した」（実測値）
SLO：「翌日到着率99%を目指す」（内部目標）
SLA：「翌日届かなければ送料返金」（顧客との約束）

エラーバジェット

エラーバジェット = 「許容されるエラーの予算」

📝 エラーバジェットの計算 
SLO: 可用性 99.9%
→ 許容ダウンタイム = 0.1% = 月43.8分

月初のエラーバジェット: 43.8分
- 障害Aで10分ダウン → 残り33.8分
- 障害Bで15分ダウン → 残り18.8分
- デプロイ失敗で5分ダウン → 残り13.8分

残りが少ない → リスクの高いリリースを延期
✓ エラーバジェットの活用
  • バジェット余裕あり：積極的に新機能リリース
  • バジェット残り少：安定性重視、リスク回避
  • バジェット使い切り：新機能凍結、信頼性改善に集中

開発速度と信頼性のバランスを取る仕組み。

SLO設計のベストプラクティス

原則 説明
ユーザー視点で選ぶ CPU使用率ではなく、レスポンスタイムなど体験に直結する指標
少数に絞る 多すぎると管理不能。3〜5個程度
SLA > SLO SLOはSLAより厳しく。余裕を持つ
達成可能な目標 100%は現実的でない。99.99%も高コスト
🔍 コードレビューの観点

SLO設計の問題を見つけたら指摘：

  • SLIが測定不可能（「ユーザー満足度」など曖昧）
  • SLOが100%（達成不可能）
  • SLOがSLAより緩い（余裕がない）
  • 内部指標のみ（CPU使用率など、UXに直結しない）

セキュリティ要件の洗い出し

📚 このページで学ぶこと
  • CIA三要素（機密性・完全性・可用性）
  • セキュリティ要件の分類
  • 要件定義で考慮すべきポイント

CIA三要素

セキュリティの基本はCIA三要素です。

要素 英語 意味 脅威例
機密性 Confidentiality 許可された人だけがアクセス 情報漏洩
完全性 Integrity データが改ざんされていない データ改ざん
可用性 Availability 必要な時に使える DoS攻撃
🏠 たとえ話：銀行の金庫

機密性：権限者だけが金庫を開けられる
完全性：お金が勝手に増減しない
可用性：営業時間中は必ず引き出せる

セキュリティ要件の分類

カテゴリ 要件例 実装例
認証 ユーザーが本人であることを確認 パスワード、MFA、生体認証
認可 許可された操作だけを許す RBAC、ABAC、ACL
暗号化 データを読めない形で保存・送信 TLS、AES-256、ハッシュ化
監査 誰が何をしたか記録 監査ログ、アクセスログ
入力検証 不正な入力を防ぐ サニタイズ、バリデーション

セキュリティ要件の書き方

【セキュリティ要件ドキュメント例】

■ 認証要件
- パスワードは12文字以上、大小文字・数字・記号を含む
- ログイン失敗5回でアカウントロック（30分）
- セッションタイムアウト: 30分
- 管理者アカウントはMFA必須

■ 暗号化要件
- 通信: TLS 1.3以上
- 保存データ: AES-256で暗号化
- パスワード: bcrypt（コスト12以上）でハッシュ化

■ 監査要件
- 全APIアクセスをログに記録
- ログ保持期間: 1年
- ログは改ざん検知可能な形式で保存

■ コンプライアンス
- GDPR対応（EU顧客のデータ処理）
- PCI DSS Level 1（クレジットカード取扱）
🔍 コードレビューの観点

セキュリティ要件の漏れを指摘：

  • パスワードポリシーが未定義
  • 暗号化アルゴリズムが古い（MD5、SHA-1）
  • 監査ログの要件がない
  • セッション管理の要件がない
  • 入力検証の基準がない

STRIDEとは

STRIDEは、Microsoftが開発した脅威分類フレームワークです。
6種類の脅威を体系的に洗い出します。

📊 STRIDE脅威モデル

各脅威と対策

脅威 意味 例 対策
S なりすまし 偽のログインフォーム 多要素認証、証明書
T 改ざん SQLインジェクション 入力検証、署名
R 否認 「注文してない」 監査ログ、電子署名
I 情報漏洩 APIでパスワード露出 暗号化、アクセス制御
D サービス拒否 DDoS攻撃 レート制限、WAF
E 権限昇格 一般ユーザーが管理者に 最小権限、RBAC

脅威モデリングの進め方

【脅威モデリングの手順】

1. システムを図示する（DFD: データフロー図）
   - ユーザー、プロセス、データストア、外部システム
   - データの流れを矢印で表現

2. 境界を特定する（Trust Boundary）
   - インターネット ↔ アプリ
   - アプリ ↔ データベース
   - 社内 ↔ 社外

3. 各要素にSTRIDEを適用
   - この通信で「なりすまし」は可能か？
   - このデータは「改ざん」されうるか？
   - ...

4. 対策を検討・優先順位付け
   - リスク = 影響度 × 発生確率
   - 高リスクから対応
🔍 コードレビューの観点

各STRIDEの観点でレビュー：

  • S：認証は十分か？セッション管理は？
  • T：入力検証は？SQLインジェクション対策は？
  • R：監査ログは記録されるか？
  • I：機密データは暗号化されているか？
  • D：レート制限は？リソース枯渇対策は？
  • E：認可チェックは全APIにあるか？

運用性・保守性の要件

📚 このページで学ぶこと
  • 運用性（Operability）の要件
  • 保守性（Maintainability）の要件
  • DevOps/SREの観点

運用性とは

運用性 = システムを安定して動かし続けるための特性

観点 意味 要件例
監視性 状態が把握できる メトリクス、ログ、トレース
デプロイ容易性 安全に素早くリリース ロールバック可能、Blue-Green
構成管理 設定変更が容易 環境変数、Feature Flag
障害対応 問題を素早く解決 ランブック、自動復旧

保守性とは

保守性 = システムを修正・拡張しやすい特性

観点 意味 要件例
モジュール性 独立した部品に分割 疎結合、高凝集
解析性 問題箇所を特定しやすい ドキュメント、コメント
修正性 変更の影響が局所的 インターフェース分離
試験性 テストしやすい DI、モック可能

運用要件の書き方

【運用要件ドキュメント例】

■ 監視要件
- アプリケーションメトリクス: Prometheus形式で公開
- ログ: JSON形式、構造化ログ、correlation ID付与
- トレース: OpenTelemetry対応
- アラート: Slack通知、PagerDuty連携

■ デプロイ要件
- デプロイ頻度: 1日複数回可能
- ロールバック: 5分以内に前バージョンへ
- デプロイ方式: Blue-Greenまたはカナリア
- デプロイ時間: 15分以内

■ 障害対応要件
- ランブック: 全アラートに対応手順あり
- オンコール: 24/365体制
- MTTAの目標: 5分以内
- MTTRの目標: 30分以内

■ バックアップ要件
- 頻度: 日次フルバックアップ、1時間ごと増分
- 保持期間: 30日
- リストア時間: 4時間以内
- リストアテスト: 月1回実施

DevOps/SREの観点

📝 設計段階で考慮すべきこと
  • Day 2 Operation：リリース後の運用を設計段階で考慮
  • Observability：ログ・メトリクス・トレースの3本柱
  • Chaos Engineering：障害を意図的に起こして耐性を確認
  • Runbook：障害対応手順を事前に文書化
🔍 コードレビューの観点

運用性の問題を見つけたら指摘：

  • ログが出力されていない、または不十分
  • 設定がハードコードされている
  • ヘルスチェックエンドポイントがない
  • テストがない、またはカバレッジが低い
  • デプロイ手順が手動で複雑

スケーラビリティの見積もり

📚 このページで学ぶこと
  • スケールアップ vs スケールアウト
  • キャパシティプランニングの方法
  • 成長予測と余裕の見積もり

スケーラビリティとは

スケーラビリティ = 負荷増加に対応できる能力

スケールアップ（垂直）

サーバーを強化する

  • CPU、メモリを増設
  • シンプルだが限界あり
  • 単一障害点のリスク

例：EC2 t3.medium → t3.xlarge

スケールアウト（水平）

サーバーを増やす

  • 同じサーバーを追加
  • 理論上は無限に拡張可能
  • 設計が複雑になる

例：EC2 2台 → 10台

キャパシティプランニング

【キャパシティ見積もりの例】

■ 現状の把握
- 現在のDAU: 10,000人
- ピーク時リクエスト: 100 req/s
- 平均レスポンス: 200ms
- サーバー: 2台（負荷50%）

■ 成長予測（1年後）
- 予測DAU: 50,000人（5倍）
- 予測ピーク: 500 req/s

■ 必要リソースの計算
- 現在の処理能力: 200 req/s（2台 × 100 req/s/台）
- 必要な処理能力: 500 req/s × 1.5（余裕）= 750 req/s
- 必要サーバー数: 750 / 100 = 8台

■ 余裕の考慮
- 通常時の余裕: 30%
- ピーク対応: 通常の2倍
- 障害時の縮退: N+1構成

スケーラビリティ要件の書き方

【スケーラビリティ要件例】

■ 容量要件
- 初期: 同時接続 1,000人、DAU 10,000人
- 1年後: 同時接続 5,000人、DAU 50,000人
- 3年後: 同時接続 20,000人、DAU 200,000人

■ スケーリング方式
- Webサーバー: 水平スケーリング（オートスケール）
- DBサーバー: 読み取りレプリカ追加
- キャッシュ: Redisクラスター（シャーディング）

■ オートスケール条件
- CPU使用率70%超過で1台追加
- CPU使用率30%未満で1台削減
- 最小: 2台、最大: 20台
- クールダウン: 5分

■ データ増加見積もり
- 1日あたり: 10GB
- 1年後のデータ量: 3.6TB
- 3年後のデータ量: 10TB以上
⚠️ スケーラビリティの罠
  • データベースがボトルネック：アプリは増やせるがDBは増やしにくい
  • セッション管理：サーバー間でセッション共有が必要
  • キャッシュの整合性：複数サーバーでキャッシュが不整合
  • ファイルストレージ：ローカルファイルは共有できない
🔍 コードレビューの観点

スケーラビリティを阻害する設計：

  • ローカルファイルへの書き込み（共有ストレージ未使用）
  • インメモリセッション（Redisなど外部化されていない）
  • シングルトンの乱用（状態を持つシングルトン）
  • 同期的な重い処理（非同期/キュー化すべき）

品質特性のトレードオフ

📚 このページで学ぶこと
  • 品質特性間のトレードオフ
  • ATAM（Architecture Tradeoff Analysis Method）
  • 意思決定の記録方法

トレードオフとは

すべての品質特性を最大化することは不可能です。
ある特性を高めると、別の特性が犠牲になります。

高める特性 犠牲になる特性 例
セキュリティ 使用性、性能 MFAで手間増加、暗号化で遅延
性能 保守性、セキュリティ キャッシュで複雑化、検証省略
信頼性 コスト、性能 冗長化でコスト増、同期で遅延
保守性 性能 抽象化レイヤーでオーバーヘッド
機能の豊富さ 使用性 機能が多すぎて複雑に
🏠 たとえ話：車の設計

燃費を良くするとパワーが下がる
安全装備を増やすと重量が増える
コストを下げると品質が下がる

すべてを最高にはできない。優先順位を決める必要がある。

ATAM（Architecture Tradeoff Analysis Method）

ATAMは、アーキテクチャのトレードオフを分析する手法です。 

【ATAMの手順】

1. ビジネス目標の明確化
   - 何を達成したいか？
   - 最も重要なことは何か？

2. 品質属性の優先順位付け
   - 性能 > セキュリティ > 保守性
   - または逆

3. アーキテクチャアプローチの評価
   - 各選択肢のメリット・デメリット
   - どの品質に影響するか

4. トレードオフポイントの特定
   - 「これを選ぶとこれが犠牲になる」
   - リスクの洗い出し

5. 意思決定の記録（ADR）
   - なぜその選択をしたか
   - 他の選択肢は何だったか

ADR（Architecture Decision Record）

【ADRテンプレート】

# ADR-001: セッション管理方式の選定

## ステータス
承認済み（2024-01-15）

## コンテキスト
ユーザーセッションの管理方式を決定する必要がある。
現在、DAU 10,000人、1年後には50,000人を想定。

## 選択肢
1. サーバーサイドセッション（インメモリ）
2. サーバーサイドセッション（Redis）
3. JWT（クライアントサイド）

## 決定
**Redis によるサーバーサイドセッション**を採用

## 根拠
- スケーラビリティ: Redisはクラスター化可能
- セキュリティ: JWTは無効化が困難
- 複雑さ: インメモリはスケールアウト困難

## トレードオフ
- JWTより遅延が増加（数ms）
- Redisの運用コストが発生

## 結果
セッション管理はRedisで一元化。
TTL 30分、最大セッション数は1ユーザー5つまで。
🔍 コードレビューの観点

トレードオフの記録漏れを指摘：

  • なぜこの技術を選んだか記録がない
  • 他の選択肢との比較がない
  • デメリットが考慮されていない
  • 将来の変更可能性が検討されていない

非機能要件レビューチェックリスト

性能要件

  • [ ] レスポンスタイムがパーセンタイル（p95/p99）で定義されているか
  • [ ] スループット目標が具体的な数値で示されているか
  • [ ] 測定条件（負荷、データ量）が明記されているか
  • [ ] ピーク時の要件が定義されているか

信頼性・可用性

  • [ ] 可用性目標がナインで定義されているか（99.9%など）
  • [ ] MTTRの目標が設定されているか
  • [ ] 障害時の縮退運転が定義されているか
  • [ ] バックアップ・リストア要件があるか
  • [ ] 災害復旧（DR）要件が検討されているか

セキュリティ

  • [ ] 認証要件（パスワードポリシー、MFA）が定義されているか
  • [ ] 認可要件（権限モデル）が定義されているか
  • [ ] 暗号化要件（通信、保存データ）が明記されているか
  • [ ] 監査ログ要件があるか
  • [ ] コンプライアンス要件（GDPR、PCI DSSなど）が考慮されているか
  • [ ] STRIDE観点での脅威分析が行われているか

運用性・保守性

  • [ ] 監視要件（ログ、メトリクス、アラート）が定義されているか
  • [ ] デプロイ要件（頻度、時間、ロールバック）が明記されているか
  • [ ] 障害対応体制（オンコール、ランブック）が定義されているか
  • [ ] 設定変更の方法が明確か

スケーラビリティ

  • [ ] 現在と将来（1年後、3年後）の容量要件が定義されているか
  • [ ] スケーリング方式（スケールアップ/アウト）が明確か
  • [ ] オートスケール条件が具体的か
  • [ ] データ増加の見積もりがあるか

トレードオフと意思決定

  • [ ] 品質特性の優先順位が明確か
  • [ ] トレードオフが認識・記録されているか
  • [ ] 重要な意思決定がADRとして残されているか
  • [ ] SLA/SLO/SLIが適切に設計されているか
