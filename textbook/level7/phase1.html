データモデリングとは何か

データモデリングとは、データの構造・関係・制約を設計することです。

🏠 たとえ話：家の設計

家を建てる前に設計図を描くように、
データベースを作る前にデータモデルを設計します。

設計図なしに家を建てると、あとから「部屋が足りない」「配管が通らない」という問題が起きます。
データモデルも同じ。設計なしに作ると修正コストが膨大になります。

なぜデータモデリングが重要か

⚠️ 設計なしの代償
  • データの重複：同じ情報が複数箇所に → 不整合の原因
  • 拡張困難：新しい要件に対応できない構造
  • パフォーマンス問題：非効率なクエリが必要になる
  • 保守性の低下：何がどこにあるか分からない

3つのモデルレベル

データモデリングには3つの抽象度があります。

📊 概念・論理・物理モデルの関係
モデル 目的 対象者 例
概念モデル ビジネス要件を表現 経営者、業務担当者 「顧客が注文を行う」
論理モデル データ構造を定義 設計者、アーキテクト 顧客(ID, 名前)、注文(ID, 顧客ID)
物理モデル 実装詳細を決定 DBA、開発者 customer_id INT PRIMARY KEY

各モデルの詳細

概念モデル
  • 技術用語を使わない
  • ビジネスの「もの」と「関係」だけを表現
  • 属性や型は含まない
顧客 ──注文する──→ 商品
         │
         └─配送先─→ 住所
論理モデル
  • エンティティと属性を定義
  • 主キー・外部キーを設計
  • 正規化を適用
顧客(顧客ID, 名前, メール)
注文(注文ID, 顧客ID, 注文日)
注文明細(明細ID, 注文ID, 商品ID)
🔧 物理モデル 
CREATE TABLE customers (
  customer_id INT PRIMARY KEY AUTO_INCREMENT,
  name VARCHAR(100) NOT NULL,
  email VARCHAR(255) UNIQUE NOT NULL,
  INDEX idx_email (email)
) ENGINE=InnoDB;

データ型、インデックス、ストレージエンジンなど実装の詳細を決定します。

🔍 コードレビューの観点

以下を見つけたら指摘しましょう：

  • 概念モデルなしで実装：ビジネス要件を理解していない可能性
  • 論理モデルがない：正規化の検討がされていない
  • 物理モデルが最適化されていない：インデックス不足など
  • 正規化の過不足：過度な正規化はJOIN地獄を生み、非正規化しすぎるとデータ不整合の温床になる。ユースケースに応じた適切なバランスか確認する
  • 外部キー制約の欠如：アプリ側でのみ参照整合性を担保しているケース。DBレベルでFOREIGN KEY制約を設定し、孤立レコードの発生を防ぐ
  • カラム命名の一貫性：userIdとuser_idが混在、createdとcreated_atが混在していないか。チーム内で命名規則を統一する

エンティティと属性の設計

📚 このページで学ぶこと

エンティティとは

エンティティとは、データとして管理したい「もの」や「概念」です。

🏠 たとえ話：管理台帳

会社で管理する「もの」を考えてみましょう。

  • 従業員台帳：従業員エンティティ
  • 商品台帳：商品エンティティ
  • 注文履歴：注文エンティティ

「台帳を作って管理したいもの」がエンティティになります。

エンティティの見つけ方

💡 エンティティ発見のヒント
  • 名詞に注目：「顧客」「注文」「商品」
  • 識別可能：一意に特定できるか？
  • 複数存在：複数のインスタンスがあるか？
  • 属性を持つ：関連する情報があるか？
エンティティになるもの
  • 顧客（ID、名前、メール...）
  • 注文（ID、日付、金額...）
  • 商品（ID、名前、価格...）
  • 従業員（ID、名前、部署...）
エンティティにならないもの
  • 「購入する」（動詞 → 関連または属性）
  • 「合計金額」（計算結果 → 導出属性）
  • 「日本円」（単位 → 属性の一部）
  • 「TRUE/FALSE」（値 → 属性値）

属性とは

属性とは、エンティティが持つ特性・情報です。

属性の種類 説明 例
単純属性 それ以上分解できない 年齢、価格
複合属性 複数の部分に分解可能 住所 → 都道府県、市区町村、番地
導出属性 他の属性から計算できる 年齢（生年月日から）、合計金額
多値属性 複数の値を持つ 電話番号（複数）、趣味（複数）

属性設計のベストプラクティス

✓ 良い属性設計
  • 原子性：1つの属性に1つの意味
  • 完全性：必要な情報が揃っている
  • 非冗長：同じ情報の重複がない
  • 一貫性：命名規則が統一されている
よくある設計ミス
-- ❌ 複数の情報を1つの属性に
顧客(
  id,
  name_and_address,  -- 名前と住所を結合？
  tel1_tel2,         -- 電話番号をカンマ区切り？
)
正しい設計
-- ⭕ 属性を適切に分離
顧客(
  id,
  name,
  prefecture,
  city,
  address_line
)
電話番号(
  id,
  customer_id,
  phone_number,
  type  -- 携帯/自宅/勤務先
)
🔍 コードレビューの観点

以下を見つけたら指摘しましょう：

  • カンマ区切りの値：多値属性を1カラムに格納
  • name1, name2, name3...：繰り返し属性 → 別テーブルに
  • address（1行）：複合属性を分解していない
  • age（年齢）：導出属性を保存している → birth_dateから計算すべき

リレーションシップの種類

📚 このページで学ぶこと
  • 1:1（1対1）リレーションシップ
  • 1:N（1対多）リレーションシップ
  • N:N（多対多）リレーションシップ

リレーションシップとは

リレーションシップとは、エンティティ間の関連性・つながりです。

🏠 たとえ話：人間関係

「AさんとBさんは親子関係」のように、
エンティティ同士も関係を持ちます。

「顧客が注文を行う」の「行う」がリレーションシップです。

1:1（1対1）リレーションシップ

1つのエンティティが1つのエンティティに対応します。 

-- 従業員と社員証の関係（1:1）
-- 1人の従業員に1枚の社員証

従業員(従業員ID, 名前, 部署)
       ↓ 1:1
社員証(社員証ID, 従業員ID, 発行日, 有効期限)

使いどころ：テーブル分割（アクセス頻度の違い、機密情報の分離）

⚠️ 1:1の注意点

1:1リレーションシップは本当に必要か？を考えましょう。

  • 理由なく分割すると、JOIN増加でパフォーマンス低下
  • 分割理由：機密データ分離、NULL多発回避、履歴管理

1:N（1対多）リレーションシップ

1つのエンティティが複数のエンティティに対応します。
最も一般的なリレーションシップです。 

-- 顧客と注文の関係（1:N）
-- 1人の顧客が複数の注文を行う

顧客(顧客ID, 名前, メール)
       ↓ 1:N
注文(注文ID, 顧客ID, 注文日, 合計金額)
    └─ 外部キーで「多」側から「1」側を参照
✓ 1:Nの実装パターン

「多」側のテーブルに外部キーを持たせます。

CREATE TABLE orders (
  order_id INT PRIMARY KEY,
  customer_id INT NOT NULL,  -- 外部キー
  order_date DATE NOT NULL,
  FOREIGN KEY (customer_id) REFERENCES customers(customer_id)
);

N:N（多対多）リレーションシップ

複数のエンティティが複数のエンティティに対応します。 

-- 学生と講座の関係（N:N）
-- 1人の学生が複数の講座を受講
-- 1つの講座に複数の学生が参加

学生(学生ID, 名前)
       ↓ N:N
講座(講座ID, 講座名)
💡 N:Nの実装：中間テーブル

N:Nは直接実装できません。中間テーブルで1:Nに分解します。 

-- 中間テーブル（受講テーブル）
学生(学生ID, 名前)
       ↓ 1:N
受講(学生ID, 講座ID, 受講日, 成績)  -- 中間テーブル
       ↓ N:1
講座(講座ID, 講座名)

-- 結果的に 学生 1:N 受講 N:1 講座 となる
よくある間違い
-- ❌ N:Nをカンマ区切りで実装
CREATE TABLE students (
  student_id INT PRIMARY KEY,
  name VARCHAR(100),
  course_ids VARCHAR(500)  -- "1,2,3"
);

検索・更新が困難、整合性も保てない

正しい実装
-- ⭕ 中間テーブルを使用
CREATE TABLE enrollments (
  student_id INT,
  course_id INT,
  enrolled_at DATE,
  PRIMARY KEY (student_id, course_id),
  FOREIGN KEY (student_id) REFERENCES students(student_id),
  FOREIGN KEY (course_id) REFERENCES courses(course_id)
);
🔍 コードレビューの観点

以下を見つけたら指摘しましょう：

  • 配列/JSON/カンマ区切りでN:Nを実装している
  • 中間テーブルに外部キー制約がない
  • 意味のない1:1分割（パフォーマンス劣化の原因）

ER図の読み方・書き方

ER図とは

ER図は、エンティティとリレーションシップを視覚化した図です。

🏠 たとえ話：地図

地図が土地の関係を示すように、
ER図はデータの関係を示します。

ER図があれば、コードを読まなくてもデータ構造が分かります。

ER図の基本要素

📊 ER図の構成要素

カーディナリティの表記法

カーディナリティとは、リレーションシップにおける「数の制約」です。

記号 意味 例
1 必ず1つ 注文には必ず1人の顧客
0..1 0または1つ 従業員は配偶者がいるかもしれない
*（または N） 0以上 顧客は0件以上の注文を持つ
1..* 1つ以上 注文には1つ以上の明細

ER図の表記法：IE記法 vs UML

IE記法（鳥の足）
  • 業務システムで広く使用
  • カーディナリティが直感的
  • 「鳥の足」で多を表現
顧客 ──┤├── 注文
      1      N
UML記法
  • オブジェクト指向設計で使用
  • 数値で表現
  • ER以外の図にも統一感
顧客 1────* 注文

ER図を読むコツ

✓ 読み方のポイント
  1. 主要エンティティを把握：中心となるテーブルを見つける
  2. リレーションシップを声に出す：「顧客が注文を行う」
  3. カーディナリティを確認：1人の顧客は何件の注文？
  4. 外部キーの位置を確認：「多」側に外部キーがあるはず
🔍 コードレビューの観点

ER図を見たら以下を確認：

  • 孤立したエンティティ：関連がないテーブルは不要では？
  • 循環参照：A→B→C→A となっていないか
  • 外部キーの方向：「多」側から「1」側を参照しているか
  • 命名の一貫性：customer_id と cust_id が混在していないか

正規化の基礎

📚 このページで学ぶこと
  • 正規化の目的

  • 第2正規形（2NF）

正規化とは

正規化とは、データの重複を排除し、整合性を保つためのルールです。

🏠 たとえ話：書類整理

同じ情報が複数の書類に書かれていると、
更新漏れで不整合が起きます。

「住所変更」したら全書類を修正？
正規化すれば、1箇所だけ変更すればOK。

正規化のレベル

📊 正規化の段階

第1正規形（1NF）

繰り返し項目を排除する。1セルに1つの値だけ。

1NF違反
| 注文ID | 商品名              |
|--------|---------------------|
| 1      | りんご, みかん, バナナ |
| 2      | メロン, いちご       |

1セルに複数の値（カンマ区切り）

1NF準拠
| 注文ID | 商品名   |
|--------|----------|
| 1      | りんご   |
| 1      | みかん   |
| 1      | バナナ   |
| 2      | メロン   |
| 2      | いちご   |

1行に1つの値

第2正規形（2NF）

部分関数従属を排除する。複合主キーの一部だけに依存する属性を分離。

2NF違反
| 注文ID | 商品ID | 商品名   | 数量 |
|--------|--------|----------|------|
| 1      | A      | りんご   | 3    |
| 1      | B      | みかん   | 2    |

-- 商品名は商品IDのみに依存（注文IDは不要）
-- = 部分関数従属
2NF準拠
注文明細:
| 注文ID | 商品ID | 数量 |

商品:
| 商品ID | 商品名   |
|--------|----------|
| A      | りんご   |
| B      | みかん   |

-- 商品名を別テーブルに分離

第3正規形（3NF）

推移的関数従属を排除する。非キー属性から別の非キー属性への依存を分離。

3NF違反
| 社員ID | 部署ID | 部署名     |
|--------|--------|------------|
| 1      | D01    | 営業部     |
| 2      | D01    | 営業部     |
| 3      | D02    | 開発部     |

-- 社員ID → 部署ID → 部署名
-- = 推移的関数従属（部署名が重複）
3NF準拠
社員:
| 社員ID | 部署ID |
|--------|--------|
| 1      | D01    |
| 2      | D01    |
| 3      | D02    |

部署:
| 部署ID | 部署名     |
|--------|------------|
| D01    | 営業部     |
| D02    | 開発部     |
✓ 正規化のメリット
  • 更新異常の防止：1箇所変えれば全体に反映
  • データ整合性：矛盾したデータが入らない
  • ストレージ効率：重複がないので省スペース

正規化の実践と非正規化

📚 このページで学ぶこと
  • 正規化の実践的な適用方法
  • 非正規化とは何か
  • 正規化と非正規化のトレードオフ

正規化の限界

正規化は万能ではありません。過度な正規化には問題があります。

⚠️ 正規化しすぎると...
  • JOIN地獄：1つのデータを取得するのに多数のJOINが必要
  • パフォーマンス低下：JOINはコストが高い
  • 複雑なクエリ：SQLが読みにくくなる

非正規化とは

非正規化とは、意図的にデータを重複させ、読み取り性能を向上させることです。

🏠 たとえ話：レシート

レシートには「商品名」「単価」が印刷されています。
本来は商品マスタを参照すべきですが、その時点の情報を保存しています。

これは「非正規化」ですが、履歴として正しい選択です。
（商品名が変わっても、過去のレシートは変わらない）

非正規化の例

正規化された設計
-- 毎回JOINが必要
SELECT
  o.order_id,
  c.name AS customer_name,
  p.name AS product_name
FROM orders o
JOIN customers c ON o.customer_id = c.id
JOIN order_items oi ON o.id = oi.order_id
JOIN products p ON oi.product_id = p.id;

データ整合性は高いがJOINが多い

非正規化された設計
-- JOINなしで取得可能
SELECT
  order_id,
  customer_name,  -- 注文時点の名前を保存
  product_name,   -- 注文時点の商品名を保存
  price           -- 注文時点の価格を保存
FROM order_details;

高速だがデータ重複がある

非正規化の判断基準

非正規化すべき場合 正規化を維持すべき場合
読み取りが頻繁で更新が少ない 更新が頻繁
レポート・分析用テーブル トランザクション処理
履歴データ（スナップショット） マスタデータ
パフォーマンスが最優先 データ整合性が最優先

実践的なアプローチ

✓ 推奨される手順
  1. まず第3正規形まで正規化する
  2. パフォーマンス計測を行う
  3. 問題がある場合のみ、計画的に非正規化
  4. 非正規化の理由を文書化する

「最初から非正規化」は避けましょう。
測定なしの最適化は早すぎる最適化です。

🔍 コードレビューの観点

以下を見つけたら確認しましょう：

  • 理由なき非正規化：パフォーマンス計測はしたか？
  • 更新処理の複雑化：複数箇所を更新する必要がないか？
  • データ不整合のリスク：重複データの同期はどう保証する？
  • 過度な正規化：JOINが5つ以上なら再設計を検討

主キーの設計戦略

📚 このページで学ぶこと
  • 自然キー（ナチュラルキー）とは
  • 代理キー（サロゲートキー）とは
  • それぞれのメリット・デメリット

主キーとは

主キー（Primary Key）は、レコードを一意に識別するための属性です。

💡 主キーの要件
  • 一意性：同じ値が存在しない
  • 非NULL：空であってはならない
  • 不変性：値が変わらないことが望ましい

自然キー vs 代理キー

📊 自然キーと代理キーの関係
自然キー（ナチュラルキー）

ビジネス上意味のある値をキーにする

-- メールアドレスを主キーに
CREATE TABLE users (
  email VARCHAR(255) PRIMARY KEY,
  name VARCHAR(100)
);
  • 意味が分かりやすい
  • JOIN結果が読みやすい
  • 変更されると問題
代理キー（サロゲートキー）

システムが自動生成する値をキーにする

-- 自動採番を主キーに
CREATE TABLE users (
  id INT AUTO_INCREMENT PRIMARY KEY,
  email VARCHAR(255) UNIQUE,
  name VARCHAR(100)
);
  • 変更の影響を受けない
  • パフォーマンスが良い（整数）
  • 意味がないので分かりにくい

実務での選択指針

状況 推奨 理由
一般的なケース 代理キー 変更に強い、パフォーマンス良好
外部システム連携 自然キー 外部のIDをそのまま使える
中間テーブル 複合キー 両側の外部キーの組み合わせ
分散システム UUID/ULID 衝突なしでID生成可能

代理キーの種類

種類 特徴 適用場面
AUTO_INCREMENT 連番、DBが自動採番 単一DBサーバー
UUID v4 ランダム、衝突なし 分散システム
ULID 時系列ソート可能、128bit 時系列データ
Snowflake ID 64bit、時系列+マシンID Twitter型大規模システム
⚠️ UUIDの注意点

UUID v4はランダムなので、インデックス効率が悪い。
B+木インデックスはソート済みデータを好むため、挿入時にページ分割が頻発します。

対策：ULIDやUUID v7（時系列ソート可能）を使う。

🔍 コードレビューの観点

以下を見つけたら確認しましょう：

  • 変更可能な値を主キーに：メールアドレス、電話番号など
  • 複合主キーが3つ以上：外部キーが複雑になる
  • 大規模システムでAUTO_INCREMENT：分散対応できない
  • UUID v4をそのまま主キー：インデックス効率を確認

外部キーと参照整合性

📚 このページで学ぶこと
  • 外部キー（Foreign Key）の役割
  • 参照整合性とは
  • ON DELETE / ON UPDATE オプション

外部キーとは

外部キーは、他のテーブルの主キーを参照するカラムです。

🏠 たとえ話：会員証番号

レンタルビデオ店の「貸出記録」には「会員証番号」が書かれています。
この会員証番号は、会員名簿に存在する番号でなければなりません。

存在しない会員に貸し出すことはできない。
これが参照整合性です。

参照整合性

参照整合性とは、外部キーが常に有効な値を指していることを保証するルールです。 

-- 外部キー制約の定義
CREATE TABLE orders (
  id INT PRIMARY KEY,
  customer_id INT NOT NULL,

  -- 外部キー制約
  FOREIGN KEY (customer_id)
    REFERENCES customers(id)
);

-- これにより以下が保証される：
-- 1. 存在しないcustomer_idは挿入できない
-- 2. 参照されているcustomerは削除できない（デフォルト）

ON DELETE / ON UPDATE オプション

親レコードが削除・更新されたときの動作を指定できます。

オプション 動作 使用例
RESTRICT 削除・更新を拒否（デフォルト） 安全第一の場合
CASCADE 子レコードも連動して削除・更新 注文削除→明細も削除
SET NULL 外部キーをNULLに設定 担当者退職→担当なし
SET DEFAULT デフォルト値に設定 カテゴリ削除→「未分類」
NO ACTION RESTRICTと同様（チェックタイミングが異なる） トリガーと組み合わせ
CASCADE の使用例
CREATE TABLE order_items (
  id INT PRIMARY KEY,
  order_id INT NOT NULL,
  product_id INT NOT NULL,
  quantity INT NOT NULL,

  FOREIGN KEY (order_id)
    REFERENCES orders(id)
    ON DELETE CASCADE  -- 注文削除→明細も削除
);

-- 注文を削除すると、明細も自動的に削除される
DELETE FROM orders WHERE id = 1;
CASCADE の危険な使用
-- ❌ 顧客削除で全注文が消える！
CREATE TABLE orders (
  id INT PRIMARY KEY,
  customer_id INT,

  FOREIGN KEY (customer_id)
    REFERENCES customers(id)
    ON DELETE CASCADE  -- 顧客削除→全注文消失
);

-- 顧客を削除すると、すべての注文履歴が消える
-- → 会計・監査で問題になる
⚠️ CASCADEの使用は慎重に
  • 親子関係が明確な場合のみ使用
  • 履歴データにはCASCADEを使わない
  • 大量データの連鎖削除はパフォーマンス問題を起こす
  • 意図しない削除を防ぐためソフトデリートも検討

外部キー制約なしの設計

💡 外部キー制約を使わない場合

外部キー制約を使わないことがあります。

  • シャーディング環境：テーブルが別DBにある
  • 高負荷システム：制約チェックのオーバーヘッド回避
  • マイクロサービス：サービス間でDBを共有しない

ただし、アプリケーション側で整合性を保証する必要があります。

🔍 コードレビューの観点

以下を確認しましょう：

  • 外部キー制約の有無：なぜ制約がないのか確認
  • ON DELETE CASCADE：意図しない大量削除のリスク
  • 孤立レコード：参照先が削除されたデータがないか
  • インデックス：外部キーにインデックスがあるか（JOIN高速化）

データ型の選択とパフォーマンス

📚 このページで学ぶこと
  • 適切なデータ型の選択基準
  • データ型がパフォーマンスに与える影響
  • よくある間違いと対策

データ型選択の重要性

データ型の選択は、ストレージ効率とパフォーマンスに直結します。

🏠 たとえ話：収納ボックス

小さな物に大きな箱を使うと、スペースの無駄。
大きな物に小さな箱を使うと、入らない。

データ型も同じ。データに合ったサイズを選びましょう。

整数型の選択

型 サイズ 範囲 使用例
TINYINT 1バイト -128 〜 127 年齢、状態フラグ
SMALLINT 2バイト -32,768 〜 32,767 年、小規模カウンター
INT 4バイト 約21億 ID、一般的な数値
BIGINT 8バイト 約922京 大規模システムのID
よくある間違い
-- ❌ 年齢にBIGINTは過剰
CREATE TABLE users (
  age BIGINT  -- 8バイト使用
);

-- ❌ ステータスにVARCHAR
CREATE TABLE orders (
  status VARCHAR(20)  -- "pending", "completed"
);
適切な選択
-- ⭕ 年齢にTINYINT UNSIGNED（0-255）
CREATE TABLE users (
  age TINYINT UNSIGNED  -- 1バイト
);

-- ⭕ ステータスにTINYINT + ENUM的運用
CREATE TABLE orders (
  status TINYINT NOT NULL  -- 0=pending, 1=completed
  -- またはENUM型を使用
);

文字列型の選択

型 特徴 使用例
CHAR(n) 固定長、常にnバイト使用 国コード(JP)、郵便番号
VARCHAR(n) 可変長、実データ+1-2バイト 名前、メールアドレス
TEXT 大量テキスト、インデックス制限あり 記事本文、コメント
⚠️ VARCHAR(255)の罠

「とりあえずVARCHAR(255)」は避けましょう。

  • メモリ確保時に最大長で計算される場合がある
  • インデックスサイズに影響
  • 実際のデータに合わせた長さを設定

日付・時刻型の選択

型 用途 注意点
DATE 日付のみ（年月日） 誕生日、有効期限
DATETIME 日時（タイムゾーンなし） ローカル時間を保存
TIMESTAMP 日時（UTC変換あり） 2038年問題、作成/更新日時
TIME 時刻のみ 営業時間、経過時間
💡 TIMESTAMPの2038年問題

TIMESTAMPは内部的に32bit整数（1970年からの秒数）で保存されます。
2038年1月19日に上限に達します。

対策：DATETIMEを使うか、BIGINTでUnixミリ秒を保存。

パフォーマンスへの影響

✓ データ型最適化のポイント
  • 小さいデータ型：キャッシュ効率向上、I/O削減
  • 固定長：検索・比較が高速
  • 数値 > 文字列：比較処理が高速
  • NULL回避：NULLABLEはインデックス効率を下げる
🔍 コードレビューの観点

以下を見つけたら指摘しましょう：

  • すべてVARCHAR(255)：適切なサイズか確認
  • 金額にFLOAT/DOUBLE：誤差が発生 → DECIMAL使用
  • ステータスにVARCHAR：TINYINT + ENUMを検討
  • 日時にVARCHAR：DATE/DATETIME/TIMESTAMP使用
  • すべてNULLABLE：本当にNULLが必要か確認

演習シナリオ：ECサイト

📋 ビジネス要件
  • 顧客はアカウント登録してログインできる
  • 顧客は複数の配送先住所を登録できる
  • 商品はカテゴリに分類される（1商品は1カテゴリ）
  • 顧客は商品をカートに入れ、注文できる
  • 注文は複数の商品を含むことができる
  • 注文には配送先と支払い方法を指定する

Step 1: エンティティの抽出

✓ 抽出されたエンティティ
エンティティ 説明
顧客（Customer） サイト利用者
住所（Address） 配送先住所
カテゴリ（Category） 商品分類
商品（Product） 販売商品
注文（Order） 購入注文
注文明細（OrderItem） 注文に含まれる商品

Step 2: リレーションシップの定義

顧客 ─1:N─ 住所      （1人の顧客が複数の住所を持つ）
顧客 ─1:N─ 注文      （1人の顧客が複数の注文を行う）
カテゴリ ─1:N─ 商品  （1カテゴリに複数の商品）
注文 ─1:N─ 注文明細  （1注文に複数の明細）
商品 ─1:N─ 注文明細  （1商品が複数の明細に登場）
注文 ─N:1─ 住所      （複数の注文が同じ住所に配送）

Step 3: 属性と主キーの設計

顧客 (
  customer_id INT PRIMARY KEY AUTO_INCREMENT,
  email VARCHAR(255) UNIQUE NOT NULL,
  password_hash VARCHAR(255) NOT NULL,
  name VARCHAR(100) NOT NULL,
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP
)

住所 (
  address_id INT PRIMARY KEY AUTO_INCREMENT,
  customer_id INT NOT NULL,  -- FK
  postal_code CHAR(7) NOT NULL,
  prefecture VARCHAR(10) NOT NULL,
  city VARCHAR(50) NOT NULL,
  address_line VARCHAR(200) NOT NULL,
  is_default BOOLEAN DEFAULT FALSE
)

カテゴリ (
  category_id INT PRIMARY KEY AUTO_INCREMENT,
  name VARCHAR(50) NOT NULL,
  parent_category_id INT  -- 自己参照FK（階層構造）
)

商品 (
  product_id INT PRIMARY KEY AUTO_INCREMENT,
  category_id INT NOT NULL,  -- FK
  name VARCHAR(200) NOT NULL,
  price DECIMAL(10, 2) NOT NULL,
  stock INT NOT NULL DEFAULT 0,
  is_active BOOLEAN DEFAULT TRUE
)

注文 (
  order_id INT PRIMARY KEY AUTO_INCREMENT,
  customer_id INT NOT NULL,  -- FK
  shipping_address_id INT NOT NULL,  -- FK
  status TINYINT NOT NULL DEFAULT 0,  -- 0:pending, 1:paid, ...
  total_amount DECIMAL(12, 2) NOT NULL,
  ordered_at DATETIME DEFAULT CURRENT_TIMESTAMP
)

注文明細 (
  order_item_id INT PRIMARY KEY AUTO_INCREMENT,
  order_id INT NOT NULL,  -- FK
  product_id INT NOT NULL,  -- FK
  quantity INT NOT NULL,
  unit_price DECIMAL(10, 2) NOT NULL,  -- 注文時点の価格を保存
  UNIQUE (order_id, product_id)  -- 同じ注文に同じ商品は1行
)

設計のポイント解説

💡 設計判断の理由
  • unit_price を明細に保存：商品価格が変わっても注文時の価格を保持（非正規化だが正しい）
  • status を TINYINT：ENUM的に運用（パフォーマンス優先）
  • price に DECIMAL：金額は誤差なく計算
  • is_default, is_active：BOOLEAN（またはTINYINT）でフラグ管理
  • parent_category_id：自己参照でカテゴリ階層を表現
