クラウドとは何か

クラウドコンピューティング = インターネット経由でコンピューティングリソースを利用するモデル

🏠 たとえ話：電気のように使う

昔は工場ごとに発電機を持っていた。
今は電力会社から必要な分だけ電気を買う。

サーバーも同じ。
昔は自社でサーバールームを持っていた。
今はクラウドプロバイダーから必要な分だけ借りる。

オンプレミス vs クラウド

オンプレミス（自社所有）
  • サーバー購入に数週間〜数ヶ月
  • 初期費用が高額（CAPEX）
  • ピーク時に合わせて購入 → 普段は遊休
  • 自社で運用・保守が必要
  • 物理的な障害対応は自己責任
クラウド
  • サーバー起動は数分
  • 従量課金（OPEX）
  • 必要な時に増やし、不要な時に減らせる
  • インフラ運用はプロバイダー任せ
  • 複数データセンターで冗長化

NISTによる5つの特徴

米国国立標準技術研究所（NIST）がクラウドの特徴を定義しています。

特徴 説明
オンデマンド・セルフサービス 人を介さず、自分でリソースを調達できる
幅広いネットワークアクセス インターネット経由でどこからでもアクセス
リソースプーリング 複数のユーザーでリソースを共有
迅速な弾力性 需要に応じてリソースを素早くスケール
測定可能なサービス 使用量を計測し、従量課金

クラウドの歴史

📜 知っておきたい歴史
  • 2006年：AWS（Amazon Web Services）がEC2/S3を開始
  • 2008年：Google App Engine（PaaS）開始
  • 2010年：Microsoft Azure正式リリース
  • 2011年：NISTがクラウドの定義を公開
  • 2014年：Google Cloud Platform本格展開

AWSの登場がクラウド時代の幕開け。
もともとAmazonは自社ECサイト用に大量のサーバーを持っていた。
その余剰リソースを外部に提供したのがAWSの始まり。

3つのサービスモデル

クラウドサービスは「どこまで管理してもらうか」で分類されます。

🏠 たとえ話：住居の選択

IaaS = 土地を借りて自分で家を建てる

SaaS = ホテルに泊まる（全部お任せ）

PaaS Platform as a Service ランタイム、ミドルウェア、OS Heroku, App Engine, Azure App Service
SaaS Software as a Service 完成されたアプリケーション Gmail, Salesforce, Slack

どのモデルを選ぶべきか

✓ 選定の指針
  • IaaS：細かい制御が必要、既存システムの移行、特殊な設定が必要
  • PaaS：アプリ開発に集中したい、素早くデプロイしたい
  • SaaS：開発不要、すぐに使いたい、標準機能で十分

原則：できるだけ高いレイヤー（SaaS > PaaS > IaaS）を選ぶ。
運用負荷を減らし、本業に集中できる。

🔍 コードレビュー・設計レビューの観点
  • IaaSで自前実装しているものが、PaaS/SaaSで代替できないか
  • 責任範囲の認識：セキュリティパッチは誰が当てる？
  • ベンダーロックイン：特定サービスに依存しすぎていないか

スケーリング（垂直 vs 水平）

📚 このページで学ぶこと
  • 垂直スケーリング（スケールアップ）とは
  • 水平スケーリング（スケールアウト）とは
  • それぞれのメリット・デメリット

スケーリングとは

スケーリング = 処理能力を増減させること

🏠 たとえ話：レストランの拡張

垂直スケーリング = シェフをより腕の良い人に変える
水平スケーリング = シェフの人数を増やす

📊 垂直スケーリング vs 水平スケーリング

垂直スケーリング（スケールアップ）

項目 説明
方法 1台のサーバーのCPU・メモリ・ディスクを増強
メリット シンプル、アプリ変更不要、データ一貫性が保ちやすい
デメリット 物理的な上限がある、ダウンタイムが必要な場合がある
向いている データベース、ステートフルなアプリ

水平スケーリング（スケールアウト）

項目 説明
方法 同じ構成のサーバーを台数を増やす
メリット 理論上無限にスケール可能、冗長性確保、ダウンタイムなし
デメリット アプリがステートレスである必要、データ同期が複雑
向いている Webサーバー、APIサーバー、ステートレスなアプリ

オートスケーリング

クラウドでは負荷に応じて自動でスケールできます。 

# AWS Auto Scaling の設定例（概念）
AutoScalingGroup:
  MinSize: 2          # 最小2台
  MaxSize: 10         # 最大10台
  DesiredCapacity: 2  # 通常は2台

ScalingPolicy:
  # CPU使用率70%を超えたら1台追加
  TargetValue: 70
  MetricType: CPUUtilization
  ScaleOutCooldown: 300  # 5分間は連続スケールしない
🔍 コードレビューの観点
  • ステートフルな設計でスケールアウトできない
  • セッションをサーバーに保存している（Redis等に外出しすべき）
  • スケールダウン時のGraceful Shutdownが考慮されていない
  • 単一障害点の存在：ロードバランサー、DB、キャッシュなど各レイヤーに冗長性があるか
  • スケーリング戦略の不在：オートスケーリングのポリシーが定義されていない、または閾値が不適切
  • コスト最適化の考慮不足：常時On-Demandで運用していないか。Reserved/Spotの活用余地がないか

データベースシャーディング

水平スケーリングの考え方はデータベースにも適用できます。
シャーディングは、データを複数のDBに分散する手法です。

Hash Sharding
  • シャードキーのハッシュ値でデータを分散
  • データが均等に分散される
  • 範囲クエリが苦手（複数シャードにまたがる）
shard_id = hash(user_id) % num_shards
// user_id=123 → hash=7 → shard 1
// user_id=456 → hash=2 → shard 2
Range Sharding
  • キーの範囲でデータを分散
  • 範囲クエリが効率的
  • ホットパーティション（偏り）が発生しやすい
// 日付でシャーディング
2025年データ → shard_2025
2026年データ → shard_2026
// 最新データに負荷集中しやすい
⚠️ シャーディングの課題
  • Hot Partition問題：特定のシャードにアクセスが集中する。例：有名ユーザーのデータが1つのシャードに集中
  • リシャーディングの困難さ：シャード数を変更するとデータの再配置が必要。大量データの移行中にダウンタイムが発生する可能性
  • クロスシャードクエリ：複数シャードにまたがるJOINやトランザクションが複雑になる

原則：シャーディングは最後の手段。まずは読み取りレプリカ、キャッシュ、クエリ最適化を検討する。

可用性と耐障害性の基礎

📚 このページで学ぶこと
  • 可用性（Availability）の定義とSLA
  • 耐障害性（Fault Tolerance）とは
  • 冗長化のパターン

可用性とは

可用性 = システムが正常に稼働している時間の割合

🏠 たとえ話：コンビニの営業時間

24時間営業のコンビニは可用性が高い。
いつ行っても開いている。

逆に、しょっちゅう閉まっている店は可用性が低い。
システムも同じで、ダウンタイムが少ないほど可用性が高い。

SLA（サービスレベル合意）

可用性は「何個9があるか」（ナイン）で表現されます。

可用性 ダウンタイム/年 ダウンタイム/月 呼び方
99% 3.65日 7.2時間 ツーナイン
99.9% 8.76時間 43.2分 スリーナイン
99.99% 52.56分 4.32分 フォーナイン
99.999% 5.26分 25.9秒 ファイブナイン
⚠️ SLAの現実

AWS EC2のSLAは99.99%（月4.32分のダウンタイム許容）。
しかし、これは複数AZ構成の場合の話。

単一サーバーに依存すると、SLAは保証されない。
冗長化が可用性の鍵。

耐障害性（Fault Tolerance）

耐障害性 = 一部が故障しても全体が停止しない能力

📊 冗長化パターン

冗長化の基本パターン

パターン 説明
Active-Standby 1台が稼働、1台が待機。障害時に切り替え
Active-Active 複数台が同時に稼働。負荷分散も兼ねる
マルチAZ 複数のデータセンター（AZ）に分散配置
マルチリージョン 複数の地理的リージョンに分散配置
🔍 コードレビュー・設計レビューの観点

単一障害点（SPOF）を見つけましょう：

  • 単一のDBサーバー
  • 単一のAPIサーバー
  • 単一のロードバランサー
  • 単一のAZ（データセンター）

ロードバランシングの仕組み

📚 このページで学ぶこと
  • ロードバランサーの役割
  • 負荷分散アルゴリズム
  • L4 vs L7ロードバランサー

ロードバランサーとは

ロードバランサー = トラフィックを複数のサーバーに分散させる装置

🏠 たとえ話：受付係

病院の受付係が患者を空いている診察室に振り分けるのと同じ。
全員が1番の診察室に殺到したら待ち時間が長くなる。

ロードバランサーは「受付係」として、
リクエストを適切なサーバーに振り分ける。

負荷分散アルゴリズム

アルゴリズム 動作 向いている場面
ラウンドロビン 順番に振り分け（1→2→3→1→...） サーバーの性能が均一
最小接続数 接続数が最も少ないサーバーへ 処理時間にばらつきがある
IPハッシュ クライアントIPで振り分け先を決定 セッション維持が必要
重み付け サーバーごとに処理比率を設定 サーバーの性能差がある

L4 vs L7 ロードバランサー

L4（トランスポート層）
  • IP/ポートで振り分け
  • 高速（パケットを見るだけ）
  • HTTPの中身は見ない
  • 例：AWS NLB、TCP/UDP負荷分散
# L4の振り分け例
# IPとポートだけで判断
192.168.1.100:80 → Server A
192.168.1.101:80 → Server B
L7（アプリケーション層）
  • HTTPヘッダー/パスで振り分け
  • 柔軟（URLで振り分け等）
  • SSL終端、キャッシュも可能
  • 例：AWS ALB、Nginx、HAProxy
# L7の振り分け例
# URLパスで判断
/api/*    → API Server
/images/* → Static Server
/admin/*  → Admin Server

ヘルスチェック

ロードバランサーは定期的にサーバーの状態を確認します。 

# ALBヘルスチェック設定例
HealthCheck:
  Protocol: HTTP
  Path: /health
  Port: 80
  HealthyThreshold: 2    # 2回連続成功で復帰
  UnhealthyThreshold: 3  # 3回連続失敗で除外
  Timeout: 5             # 5秒でタイムアウト
  Interval: 30           # 30秒ごとにチェック
🔍 コードレビューの観点
  • ヘルスチェックエンドポイントが実装されているか
  • ヘルスチェックが実際の依存サービスも確認しているか
  • セッションスティッキーに頼りすぎていないか

CDNとエッジコンピューティング

CDNとは

CDN = 世界中に分散配置されたサーバー群でコンテンツを配信

🏠 たとえ話：コンビニの配送センター

東京の本社倉庫から北海道のお店に直接配送 → 遅い
北海道に配送センターを置いて、そこから配送 → 速い

CDNは「配送センター」をユーザーの近くに置くことで、
コンテンツを高速に配信します。

CDNの仕組み

┌─────────────────────────────────────────────────────────┐
│                   CDNの動作フロー                        │
└─────────────────────────────────────────────────────────┘

1. ユーザーがコンテンツをリクエスト
   └─→ DNSが最寄りのエッジサーバーを返す

2. エッジサーバーがキャッシュを確認
   ├─→ キャッシュあり → 即座にレスポンス（キャッシュヒット）
   └─→ キャッシュなし → オリジンサーバーに取得しにいく

3. オリジンから取得したコンテンツ
   └─→ エッジにキャッシュ保存 → ユーザーに返却

次回以降の同じリクエスト
   └─→ エッジから直接配信（高速）

キャッシュ戦略

コンテンツ種別 キャッシュ時間 理由
静的アセット
（JS, CSS, 画像）		 長期間（1年等） ファイル名にハッシュ付与で更新対応
HTML 短期間（数分）or キャッシュなし コンテンツ更新を反映するため
API ケースバイケース データ鮮度の要件による 
# キャッシュ制御ヘッダー例
# 静的アセット（1年キャッシュ）
Cache-Control: public, max-age=31536000, immutable

# HTML（キャッシュしない）
Cache-Control: no-cache, no-store, must-revalidate

# API（5分キャッシュ）
Cache-Control: public, max-age=300

エッジコンピューティング

エッジコンピューティング = ユーザーに近い場所で処理を実行

サービス できること
CloudFront Functions URLリダイレクト、ヘッダー操作、簡単な認証
Lambda@Edge より複雑な処理、動的コンテンツ生成
Cloudflare Workers フルスタックなエッジアプリケーション
🔍 コードレビューの観点
  • 静的アセットにCache-Controlが設定されているか
  • 個人情報を含むページがキャッシュされていないか
  • キャッシュ無効化（Purge）の仕組みがあるか

  • 3つの状態と遷移

サーキットブレーカーとは

サーキットブレーカー = 障害を検知して自動的に遮断するパターン

🏠 たとえ話：電気のブレーカー

家の電気ブレーカーは、過電流を検知すると自動で遮断する。
これにより、火災（大障害）を防ぐ。

ソフトウェアでも同じ。
外部サービスが障害を起こしたら、一時的に遮断して、
連鎖障害（カスケード障害）を防ぐ。

なぜ必要か：カスケード障害

⚠️ カスケード障害の例 
1. 外部決済サービスがダウン
   ↓
2. 決済APIのタイムアウト待ち（30秒）でリクエストが滞留
   ↓
3. スレッドプールが枯渇、コネクションプールが枯渇
   ↓
4. 関係ない機能（商品一覧など）も応答不能に
   ↓
5. システム全体がダウン

1つのサービスの障害が、システム全体を巻き込む。

3つの状態

📊 サーキットブレーカーの状態遷移
状態 動作 遷移条件
Closed リクエストを通常通り処理 エラー率が閾値を超えたらOpenへ
Open リクエストを即座に失敗させる 一定時間後にHalf-Openへ
Half-Open 限定的にリクエストを試行 成功→Closed、失敗→Open

実装例（概念）

class CircuitBreaker {
  private state: 'CLOSED' | 'OPEN' | 'HALF_OPEN' = 'CLOSED';
  private failureCount = 0;
  private lastFailureTime: number | null = null;

  private readonly threshold = 5;       // 5回失敗でOpen
  private readonly timeout = 30000;     // 30秒後にHalf-Open

  async call<T>(fn: () => Promise<T>): Promise<T> {
    if (this.state === 'OPEN') {
      if (Date.now() - this.lastFailureTime! > this.timeout) {
        this.state = 'HALF_OPEN';
      } else {
        throw new Error('Circuit is OPEN');  // 即座に失敗
      }
    }

    try {
      const result = await fn();
      this.onSuccess();
      return result;
    } catch (error) {
      this.onFailure();
      throw error;
    }
  }

  private onSuccess(): void {
    this.failureCount = 0;
    this.state = 'CLOSED';
  }

  private onFailure(): void {
    this.failureCount++;
    this.lastFailureTime = Date.now();
    if (this.failureCount >= this.threshold) {
      this.state = 'OPEN';
    }
  }
}
🔍 コードレビューの観点
  • 外部サービス呼び出しにサーキットブレーカーが適用されているか
  • フォールバック処理（代替動作）が実装されているか
  • 閾値やタイムアウトが設定可能になっているか

リトライとは

リトライ = 一時的な障害に対して、再度処理を試みること

🏠 たとえ話：電話の再ダイヤル

電話が話し中なら、しばらく待ってからかけ直す。
すぐにかけ直しても、まだ話し中の可能性が高い。

ネットワークも同じ。
一時的な障害なら、少し待ってリトライすれば成功する。

リトライすべき/すべきでないエラー

リトライすべき（一時的障害）
  • ネットワークタイムアウト
  • 503 Service Unavailable
  • 429 Too Many Requests
  • 接続エラー
リトライすべきでない
  • 400 Bad Request（リクエストが不正）
  • 401 Unauthorized（認証エラー）
  • 403 Forbidden（権限なし）
  • 404 Not Found（リソースなし）

指数バックオフ（Exponential Backoff）

リトライ間隔を指数的に増やす戦略です。 

// 指数バックオフの例
1回目リトライ: 1秒後
2回目リトライ: 2秒後
3回目リトライ: 4秒後
4回目リトライ: 8秒後
5回目リトライ: 16秒後
...

// 計算式: delay = baseDelay * 2^(attempt - 1)

ジッター（Jitter）の重要性

⚠️ ジッターなしの問題：Thundering Herd

1000クライアントが同時に障害を検知 → 全員が1秒後にリトライ
→ サーバーに1000リクエストが殺到 → また障害

これをThundering Herd（雷鳴の群れ）問題といいます。 

// ジッター付き指数バックオフ
function calculateDelay(attempt: number): number {
  const baseDelay = 1000;  // 1秒
  const maxDelay = 30000;  // 最大30秒

  // 指数バックオフ
  const exponentialDelay = baseDelay * Math.pow(2, attempt - 1);

  // 上限を設定
  const cappedDelay = Math.min(exponentialDelay, maxDelay);

  // ジッター（0〜100%のランダム）を追加
  const jitter = Math.random() * cappedDelay;

  return cappedDelay + jitter;
}

// 結果例（attempt=3の場合）
// 基本: 4000ms
// ジッター: 0〜4000ms
// 実際の待機: 4000〜8000ms（ランダム）

実装例

async function fetchWithRetry<T>(
  fn: () => Promise<T>,
  maxRetries = 3
): Promise<T> {
  let lastError: Error;

  for (let attempt = 1; attempt <= maxRetries + 1; attempt++) {
    try {
      return await fn();
    } catch (error) {
      lastError = error as Error;

      // リトライ不可能なエラーは即座に失敗
      if (!isRetryable(error)) {
        throw error;
      }

      // 最大リトライ回数に達したら失敗
      if (attempt > maxRetries) {
        break;
      }

      // ジッター付き指数バックオフで待機
      const delay = calculateDelay(attempt);
      await sleep(delay);
    }
  }

  throw lastError!;
}

function isRetryable(error: unknown): boolean {
  if (error instanceof HttpError) {
    return [408, 429, 500, 502, 503, 504].includes(error.status);
  }
  return true;  // ネットワークエラー等はリトライ
}
🔍 コードレビューの観点
  • リトライ上限が設定されているか（無限リトライは危険）
  • べき等でない操作をリトライしていないか
  • ジッターが含まれているか
  • リトライ対象のエラーを適切に判定しているか

ヘルスチェックとは

ヘルスチェック = サービスが正常に動作しているか確認する仕組み

🏠 たとえ話：定期健康診断

人間も定期的に健康診断を受ける。
問題が見つかれば早めに治療できる。

サービスも同じ。
定期的にチェックして、問題があれば早めに対処する。

Liveness vs Readiness

Liveness Probe

「生きているか？」

  • アプリケーションが応答可能か
  • 失敗すると再起動される
  • デッドロック検出に有効
// シンプルなLivenessチェック
app.get('/healthz', (req, res) => {
  res.status(200).send('OK');
});
Readiness Probe

「準備ができているか？」

  • トラフィックを受け入れ可能か
  • 失敗するとトラフィックが来なくなる
  • 起動時やDB接続待ちに使用
// 依存サービスも確認するReadinessチェック
app.get('/ready', async (req, res) => {
  const dbOk = await checkDatabase();
  const cacheOk = await checkCache();
  if (dbOk && cacheOk) {
    res.status(200).send('Ready');
  } else {
    res.status(503).send('Not Ready');
  }
});

自動回復（Self-Healing）

自動回復 = 障害を検知して自動的に修復する仕組み

障害 自動回復 例
プロセスクラッシュ コンテナ再起動 Kubernetes restartPolicy
メモリリーク 定期的なローリング再起動 cronジョブでの再起動
サーバー障害 新しいインスタンス起動 Auto Scaling Group
AZ障害 別AZへフェイルオーバー Multi-AZ RDS 
# Kubernetes Liveness/Readiness設定例
spec:
  containers:
  - name: app
    livenessProbe:
      httpGet:
        path: /healthz
        port: 8080
      initialDelaySeconds: 30    # 起動後30秒待ってからチェック開始
      periodSeconds: 10          # 10秒ごとにチェック
      failureThreshold: 3        # 3回失敗で再起動
    readinessProbe:
      httpGet:
        path: /ready
        port: 8080
      initialDelaySeconds: 5
      periodSeconds: 5
      failureThreshold: 3        # 3回失敗でトラフィック停止
🔍 コードレビューの観点
  • ヘルスチェックエンドポイントが実装されているか
  • Liveness が依存サービスを含まないこと（含むと連鎖再起動）
  • Readiness が必要な依存をチェックしていること
  • initialDelaySecondsが適切か（起動時間より長く）

ベンダーロックイン

ベンダーロックイン = 特定のベンダーに依存し、移行が困難になること

ロックインしやすい
  • AWS Lambda + DynamoDB + API Gateway
  • Firebase全部入り
  • 独自の認証/認可サービス
移行しやすい
  • Kubernetes（どこでも動く）
  • PostgreSQL/MySQL（標準DB）
  • Terraform（マルチクラウド対応）

選定のフローチャート

1. 要件の明確化
   └─→ パフォーマンス要件は？可用性要件は？

2. マネージドサービスで実現可能か？
   ├─→ Yes → マネージドサービスを優先検討
   └─→ No → IaaS/コンテナで自前構築

3. コスト試算
   └─→ 初期費用、運用費用、成長時のコスト

4. ロックインリスクの評価
   └─→ 移行コスト vs 生産性向上のトレードオフ

5. PoC（概念実証）
   └─→ 小規模で検証してから本番採用
