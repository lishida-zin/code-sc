RAGとは何か

RAG（Retrieval-Augmented Generation）は、
LLMの出力を外部知識で強化するアーキテクチャです。

🏠 たとえ話：オープンブック試験

通常のLLM = 記憶だけで答える（暗記型試験）
RAG = 参考資料を見ながら答える（オープンブック試験）

LLMの「知らないこと」「古い情報」を
外部データベースから補完できます。

なぜRAGが必要か

⚠️ LLM単体の限界
  • 知識のカットオフ：学習データ以降の情報を知らない
  • ハルシネーション：存在しない情報を「捏造」する
  • プライベートデータ：社内文書などは学習していない
  • 専門知識：特定ドメインの深い知識が不足

RAGアーキテクチャの全体像

📊 RAGアーキテクチャ図

1. クエリをベクトル化 → 2. 類似文書を検索 → 3. 関連文書を取得 → 4. プロンプトを構築 → 5. LLMで生成

RAGの処理フロー

ステップ 処理内容 技術要素
1. 埋め込み ユーザーの質問をベクトル化 Embedding Model（text-embedding-ada-002等）
2. 検索 類似度の高い文書を検索 Vector DB（Pinecone, Weaviate等）
3. 取得 関連文書のテキストを取得 Top-K選択、リランキング
4. 構築 プロンプトに文脈を組み込む プロンプトテンプレート
5. 生成 LLMで回答を生成 GPT-4, Claude等

RAGの実装例

// シンプルなRAGの実装例
async function ragQuery(question: string): Promise<string> {
  // 1. 質問をベクトル化
  const queryEmbedding = await embedText(question);

  // 2. 類似文書を検索（Top-5）
  const relevantDocs = await vectorDB.search({
    vector: queryEmbedding,
    topK: 5,
    minScore: 0.7  // 類似度閾値
  });

  // 3. コンテキストを構築
  const context = relevantDocs
    .map(doc => doc.content)
    .join('\n\n');

  // 4. プロンプトを構築
  const prompt = `
以下のコンテキストを参考に質問に答えてください。
コンテキストに情報がない場合は「情報がありません」と答えてください。

## コンテキスト
${context}

## 質問
${question}
`;

  // 5. LLMで回答を生成
  const response = await llm.generate(prompt);

  return response;
}

ベクトルデータベースとは

ベクトルデータベースは、
高次元ベクトルの類似度検索に特化したデータベースです。

🏠 たとえ話：図書館の検索システム

従来のDB = キーワード検索（「JavaScript」で検索）
ベクトルDB = 意味検索（「Web開発の言語」で関連本を発見）

「意味的に近い」データを高速に見つけられます。

主要なベクトルデータベース

製品 タイプ 特徴 適した用途
Pinecone マネージド フルマネージド、スケーラブル 本番環境、大規模
Weaviate オープンソース GraphQL API、マルチモーダル 柔軟性が必要な場合
Milvus オープンソース 高性能、分散処理 大規模、オンプレ
Chroma オープンソース 軽量、埋め込み型 開発、プロトタイプ
pgvector PostgreSQL拡張 既存DBに追加可能 小〜中規模、既存PG利用
Qdrant オープンソース Rust製、高速フィルタリング 高速検索が必要な場合

選定基準

🎯 ベクトルDB選定の判断基準
観点 検討ポイント
スケール ベクトル数：100万以下ならpgvector、それ以上なら専用DB
運用 マネージド（Pinecone）vs セルフホスト（Milvus）
レイテンシ リアルタイム要件があるか
フィルタリング メタデータによる絞り込みの複雑さ

  • コスト試算：ベクトル数×クエリ数での料金を計算

チャンキングとは

チャンキングは、大きな文書を
検索可能な小さな単位に分割することです。

🏠 たとえ話：本の索引

本全体を1つとして扱うと、検索精度が下がる。
章・節・段落に分けることで、
必要な部分だけを正確に見つけられる。

チャンキング手法の比較

手法 説明 適した用途
固定長 一定の文字数・トークン数で分割 汎用的、実装が簡単
オーバーラップ 固定長 + 前後で重複を持たせる 文脈の断絶を防ぐ
セマンティック 意味的なまとまりで分割 文書構造が明確な場合
再帰的 段落→文→単語と段階的に分割 柔軟なサイズ調整が必要な場合

実装例：オーバーラップ付きチャンキング

interface ChunkConfig {
  chunkSize: number;      // チャンクの目標サイズ
  chunkOverlap: number;   // オーバーラップサイズ
}

function chunkText(text: string, config: ChunkConfig): string[] {
  const { chunkSize, chunkOverlap } = config;
  const chunks: string[] = [];

  let start = 0;
  while (start < text.length) {
    // チャンク終端を計算
    let end = start + chunkSize;

    // 文の途中で切れないよう調整
    if (end < text.length) {
      const lastPeriod = text.lastIndexOf('。', end);
      if (lastPeriod > start) {
        end = lastPeriod + 1;
      }
    }

    chunks.push(text.slice(start, end));

    // 次の開始位置（オーバーラップを考慮）
    start = end - chunkOverlap;
  }

  return chunks;
}

// 使用例
const chunks = chunkText(document, {
  chunkSize: 500,     // 500文字
  chunkOverlap: 50    // 50文字の重複
});

チャンクサイズの決め方

小さすぎるチャンク
  • 文脈が失われる
  • 検索結果が多くなりすぎる
  • LLMへの入力が断片的
大きすぎるチャンク
  • 関係ない情報が混入
  • 検索精度が下がる
  • コンテキスト制限に達しやすい
✓ 推奨設定
  • チャンクサイズ：200〜500トークン（用途による）
  • オーバーラップ：チャンクサイズの10〜20%
  • テスト：実際のクエリで精度を検証する
🔍 コードレビューの観点
  • 文の途中で切断していないか
  • オーバーラップなしで文脈が失われていないか
  • メタデータ（元文書、位置情報）を保存しているか

埋め込みモデルとは

埋め込みモデルは、テキストを
数値ベクトルに変換するモデルです。

🏠 たとえ話：座標システム

テキストを「意味空間」の座標に変換。
「犬」と「猫」は近い座標、「犬」と「車」は遠い座標になる。

この距離で「類似度」を計算できます。

主要な埋め込みモデル

モデル 次元数 特徴 コスト
text-embedding-3-small 1536 OpenAI最新、コスパ良好 $0.02/1M tokens
text-embedding-3-large 3072 OpenAI高精度 $0.13/1M tokens
voyage-large-2 1024 検索特化、高精度 有料
Cohere embed 1024 多言語対応が強い 有料
sentence-transformers 768 オープンソース、セルフホスト可 無料（計算リソースのみ）
E5-large-v2 1024 オープンソース、高精度 無料（計算リソースのみ）

モデル選択の基準

🎯 選択時の検討ポイント
  • 精度：MTEBベンチマークでの性能
  • 次元数：高いほど表現力↑、コスト↑
  • 速度：リアルタイム要件があるか
  • 言語：日本語対応の精度
  • コスト：API課金 vs セルフホスト
  • プライバシー：データを外部に送れるか

実装例

import OpenAI from 'openai';

const openai = new OpenAI();

async function getEmbedding(text: string): Promise<number[]> {
  const response = await openai.embeddings.create({
    model: 'text-embedding-3-small',
    input: text,
    encoding_format: 'float'
  });

  return response.data[0].embedding;
}

// バッチ処理（効率的）
async function getEmbeddings(texts: string[]): Promise<number[][]> {
  const response = await openai.embeddings.create({
    model: 'text-embedding-3-small',
    input: texts,  // 配列で渡す
    encoding_format: 'float'
  });

  return response.data.map(d => d.embedding);
}

// コサイン類似度の計算
function cosineSimilarity(a: number[], b: number[]): number {
  const dotProduct = a.reduce((sum, val, i) => sum + val * b[i], 0);
  const normA = Math.sqrt(a.reduce((sum, val) => sum + val * val, 0));
  const normB = Math.sqrt(b.reduce((sum, val) => sum + val * val, 0));
  return dotProduct / (normA * normB);
}
⚠️ 注意点
  • モデル変更時：全ベクトルの再計算が必要
  • バージョン：同じモデルでもバージョン違いで互換性なし
  • 正規化：モデルによって正規化済み/未済が異なる

AIエージェントとは

AIエージェントは、目標を達成するために
自律的に行動を選択・実行するシステムです。

🏠 たとえ話：秘書

通常のLLM = 質問に答えるだけ
AIエージェント = 指示を受けて、自分で調べ、ツールを使い、タスクを完了する

「旅行の予約をして」と言えば、
検索→比較→予約→報告まで自律的に行う。

エージェントの構成要素

📊 AIエージェントの構造

エージェントは目標→計画→実行→反省のループを回す

主要なエージェントパターン

パターン 説明 適した用途
ReAct Reasoning + Action。思考→行動を繰り返す 汎用タスク
Plan-and-Execute まず計画を立て、順に実行 複雑なタスク
LATS 木構造で選択肢を探索 最適解が必要な場合
Multi-Agent 複数エージェントが協調 専門性が異なるタスク

ReActパターンの実装例

interface AgentState {
  goal: string;
  thoughts: string[];
  actions: Action[];
  observations: string[];
  isComplete: boolean;
}

async function runReActAgent(goal: string): Promise<string> {
  const state: AgentState = {
    goal,
    thoughts: [],
    actions: [],
    observations: [],
    isComplete: false
  };

  const maxIterations = 10;

  for (let i = 0; i < maxIterations && !state.isComplete; i++) {
    // 1. 思考：現状を分析し、次のアクションを決定
    const thought = await think(state);
    state.thoughts.push(thought);

    // 2. 行動：ツールを選択して実行
    const action = await decideAction(state);
    state.actions.push(action);

    // 3. 観察：結果を取得
    const observation = await executeAction(action);
    state.observations.push(observation);

    // 4. 完了判定
    state.isComplete = await checkCompletion(state);
  }

  return generateFinalAnswer(state);
}

async function think(state: AgentState): Promise<string> {
  const prompt = `
目標: ${state.goal}

これまでの行動と観察:
${state.actions.map((a, i) =>
  `行動: ${a.type} - ${a.input}\n観察: ${state.observations[i]}`
).join('\n')}

次に何をすべきか、考えを述べてください。
`;
  return await llm.generate(prompt);
}

  • エラーハンドリング：ツール実行失敗時の対処
  • コスト制限：API呼び出し回数の上限
  • ログ記録：思考過程を追跡可能に

ツール実行のフロー

async function runWithTools(userMessage: string): Promise<string> {
  // 1. LLMにツール情報と共にメッセージを送信
  const response = await openai.chat.completions.create({
    model: 'gpt-4',
    messages: [{ role: 'user', content: userMessage }],
    tools: tools,
    tool_choice: 'auto'  // LLMがツール使用を判断
  });

  const message = response.choices[0].message;

  // 2. ツール呼び出しがあれば実行
  if (message.tool_calls) {
    const toolResults = await Promise.all(
      message.tool_calls.map(async (toolCall) => {
        const args = JSON.parse(toolCall.function.arguments);
        const result = await executeToolSafely(
          toolCall.function.name,
          args
        );
        return {
          tool_call_id: toolCall.id,
          role: 'tool' as const,
          content: JSON.stringify(result)
        };
      })
    );

    // 3. ツール結果を含めて再度LLMに送信
    const finalResponse = await openai.chat.completions.create({
      model: 'gpt-4',
      messages: [
        { role: 'user', content: userMessage },
        message,
        ...toolResults
      ]
    });

    return finalResponse.choices[0].message.content;
  }

  return message.content;
}

安全なツール実行

// ツールのホワイトリストと権限管理
const toolRegistry: Record<string, ToolHandler> = {
  search_web: {
    execute: searchWeb,
    permissions: ['read'],
    rateLimit: { requests: 10, period: '1m' }
  },
  send_email: {
    execute: sendEmail,
    permissions: ['write'],
    requiresConfirmation: true  // ユーザー確認が必要
  }
};

async function executeToolSafely(
  name: string,
  args: unknown
): Promise<unknown> {
  // 1. ツールの存在確認
  const tool = toolRegistry[name];
  if (!tool) {
    throw new Error(`Unknown tool: ${name}`);
  }

  // 2. 引数のバリデーション
  const validatedArgs = validateToolArgs(name, args);

  // 3. レート制限チェック
  await checkRateLimit(name, tool.rateLimit);

  // 4. 必要なら確認を求める
  if (tool.requiresConfirmation) {
    const confirmed = await requestUserConfirmation(name, validatedArgs);
    if (!confirmed) {
      return { error: 'User declined' };
    }
  }

  // 5. 実行
  try {
    return await tool.execute(validatedArgs);
  } catch (error) {
    return { error: error.message };
  }
}
🔍 コードレビューの観点：セキュリティ
  • ホワイトリスト：許可されたツールのみ実行可能か
  • 引数検証：LLMの出力を信頼せず、必ず検証
  • 権限分離：破壊的操作には確認を要求
  • レート制限：無限ループ攻撃を防止
  • ログ記録：全てのツール呼び出しを記録

Human-in-the-Loopとは

HITLは、AIの処理ループに
人間の判断・確認を組み込む設計です。

🏠 たとえ話：自動運転の監視

完全自動運転ではなく、人間が監視している状態。
危険を察知したら人間が介入できる。

AIの判断を最終決定前に人間がレビューする仕組み。

HITLが必要な場面

⚠️ 人間の確認が必要なケース
  • 高リスク操作：削除、送信、支払いなど取り消し不可の操作
  • 不確実性が高い：AIの確信度が低い判断
  • 法的・倫理的判断：コンプライアンスに関わる決定
  • 例外処理：想定外のケースへの対応
  • 学習データ：AIの改善に使うデータの品質管理
📊 Human-in-the-Loop フロー

HITL設計パターン

interface HITLConfig {
  // 確認が必要な条件
  requiresApproval: (action: Action) => boolean;
  // 確認のタイムアウト
  approvalTimeout: number;
  // タイムアウト時のデフォルト動作
  timeoutBehavior: 'approve' | 'reject' | 'escalate';
}

async function executeWithHITL(
  action: Action,
  config: HITLConfig
): Promise<ActionResult> {
  // 1. 確認が必要か判定
  if (!config.requiresApproval(action)) {
    return executeAction(action);
  }

  // 2. 人間に確認リクエストを送信
  const request = await createApprovalRequest(action);
  notifyReviewer(request);

  // 3. 承認を待機
  const approval = await waitForApproval(request.id, {
    timeout: config.approvalTimeout
  });

  // 4. 結果に応じて処理
  switch (approval.status) {
    case 'approved':
      return executeAction(action);

    case 'rejected':
      return { status: 'rejected', reason: approval.reason };

    case 'modified':
      return executeAction(approval.modifiedAction);

    case 'timeout':
      return handleTimeout(action, config.timeoutBehavior);
  }
}

function requiresApproval(action: Action): boolean {
  // 高リスク操作は確認必須
  const highRiskActions = ['delete', 'send_email', 'payment', 'publish'];
  if (highRiskActions.includes(action.type)) {
    return true;
  }

  // AIの確信度が低い場合も確認
  if (action.confidence < 0.8) {
    return true;
  }

  // 金額が閾値を超える場合
  if (action.amount && action.amount > 10000) {
    return true;
  }

  return false;
}

async function logAIRequest(log: AIRequestLog): Promise<void> {
  // 1. 機密情報のマスキング
  const sanitizedLog = sanitizeLog(log);

  await logger.info('ai_request', sanitizedLog);

  metrics.increment('ai.requests.total');
  metrics.histogram('ai.latency', log.output.latencyMs);

  // 4. 異常検知
  await detectAnomalies(log);
}

異常検知とアラート

async function detectAnomalies(log: AIRequestLog): Promise<void> {
  // コスト急増の検出
  const hourlySpend = await getHourlySpend();
  if (hourlySpend > COST_THRESHOLD) {
    await alert({
      severity: 'high',
      title: 'AI API コスト急増',
      message: `1時間のコストが$${hourlySpend}に達しました`
    });
  }

  // 有害コンテンツの検出
  if (log.quality?.flaggedContent) {
    await alert({
      severity: 'critical',
      title: '有害コンテンツ検出',
      message: `RequestID: ${log.requestId}`,
      action: 'immediate_review'
    });
  }

  // レイテンシ異常
  if (log.output.latencyMs > LATENCY_THRESHOLD) {
    await alert({
      severity: 'medium',
      title: 'AI応答遅延',
      message: `レイテンシ: ${log.output.latencyMs}ms`
    });
  }

  // ハルシネーション疑い（groundednessスコアが低い）
  if (log.quality?.groundedness && log.quality.groundedness < 0.5) {
    await logForReview({
      type: 'potential_hallucination',
      log,
      reason: `Groundedness score: ${log.quality.groundedness}`
    });
  }
}

  • プロンプト漏洩：システムプロンプトはログに含めない
  • ストレージコスト：全プロンプトを保存すると膨大に
  • 保持期間：コンプライアンス要件を確認

A/Bテストの設計

interface ABTestConfig {
  name: string;
  variants: {
    control: AIConfig;
    treatment: AIConfig;
  };
  trafficSplit: number;  // treatmentへの割り当て率
  metrics: string[];     // 評価する指標
  minSampleSize: number;
  maxDuration: number;
}

async function runABTest(
  userId: string,
  request: AIRequest,
  config: ABTestConfig
): Promise<AIResponse> {
  // 1. ユーザーをグループに割り当て（一貫性を保つ）
  const variant = assignVariant(userId, config);

  // 2. 対応する設定で実行
  const aiConfig = variant === 'treatment'
    ? config.variants.treatment
    : config.variants.control;

  const response = await executeAI(request, aiConfig);

  // 3. 結果を記録
  await logExperimentResult({
    experimentName: config.name,
    userId,
    variant,
    request,
    response,
    timestamp: new Date()
  });

  return response;
}

// 統計的有意性の確認
function analyzeExperiment(results: ExperimentResult[]): Analysis {
  const control = results.filter(r => r.variant === 'control');
  const treatment = results.filter(r => r.variant === 'treatment');

  // 各指標についてt検定
  const metrics = {};
  for (const metric of ['satisfaction', 'accuracy', 'latency']) {
    const tTest = performTTest(
      control.map(r => r[metric]),
      treatment.map(r => r[metric])
    );

    metrics[metric] = {
      controlMean: tTest.mean1,
      treatmentMean: tTest.mean2,
      pValue: tTest.pValue,
      significant: tTest.pValue < 0.05
    };
  }

  return { metrics, sampleSize: results.length };
}
🔍 コードレビューの観点
  • サンプルサイズ：十分なデータが集まる前に判断していないか
  • 一貫性：同じユーザーが常に同じグループに入るか
  • 複数指標：1つの指標だけで判断していないか
  • 副作用：良い指標が他の悪影響を隠していないか

失敗パターン1：過度な期待

失敗パターン

「AIを入れれば全て解決」と期待。
現実のAIの限界を理解せずに導入。

  • 100%の精度を期待
  • 人間の監視なしで運用
  • 全タスクをAIに任せる
対策

AIは「支援ツール」として位置づける。
適切な期待値を設定。

  • 精度目標を現実的に設定（例：80%）
  • Human-in-the-Loopを組み込む
  • AIが苦手な領域を把握

失敗パターン2：データの軽視

失敗パターン

「とりあえず最新のモデルを使えばいい」
データの品質・量を軽視。

  • ノイズの多いデータをそのまま使用
  • チャンキング戦略が不適切
  • データの更新頻度を考慮しない
対策

「Garbage In, Garbage Out」を意識。
データパイプラインを整備。

  • データクレンジングを実施
  • 複数のチャンキング戦略を比較検証
  • 定期的なデータ更新の仕組みを構築

失敗パターン3：評価の欠如

失敗パターン

「動いているから大丈夫」
体系的な評価なしで運用。

  • 主観的な「良さそう」で判断
  • 本番環境での品質を監視しない
  • ユーザーフィードバックを収集しない
対策

定量的な評価指標を設定。
継続的に監視・改善。

  • 評価データセットを作成
  • A/Bテストで改善を検証
  • ユーザーフィードバックを収集・分析

失敗パターン4：セキュリティの軽視

失敗パターン

セキュリティを後回しにして開発。
本番で脆弱性が発覚。

  • プロンプトインジェクション対策なし
  • 機密情報をLLMに送信
  • ツール呼び出しの権限管理なし
対策

設計段階からセキュリティを考慮。
多層防御を実装。

  • 入力のサニタイズ・検証
  • 機密情報のマスキング
  • 最小権限の原則でツール設計

失敗パターン5：コスト爆発

失敗パターン

本番でAPIコストが想定の10倍に。
予算超過でプロジェクト中止。

  • 開発時のコスト試算が不十分
  • 冗長なAPI呼び出し
  • コスト監視・制限なし
対策

事前のコスト試算と監視を徹底。
最適化の余地を検討。

  • トークン数を事前に見積もり
  • キャッシュの活用
  • 日次・月次の予算上限を設定
