インデックスの仕組みと種類

📚 このページで学ぶこと

インデックスとは

インデックス = データを高速に検索するための「索引」

🏠 たとえ話：本の索引

1000ページの本で「データベース」という単語を探すとき：

索引なし：1ページ目から順番に探す → O(n)
索引あり：巻末の索引で「タ行」を見る → O(log n)

データベースのインデックスも同じ原理。
全件スキャンを回避して高速に検索できる。

インデックスなしの検索

⚠️ フルテーブルスキャン 
-- 100万行のテーブルから検索
SELECT * FROM users WHERE email = 'user@example.com';

-- インデックスなし：全行を順番に確認
-- → 最悪100万行を読み込む（O(n)）
-- → 遅い！

インデックスありの検索

✓ インデックススキャン 
-- emailカラムにインデックスを作成
CREATE INDEX idx_users_email ON users(email);

-- インデックスあり：B-tree構造で効率的に検索
-- → 約20回の比較で見つかる（O(log n)）
-- → 高速！

主要なインデックスの種類

種類 特徴 適した用途
B-tree 最も一般的。範囲検索も可能 等価検索、範囲検索、ソート
Hash 等価検索のみ。O(1)で高速 完全一致検索のみ
GIN/GiST 全文検索、配列、JSON用 PostgreSQLの高度な検索
Bitmap 低カーディナリティ向け 性別、ステータスなど

複合インデックス

複数カラムを組み合わせたインデックスも作成できます。 

-- 複合インデックス
CREATE INDEX idx_orders_user_date
ON orders(user_id, created_at);

-- 効果的な検索パターン
SELECT * FROM orders
WHERE user_id = 123 AND created_at > '2026-01-01';

-- 左端のカラムから順に使われる
-- user_id単独の検索にも使える
-- created_at単独の検索には使えない（左端原則）
🔍 コードレビューの観点

以下を見つけたら指摘しましょう：

  • WHERE句の頻出カラムにインデックスがない
  • 複合インデックスの順序が不適切（カーディナリティを考慮していない）
  • インデックスの過剰作成（INSERT/UPDATE性能低下）

❌ インデックスの過剰作成

-- 全カラムにインデックスを貼る（やりすぎ）
CREATE INDEX idx_name ON users(name);
CREATE INDEX idx_email ON users(email);
CREATE INDEX idx_age ON users(age);
CREATE INDEX idx_city ON users(city);
CREATE INDEX idx_phone ON users(phone);
-- INSERT/UPDATEが遅くなる！

⭕ 必要なインデックスだけ作成

-- WHERE句・JOIN・ORDER BYで頻出するカラムのみ
CREATE INDEX idx_email ON users(email);
-- 複合インデックスでカバー
CREATE INDEX idx_city_age ON users(city, age);
-- 選択性の低いカラム（性別等）は不要

B-tree構造の理解

B-treeとは

B-tree（Balanced tree） = 自己平衡多分木。
ディスクI/Oを最小化するために設計されたデータ構造です。

🏠 たとえ話：図書館の分類システム

大きな図書館では、本を階層的に分類します：
フロア → 棚 → 段 → 本

B-treeも同じように、データを階層的に整理。
各階層で「次にどこを見るか」が分かり、効率的にたどれる。

B-tree構造図

📊 B-tree構造

B-treeの特徴

特徴 説明
バランス保持 すべてのリーフが同じ深さ。偏りがない
多分岐 1ノードに複数のキー。ディスク読み込み回数を減らす
ソート済み キーが常にソートされている。範囲検索に強い
O(log n) 検索・挿入・削除すべてO(log n)

なぜB-treeがDBで使われるか

✓ ディスクI/O最適化

データベースはディスク上にデータを保存します。
ディスクアクセスはメモリの100,000倍遅い。

B-treeは1ノードをディスクの1ブロック（通常4KB〜16KB）に対応させ、
ディスク読み込み回数を最小化します。

100万行のテーブルでも、
B-treeなら3〜4回のディスクアクセスで検索できる。

B-treeの計算量

-- 100万行のテーブル（1,000,000行）
-- B-tree（分岐数 = 100と仮定）

-- 深さ = log_100(1,000,000) ≈ 3
-- つまり3回の比較で目的のデータに到達

-- 二分探索木なら
-- 深さ = log_2(1,000,000) ≈ 20
-- 20回の比較が必要

-- B-treeは「広く浅い」木構造で効率的

クエリ最適化の基礎

EXPLAINとは

EXPLAIN = クエリの実行計画を確認するコマンド。
「DBがどうやってデータを取得するか」が分かります。 

-- 実行計画を確認
EXPLAIN SELECT * FROM users WHERE email = 'user@example.com';

-- PostgreSQLの出力例
-- Seq Scan on users  (cost=0.00..1234.00 rows=1 width=100)
--   Filter: (email = 'user@example.com'::text)

-- 「Seq Scan」= フルテーブルスキャン → 遅い！

良い実行計画 vs 悪い実行計画

悪い例：Seq Scan
EXPLAIN SELECT * FROM users
WHERE email = 'test@example.com';

-- 結果
Seq Scan on users
  Filter: email = 'test@example.com'
  Rows Removed by Filter: 999999

-- 全行をスキャン → 遅い
良い例：Index Scan
-- インデックス作成後
CREATE INDEX idx_email ON users(email);

EXPLAIN SELECT * FROM users
WHERE email = 'test@example.com';

-- 結果
Index Scan using idx_email on users
  Index Cond: email = 'test@example.com'

-- インデックスで直接アクセス → 高速

よくあるパフォーマンス問題

⚠️ インデックスが使われないケース 
-- ❌ 関数でラップ → インデックス無効
SELECT * FROM users WHERE LOWER(email) = 'test@example.com';

-- ❌ 型の不一致 → インデックス無効
SELECT * FROM users WHERE id = '123';  -- idがINTの場合

-- ❌ LIKE前方一致以外 → インデックス無効
SELECT * FROM users WHERE email LIKE '%@example.com';

-- ❌ OR条件 → インデックスが効きにくい
SELECT * FROM users WHERE email = 'a@test.com' OR name = 'test';

N+1問題

N+1問題 = 1回のクエリで済むところを N+1回実行してしまう問題

N+1問題（悪い例）
// 1回目：全ユーザー取得
const users = await db.query('SELECT * FROM users');

// N回：各ユーザーの注文を個別に取得
for (const user of users) {
  const orders = await db.query(
    'SELECT * FROM orders WHERE user_id = ?',
    [user.id]
  );
}

// users が1000人なら1001回のクエリ！
JOINで解決（良い例）
// 1回のクエリで全データ取得
const result = await db.query(`
  SELECT u.*, o.*
  FROM users u
  LEFT JOIN orders o ON u.id = o.user_id
`);

// または IN句で2回に抑える
const users = await db.query('SELECT * FROM users');
const userIds = users.map(u => u.id);
const orders = await db.query(
  'SELECT * FROM orders WHERE user_id IN (?)',
  [userIds]
);
🔍 コードレビューの観点
  • ループ内でクエリ実行 → N+1問題の兆候
  • SELECT * → 必要なカラムだけ指定すべき
  • インデックスなしの大量データ検索 → EXPLAIN確認を推奨
  • WHERE句に関数 → インデックス無効化の可能性

トランザクションとACID特性

トランザクションとは

トランザクション = 複数の操作を1つの単位として扱う仕組み

🏠 たとえ話：銀行振込

AさんからBさんへ1万円を振り込む：

  1. Aさんの口座から1万円を引く
  2. Bさんの口座に1万円を足す

この2つの操作は両方成功するか、両方失敗するかでなければならない。
1だけ成功してお金が消えたら大問題！

ACID特性

特性 英語 意味
A Atomicity（原子性） 全部成功か全部失敗か。中途半端な状態は許さない
C Consistency（一貫性） 制約違反のデータは保存されない
I Isolation（分離性） 他のトランザクションの影響を受けない
D Durability（永続性） 一度確定したデータは消えない

トランザクションの使い方

-- トランザクション開始
BEGIN;

-- 操作1：Aさんから引く
UPDATE accounts SET balance = balance - 10000 WHERE user_id = 'A';

-- 操作2：Bさんに足す
UPDATE accounts SET balance = balance + 10000 WHERE user_id = 'B';

-- すべて成功したらコミット
COMMIT;

-- エラーが起きたらロールバック
-- ROLLBACK;

アプリケーションでの実装

トランザクションなし
// ❌ 危険：途中でエラーが起きると不整合
await db.query(
  'UPDATE accounts SET balance = balance - 10000 WHERE user_id = ?',
  ['A']
);
// ここでエラーが起きると...
await db.query(
  'UPDATE accounts SET balance = balance + 10000 WHERE user_id = ?',
  ['B']
);
// Aから引いたお金が消失！
トランザクションあり
// ⭕ 安全：エラー時は自動ロールバック
await db.transaction(async (tx) => {
  await tx.query(
    'UPDATE accounts SET balance = balance - 10000 WHERE user_id = ?',
    ['A']
  );
  await tx.query(
    'UPDATE accounts SET balance = balance + 10000 WHERE user_id = ?',
    ['B']
  );
});
// エラー時は両方の操作が取り消される
🔍 コードレビューの観点
  • 複数テーブルの更新がトランザクションで囲まれていない
  • お金・在庫など重要データの操作にトランザクションがない
  • 長時間トランザクション（ロック長期化の原因）

分離レベルとは

分離レベル（Isolation Level） = 同時実行時にどこまで他のトランザクションの影響を受けるかを決める設定

🏠 たとえ話：作業部屋のドア

完全開放：誰でも入れる → 干渉が多い
ノック必要：許可制 → 少し待つが安全
完全施錠：誰も入れない → 安全だが効率悪い

分離レベルが高いほど安全だが性能が下がる。
用途に応じて適切なレベルを選ぶ必要があります。

分離レベル図解

📊 分離レベルと発生する問題

4つの分離レベル

レベル ダーティリード 反復不能読取り ファントムリード
READ UNCOMMITTED 発生する 発生する 発生する
READ COMMITTED 防止 発生する 発生する
REPEATABLE READ 防止 防止 発生する
SERIALIZABLE 防止 防止 防止

各問題の説明

⚠️ 同時実行で起こる問題

ダーティリード：他のトランザクションの未コミットデータを読む
→ ロールバックされたら不正なデータを使ってしまう

反復不能読取り：同じクエリで違う結果が返る
→ トランザクション中に他が更新したデータを読んでしまう

ファントムリード：同じ条件で行数が変わる
→ トランザクション中に他が行を追加/削除した

どのレベルを選ぶべきか

✓ 実務での選択指針
  • PostgreSQL：デフォルト READ COMMITTED、多くの場合これで十分
  • MySQL (InnoDB)：デフォルト REPEATABLE READ
  • 金融系：SERIALIZABLE を検討（性能とのトレードオフ）
  • レポート系：READ COMMITTED で十分な場合が多い

デッドロックの検出と回避

📚 このページで学ぶこと

  • デッドロックの検出方法
  • デッドロックを防ぐ設計

デッドロックとは

デッドロック = 2つ以上のトランザクションが互いにロックを待ち合い、永遠に進まない状態

🏠 たとえ話：狭い道での対向車

2台の車が狭い一本道で鉢合わせ。
どちらも「相手がバックしたら進む」と考えて動かない。

データベースでも同じことが起きます：
TX1：「Aをロック」→「Bを待つ」
TX2：「Bをロック」→「Aを待つ」
→ 両方とも永遠に待ち続ける

デッドロックの例

⚠️ デッドロック発生パターン 
-- Transaction 1
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;  -- ロック取得
-- ここで待機...
UPDATE accounts SET balance = balance + 100 WHERE id = 2;  -- TX2のロック待ち

-- Transaction 2（同時実行）
BEGIN;
UPDATE accounts SET balance = balance - 50 WHERE id = 2;   -- ロック取得
-- ここで待機...
UPDATE accounts SET balance = balance + 50 WHERE id = 1;   -- TX1のロック待ち

-- TX1はTX2を待ち、TX2はTX1を待つ → デッドロック！

デッドロックの検出

多くのDBMSはデッドロック検出機能を持っています。 

-- PostgreSQLでデッドロックを検出
-- 一方のトランザクションを強制的にロールバック

ERROR: deadlock detected
DETAIL: Process 12345 waits for ShareLock on transaction 67890;
        blocked by process 67890.
        Process 67890 waits for ShareLock on transaction 12345;
        blocked by process 12345.
HINT: See server log for query details.

デッドロックの回避策

悪い例：順序がバラバラ
// TX1: A → B の順でロック
await tx1.query('UPDATE ... WHERE id = 1');
await tx1.query('UPDATE ... WHERE id = 2');

// TX2: B → A の順でロック
await tx2.query('UPDATE ... WHERE id = 2');
await tx2.query('UPDATE ... WHERE id = 1');

// 異なる順序 → デッドロックの可能性
良い例：順序を統一
// 両方とも ID昇順でロック
// TX1: 1 → 2 の順
await tx1.query('UPDATE ... WHERE id = 1');
await tx1.query('UPDATE ... WHERE id = 2');

// TX2: 1 → 2 の順（同じ順序）
await tx2.query('UPDATE ... WHERE id = 1');
await tx2.query('UPDATE ... WHERE id = 2');

// 同じ順序 → デッドロック回避
✓ デッドロック回避のベストプラクティス
  1. ロック順序を統一：常に同じ順序でロックを取得
  2. トランザクションを短く：ロック保持時間を最小化
  3. タイムアウト設定：長時間ロックを自動解除
  4. 必要最小限のロック：行ロックを使い、テーブルロックを避ける
🔍 コードレビューの観点
  • 複数テーブル/行の更新順序がバラバラ
  • 長時間トランザクション（外部API呼び出しを含む等）
  • SELECT ... FOR UPDATE の乱用

パーティショニングとは

パーティショニング = 大きなテーブルを複数の小さな部分に分割する技術

🏠 たとえ話：書類整理

10万枚の書類を1つの棚に入れると、探すのが大変。
「年度別」「部署別」にファイリングすれば効率的。

DBでも同じ。論理的には1つのテーブルだが、
物理的には複数のパーティションに分割。

パーティショニングの種類

種類 分割方法 適した用途
Range 値の範囲で分割（日付、ID範囲） 時系列データ、ログ
List 特定の値リストで分割 地域、カテゴリ
Hash ハッシュ値で均等分割 均等分散が必要な場合

Rangeパーティショニングの例

-- PostgreSQLでの Range パーティショニング
CREATE TABLE orders (
    id BIGSERIAL,
    user_id BIGINT,
    created_at TIMESTAMP,
    amount DECIMAL(10, 2)
) PARTITION BY RANGE (created_at);

-- 月別パーティション作成
CREATE TABLE orders_2026_01 PARTITION OF orders
    FOR VALUES FROM ('2026-01-01') TO ('2026-02-01');

CREATE TABLE orders_2026_02 PARTITION OF orders
    FOR VALUES FROM ('2026-02-01') TO ('2026-03-01');

-- クエリは通常通り
SELECT * FROM orders WHERE created_at >= '2026-01-15';
-- 自動的に該当パーティションのみ検索（パーティションプルーニング）

パーティショニングのメリット

✓ パーティショニングの効果
  • クエリ性能向上：検索対象を絞り込める（パーティションプルーニング）
  • メンテナンス効率：古いパーティションだけDROP/ARCHIVE
  • 並列処理：パーティション単位で並列スキャン
  • ストレージ最適化：パーティションごとに異なるストレージに配置

パーティショニングの注意点

⚠️ 注意すべき点
  • パーティションキーがWHERE句にないと全パーティションスキャン
  • パーティション数が多すぎるとオーバーヘッド増大
  • JOINが複雑になる場合がある
  • UNIQUE制約にはパーティションキーを含める必要がある

❌ パーティションキーなしの検索

-- パーティションキー(created_at)がWHERE句にない
-- → 全パーティションをスキャンしてしまう
SELECT * FROM orders
WHERE user_id = 123;

⭕ パーティションキーを含めた検索

-- パーティションキーを含める
-- → 対象パーティションだけスキャン（プルーニング）
SELECT * FROM orders
WHERE user_id = 123
  AND created_at >= '2024-01-01'
  AND created_at < '2024-04-01';

💀 コードレビューの観点

  • パーティションキーの選択：クエリのWHERE句で頻繁に使われるカラムを選んでいるか？
  • パーティション数の見積もり：多すぎず少なすぎず（目安: 数十〜数百程度）で計画されているか？
  • UNIQUE制約との整合性：UNIQUEインデックスにパーティションキーが含まれているか？

シャーディングとは

シャーディング = データを複数のデータベースサーバーに水平分割する技術

🏠 たとえ話：支店展開

1つの店舗では対応しきれなくなったら、支店を作る。
各支店が独立して営業（= 独立したDBサーバー）。

パーティショニング：1台のサーバー内で分割
シャーディング：複数のサーバーに分散

キー候補 メリット デメリット
user_id ユーザー単位で完結しやすい 人気ユーザーに偏る可能性
tenant_id マルチテナントに最適 テナント間クエリが困難
geo_region 地域ごとにサーバー配置可能 グローバルクエリが困難
hash(id) 均等分散 範囲クエリが全シャードスキャン

シャーディングの課題

⚠️ シャーディングの難しさ
  • クロスシャードクエリ：複数シャードにまたがるJOINは困難
  • トランザクション：分散トランザクションは複雑
  • リシャーディング：データ移動が大変
  • ホットスポット：特定シャードへのアクセス集中
✓ シャーディング設計の原則
  1. 可能な限り避ける：まずはスケールアップ、パーティショニングを検討
  2. シャードキーを慎重に選ぶ：クエリパターンを分析
  3. シャード間の依存を最小化：1シャードで完結する設計
  4. リシャーディング計画：将来の分割を見据える

レプリケーションとは

レプリケーション = データベースの複製を作成し、同期を保つ仕組み

🏠 たとえ話：バックアップ要員

主担当（プライマリ）が休むとき、
同じ情報を持つバックアップ担当（レプリカ）が対応。

目的：
1. 可用性向上（障害時に切り替え）
2. 読み取り負荷分散（レプリカで読み取り）

レプリケーションの種類

種類 特徴 トレードオフ
同期レプリケーション 全レプリカに書き込み完了まで待つ データ一貫性◎、性能△
非同期レプリケーション プライマリ書き込み後すぐ応答 性能◎、データ遅延あり
半同期レプリケーション 1つのレプリカには同期 バランス型

読み書き分離

// 読み書き分離パターン
class DatabasePool {
  private primary: Connection;    // 書き込み用
  private replicas: Connection[]; // 読み取り用

  // 書き込みはプライマリへ
  async write(query: string): Promise<void> {
    return this.primary.execute(query);
  }

  // 読み取りはレプリカへ（ラウンドロビン）
  async read(query: string): Promise<any> {
    const replica = this.getNextReplica();
    return replica.execute(query);
  }
}

// 使用例
await db.write('INSERT INTO users ...');  // プライマリ
await db.read('SELECT * FROM users');     // レプリカ

フェイルオーバー

フェイルオーバー = プライマリ障害時にレプリカを昇格させる仕組み

✓ フェイルオーバーの流れ
  1. 障害検出：ヘルスチェックでプライマリ異常を検知
  2. 昇格判断：最も同期が進んでいるレプリカを選択
  3. 切り替え：レプリカを新プライマリに昇格
  4. 接続切り替え：アプリケーションの接続先を変更

レプリケーションラグ

⚠️ レプリカ遅延に注意 
// ❌ 書き込み直後に読み取り → 古いデータの可能性
await db.write('INSERT INTO users (name) VALUES ("Alice")');
const user = await db.read('SELECT * FROM users WHERE name = "Alice"');
// レプリケーションラグでまだ反映されていない可能性！

// ⭕ 書き込み直後はプライマリから読む
await db.write('INSERT INTO users (name) VALUES ("Alice")');
const user = await db.primary('SELECT * FROM users WHERE name = "Alice"');
// または十分な待機時間を設ける

💀 コードレビューの観点

  • Write-after-Read一貫性：書き込み直後の読み取りでプライマリを使用しているか？レプリカからの読み取りでは古いデータを返す可能性がある
  • フェイルオーバー戦略：プライマリ障害時のレプリカ昇格手順が明確か？自動/手動の判断基準はあるか？
  • レプリケーションラグの監視：レプリカの遅延をモニタリングする仕組みがあるか？許容遅延の閾値は設定されているか？
