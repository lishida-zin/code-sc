  • 要件定義の失敗がもたらす影響

要件定義とは何か

要件定義 = システムが「何を」すべきかを明確にすること

🏠 たとえ話：家を建てる前の打ち合わせ

家を建てる前に「どんな家が欲しいか」を決める。
何部屋必要か、どんな設備が欲しいか、予算はいくらか。

これを曖昧にしたまま建て始めると...
「思っていたのと違う」「やり直し」の連続になる。

機能要件 vs 非機能要件

機能要件（Functional Requirements）

「システムが何をするか」

  • ユーザー登録ができる
  • 商品を検索できる
  • 注文履歴を表示できる
  • 在庫数を更新できる

ビジネスの「やりたいこと」を表現

非機能要件（Non-Functional Requirements）

「システムがどうあるべきか」

  • 応答時間は3秒以内
  • 同時1000ユーザーに対応
  • 99.9%の可用性
  • 個人情報を暗号化

品質・制約条件を表現

非機能要件の分類

カテゴリ 内容 例
性能 速度、スループット ページ表示2秒以内
可用性 稼働率、障害復旧 99.9%稼働、RTO 4時間
セキュリティ 認証、暗号化、監査 2要素認証必須
拡張性 将来の成長対応 3年後10倍のユーザー
保守性 変更の容易さ 新機能追加2週間以内
運用性 監視、デプロイ ダウンタイムなしデプロイ
⚠️ 非機能要件を軽視すると...

機能は動くが遅い、落ちる、セキュリティ事故が発生。
後から対応するとコストが10倍以上かかることも。

「性能は後で改善すればいい」は最も危険な思考です。

🔍 レビューの観点

要件定義書をレビューするとき：

  • 非機能要件が書かれているか？（ないなら指摘）
  • 数値で測定可能か？（「速い」ではなく「2秒以内」）
  • 優先度がついているか？

ステークホルダー分析

📚 このページで学ぶこと
  • ステークホルダーとは誰か
  • ステークホルダーの特定方法
  • 利害関係の整理と優先度付け

ステークホルダーとは

ステークホルダー = プロジェクトに関係する全ての人・組織

🏠 たとえ話：結婚式の準備

結婚式のステークホルダーは新郎新婦だけではない。
両家の親、友人、式場、料理人、司会者...

全員の期待を把握しないと「誰かが不満」という事態に。

典型的なステークホルダー

ステークホルダー 関心事 影響力
経営層 ROI、競合優位性、リスク 高（予算決定権）
エンドユーザー 使いやすさ、機能充実 中（実際に使う人）
運用チーム 保守性、監視、障害対応 中（運用を担う）
開発チーム 技術的実現可能性、期間 中（作る人）
法務/コンプライアンス 法令遵守、リスク 高（拒否権を持つ）
外部パートナー 連携仕様、スケジュール 状況による

ステークホルダーマップ

影響力と関心度で分類し、対応戦略を決める。

関心度
低い 高い
影響力 高い 満足させ続ける
（経営層の一部）		 密に管理する
（プロジェクトオーナー）
影響力 低い 監視のみ
（間接部門）		 情報提供を続ける
（エンドユーザー）

要件の矛盾を見つける

⚠️ ステークホルダー間の対立
  • 経営層：早くリリースしたい
  • 開発チーム：品質を担保したい
  • ユーザー：機能を増やしてほしい

これらの対立を事前に把握し、調整することが要件定義の重要な仕事。

🔍 レビューの観点
  • 全ステークホルダーが特定されているか？
  • 運用チームの意見は聞いたか？（見落としがち）
  • 法務確認は必要か？（個人情報を扱う場合は必須）

❌ ステークホルダー分析なし

要件定義の参加者:
- 開発チーム
- プロジェクトマネージャー
（これだけで要件定義を進めてしまう）

結果:
→ リリース後に運用チームから「監視要件がない」
→ 法務から「個人情報の取り扱いルールが未定義」
→ 大幅な手戻り発生

⭕ ステークホルダーを網羅的に特定

ステークホルダー一覧:
- 経営層（承認権限・予算）
- 業務部門（実際の利用者）
- 開発チーム（実装担当）
- 運用チーム（保守・監視）
- 法務/コンプライアンス
- セキュリティチーム
- 外部パートナー

→ 全員の要件を事前にヒアリング
→ 抜け漏れのない要件定義が可能

ユースケースの書き方

📚 このページで学ぶこと

  • 代替フロー・例外フローの重要性

ユースケースとは

ユースケース = ユーザーがシステムを使って達成する「目的」を記述したもの

🏠 たとえ話：レストランの注文

「料理を注文する」というユースケース：
1. お客さんがメニューを見る
2. 料理を選ぶ
3. ウェイターに伝える
4. 注文が厨房に伝わる

誰が、何を、どうやって達成するかを明確にする。

ユースケース記述のテンプレート

項目 内容
ユースケース名 商品を購入する
アクター 会員ユーザー
事前条件 ユーザーがログイン済み、カートに商品がある
事後条件 注文が確定し、確認メールが送信される
基本フロー 1. カートを確認 → 2. 配送先入力 → 3. 支払い → 4. 確定
代替フロー 3a. クーポン適用時の割引処理
例外フロー 3b. 決済失敗時のエラー表示

基本フロー・代替フロー・例外フロー

【基本フロー】（Happy Path）
1. ユーザーがカートページを開く
2. システムがカート内容を表示する
3. ユーザーが「購入手続きへ」を押す
4. システムが配送先入力画面を表示する
5. ユーザーが配送先を入力する
6. ユーザーが支払い方法を選択する
7. システムが決済処理を行う
8. システムが注文完了画面を表示する
9. システムが確認メールを送信する

【代替フロー】
5a. 登録済み住所を選択する場合
    5a1. システムが登録済み住所一覧を表示
    5a2. ユーザーが住所を選択
    5a3. 基本フロー6へ

【例外フロー】
7a. 決済失敗の場合
    7a1. システムがエラーメッセージを表示
    7a2. ユーザーに再入力を促す
    7a3. 基本フロー6へ戻る
⚠️ 例外フローが重要な理由

バグの多くは例外フローで発生します。
「正常系は動くが、エラー時に落ちる」が典型的な問題。

例外フローを詳細に書くことで、テストケースの抜け漏れを防ぐ。

🔍 レビューの観点
  • 事前条件・事後条件は明確か？
  • 例外フローは網羅されているか？
  • アクターは正しく特定されているか？
❓ 確認クイズ

ユースケースで最も見落としやすいのは？

ユースケース図の読み方

📚 このページで学ぶこと

  • include / extend の違い
  • ユースケース図の読み解き方

ユースケース図とは

ユースケース図 = システムの機能と利用者の関係を視覚化したもの

📊 ユースケース図の例：ECサイト

楕円=ユースケース、人型=アクター、破線=関係

構成要素

要素 記号 説明
アクター 人型（棒人間） システムを利用する人・外部システム
ユースケース 楕円 システムの機能（動詞で表現）
システム境界 四角形 システムの範囲を示す
関連 実線 アクターとユースケースの接続

include vs extend

<<include>>（含む）

必ず実行される共通処理

  • 「商品を購入」は「認証する」を必ず含む
  • 基底ユースケースが子を呼び出す
<<extend>>（拡張）

条件付きで実行される追加処理

  • 「クーポン適用」は「商品を購入」を条件付きで拡張
  • 子が基底ユースケースを拡張する
// include: 必ず呼ばれる
商品を購入する
  ├── <<include>> 認証する      // 必須
  └── <<include>> 決済処理する  // 必須

// extend: 条件付きで呼ばれる
商品を購入する
  └── <<extend>> クーポン適用する [クーポンがある場合]
🔍 レビューの観点
  • include/extendの方向は正しいか？
  • システム境界の外に必要なアクターはないか？
  • ユースケースが細かすぎないか？（CRUD個別は過剰）

ユーザーストーリーとは

ユーザーストーリー = ユーザー視点で書いた短い要件記述

📝 ユーザーストーリーのテンプレート 
＜ユーザー種別＞として、
＜達成したいこと＞をしたい。
なぜなら＜理由/価値＞だから。

---
例：
会員ユーザーとして、
購入履歴を確認したい。
なぜなら過去の注文状況を把握したいから。

INVEST基準

良いユーザーストーリーはINVESTを満たす。

基準 意味 説明
I Independent（独立） 他のストーリーに依存しない
N Negotiable（交渉可能） 実装詳細は議論で決める
V Valuable（価値がある） ユーザーに価値を提供する
E Estimable（見積可能） 工数を見積もれる具体性
S Small（小さい） 1スプリントで完了できるサイズ
T Testable（テスト可能） 完了条件が明確

アクセプタンス基準

アクセプタンス基準 = 「何をもって完了とするか」の明確な条件

✓ Gherkin形式（Given-When-Then） 
ストーリー：会員ユーザーとして、購入履歴を確認したい

シナリオ：過去の注文一覧を表示
Given: ログイン済みのユーザーがいる
 And: 過去に3件の注文がある
When: 購入履歴ページにアクセスする
Then: 3件の注文が新しい順に表示される
 And: 各注文に日付、金額、ステータスが表示される

シナリオ：注文がない場合
Given: ログイン済みのユーザーがいる
 And: 過去の注文が0件
When: 購入履歴ページにアクセスする
Then: 「注文履歴がありません」と表示される
曖昧なアクセプタンス基準
- 購入履歴が見える
- 使いやすい画面
- 速く表示される

何をテストすればいいか分からない

明確なアクセプタンス基準
- 直近100件の注文が表示される
- 注文日、金額、ステータスが表示
- 3秒以内に表示される
- 注文がない場合のメッセージ表示

テストケースに直接変換できる

  • アクセプタンス基準は具体的で測定可能か？
  • 異常系のシナリオも含まれているか？

要件のトレーサビリティ

📚 このページで学ぶこと

トレーサビリティとは

トレーサビリティ = 要件がどこから来て、どこに実装されたかを追跡できること

🏠 たとえ話：料理のレシピ

「この料理になぜ塩が入っているの？」と聞かれたとき、
「レシピの手順3に書いてある」と答えられる。

実装の根拠を説明できることがトレーサビリティ。

トレーサビリティの方向

📊 双方向トレーサビリティ

要件トレーサビリティマトリクス（RTM）

要件ID 要件概要 設計 実装 テスト 状態
REQ-001 ユーザー登録 DES-101 USR-001 TC-001 完了
REQ-002 ログイン DES-102 AUTH-001 TC-002 完了
REQ-003 商品検索 DES-201 - - 設計中
REQ-004 カート機能 - - - 未着手

トレーサビリティがないと...

⚠️ トレーサビリティ欠如の問題
  • 変更影響分析ができない：「この要件を変えたらどこに影響？」
  • テスト漏れ：要件に対応するテストがあるか不明
  • ゴールドプレーティング：要件にない機能を勝手に追加
  • 要件漏れ：実装されていない要件に気づかない
🔍 レビューの観点
  • 全要件にIDが振られているか？
  • 実装・テストとの対応が記録されているか？
  • 孤立した要件（どこにも紐づかない）はないか？
❓ 確認クイズ

「このコードはどの要件に基づいているか？」を調べるのは？

優先度付け（MoSCoW法）

📚 このページで学ぶこと
  • 要件の優先度付けの重要性
  • MoSCoW法の4分類
  • 優先度付けの実践的なコツ

なぜ優先度付けが必要か

全ての要件を実装する時間とリソースはない。
何を先にやるか、何を諦めるかを決める必要がある。

🏠 たとえ話：引っ越しの荷造り

トラックに全部は載らない。
絶対必要なもの、あると便利なもの、なくても困らないものを分類する。

MoSCoW法

📊 MoSCoW法による優先度分類
分類 意味 例
Must 絶対必要。ないとリリース不可 ログイン、決済機能
Should 重要だが、なくても動く パスワードリマインダー
Could あれば嬉しい お気に入り機能
Won't 今回はやらない（明示的除外） 多言語対応

優先度付けの落とし穴

⚠️ よくある失敗
  • 全部Mustになる：優先度付けの意味がない
  • ステークホルダーごとに違う優先度：合意形成が必要
  • Won'tが記録されない：後から「やると思ってた」問題
  • 非機能要件の優先度が低い：性能・セキュリティを軽視

優先度を決める観点

観点 質問
ビジネス価値 売上・コスト削減にどれだけ貢献するか？
リスク やらなかったらどんなリスクがあるか？
依存関係 他の機能の前提条件になっているか？
緊急度 法規制や契約上の締め切りがあるか？
🔍 レビューの観点
  • 優先度の根拠は明確か？
  • ステークホルダー間で合意されているか？
  • Won'tが明示的に記録されているか？

要件の曖昧さを排除する技法

📚 このページで学ぶこと
  • 曖昧な要件の危険性
  • 曖昧さを見つける方法
  • 具体化するための質問技法

曖昧な要件とは

解釈の余地がある要件は、必ず問題を引き起こす。

曖昧な要件
  • 「使いやすい画面」
  • 「高速に動作する」
  • 「大量のデータを処理」
  • 「適切なセキュリティ」
  • 「必要に応じて通知」

10人いれば10通りの解釈

具体的な要件
  • 「3クリック以内で目的達成」
  • 「ページ表示2秒以内」
  • 「100万件のデータを処理」
  • 「TLS 1.3で暗号化」
  • 「注文確定時にメール送信」

誰が読んでも同じ理解

曖昧さを見つけるキーワード

⚠️ 要注意ワード
ワード 問題 質問例
「など」「等」 範囲が不明確 具体的に何が含まれる？
「適切に」 基準が不明 何をもって適切とする？
「速く」「多く」 数値が不明 具体的な数値は？
「必要に応じて」 条件が不明 いつ、どんな条件で？
「できるだけ」 優先度が不明 最低ラインは？

具体化するための質問

❓ 5W1H + 数値化
  • Who：誰が使う？権限は？
  • What：具体的に何を？範囲は？
  • When：いつ？頻度は？
  • Where：どこで？環境は？
  • Why：なぜ必要？目的は？
  • How：どのように？手順は？
  • How much/many：数値で表すと？

具体化の例

【曖昧】
「商品検索は高速に動作すること」

【質問】
- 「高速」とは具体的に何秒以内？
- 何件のデータを検索する想定？
- どんなネットワーク環境を想定？

【具体化後】
「商品検索は、100万件のデータから
 3秒以内に結果を返すこと。
 検索条件：商品名、カテゴリ、価格範囲
 対象環境：4G回線以上」
🔍 レビューの観点
  • 曖昧ワードが含まれていないか？
  • 数値で測定可能か？
  • 境界条件は明確か？（最小、最大、エラー時）
❓ 確認クイズ

「大量のデータを処理できること」の問題点は？

要件レビューの目的

要件の問題を早期に発見することで、手戻りを防ぐ。

📈 修正コストの法則

バグの修正コストは、工程が進むほど指数的に増大する。

発見フェーズ 相対コスト
要件定義 1倍
設計 5倍
実装 10倍
テスト 20倍
本番リリース後 100倍以上

レビューチェックリスト

✓ 基本チェック項目
観点 確認内容
完全性 すべての機能・非機能要件が網羅されているか
一貫性 要件間に矛盾がないか
明確性 曖昧な表現がないか、誰が読んでも同じ理解か
検証可能性 テストで確認できるか
追跡可能性 要件IDが振られ、上位要件と紐づいているか
実現可能性 技術的・コスト的に実現可能か

よくある指摘パターン

⚠️ レビューで見つかる典型的な問題
  • 抜け：エラー処理、境界条件が未定義
  • 矛盾：A画面とB画面で仕様が違う
  • 曖昧：「適切に処理する」などの表現
  • 過剰：実現困難または不要な要件
  • 不足：非機能要件がない

レビュー技法

技法 説明 適用場面
ウォークスルー 作成者が説明、参加者が質問 早期のドラフトレビュー

🔍 レビュー時の質問集
  • 「この要件のテストケースを書けますか？」
  • 「エラーの場合はどうなりますか？」
  • 「データが0件/上限値の場合は？」
  • 「この機能は誰がいつ使いますか？」
  • 「この要件の根拠は何ですか？」

❌ 形だけのレビュー

レビュー会議:
- 作成者が30分プレゼン
- 参加者は事前に読んでいない
- 「特に問題ありません」で終了
- 指摘事項の記録なし

→ 後工程で重大な漏れが発覚
→ 要件レビューが形骸化

⭕ 効果的なレビュー

レビュー会議:
- 事前に資料を配布（2日前）
- 参加者は個人レビュー済み
- チェックリストに基づく指摘
- 指摘事項はIssue/チケットで管理
- 修正後の再レビューを実施

→ 曖昧な要件・矛盾を早期発見
→ 手戻りコストを大幅削減

SRS（Software Requirements Specification）

SRS = ソフトウェア要件仕様書。IEEE 830規格が有名。

📄 SRSの標準的な構成
章 セクション 内容
1 はじめに 目的、スコープ、用語定義、参照文書
2 全体説明 製品の概要、ユーザー特性、制約、前提条件
3 機能要件 ユースケース、画面仕様、業務フロー
4 非機能要件 性能、セキュリティ、可用性、保守性
5 外部インターフェース UI、API、ハードウェア、他システム連携
6 付録 用語集、データ辞書、変更履歴

各セクションの書き方のコツ

1. はじめに
- 目的：このドキュメントが何のために存在するか
- スコープ：対象範囲と対象外を明記
- 用語定義：プロジェクト固有の用語を説明

3. 機能要件
- 要件IDを振る（REQ-001, FR-001など）
- 「〜できること」の形式で記述
- 正常系・異常系を分けて記述

4. 非機能要件
- 必ず数値で定量化する
- 測定方法も明記する
- カテゴリ別に整理（性能/可用性/セキュリティ等）

ドキュメント管理

項目 ベストプラクティス
バージョン管理 Gitで管理、変更履歴を残す
レビュー記録 レビュー日、参加者、指摘事項を記録
承認フロー ステークホルダーの承認を得る
変更管理 変更要求→影響分析→承認→反映
⚠️ よくある失敗
  • 巨大な一枚岩ドキュメント：更新・レビューが困難
  • バージョン管理なし：「どれが最新？」問題
  • 承認なしで開発開始：後から「そんな仕様ではない」
  • 変更履歴がない：なぜ変わったか分からない

🔍 レビューの総まとめ
  • 機能要件と非機能要件の両方があるか？
  • 曖昧な表現がないか？
  • テストで検証可能か？
  • トレーサビリティが確保されているか？
  • ステークホルダーの合意を得ているか？
