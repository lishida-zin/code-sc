なぜマルチリージョンが必要か

単一リージョンでの運用にはリスクと制約があります。

🏠 たとえ話：支店展開

東京に1店舗だけの会社 → 地震で全滅のリスク。
大阪・福岡にも支店があれば、1つが被災しても事業継続可能。

クラウドも同じ。複数リージョンに展開することで、
自然災害やリージョン障害から守れます。

マルチリージョンの利点

利点 説明
高可用性 1つのリージョンが障害でも他でサービス継続
低レイテンシ ユーザーに近いリージョンから応答
コンプライアンス データ居住地要件（GDPR等）への対応
災害復旧 地理的に離れた場所でのバックアップ

アクティブ-アクティブ vs アクティブ-スタンバイ

アクティブ-アクティブ
  • 両リージョンが同時に稼働
  • トラフィックを分散
  • 低レイテンシ（最寄りで処理）
  • データ同期が複雑
  • コストは高い
// Active-Active構成
リージョンA: 50%のトラフィック
リージョンB: 50%のトラフィック
→ 両方が書き込み可能（コンフリクト管理必要）
アクティブ-スタンバイ
  • Primary のみが通常稼働
  • Secondary は待機状態
  • 障害時にフェイルオーバー
  • データ同期はシンプル
  • コストは抑えめ
// Active-Standby構成
リージョンA: 100%のトラフィック（Primary）
リージョンB: 0%（Standby、障害時に昇格）
→ 単方向レプリケーションで済む

データ同期の課題

⚠️ CAP定理の制約

分散システムではConsistency（一貫性）、Availability（可用性）、Partition Tolerance（分断耐性）の3つを同時に満たすことはできません。

ここで重要なのは、ネットワーク分断（Partition）は現実の分散システムでは避けられないという点です。 ノード間の通信は遅延・切断・パケットロスが必ず発生します。 したがってPartition Toleranceは前提条件であり、実質的な選択はCP（一貫性優先）か AP（可用性優先）かの二択になります。

  • CA：単一ノードの従来型RDBMS。ネットワーク分断が起きない前提であり、分散システムとは言えない
  • CP：分断が発生した際に一貫性を優先し、可用性を犠牲にする。分断中は書き込みを拒否してでもデータの整合性を保つ（例：ZooKeeper, HBase, MongoDB strong read）
  • AP：分断が発生した際に可用性を優先し、結果整合性を許容する。分断中もリクエストに応答し、分断解消後にデータを同期する（例：Cassandra, DynamoDB, CouchDB）

マルチリージョン構成では通常APを選択し、結果整合性（Eventual Consistency）を受け入れます。

📚 CAP定理：各組み合わせの具体例
選択 システム例 特徴
CA 従来のRDBMS（単一ノード PostgreSQL, MySQL） ネットワーク分断がない環境が前提。単一障害点になりやすい
CP ZooKeeper, HBase, MongoDB（strong read） 分断時に書き込みを拒否して一貫性を保持。金融取引・在庫管理など整合性が最優先の用途
AP Cassandra, DynamoDB, CouchDB 分断時もリクエストに応答し、後で同期。SNSフィード・ショッピングカートなど可用性が重要な用途

Circuit Breaker（サーキットブレーカー）パターン

障害が発生したサービスへのリクエストを「遮断機」のように止め、障害の連鎖（カスケード障害）を防ぎます。 状態は3つ遷移します：

  • Closed（通常稼働）：リクエストをそのまま転送。失敗がしきい値を超えるとOpenへ
  • Open（遮断中）：リクエストを即座にエラーで返す。一定時間後にHalf-Openへ
  • Half-Open（試行中）：少数のリクエストだけ通して回復を確認。成功すればClosed、失敗すればOpenに戻る
// Circuit Breaker 疑似コード
class CircuitBreaker {
  state = "CLOSED"       // CLOSED | OPEN | HALF_OPEN
  failureCount = 0
  threshold = 5
  resetTimeout = 30000   // 30秒

  async call(request) {
    if (this.state === "OPEN") {
      if (now() - this.lastFailureTime > this.resetTimeout) {
        this.state = "HALF_OPEN"
      } else {
        throw new Error("Circuit is OPEN - request blocked")
      }
    }

    try {
      const result = await request()
      this.onSuccess()
      return result
    } catch (error) {
      this.onFailure()
      throw error
    }
  }

  onSuccess() {
    this.failureCount = 0
    this.state = "CLOSED"
  }

  onFailure() {
    this.failureCount++
    this.lastFailureTime = now()
    if (this.failureCount >= this.threshold) {
      this.state = "OPEN"
    }
  }
}

Saga パターン

分散トランザクションを補償トランザクション（Compensation）のチェーンで管理します。 各サービスがローカルトランザクションを実行し、途中で失敗した場合は完了済みのステップを逆順に取り消します。 

// Saga パターン 疑似コード（オーケストレーション方式）
class OrderSaga {
  async execute(orderData) {
    const steps = []

    try {
      // Step 1: 在庫を予約
      const reservation = await inventoryService.reserve(orderData.items)
      steps.push({ compensate: () => inventoryService.cancelReserve(reservation.id) })

      // Step 2: 決済を実行
      const payment = await paymentService.charge(orderData.payment)
      steps.push({ compensate: () => paymentService.refund(payment.id) })

      // Step 3: 配送を手配
      const shipment = await shippingService.schedule(orderData.address)
      steps.push({ compensate: () => shippingService.cancel(shipment.id) })

      return { status: "completed" }
    } catch (error) {
      // 失敗時：完了済みステップを逆順に補償
      for (const step of steps.reverse()) {
        await step.compensate()
      }
      return { status: "rolled_back", error: error.message }
    }
  }
}

災害復旧（DR）とは

DR（Disaster Recovery） = 災害発生時にシステムを復旧する計画と仕組み

🏠 たとえ話：火災保険と避難訓練

バックアップ = 火災保険（被害を補償）
DR計画 = 避難訓練（いざという時の行動計画）

保険だけでは家は建て直せない。
どこに避難し、どう復旧するかの計画が必要です。

DR戦略の4パターン

📊 DR戦略とRTO/RPO/コストの関係

コストをかけるほど復旧時間（RTO）は短縮できる

戦略 RTO コスト 特徴
Backup & Restore 24時間+ 最低 バックアップからの復元。最もシンプル
Pilot Light 数時間 低 最小限のコアシステムを常時稼働
Warm Standby 数十分 中 縮小版の本番環境を常時稼働
Multi-Site Active-Active ほぼゼロ 最高 複数サイトで同時稼働

各戦略の詳細

🔥 Pilot Light（パイロットライト）

ガスコンロの種火のように、最小限のコアコンポーネントだけを稼働させておく。 

// Pilot Light構成
DRサイト:
- DB: レプリカを常時同期 ✓
- アプリサーバー: AMI/イメージのみ保持（停止状態）
- LB: 設定済み（無効状態）

災害時:
1. アプリサーバーを起動（数分）
2. スケールアウト（数十分）
3. DNS切り替え
→ RTO: 1〜数時間
🌡️ Warm Standby

本番の縮小版を常時稼働。災害時はスケールアップするだけ。 

// Warm Standby構成
本番: App x 10台, DB Primary
DRサイト: App x 2台（稼働中）, DB Replica

災害時:
1. DRサイトのAppを10台にスケールアウト
2. DBをPrimaryに昇格
3. DNS切り替え
→ RTO: 数十分

  • 復旧優先度：どのシステムから復旧するか

RTO/RPOの定義と計算

📚 このページで学ぶこと

  • RPO（Recovery Point Objective）の定義
  • ビジネス要件からの算出方法

RTO と RPO

災害復旧計画で最も重要な2つの指標です。

🏠 たとえ話：病院の緊急対応

RTO = 救急車が到着するまでの時間（許容できる停止時間）
RPO = 最後の健康診断からの経過時間（許容できるデータ損失）

RTOが短いほど、すぐに治療を開始できる。
RPOが短いほど、最新の健康状態を把握できる。

📊 RTO/RPOのタイムライン

RPO = データ損失の許容範囲、RTO = ダウンタイムの許容範囲

指標 定義 例
RTO 障害発生から復旧完了までの許容時間 RTO=4時間 → 4時間以内に復旧必須
RPO 障害発生時に失っても許容できるデータ量（時間） RPO=1時間 → 最大1時間分のデータ損失OK

ビジネス要件からの算出

💰 損失計算の例 
// ECサイトの例
1時間あたりの売上: 1,000万円
1時間あたりの運用コスト: 50万円

【RTO算出】
許容できる損失: 5,000万円
→ RTO = 5,000万 / 1,050万 ≈ 4.8時間
→ RTO目標: 4時間（余裕を持たせる）

【RPO算出】
- 注文データ: 損失不可 → RPO = 0（同期レプリケーション）
- アクセスログ: 1時間分まで許容 → RPO = 1時間
- キャッシュデータ: 再構築可能 → RPO = 考慮不要

RTO/RPOと実装コスト

⚠️ トレードオフ
RTO/RPO 必要な実装 コスト
RTO: 24h, RPO: 24h 日次バックアップ 低
RTO: 4h, RPO: 1h Pilot Light + 1時間ごとのバックアップ 中
RTO: 1h, RPO: 15min Warm Standby + 継続的レプリケーション 高
RTO: 0, RPO: 0 Active-Active + 同期レプリケーション 最高

RPO=0は非常に高コスト。本当に必要か要件を精査すること。

🔍 設計レビューの観点
  • RTO/RPOの根拠：ビジネス要件から算出されているか
  • 現実的な目標：予算と技術で実現可能か
  • テスト済み：実際に目標を達成できることを確認済みか
  • データ種別ごとの設定：一律ではなく重要度に応じて設定

3-2-1 バックアップルール

バックアップの黄金律と呼ばれる基本原則です。

✓ 3-2-1 ルール
  • 3つのコピーを持つ（本番 + バックアップ2つ）
  • 2つの異なるメディアに保存（SSD + S3 など）
  • 1つは別の場所に保管（別リージョン、オフサイト）
// 3-2-1の実装例
本番DB: RDS (ap-northeast-1)
バックアップ1: RDS自動スナップショット（同リージョン、別AZ）
バックアップ2: S3クロスリージョンレプリケーション（ap-northeast-3）

→ ランサムウェア、リージョン障害、人為的ミスに対応

バックアップの種類

種類 内容 特徴
フルバックアップ 全データをコピー 復元が簡単、時間とストレージ大
差分バックアップ 最後のフルからの変更分 復元：フル + 最新差分
増分バックアップ 前回バックアップからの変更分 最小ストレージ、復元は複雑 
// バックアップスケジュール例
日曜 00:00: フルバックアップ
月〜土 00:00: 増分バックアップ
毎時 00分: WALアーカイブ（PostgreSQL）

復元時:
1. 日曜のフルバックアップを復元
2. 月〜土の増分を順番に適用
3. WALを適用してPITR（Point-in-Time Recovery）

イミュータブルバックアップ

⚠️ ランサムウェア対策

イミュータブル（不変）バックアップ：一度作成したら変更・削除不可 

// S3 Object Lock（WORM: Write Once Read Many）
aws s3api put-object-lock-configuration \
  --bucket my-backup-bucket \
  --object-lock-configuration '{
    "ObjectLockEnabled": "Enabled",
    "Rule": {
      "DefaultRetention": {
        "Mode": "GOVERNANCE",
        "Days": 30
      }
    }
  }'

// 30日間は削除不可（管理者でも）
// ランサムウェアに感染してもバックアップは守られる

バックアップのテスト

🔍 レビューの観点

バックアップは復元できて初めて意味がある

  • 定期的な復元テスト：月1回以上実施しているか
  • 復元手順書：明文化されているか
  • 復元時間の計測：RTOを満たせるか
  • データ整合性の検証：復元後のデータは正しいか
// 復元テストの自動化例
# 毎月1日に自動実行
0 3 1 * * /scripts/backup-restore-test.sh

# スクリプト内容:
# 1. 最新バックアップから別環境に復元
# 2. 基本的なクエリを実行してデータ検証
# 3. 結果をSlackに通知
# 4. テスト環境を削除

❌ 不十分なバックアップ戦略

# 同一リージョンのみにバックアップ

  --db-instance-identifier mydb \
  --db-snapshot-identifier mydb-backup
# リージョン障害時にバックアップも失われる！
# 復元テストもしていない...

⭕ 3-2-1ルールに従ったバックアップ

# 自動バックアップ + クロスリージョンコピー

  --backup-retention-period 30

  --source-region ap-northeast-1 \
  --target-region us-west-2
# 月次で復元テストを自動実行

クラウドコストの構成

クラウドのコストは使った分だけですが、最適化しないと高額になります。

コスト項目 内容 最適化のポイント
コンピュート EC2, Lambda, ECS RI, スポット, 適切なサイジング
ストレージ S3, EBS, RDS ライフサイクル, 不要データ削除
データ転送 リージョン間, インターネット CDN活用, 同一AZ配置
その他 監視, DNS, サポート 必要なものだけ利用

インスタンス購入オプション

オンデマンド
  • いつでも起動・停止可能
  • 秒単位の課金
  • 最も高い単価
  • 用途：開発環境、不定期な負荷
リザーブド（RI）
  • 1年/3年の長期契約
  • 最大72%割引
  • キャパシティ予約あり
  • 用途：本番環境、ベースライン負荷
スポットインスタンス
  • 余剰キャパシティを利用
  • 最大90%割引
  • 2分前通知で中断の可能性
  • 用途：バッチ処理、CI/CD
Savings Plans
  • 使用量をコミット（$/時間）
  • 最大66%割引
  • EC2, Lambda, Fargateに適用
  • 用途：マルチサービス環境

⚠️ 暗号化の必須事項

❌ 障害時の対応がない

// APIコール: リトライなし
const response = await fetch(apiUrl);
// 一時的なネットワーク障害で即エラー
if (!response.ok) throw new Error('Failed');

⭕ 指数バックオフ付きリトライ

// 指数バックオフでリトライ
async function fetchWithRetry(url, maxRetries = 3) {
  for (let i = 0; i < maxRetries; i++) {
    try {
      const res = await fetch(url);
      if (res.ok) return res;
    } catch (e) { /* 一時障害 */ }
    await sleep(Math.pow(2, i) * 1000); // 1s,2s,4s
  }
  throw new Error('All retries failed');
}

⭕ Cache-Asideパターン

app.get('/products/:id', async (req, res) => {
  const key = `product:${req.params.id}`;
  // 1. まずキャッシュを確認
  let product = await redis.get(key);
  if (!product) {
    // 2. キャッシュミス時のみDBアクセス
    product = await db.query(
      'SELECT * FROM products WHERE id = ?',
      [req.params.id]
    );
    // 3. キャッシュに保存(TTL: 5分)
    await redis.set(key, product, 'EX', 300);
  }
  res.json(product);
});
