デザインパターンとは？

デザインパターンは、よくある設計上の問題に対する再利用可能な解決策です。

🏠 たとえ話

料理のレシピのようなものです。
「カレーを作りたい」→「カレーのレシピ」があれば、ゼロから考えなくていい。

同様に「オブジェクトの生成を柔軟にしたい」→「Factoryパターン」を使えばいい。
車輪の再発明を防ぐのがパターンの役割です。

GoF（Gang of Four）とは

1994年に4人の著者（Gamma, Helm, Johnson, Vlissides）が出版した
『Design Patterns』という本で23のパターンが体系化されました。

「GoF」は「4人のギャング」という意味で、この4人の著者を指します。

パターンの3分類

📦 生成パターン（5個）

オブジェクトの作り方に関するパターン
Singleton, Factory Method, Abstract Factory, Builder, Prototype

🏗️ 構造パターン（7個）

クラスの組み合わせ方に関するパターン
Adapter, Bridge, Composite, Decorator, Facade, Flyweight, Proxy

🎭 振る舞いパターン（11個）

オブジェクト間の連携方法に関するパターン
Strategy, Observer, Command, State など

パターンを学ぶ意義

  • 共通言語: 「Factoryパターンで」と言えば伝わる
  • 設計の引き出し: 選択肢が増える
  • 既存コードの理解: フレームワークの設計が読める
⚠️ パターンの過剰適用に注意

「パターンを知っている」→「とりあえず使う」は危険。
問題があるから解決策を適用するのが正しい順序です。
シンプルなコードを複雑にするのは本末転倒。

Singleton パターン

📚 このページで学ぶこと

Singletonとは？

インスタンスを1つだけに制限するパターンです。

🏠 たとえ話

会社の「社長」は1人だけ。
どの部署から呼んでも、同じ社長がやってくる。
これがSingletonの考え方です。

使用場面

  • 設定情報の管理（Config）
  • ログ出力（Logger）
  • データベース接続プール

実装例

📝 TypeScriptでのSingleton 
class ConfigManager {
  private static instance: ConfigManager;
  private settings: Map<string, string> = new Map();

  // privateコンストラクタで外部からnewできない
  private constructor() {}

  static getInstance(): ConfigManager {
    if (!ConfigManager.instance) {
      ConfigManager.instance = new ConfigManager();
    }
    return ConfigManager.instance;
  }

  get(key: string): string | undefined {
    return this.settings.get(key);
  }

  set(key: string, value: string): void {
    this.settings.set(key, value);
  }
}

// 使い方
const config1 = ConfigManager.getInstance();
const config2 = ConfigManager.getInstance();
console.log(config1 === config2); // true（同じインスタンス）

Singletonの問題点

🔥 グローバル状態という罠

Singletonは隠れた依存性を生みます。 

// ❌ 依存関係が見えない
class UserService {
  getUser(id: string): User {
    // ConfigManager.getInstance()がどこからでも呼べる
    const apiUrl = ConfigManager.getInstance().get('API_URL');
    // テストでモックしにくい！
  }
}

コンストラクタを見ても依存関係が分からない。
テストでモックを差し込むのも困難です。

モダンな代替：依存性注入（DI）

❌ Singleton直接呼び出し
class UserService {
  getUser(id: string): User {
    const config = ConfigManager.getInstance();
    // 依存が隠れている
  }
}
✓ DIで注入
class UserService {
  constructor(private config: Config) {}
  // 依存が明示的

  getUser(id: string): User {
    const apiUrl = this.config.get('API_URL');
    // テストでモック可能
  }
}

Factory Method パターン

📚 このページで学ぶこと
  • Factory Methodの目的
  • switch文を使わない生成
  • 開放閉鎖の原則（OCP）との関係

Factory Methodとは？

オブジェクトの生成をサブクラスに委譲するパターンです。

🏠 たとえ話

ピザ屋のチェーン店を考えてください。
本部は「ピザを作れ」という指示だけ出す。
東京店は「東京風ピザ」、大阪店は「大阪風ピザ」を作る。
作り方は各店舗に任せるのがFactory Methodです。

問題：switch文での生成

🔥 新しい種類を追加するたびに修正が必要 
// ❌ OCP違反：新しい通知方法を追加するたびに修正
function createNotification(type: string): Notification {
  switch (type) {
    case 'email':
      return new EmailNotification();
    case 'sms':
      return new SMSNotification();
    case 'push':
      return new PushNotification(); // 追加のたびにここを修正
    default:
      throw new Error('Unknown type');
  }
}

解決：Factory Method

✓ 拡張に開いた設計 
// インターフェースを定義
interface Notification {
  send(message: string): void;
}

interface NotificationFactory {
  create(): Notification;
}

// 各通知タイプごとにファクトリを実装
class EmailNotificationFactory implements NotificationFactory {
  create(): Notification {
    return new EmailNotification();
  }
}

class SMSNotificationFactory implements NotificationFactory {
  create(): Notification {
    return new SMSNotification();
  }
}

// 新しい通知タイプは新クラスを追加するだけ
class SlackNotificationFactory implements NotificationFactory {
  create(): Notification {
    return new SlackNotification();
  }
}

// 使う側
function sendNotification(factory: NotificationFactory, message: string) {
  const notification = factory.create();
  notification.send(message);
}

OCPとの関係

Factory Methodは開放閉鎖の原則（OCP）を実現します。

  • 拡張に開いている: 新しいFactoryクラスを追加するだけ
  • 修正に閉じている: 既存コードを変更しない

Abstract Factory パターン

📚 このページで学ぶこと
  • Abstract Factoryの目的
  • Factory Methodとの違い
  • 関連オブジェクト群の一貫した生成

Abstract Factoryとは？

関連するオブジェクト群をまとめて生成するパターンです。

🏠 たとえ話

家具ショップを考えてください。
「モダンスタイル」を選ぶと、モダンな椅子・テーブル・ソファがセットで出てくる。
「和風スタイル」を選ぶと、和風の椅子・テーブル・ソファがセットで出てくる。
スタイルに一貫性のある家具群を生成するのがAbstract Factoryです。

使用場面

  • UIテーマ（ダークモード/ライトモード）
  • データベースドライバ（MySQL/PostgreSQL）
  • OSごとの部品（Windows/Mac）

実装例

// 製品のインターフェース
interface Button {
  render(): void;
}

interface TextField {
  render(): void;
}

// 抽象ファクトリ
interface UIFactory {
  createButton(): Button;
  createTextField(): TextField;
}

// ダークテーマの実装
class DarkButton implements Button {
  render() { console.log('Dark Button'); }
}

class DarkTextField implements TextField {
  render() { console.log('Dark TextField'); }
}

class DarkUIFactory implements UIFactory {
  createButton(): Button { return new DarkButton(); }
  createTextField(): TextField { return new DarkTextField(); }
}

// ライトテーマの実装
class LightButton implements Button {
  render() { console.log('Light Button'); }
}

class LightTextField implements TextField {
  render() { console.log('Light TextField'); }
}

class LightUIFactory implements UIFactory {
  createButton(): Button { return new LightButton(); }
  createTextField(): TextField { return new LightTextField(); }
}

// 使う側：ファクトリを差し替えるだけでテーマ変更
function buildUI(factory: UIFactory) {
  const button = factory.createButton();
  const textField = factory.createTextField();
  button.render();
  textField.render();
}

buildUI(new DarkUIFactory());  // 全部ダークテーマ
buildUI(new LightUIFactory()); // 全部ライトテーマ

Factory Method との違い

Factory Method

1種類のオブジェクトを生成
サブクラスで生成方法をオーバーライド

Abstract Factory

複数種類の関連オブジェクトを生成
ファクトリ全体を差し替える

⚠️ 過度な階層化に注意

製品が増えるとファクトリの変更が大変になります。
「本当に関連する製品群か？」を見極めてから適用しましょう。

Builder パターン

📚 このページで学ぶこと
  • Builderの目的と実装
  • 長いコンストラクタ問題の解決
  • メソッドチェーンによる可読性向上

Builderとは？

複雑なオブジェクトを段階的に構築するパターンです。

🏠 たとえ話

ハンバーガーの注文を考えてください。
「パティ2枚、チーズあり、ピクルス抜き、オニオン多め」
一度に全部言うのは大変。
1つずつ選んでいくのがBuilderの考え方です。

問題：引数が多すぎるコンストラクタ

🔥 何番目が何の引数か分からない 
// ❌ 引数の順番を間違えやすい
const request = new HttpRequest(
  'POST',           // method
  '/api/users',     // url
  { 'Content-Type': 'application/json' },  // headers
  '{"name":"test"}', // body
  5000,             // timeout
  3,                // retries
  null,             // auth
  null              // proxy
);

// 8個の引数、何がなんだか分からない！

解決：Builder パターン

✓ 読みやすく、間違いにくい 
class HttpRequestBuilder {
  private method = 'GET';
  private url = '';
  private headers: Record<string, string> = {};
  private body: string | null = null;
  private timeout = 30000;
  private retries = 0;

  setMethod(method: string): this {
    this.method = method;
    return this;  // thisを返すことでチェーン可能
  }

  setUrl(url: string): this {
    this.url = url;
    return this;
  }

  setHeader(key: string, value: string): this {
    this.headers[key] = value;
    return this;
  }

  setBody(body: string): this {
    this.body = body;
    return this;
  }

  setTimeout(timeout: number): this {
    this.timeout = timeout;
    return this;
  }

  build(): HttpRequest {
    return new HttpRequest(
      this.method, this.url, this.headers,
      this.body, this.timeout, this.retries
    );
  }
}

// 使い方：何を設定しているか一目瞭然
const request = new HttpRequestBuilder()
  .setMethod('POST')
  .setUrl('/api/users')
  .setHeader('Content-Type', 'application/json')
  .setBody('{"name":"test"}')
  .setTimeout(5000)
  .build();

Builderの利点

  • 可読性: 何を設定しているか明確
  • デフォルト値: 必要なものだけ設定すればOK
  • バリデーション: build()で整合性チェック可能
  • 不変オブジェクト: 構築後は変更不可にできる

Prototype パターン

📚 このページで学ぶこと
  • Prototypeの目的
  • 浅いコピーと深いコピー
  • クローン実装の注意点

Prototypeとは？

既存のオブジェクトをコピーして新しいオブジェクトを作るパターンです。

🏠 たとえ話

書類のコピー機を考えてください。
原本を1から作るのは大変。
でもコピーなら一瞬で複製できる。
原本（プロトタイプ）から複製するのがこのパターンです。

使用場面

  • 初期化コストが高いオブジェクト
  • 設定済みオブジェクトのテンプレート
  • 実行時に型を決定する必要がある場合

実装例

interface Prototype<T> {
  clone(): T;
}

class DocumentTemplate implements Prototype<DocumentTemplate> {
  constructor(
    public title: string,
    public content: string,
    public metadata: { author: string; tags: string[] }
  ) {}

  clone(): DocumentTemplate {
    // 深いコピーが必要！
    return new DocumentTemplate(
      this.title,
      this.content,
      {
        author: this.metadata.author,
        tags: [...this.metadata.tags]  // 配列もコピー
      }
    );
  }
}

// 使い方
const template = new DocumentTemplate(
  '議事録テンプレート',
  '日時：\n参加者：\n議題：',
  { author: '管理者', tags: ['会議', 'テンプレート'] }
);

const doc1 = template.clone();
doc1.title = '2026年1月会議 議事録';
doc1.metadata.tags.push('1月');

// 元のテンプレートは変更されない
console.log(template.title); // '議事録テンプレート'
console.log(template.metadata.tags); // ['会議', 'テンプレート']

浅いコピー vs 深いコピー

🔥 浅いコピーの罠 
// ❌ 浅いコピー：参照が共有される
const original = {
  name: 'test',
  items: ['a', 'b', 'c']
};

const shallowCopy = { ...original };
shallowCopy.items.push('d');  // 元の配列も変わる！

console.log(original.items); // ['a', 'b', 'c', 'd'] ← 変わってる！
✓ 深いコピー：完全に独立 
// ⭕ 深いコピー
const deepCopy = {
  name: original.name,
  items: [...original.items]  // 配列も新しく作る
};

deepCopy.items.push('d');
console.log(original.items); // ['a', 'b', 'c'] ← 変わらない

Adapter パターン

📚 このページで学ぶこと
  • Adapterの目的
  • 互換性のないインターフェースの変換
  • レガシーシステムとの統合

Adapterとは？

互換性のないインターフェースを変換するパターンです。

🏠 たとえ話

海外旅行の電源プラグを考えてください。
日本のプラグ（2極）はヨーロッパのコンセント（丸型）に刺さらない。
でも変換アダプターがあれば使える。
コードを変えずに互換性を持たせるのがAdapterです。

使用場面

  • レガシーシステムとの統合
  • サードパーティライブラリのラップ
  • 異なるAPIの統一

実装例

// 新システムが期待するインターフェース
interface PaymentProcessor {
  processPayment(amount: number, currency: string): Promise<PaymentResult>;
}

// レガシーシステムの既存クラス（変更できない）
class LegacyPaymentSystem {
  makePayment(yen: number): { success: boolean; transactionId: string } {
    // 古い実装（円のみ対応）
    return { success: true, transactionId: 'LEGACY-123' };
  }
}

// Adapter：レガシーを新インターフェースに適合させる
class LegacyPaymentAdapter implements PaymentProcessor {
  constructor(private legacy: LegacyPaymentSystem) {}

  async processPayment(amount: number, currency: string): Promise<PaymentResult> {
    // 通貨変換
    const yen = currency === 'JPY' ? amount : this.convertToYen(amount, currency);

    // レガシーシステムを呼び出し
    const result = this.legacy.makePayment(yen);

    // 結果を新形式に変換
    return {
      success: result.success,
      transactionId: result.transactionId,
      processedAt: new Date()
    };
  }

  private convertToYen(amount: number, currency: string): number {
    // 為替変換ロジック
    return amount * 150; // 簡略化
  }
}

// 使う側：レガシーを意識せずに使える
const processor: PaymentProcessor = new LegacyPaymentAdapter(
  new LegacyPaymentSystem()
);
await processor.processPayment(100, 'USD');

Adapterの利点

  • 既存コード不変: レガシーを変更せずに統合
  • 段階的移行: 新旧システムを共存させられる
  • テスト容易: Adapterをモックに差し替え可能

Decorator パターン

📚 このページで学ぶこと
  • Decoratorの目的
  • 継承 vs コンポジション
  • 機能の動的な追加

Decoratorとは？

オブジェクトに動的に機能を追加するパターンです。

🏠 たとえ話

コーヒーのトッピングを考えてください。
ベースのコーヒーに「ミルク追加」「シロップ追加」「ホイップ追加」
組み合わせは自由。
ベースを変えずに機能を重ねるのがDecoratorです。

問題：継承での機能追加

🔥 継承の組み合わせ爆発 
// ❌ 継承で機能を追加すると...
class Logger {}
class TimestampLogger extends Logger {}       // タイムスタンプ付き
class JsonLogger extends Logger {}            // JSON形式
class EncryptedLogger extends Logger {}       // 暗号化

// 組み合わせが必要になると爆発！
class TimestampJsonLogger extends Logger {}
class TimestampEncryptedLogger extends Logger {}
class JsonEncryptedLogger extends Logger {}
class TimestampJsonEncryptedLogger extends Logger {}
// 3機能で7クラス、4機能なら15クラス...

解決：Decorator パターン

✓ 自由に組み合わせ可能 
// 基本インターフェース
interface Logger {
  log(message: string): void;
}

// 基本実装
class BasicLogger implements Logger {
  log(message: string): void {
    console.log(message);
  }
}

// Decorator基底クラス
class LoggerDecorator implements Logger {
  constructor(protected logger: Logger) {}

  log(message: string): void {
    this.logger.log(message);
  }
}

// 各機能をDecoratorとして実装
class TimestampDecorator extends LoggerDecorator {
  log(message: string): void {
    const timestamp = new Date().toISOString();
    super.log(`[${timestamp}] ${message}`);
  }
}

class JsonDecorator extends LoggerDecorator {
  log(message: string): void {
    super.log(JSON.stringify({ message, time: Date.now() }));
  }
}

class UppercaseDecorator extends LoggerDecorator {
  log(message: string): void {
    super.log(message.toUpperCase());
  }
}

// 使い方：自由に組み合わせ！
const logger = new TimestampDecorator(
  new JsonDecorator(
    new BasicLogger()
  )
);

logger.log('Hello');
// [2024-01-15T10:30:00.000Z] {"message":"Hello","time":1705315800000}

Decoratorの利点

  • 柔軟な組み合わせ: 実行時に機能を追加/削除
  • 単一責任: 各Decoratorは1つの機能のみ
  • 開放閉鎖原則: 既存コードを変更せずに拡張

Facade パターン

📚 このページで学ぶこと
  • Facadeの目的
  • 複雑なサブシステムの単純化
  • 薄すぎるFacadeの問題

Facadeとは？

複雑なサブシステムに対するシンプルなインターフェースを提供するパターンです。

「Facade」は「建物の正面」という意味。
内部の複雑さを隠して、きれいな入口を見せます。

🏠 たとえ話

ホテルのコンシェルジュを考えてください。
タクシー手配、レストラン予約、チケット購入...
お客さんは「○○したい」と言うだけ。
複雑な手配は全部コンシェルジュがやってくれるのがFacadeです。

実装例

// 複雑なサブシステムたち
class VideoDecoder {
  decode(file: string): Buffer { /* ... */ }
}

class AudioDecoder {
  decode(file: string): Buffer { /* ... */ }
}

class SubtitleParser {
  parse(file: string): Subtitle[] { /* ... */ }
}

class VideoRenderer {
  render(video: Buffer, audio: Buffer, subtitles: Subtitle[]): void { /* ... */ }
}

class Display {
  show(frame: Frame): void { /* ... */ }
}

// ❌ Facadeなし：使う側が全部知る必要がある
const videoDecoder = new VideoDecoder();
const audioDecoder = new AudioDecoder();
const subtitleParser = new SubtitleParser();
const renderer = new VideoRenderer();
const display = new Display();

const video = videoDecoder.decode('movie.mp4');
const audio = audioDecoder.decode('movie.mp4');
const subtitles = subtitleParser.parse('movie.srt');
renderer.render(video, audio, subtitles);
// ... 複雑すぎる！

// ⭕ Facade：シンプルなインターフェース
class VideoPlayerFacade {
  private videoDecoder = new VideoDecoder();
  private audioDecoder = new AudioDecoder();
  private subtitleParser = new SubtitleParser();
  private renderer = new VideoRenderer();
  private display = new Display();

  play(videoFile: string, subtitleFile?: string): void {
    const video = this.videoDecoder.decode(videoFile);
    const audio = this.audioDecoder.decode(videoFile);
    const subtitles = subtitleFile
      ? this.subtitleParser.parse(subtitleFile)
      : [];
    this.renderer.render(video, audio, subtitles);
  }

  pause(): void { /* ... */ }
  stop(): void { /* ... */ }
}

// 使う側：シンプル！
const player = new VideoPlayerFacade();
player.play('movie.mp4', 'movie.srt');

注意：薄すぎるFacade

⚠️ 単なるラッパーになっていないか？ 
// ❌ 薄すぎるFacade：価値がない
class UserFacade {
  createUser(data: UserData): User {
    return this.userService.createUser(data);  // ただの転送
  }
}

// Facadeは「複雑さを隠す」のが目的

Compositeとは？

部分と全体を同一視して扱うパターンです。
ツリー構造を表現するのに最適です。

🏠 たとえ話

ファイルシステムを考えてください。
「フォルダ」は「ファイル」と「フォルダ」を含む。
フォルダの中にフォルダがあり、その中にもファイルとフォルダ...
同じ操作（削除、コピー）がどちらにも使えるのがCompositeです。

使用場面

  • ファイルシステム
  • メニュー構造
  • 組織図
  • UIコンポーネントのツリー

実装例

// 共通インターフェース
interface FileSystemNode {
  name: string;
  getSize(): number;
  print(indent?: string): void;
}

// 葉（Leaf）：ファイル
class File implements FileSystemNode {
  constructor(public name: string, private size: number) {}

  getSize(): number {
    return this.size;
  }

  print(indent = ''): void {
    console.log(`${indent}📄 ${this.name} (${this.size}KB)`);
  }
}

// 複合体（Composite）：フォルダ
class Folder implements FileSystemNode {
  private children: FileSystemNode[] = [];

  constructor(public name: string) {}

  add(node: FileSystemNode): void {
    this.children.push(node);
  }

  remove(node: FileSystemNode): void {
    const index = this.children.indexOf(node);
    if (index !== -1) {
      this.children.splice(index, 1);
    }
  }

  // フォルダのサイズ = 中身の合計
  getSize(): number {
    return this.children.reduce((sum, child) => sum + child.getSize(), 0);
  }

  print(indent = ''): void {
    console.log(`${indent}📁 ${this.name}/`);
    for (const child of this.children) {
      child.print(indent + '  ');
    }
  }
}

// 使い方
const root = new Folder('root');
const docs = new Folder('documents');
const images = new Folder('images');

docs.add(new File('report.pdf', 500));
docs.add(new File('notes.txt', 10));

images.add(new File('photo1.jpg', 2000));
images.add(new File('photo2.jpg', 1500));

root.add(docs);
root.add(images);
root.add(new File('readme.txt', 5));

root.print();
// 📁 root/
//   📁 documents/
//     📄 report.pdf (500KB)
//     📄 notes.txt (10KB)
//   📁 images/
//     📄 photo1.jpg (2000KB)
//     📄 photo2.jpg (1500KB)
//   📄 readme.txt (5KB)

console.log(`Total size: ${root.getSize()}KB`);
// Total size: 4015KB

Compositeの特徴

  • 再帰的構造: CompositeがCompositeを含む
  • 統一的な扱い: LeafもCompositeも同じインターフェース
  • クライアントの単純化: 使う側は構造を意識しない
