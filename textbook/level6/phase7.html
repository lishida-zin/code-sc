1. DDDとは

🎯 このページのゴール

ドメイン駆動設計の目的と価値を説明できる

DDDを一言で

DDD（Domain-Driven Design / ドメイン駆動設計）とは、 ビジネスの問題領域（ドメイン）を中心にソフトウェアを設計する手法です。

💡 たとえ話

DDDは「通訳者」のような役割です。
ビジネスの専門家（お医者さん、銀行員など）が使う言葉と、 エンジニアが書くコードを同じ言葉でつなぐのがDDDの目的です。

「顧客」「注文」「在庫」といったビジネス用語が、 そのままコードのクラス名やメソッド名になります。

なぜDDDが必要？

複雑なビジネスロジックを扱うシステムで、以下の問題を解決します。

DDDなしの問題
  • ビジネス担当者とエンジニアの会話が噛み合わない
  • コードを読んでもビジネスルールがわからない
  • 変更のたびに予期せぬバグが発生
  • システムが巨大化して誰も全体を把握できない
DDDありの解決
  • 共通言語でコミュニケーションが円滑に
  • コードがビジネスルールを表現している
  • 変更の影響範囲が明確
  • 境界で区切られた理解しやすい構造

DDDの2つの側面

側面 内容 対象
戦略的設計 大きな構造の設計。境界、コンテキスト、統合 アーキテクト、PO
戦術的設計 コードレベルの設計。エンティティ、値オブジェクト、集約 開発者
⚠️ よくある誤解

DDDは「エンティティや値オブジェクトを使うこと」ではありません。
それは戦術的パターンの一部に過ぎません。
本質は「ドメインを深く理解し、それをコードに反映すること」です。

DDDが適している場面

適している 適していない
複雑なビジネスロジック 単純なCRUDアプリ
長期間メンテナンスするシステム 使い捨てのプロトタイプ
ドメインエキスパートと協業できる 技術的な問題のみ（ライブラリなど）

2. ユビキタス言語

🎯 このページのゴール

ユビキタス言語の重要性を理解し、実践できる

ユビキタス言語とは？

ユビキタス言語（Ubiquitous Language）とは、 開発チームとドメインエキスパートが共通で使う言葉です。

「Ubiquitous」は「どこにでもある」という意味。
会話でも、ドキュメントでも、コードでも、同じ言葉を使うことがポイントです。

💡 たとえ話

病院で「患者」と呼ぶ人を、システムでは「User」と呼んでいたらどうなるでしょう？
「この患者のUserデータを更新して」という会話になり、混乱します。

ユビキタス言語では、「患者（Patient）」という言葉を 会話でもコードでも統一して使います。

コードでの実践

技術用語とのずれ
// ビジネスでは「会員」「休会中」「仮登録」
class User {
  status: 'active' | 'inactive' | 'pending';

  // 「退会処理」なのに delete
  delete(): void { ... }
}

// 「購入」なのに create
orderService.createOrder(data);
ユビキタス言語を反映
// ビジネス用語をそのまま使う
class Member {
  membershipStatus: MembershipStatus;
  // 'active' | 'suspended' | 'provisional'

  // ビジネス用語「退会」
  withdraw(): void { ... }
}

// ビジネス用語「購入」
orderService.placeOrder(data);

ユビキタス言語を育てる

活動 内容
ドメインエキスパートとの対話 業務担当者から「本当の言葉」を聞き出す
用語集の作成 チームで共有する用語辞書を作る
コードへの反映 用語をクラス名、メソッド名に使う
継続的な更新 理解が深まったら言葉も進化させる
⚠️ レビュー観点

コード内の命名がビジネス用語と一致しているか？
技術的な名前（User, Data, Manager, Helper）ではなく、 ドメインの言葉（Member, Order, Inventory）を使っているか確認。

3. ドメインの分析

🎯 このページのゴール

コアドメイン、サポートドメイン、汎用ドメインの違いを説明できる

ドメインを分類する

DDDでは、ビジネス領域を3種類のドメインに分類します。
この分類によって、どこにリソースを集中すべきかが明確になります。

💡 たとえ話：ECサイトの場合

コアドメイン: レコメンドエンジン（競合との差別化）
サポートドメイン: 在庫管理（自社固有のルールあり）
汎用ドメイン: 決済処理（Stripeで十分）

3種類のドメイン

種類 説明 投資レベル 例
コアドメイン 競争優位の源泉、ビジネスの差別化要因 最大投資 独自のマッチングアルゴリズム
サポートドメイン コアを支える、自社固有のルールあり 適度な投資 社内の承認ワークフロー
汎用ドメイン どの企業でも同じ（認証、決済等） 外部サービス利用 認証（Auth0）、決済（Stripe）

なぜ分類が重要？

分類しない問題
  • すべてに同じ労力をかけてしまう
  • 汎用的な機能を自作して車輪の再発明
  • コアドメインが手薄になる
  • 外注すべきでないものを外注してしまう
分類する効果
  • コアドメインに優秀なエンジニアを配置
  • 汎用ドメインは外部サービスで効率化
  • サポートドメインは適度な品質でOK
  • リソース配分が最適化される

コアドメインを見つける質問

  • この機能がなくなると、ビジネスが成り立たない？
  • 競合と差別化できているポイントは？
  • この部分で負けると、事業に致命的？
  • 外部サービスで代替できない理由は？
⚠️ レビュー観点

コアドメインに投資が集中しているか？
汎用ドメイン（認証、決済など）を自作していないか、 逆にコアドメインを外部に依存していないか確認。

4. 境界づけられたコンテキスト

🎯 このページのゴール

境界づけられたコンテキストの概念を理解し、識別できる

境界づけられたコンテキストとは？

境界づけられたコンテキスト（Bounded Context）とは、 特定のモデルが意味を持つ範囲のことです。

同じ言葉でも、コンテキストによって意味が変わります。

💡 たとえ話

「アカウント」という言葉を考えてみましょう。
銀行では「口座」
SNSでは「ユーザープロフィール」
経理では「勘定科目」

同じ「Account」でも、コンテキストが違えば全く別のモデルです。 これを無理に1つにまとめると、複雑で理解しにくいシステムになります。

コンテキストごとに異なるモデル

1つの巨大モデル
// 全コンテキストで共有（神クラス）
class User {
  id: string;
  email: string;
  name: string;
  address: Address;           // 配送
  paymentMethods: Payment[];  // 請求
  supportTickets: Ticket[];   // サポート
  orders: Order[];            // 販売
  loyaltyPoints: number;      // マーケ
  // どんどん肥大化...
}
コンテキストごとのモデル
// 販売コンテキスト
class Customer {
  id: CustomerId;
  email: Email;
  loyaltyTier: LoyaltyTier;
}

// 配送コンテキスト
class Recipient {
  name: string;
  shippingAddress: Address;
}

// 請求コンテキスト
class BillingAccount {
  accountId: AccountId;
  paymentMethods: PaymentMethod[];
}

コンテキストを分ける基準

基準 説明
言葉の意味が変わる 同じ用語が異なる意味で使われる
チームが異なる 別チームが担当している領域
変更理由が異なる 異なるビジネス要因で変更される
ライフサイクルが異なる 独立してデプロイ・スケールしたい
⚠️ レビュー観点

コンテキストが適切なサイズか？
巨大すぎる（神クラス的）コンテキストや、 細かすぎる（1クラス1コンテキスト）分割になっていないか確認。

5. コンテキストマップ

🎯 このページのゴール

コンテキストマップを描き、コンテキスト間の関係を可視化できる

コンテキストマップとは？

コンテキストマップは、複数の境界づけられたコンテキストが どのように関係しているかを図示したものです。

💡 たとえ話

コンテキストマップは「国の地図」のようなものです。
各コンテキストは「国」、コンテキスト間の関係は「外交関係」です。
同盟国もあれば、支配-従属関係もあり、通訳が必要な国もあります。

マップの例

マップを描くメリット

  • 全体像の把握: システム全体の構造が一目でわかる
  • 依存関係の明確化: どこが上流でどこが下流か
  • 統合ポイントの識別: 問題が起きやすい箇所がわかる
  • チーム間の認識合わせ: 共通の理解を持てる
⚠️ レビュー観点

コンテキスト間の関係が定義されているか？
暗黙の依存関係がないか、統合パターンが明確か確認。

6. 統合パターン

🎯 このページのゴール

コンテキスト間の主要な統合パターンを説明できる

統合パターンとは？

コンテキスト間でどのようにモデルを共有・変換するかのパターンです。
チーム間の力関係や協力度合いによって、適切なパターンが変わります。

主要な統合パターン

パターン 説明 適用場面
共有カーネル 一部のモデルを複数チームで共有 密接に連携するチーム
顧客/供給者 上流（供給者）が下流（顧客）の要件を考慮 社内チーム間のAPI提供
適合者 下流が上流のモデルにそのまま従う 変更権限のない外部API
腐敗防止層 変換層を挟んで自コンテキストを守る レガシー統合、外部システム
公開ホストサービス 標準化されたAPIを多数に公開 プラットフォーム、外部向けAPI

パターンの選び方

自チームが変更権限を持っている？
  │
  ├─ Yes: 相手チームと協力できる？
  │        ├─ Yes: 共有カーネル or 顧客/供給者
  │        └─ No: 分離された道
  │
  └─ No: 相手のモデルに従うか？
          ├─ Yes: 適合者
          └─ No: 腐敗防止層
💡 たとえ話

共有カーネル: 夫婦で共有する銀行口座
顧客/供給者: 要望を聞いてくれる取引先
適合者: 政府のルールに従う
腐敗防止層: 通訳を介した外国との取引

⚠️ レビュー観点

統合パターンがチーム間の実態と合っているか？
変更権限がないのに共有カーネルを選んでいないか、 腐敗防止層が必要な箇所で直接依存していないか確認。

7. 腐敗防止層（ACL）

🎯 このページのゴール

腐敗防止層の役割を理解し、適切に実装できる

腐敗防止層（ACL）とは？

ACL（Anti-Corruption Layer）は、 外部システムやレガシーシステムのモデルが 自コンテキストに漏れ出すのを防ぐ変換層です。

💡 たとえ話

ACLは「通訳」のようなものです。
外国（レガシーシステム）の言葉を、自国（新システム）の言葉に翻訳します。
通訳がいないと、外国語が自国に混入して混乱します。

ACLが必要な場面

  • レガシーシステムとの統合
  • 外部APIの利用
  • 異なるチームが管理するシステムとの連携
  • 命名規則やデータ形式が異なるシステム

実装例

ACLなし（漏れ出す）
// レガシーの型が新システムに漏れ出す
interface LegacyCustomerData {
  CUST_ID: string;
  CUST_NM: string;
  ACTIVE_FLG: 'Y' | 'N';  // boolean じゃない
}

class CustomerService {
  // レガシー型がそのまま使われる
  async getCustomer(id: string)
    : Promise<LegacyCustomerData> {
    return await legacyApi.get(id);
  }
}
ACLあり（変換する）
// ACL: 変換層
class CustomerTranslator {
  toDomain(legacy: LegacyCustomerData)
    : Customer {
    return new Customer(
      CustomerId.create(legacy.CUST_ID),
      CustomerName.create(legacy.CUST_NM),
      legacy.ACTIVE_FLG === 'Y'
    );
  }
}

class CustomerService {
  // ドメインモデルを返す
  async getCustomer(id: CustomerId)
    : Promise<Customer> {
    const legacy = await this.legacyApi
      .get(id.value);
    return this.translator.toDomain(legacy);
  }
}

ACLの構成要素

要素 役割
Translator 外部モデル ⇔ ドメインモデルの変換
Adapter 外部システムへの通信を抽象化
Facade 複雑な外部APIを単純化したインターフェース
🚨 よくあるミス

ACLを設けても、レガシーの型をimportしてしまうと意味がありません。
ACLより内側（ドメイン層）では、外部の型を一切参照しないようにしましょう。

8. イベントストーミング

🎯 このページのゴール

イベントストーミングの進め方を理解する

イベントストーミングとは？

イベントストーミングは、ドメインエキスパートと開発者が 付箋を使ってドメインを発見するワークショップ手法です。

💡 たとえ話

イベントストーミングは「ブレインストーミング」のドメイン版です。
付箋を使って「何が起きるか」を書き出し、壁に貼っていきます。
参加者全員でビジネスの流れを可視化します。

付箋の色と意味

色 要素 例
オレンジ ドメインイベント 注文が確定された、支払いが完了した
青 コマンド 注文を確定する、支払いを処理する
黄色 アクター 顧客、管理者、システム
ピンク 外部システム 決済サービス、配送業者
紫 ポリシー 〜が起きたら〜する
緑 集約 注文、在庫、顧客

進め方

  1. ドメインイベントを書き出す: 「〜された」という過去形で
  2. 時系列に並べる: 左から右へ
  3. コマンドを追加: イベントを引き起こすアクション
  4. アクターを追加: 誰がコマンドを実行するか
  5. 集約を識別: コマンドを受け付ける責任を持つ
  6. 境界を引く: コンテキストの境界を発見
【イベントストーミングの流れ】

[顧客]──>[カートに追加]──>[商品がカートに追加された]
                                    │
                                    v
[顧客]──>[注文を確定]──────>[注文が確定された]
                                    │
                                    ├──>[在庫引当イベント]
                                    │
                                    └──>[決済処理イベント]
⚠️ ポイント

イベントストーミングは技術者だけでやらないのが重要。
ドメインエキスパート（業務担当者）と一緒に行うことで、 本当のビジネスフローを発見できます。

9. ドメインストーリーテリング

🎯 このページのゴール

ドメインストーリーテリングの手法を理解する

ドメインストーリーテリングとは？

ドメインストーリーテリングは、 絵と文章でビジネスの物語を描く手法です。
イベントストーミングよりもシンプルで、非技術者にも理解しやすいのが特徴です。

💡 たとえ話

ドメインストーリーテリングは「絵本」を作るようなものです。
「誰が」「何を」「どうする」を絵と文章で表現します。
子どもでも理解できるくらいシンプルに描きます。

基本要素

要素 記号 例
アクター 人のアイコン 顧客、店員、管理者
ワークオブジェクト 四角形 注文書、商品、請求書
アクティビティ 矢印 + 動詞 作成する、送る、確認する
番号 1, 2, 3... ストーリーの順序

ストーリーの例

【オンライン注文のストーリー】

1. [顧客] ──商品を選ぶ──> [商品カタログ]

2. [顧客] ──カートに入れる──> [ショッピングカート]

3. [顧客] ──注文を確定する──> [注文]

4. [システム] ──在庫を確認する──> [在庫]

5. [システム] ──決済を依頼する──> [決済サービス]

6. [倉庫スタッフ] ──商品を発送する──> [配送]

イベントストーミングとの違い

観点 イベントストーミング ドメインストーリーテリング
焦点 何が起きたか（イベント） 誰が何をするか（アクター）
形式 付箋を壁に貼る 絵と文章で描く
難易度 やや複雑 シンプル
適した場面 複雑なドメインの発見 初期の理解、共有

10. 戦略的設計のまとめ

🎯 このページのゴール

戦略的設計の全体像を理解し、マイクロサービスとの関係を説明できる

戦略的設計の全体像

【戦略的設計のフロー】

1. ドメインを理解する
   └─> イベントストーミング、ドメインストーリーテリング

2. ドメインを分類する
   └─> コア / サポート / 汎用

3. 境界を引く
   └─> 境界づけられたコンテキストを識別

4. 関係を定義する
   └─> コンテキストマップ、統合パターン

5. 言語を統一する
   └─> ユビキタス言語を確立

マイクロサービスとの関係

💡 重要なポイント

境界づけられたコンテキスト ≒ マイクロサービスの境界
DDDの戦略的設計は、マイクロサービスの分割指針として最適です。

DDDの概念 マイクロサービスでの対応
境界づけられたコンテキスト サービスの境界
コンテキストマップ サービス間の依存関係
腐敗防止層 API Gateway、BFF
ドメインイベント 非同期メッセージング

戦略的設計チェックリスト

⚠️ レビュー観点
  • ユビキタス言語がコードに反映されているか？
  • コアドメインに投資が集中しているか？
  • 境界づけられたコンテキストが識別されているか？
  • コンテキスト間の統合パターンが定義されているか？
  • 腐敗防止層でレガシー/外部を隔離しているか？

よくある失敗パターン

失敗 原因 対策
巨大なコンテキスト 分割の判断基準がない 言葉の意味が変わる箇所で分ける
技術的な分割 ビジネス視点の欠如 ビジネス機能で分ける
暗黙の依存 コンテキストマップがない 関係を可視化・定義する
外部モデルの漏洩 ACLがない 変換層を設ける
