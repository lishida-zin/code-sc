SOLID原則とは

SOLIDは、オブジェクト指向設計の5つの原則の頭文字です。

🏠 たとえ話：建築の法則

建築には「耐震基準」「採光基準」などの法則がある。
これを守らないと、住みにくい・危険な家ができる。

ソフトウェアにもSOLIDという「設計基準」がある。
これを守らないと、保守しにくい・壊れやすいコードができる。

5つの原則

頭文字 原則 意味
S Single Responsibility 1クラス1責務
O Open/Closed 拡張に開き、修正に閉じる
L Liskov Substitution 派生型は基底型と置換可能
I Interface Segregation インターフェースを小さく
D Dependency Inversion 抽象に依存する

なぜSOLIDが必要か

⚠️ SOLID違反のコードは...
  • 変更が難しい：1箇所を直すと他が壊れる
  • テストが難しい：依存が多くてモックできない
  • 理解が難しい：1つのクラスがやることが多すぎる
  • 再利用が難しい：特定の状況に依存している

📜 知っておきたい歴史

SOLIDの「S」は何の原則？

単一責任の原則（SRP）

📚 このページで学ぶこと
  • SRP（Single Responsibility Principle）とは
  • 「変更の理由」という考え方
  • 責務の見つけ方

SRPとは

「クラスを変更する理由は1つであるべき」

🏠 たとえ話：専門店

良い店：寿司屋は寿司だけ。ラーメン屋はラーメンだけ。
それぞれの専門に集中できる。

悪い店：寿司もラーメンもピザもカレーも出す店。
どれも中途半端になりがち。

「変更の理由」で考える

「このクラスを変更するのは、どんなときか？」を考えます。 

// ❌ 複数の変更理由がある
class UserService {
  createUser(data: UserData): Promise<User> {
    // 1. バリデーション → バリデーションルールが変わったら修正
    if (!data.email.includes('@')) throw new Error('Invalid email');

    // 2. 永続化 → DBスキーマが変わったら修正
    const user = await db.users.create(data);

    // 3. メール送信 → メールテンプレートが変わったら修正
    await sendEmail(user.email, 'Welcome!');

    // 4. ログ出力 → ログ形式が変わったら修正
    console.log(`User created: ${user.id}`);

    return user;
  }
}

このクラスは4つの理由で変更される可能性がある。
→ SRP違反

責務を分離する

SRP違反
class UserService {
  // バリデーション
  // 永続化
  // メール送信
  // ログ出力
  // 全部やる
}
SRP準拠
class UserValidator {
  validate(data: UserData): Result {}
}

class UserRepository {
  create(data: UserData): Promise<User> {}
}

class WelcomeEmailSender {
  send(user: User): Promise<void> {}
}

class UserService {
  // 各クラスを組み合わせるだけ
  constructor(
    private validator: UserValidator,
    private repository: UserRepository,
    private emailSender: WelcomeEmailSender,
    private logger: Logger
  ) {}
}

責務の見つけ方

✓ 責務を見つけるヒント
  • 「〜を担当」で説明できるか？（「ユーザーの永続化を担当」）
  • 「and」が入るなら分割すべき（「バリデーションと永続化を担当」→分割）
  • 異なるチームが変更するなら分割（UI担当、DB担当、セキュリティ担当...）
🔍 コードレビューの観点

SRP違反の兆候：

  • クラスが500行以上
  • メソッドが20個以上
  • クラス名に「Manager」「Handler」「Processor」
  • 複数のimportが必要（DB、メール、ログ、API...）

// Before: SRP違反
class OrderService {
  async createOrder(data: OrderData): Promise<Order> {
    // 1. バリデーション
    if (!data.items.length) throw new Error('Empty order');
    if (data.items.some(i => i.quantity <= 0)) throw new Error('Invalid quantity');

    // 2. 在庫チェック
    for (const item of data.items) {
      const stock = await db.inventory.findOne({ productId: item.productId });
      if (stock.quantity < item.quantity) throw new Error('Out of stock');
    }

    // 3. 価格計算
    let total = 0;
    for (const item of data.items) {
      const product = await db.products.findOne({ id: item.productId });
      total += product.price * item.quantity;
    }
    const tax = total * 0.1;
    const grandTotal = total + tax;

    // 4. 永続化
    const order = await db.orders.create({
      ...data,
      total: grandTotal,
      status: 'pending'
    });

    // 5. メール送信
    await sendEmail(data.customerEmail, 'Order confirmed', `Total: ${grandTotal}`);

    // 6. 分析イベント送信
    await analytics.track('order_created', { orderId: order.id, total: grandTotal });

    return order;
  }
}
// After: SRP準拠

// 各責務を独立したクラスに
class OrderValidator {
  validate(data: OrderData): void {
    if (!data.items.length) throw new Error('Empty order');
    if (data.items.some(i => i.quantity <= 0)) throw new Error('Invalid quantity');
  }
}

class InventoryChecker {
  async checkAvailability(items: OrderItem[]): Promise<void> {
    for (const item of items) {
      const stock = await this.inventoryRepo.findByProductId(item.productId);
      if (stock.quantity < item.quantity) throw new Error('Out of stock');
    }
  }
}

class PriceCalculator {
  async calculate(items: OrderItem[]): Promise<PriceBreakdown> {
    let subtotal = 0;
    for (const item of items) {
      const product = await this.productRepo.findById(item.productId);
      subtotal += product.price * item.quantity;
    }
    const tax = subtotal * 0.1;
    return { subtotal, tax, total: subtotal + tax };
  }
}

class OrderRepository {
  async create(data: OrderData, price: PriceBreakdown): Promise<Order> {
    return await db.orders.create({ ...data, ...price, status: 'pending' });
  }
}

class OrderConfirmationEmailSender {
  async send(email: string, order: Order): Promise<void> {
    await sendEmail(email, 'Order confirmed', `Total: ${order.total}`);
  }
}

// オーケストレーション
class OrderService {
  constructor(
    private validator: OrderValidator,
    private inventoryChecker: InventoryChecker,
    private priceCalculator: PriceCalculator,
    private orderRepo: OrderRepository,
    private emailSender: OrderConfirmationEmailSender,
    private analytics: AnalyticsService
  ) {}

  async createOrder(data: OrderData): Promise<Order> {
    this.validator.validate(data);
    await this.inventoryChecker.checkAvailability(data.items);
    const price = await this.priceCalculator.calculate(data.items);
    const order = await this.orderRepo.create(data, price);
    await this.emailSender.send(data.customerEmail, order);
    await this.analytics.track('order_created', { orderId: order.id });
    return order;
  }
}

開放閉鎖の原則（OCP）

📚 このページで学ぶこと
  • OCP（Open/Closed Principle）とは
  • 「拡張に開き、修正に閉じる」の意味
  • なぜ既存コードの修正を避けるべきか

OCPとは

「拡張に対して開いていて、修正に対して閉じている」

🏠 たとえ話：コンセントと家電

コンセントの規格は変わらない（修正に閉じている）。
でも新しい家電をいくらでも繋げる（拡張に開いている）。

新しい家電が出るたびにコンセントの形を変えていたら大変！
ソフトウェアも同じ。既存コードを変えずに機能追加できる設計が理想。

OCP違反の例

// ❌ 新しい支払い方法を追加するたびに修正が必要
class PaymentProcessor {
  process(payment: Payment): void {
    if (payment.type === 'credit') {
      // クレジットカード処理
      this.processCreditCard(payment);
    } else if (payment.type === 'paypal') {
      // PayPal処理
      this.processPayPal(payment);
    } else if (payment.type === 'crypto') {
      // 暗号通貨処理 ← 追加のたびにここを修正
      this.processCrypto(payment);
    }
    // 新しい支払い方法が増えるたびに
    // このファイルを修正 + テストやり直し
  }
}

「Apple Pay対応して」と言われたら、既存コードを修正する必要がある。
修正 = バグのリスク、テストのやり直し。

OCP準拠の設計

修正が必要
// 新機能 = 既存コード修正
class PaymentProcessor {
  process(payment: Payment): void {
    if (payment.type === 'credit') { ... }
    else if (payment.type === 'paypal') { ... }
    // 新しい支払い方法を追加するには
    // ここにelse ifを追加
  }
}
拡張で対応
// 新機能 = 新クラス追加
interface PaymentStrategy {
  process(amount: number): Promise<Result>;
}

class CreditCardPayment implements PaymentStrategy {
  async process(amount: number): Promise<Result> { ... }
}

class PayPalPayment implements PaymentStrategy {
  async process(amount: number): Promise<Result> { ... }
}

// 新しい支払い方法は新クラスを追加するだけ
class CryptoPayment implements PaymentStrategy {
  async process(amount: number): Promise<Result> { ... }
}

// 既存コードは変更不要
class PaymentProcessor {
  constructor(private strategy: PaymentStrategy) {}

  async process(amount: number): Promise<Result> {
    return this.strategy.process(amount);
  }
}

なぜ修正を避けるべきか

⚠️ 既存コード修正のリスク
  • バグの混入：動いていたコードを壊す可能性
  • テストの再実行：変更箇所だけでなく全体のテストが必要
  • レビューの負担：既存ロジックの理解が必要
  • デプロイのリスク：変更が広範囲に影響

Strategyパターン

アルゴリズムをオブジェクトとして切り出すパターンです。 

// 割引計算のStrategy
interface DiscountStrategy {
  calculate(price: number): number;
}

class NoDiscount implements DiscountStrategy {
  calculate(price: number): number {
    return price;
  }
}

class PercentageDiscount implements DiscountStrategy {
  constructor(private percent: number) {}

  calculate(price: number): number {
    return price * (1 - this.percent / 100);
  }
}

class FixedDiscount implements DiscountStrategy {
  constructor(private amount: number) {}

  calculate(price: number): number {
    return Math.max(0, price - this.amount);
  }
}

// 新しい割引タイプは新クラスを追加するだけ
class BuyOneGetOneFree implements DiscountStrategy {
  calculate(price: number): number {
    return price / 2;
  }
}

// 利用側は変更不要
class PriceCalculator {
  constructor(private discount: DiscountStrategy) {}

  calculate(basePrice: number): number {
    return this.discount.calculate(basePrice);
  }
}

Template Methodパターン

処理の骨格を定義し、詳細をサブクラスに任せるパターンです。 

// 処理の骨格を定義
abstract class DataExporter {
  // テンプレートメソッド（骨格）
  export(data: Data[]): string {
    const header = this.createHeader();
    const body = this.formatData(data);
    const footer = this.createFooter();
    return header + body + footer;
  }

  // サブクラスで実装
  protected abstract createHeader(): string;
  protected abstract formatData(data: Data[]): string;
  protected abstract createFooter(): string;
}

class CSVExporter extends DataExporter {
  protected createHeader(): string {
    return "id,name,value\n";
  }

  protected formatData(data: Data[]): string {
    return data.map(d => `${d.id},${d.name},${d.value}`).join("\n");
  }

  protected createFooter(): string {
    return "";
  }
}

class XMLExporter extends DataExporter {
  protected createHeader(): string {
    return "<?xml version=\"1.0\"?><data>";
  }

  protected formatData(data: Data[]): string {
    return data.map(d => `<item id="${d.id}">...</item>`).join("");
  }

  protected createFooter(): string {
    return "</data>";
  }
}

// 新しいフォーマットは新クラスを追加するだけ
class JSONExporter extends DataExporter {
  // ...
}

リスコフの置換原則（LSP）

📚 このページで学ぶこと
  • LSP（Liskov Substitution Principle）とは
  • 「置換可能」の意味
  • 継承の正しい使い方

LSPとは

「派生型（子クラス）は基底型（親クラス）と置換可能でなければならない」

🏠 たとえ話：代打

野球で「代打」が出ても、打席に立ってバットを振ることは同じ。
代打が突然サッカーを始めたらルール違反。

子クラスも同じ。親クラスの「契約」を守る必要がある。
親クラスを使っていた場所に子クラスを入れても、正しく動くべき。

LSP違反の例：正方形と長方形

// ❌ 有名なLSP違反の例
class Rectangle {
  constructor(protected width: number, protected height: number) {}

  setWidth(width: number): void { this.width = width; }
  setHeight(height: number): void { this.height = height; }
  getArea(): number { return this.width * this.height; }
}

class Square extends Rectangle {
  // 正方形は幅と高さが同じ
  setWidth(width: number): void {
    this.width = width;
    this.height = width;  // 予期しない副作用！
  }
  setHeight(height: number): void {
    this.width = height;
    this.height = height;  // 予期しない副作用！
  }
}

// Rectangleを使うコード
function testRectangle(rect: Rectangle): void {
  rect.setWidth(5);
  rect.setHeight(4);
  console.assert(rect.getArea() === 20);  // 期待: 5 * 4 = 20
}

const rect = new Rectangle(0, 0);
testRectangle(rect);  // OK: 20

const square = new Square(0, 0);
testRectangle(square);  // NG: 16（4 * 4）
// 「長方形」のつもりで使ったら壊れた！

LSP準拠の設計

LSP違反
// 「正方形は長方形である」は
// 数学的には正しいが
// プログラム的には問題

class Square extends Rectangle {
  // setWidth/setHeightの契約を破る
}
LSP準拠
// 継承関係を見直す
interface Shape {
  getArea(): number;
}

class Rectangle implements Shape {
  constructor(private width: number, private height: number) {}
  getArea(): number { return this.width * this.height; }
}

class Square implements Shape {
  constructor(private side: number) {}
  getArea(): number { return this.side * this.side; }
}

// 共通インターフェースで扱える
// でも「契約」は破らない

契約とは

📝 契約の要素
  • 事前条件：メソッド呼び出し前に満たすべき条件
  • 事後条件：メソッド呼び出し後に保証される条件
  • 不変条件：常に満たされるべき条件

子クラスは：
・事前条件を緩めるのはOK（より多くの入力を受け付ける）
・事後条件を厳しくするのはOK（より多くを保証する）
・逆はNG

🔍 コードレビューの観点

LSP違反の兆候：

  • オーバーライドで例外をthrowする
  • オーバーライドで何もしない（空実装）
  • instanceofで型をチェックしてから処理
// ❌ 危険なパターン
class Bird {
  fly(): void { ... }
}

class Penguin extends Bird {
  fly(): void {
    throw new Error("Penguins can't fly");  // 契約違反
  }
}

インターフェース分離の原則（ISP）

📚 このページで学ぶこと
  • ISP（Interface Segregation Principle）とは
  • 「太った」インターフェースの問題
  • 適切な分割の仕方

ISPとは

「クライアントは使わないメソッドに依存すべきでない」

🏠 たとえ話：多機能リモコン

テレビ、エアコン、照明、カーテン...全部操作できる万能リモコン。
でもテレビだけ見たい人にはボタンが多すぎて使いづらい。

インターフェースも同じ。
使わない機能まで実装を強制されるのは問題。

ISP違反の例

// ❌ 肥大なインターフェース
interface Worker {
  work(): void;
  eat(): void;
  sleep(): void;
  code(): void;
  manage(): void;
}

// 人間は全部できる
class Human implements Worker {
  work(): void { console.log("働く"); }
  eat(): void { console.log("食べる"); }
  sleep(): void { console.log("寝る"); }
  code(): void { console.log("コードを書く"); }
  manage(): void { console.log("管理する"); }
}

// ロボットは食べたり寝たりできない
class Robot implements Worker {
  work(): void { console.log("働く"); }
  eat(): void { throw new Error("Robots can't eat"); }  // 無意味
  sleep(): void { throw new Error("Robots can't sleep"); }  // 無意味
  code(): void { console.log("コードを書く"); }
  manage(): void { throw new Error("Not applicable"); }  // 無意味
}

ロボットは使えないメソッドの実装を強制されている。
→ ISP違反

ISP準拠の設計

太いインターフェース
interface Worker {
  work(): void;
  eat(): void;
  sleep(): void;
  code(): void;
  manage(): void;
}

// 全部実装が必要
分離されたインターフェース
interface Workable {
  work(): void;
}

interface Eatable {
  eat(): void;
}

interface Sleepable {
  sleep(): void;
}

interface Codeable {
  code(): void;
}

// 必要なものだけ実装
class Human implements Workable, Eatable, Sleepable, Codeable {
  work(): void { ... }
  eat(): void { ... }
  sleep(): void { ... }
  code(): void { ... }
}

class Robot implements Workable, Codeable {
  work(): void { ... }
  code(): void { ... }
  // eat, sleepは不要
}

✓ インターフェース分割のヒント
  • 役割ごとに分ける（Reader, Writer, Validator...）
  • クライアントの視点で考える（何を使いたいか？）
  • 「使わないメソッドがある」と感じたら分割を検討

  • インターフェースにメソッドが10個以上
  • 実装クラスでthrow new Error("Not implemented")

依存性逆転の原則（DIP）

📚 このページで学ぶこと
  • DIP（Dependency Inversion Principle）とは
  • 「抽象に依存する」の意味
  • なぜ具象への依存が問題か

DIPとは

「上位モジュールは下位モジュールに依存すべきでない。どちらも抽象に依存すべき」

🏠 たとえ話：電源コンセント

掃除機はコンセントの規格（抽象）に依存している。
「東京電力の電気」とか「関西電力の電気」（具象）には依存していない。

だからどこでも使える。
電力会社を変えても、掃除機を買い替える必要はない。

DIP違反の例

// ❌ 具象クラスに直接依存
class OrderService {
  // 具体的なクラスをnewしている
  private emailSender = new GmailSender();
  private repository = new MySQLOrderRepository();

  async createOrder(data: OrderData): Promise<Order> {
    const order = await this.repository.save(data);
    await this.emailSender.send(order.userEmail, 'Order confirmed');
    return order;
  }
}

// 問題点：
// 1. GmailをSendGridに変えたい → OrderServiceを修正
// 2. MySQLをPostgreSQLに変えたい → OrderServiceを修正
// 3. テストでモックを使いたい → できない！

DIP準拠の設計

具象に依存
class OrderService {
  // 具体的なクラスをnew
  private email = new GmailSender();
  private repo = new MySQLRepo();
}

// テスト困難
// 変更が波及
抽象に依存
// インターフェース（抽象）を定義
interface EmailSender {
  send(to: string, msg: string): Promise<void>;
}

interface OrderRepository {
  save(data: OrderData): Promise<Order>;
}

class OrderService {
  // インターフェースに依存
  constructor(
    private emailSender: EmailSender,
    private repository: OrderRepository
  ) {}

  async createOrder(data: OrderData): Promise<Order> {
    const order = await this.repository.save(data);
    await this.emailSender.send(order.userEmail, 'Order confirmed');
    return order;
  }
}

// 実装は外から注入
const service = new OrderService(
  new GmailSender(),  // または SendGridSender
  new MySQLOrderRepository()  // または PostgreSQLRepo
);

依存関係の「逆転」

// 従来の依存方向
// OrderService → GmailSender（上位が下位に依存）

// DIP適用後の依存方向
// OrderService → EmailSender（インターフェース）← GmailSender
// 上位モジュール → 抽象 ← 下位モジュール

// 「依存の方向」が逆転している！
// 下位モジュール（GmailSender）が抽象（EmailSender）に依存するようになった

  • クラス内でnew 具象クラス()している
  • importで具象クラスを直接読み込んでいる
  • テストでモックできない依存がある

依存性注入（DI）

依存性注入 = 依存するオブジェクトを外から渡すこと

自分でnewする
class UserService {
  // 自分で依存を作る
  private repo = new UserRepository();
  private logger = new ConsoleLogger();
}
外から注入
class UserService {
  // 外から渡してもらう
  constructor(
    private repo: UserRepository,
    private logger: Logger
  ) {}
}

コンストラクタ注入

最も一般的な注入方法です。 

// インターフェース定義
interface Logger {
  log(message: string): void;
}

interface UserRepository {
  findById(id: string): Promise<User | null>;
  save(user: User): Promise<void>;
}

// 実装クラス
class ConsoleLogger implements Logger {
  log(message: string): void {
    console.log(`[LOG] ${message}`);
  }
}

class PostgresUserRepository implements UserRepository {
  async findById(id: string): Promise<User | null> { ... }
  async save(user: User): Promise<void> { ... }
}

// コンストラクタで注入
class UserService {
  constructor(
    private repository: UserRepository,
    private logger: Logger
  ) {}

  async getUser(id: string): Promise<User> {
    this.logger.log(`Getting user: ${id}`);
    const user = await this.repository.findById(id);
    if (!user) throw new Error('User not found');
    return user;
  }
}

// 組み立て（本番）
const userService = new UserService(
  new PostgresUserRepository(),
  new ConsoleLogger()
);

// 組み立て（テスト）
const mockRepo: UserRepository = {
  findById: jest.fn().mockResolvedValue({ id: '1', name: 'Test' }),
  save: jest.fn()
};
const mockLogger: Logger = { log: jest.fn() };
const testService = new UserService(mockRepo, mockLogger);

IoC（制御の逆転）

📝 IoCとは

制御の逆転（Inversion of Control） = 制御フローを外部に委ねること

  • 従来：UserServiceが自分でUserRepositoryをnewする（制御している）
  • IoC：外部（フレームワーク/コンテナ）がUserRepositoryを渡す（制御を委ねる）

DIはIoCを実現する手段の1つです。

DIコンテナ

// 実務ではDIコンテナを使うことが多い
// 例: tsyringe, inversify, NestJS

// NestJSの例
@Injectable()
class UserService {
  constructor(
    @Inject('UserRepository')
    private repository: UserRepository,
    private logger: Logger
  ) {}
}

// モジュールで登録
@Module({
  providers: [
    UserService,
    { provide: 'UserRepository', useClass: PostgresUserRepository },
    Logger
  ]
})
class UserModule {}

// フレームワークが自動で依存を解決して注入してくれる

SOLID原則の関数型での解釈

SOLID原則はOOPの文脈で生まれましたが、
関数型プログラミングにも適用できます。

原則 OOPでの意味 関数型での解釈
S 1クラス1責務 1関数1責務、純粋関数
O 拡張に開き修正に閉じる 高階関数、関数合成
L 派生型は基底型と置換可能 型の置換性、ジェネリクス
I インターフェースを小さく 小さな関数シグネチャ
D 抽象に依存 関数を引数で受け取る

SRP：純粋関数

複数の責務
// ❌ 1つの関数で複数のことをやる
function processUser(user: User): void {
  // バリデーション
  if (!user.email) throw new Error('Invalid');

  // 変換
  user.name = user.name.toUpperCase();

  // 保存
  database.save(user);

  // 通知
  sendEmail(user.email, 'Welcome');
}
単一責務の純粋関数
// ⭕ 各関数が1つのことだけをする
const validate = (user: User): boolean =>
  !!user.email;

const normalizeUser = (user: User): User =>
  ({ ...user, name: user.name.toUpperCase() });

// 組み合わせて使う
const processUser = async (user: User): Promise<void> => {
  if (!validate(user)) throw new Error('Invalid');
  const normalized = normalizeUser(user);
  await saveUser(normalized);
  await sendWelcomeEmail(normalized.email);
};

OCP：高階関数

// 高階関数でOCPを実現
type Middleware<T> = (data: T) => T;

// 基本の処理（修正に閉じている）
const process = <T>(data: T, middlewares: Middleware<T>[]): T =>
  middlewares.reduce((acc, fn) => fn(acc), data);

// 機能追加は新しい関数を追加するだけ（拡張に開いている）
const addTimestamp: Middleware<Request> = (req) =>
  ({ ...req, timestamp: Date.now() });

const addUserId: Middleware<Request> = (req) =>
  ({ ...req, userId: getCurrentUserId() });

// 組み合わせ
const result = process(request, [addTimestamp, addUserId]);

DIP：関数を引数で受け取る

// 具象に依存しない関数
type Logger = (message: string) => void;
type Repository<T> = {
  save: (item: T) => Promise<void>;
  findById: (id: string) => Promise<T | null>;
};

// 依存を引数で受け取る（関数版DI）
const createUserService = (
  repo: Repository<User>,
  logger: Logger
) => ({
  getUser: async (id: string): Promise<User> => {
    logger(`Getting user: ${id}`);
    const user = await repo.findById(id);
    if (!user) throw new Error('Not found');
    return user;
  },

  saveUser: async (user: User): Promise<void> => {
    logger(`Saving user: ${user.id}`);
    await repo.save(user);
  }
});

// 本番
const userService = createUserService(
  postgresRepo,
  console.log
);

// テスト
const testService = createUserService(
  mockRepo,
  () => {}  // ログ無効化
);

  • SRP: このクラス/関数は1つの理由でのみ変更されるか？
  • OCP: 新機能追加で既存コードを修正していないか？
  • LSP: サブクラスは親クラスの契約を守っているか？
  • ISP: 使わないメソッドの実装を強制していないか？
