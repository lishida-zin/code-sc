1. エンティティ

🎯 このページのゴール

エンティティの特徴と設計方法を理解する

エンティティとは？

エンティティ（Entity）とは、 一意のIDによって識別されるドメインオブジェクトです。
属性が変わっても、IDが同じなら同一のオブジェクトとみなします。

💡 たとえ話

人間はエンティティです。
名前が変わっても、住所が変わっても、髪型が変わっても、 「マイナンバー」が同じなら同一人物です。

逆に、全く同じ名前・同じ住所の人がいても、 マイナンバーが違えば別人です。

エンティティの特徴

特徴 説明
同一性 IDで識別される（属性ではない）
ライフサイクル 作成され、変更され、削除される
可変性 状態が時間とともに変化する
連続性 変更後も同一のオブジェクトとして追跡

実装例

IDなしのエンティティ
// IDがない or 後付け
class User {
  name: string;
  email: string;

  // IDをどうやって管理する？
  // 同一性の判定ができない
}
正しいエンティティ
class User {
  // IDは必須かつ不変
  constructor(
    public readonly id: UserId,
    private name: UserName,
    private email: Email
  ) {}

  // 属性は変更可能
  changeName(newName: UserName): void {
    this.name = newName;
  }

  changeEmail(newEmail: Email): void {
    this.email = newEmail;
  }

  // 同一性の判定
  equals(other: User): boolean {
    return this.id.equals(other.id);
  }
}

エンティティの設計原則

  • IDは不変: 一度決まったIDは変更しない
  • IDはコンストラクタで受け取る: 後から設定しない
  • 等価性はIDで判定: equalsメソッドを実装
  • ビジネスルールを内包: setterではなくビジネスメソッド
⚠️ レビュー観点

エンティティにIDが適切に設定されているか？
auto-increment のDB IDをそのまま使っていないか、 ビジネス上の同一性と技術的な同一性を混同していないか確認。

2. 値オブジェクト

🎯 このページのゴール

値オブジェクトの特徴と設計方法を理解する

値オブジェクトとは？

値オブジェクト（Value Object）とは、 属性の組み合わせで識別される不変のドメインオブジェクトです。
IDを持たず、属性がすべて同じなら等価とみなします。

💡 たとえ話

お金は値オブジェクトです。
100円玉Aと100円玉Bは、見た目は違っても「100円」という価値は同じ。
交換しても問題ありません。

逆に、人間（エンティティ）は交換できません。
同じ名前の人でも、別人です。

エンティティ vs 値オブジェクト

観点 エンティティ 値オブジェクト
同一性 IDで識別 属性で識別
可変性 変更可能 不変
等価性 ID一致で等価 全属性一致で等価
例 User, Order, Product Email, Money, Address

実装例

プリミティブ型の乱用
class User {
  constructor(
    public id: string,      // 何でも入る
    public email: string,   // バリデーションなし
    public age: number      // マイナスも入る
  ) {}
}

// 不正なデータが作れてしまう
const user = new User(
  '',
  'invalid-email',
  -5
);
値オブジェクトで型安全
class Email {
  private constructor(
    public readonly value: string
  ) {}

  static create(value: string): Email {
    const regex = /^[^\s@]+@[^\s@]+\.[^\s@]+$/;
    if (!regex.test(value)) {
      throw new DomainError('Invalid email');
    }
    return new Email(value.toLowerCase());
  }

  equals(other: Email): boolean {
    return this.value === other.value;
  }
}

class Age {
  private constructor(
    public readonly value: number
  ) {}

  static create(value: number): Age {
    if (value < 0 || value > 150) {
      throw new DomainError('Invalid age');
    }
    return new Age(value);
  }
}

// 不正なデータは作れない
// Email.create('invalid'); // エラー
// Age.create(-5);          // エラー

値オブジェクトの設計原則

  • 不変（Immutable）: 作成後は変更しない
  • 自己検証: コンストラクタでバリデーション
  • 属性で等価判定: equalsメソッドを実装
  • 副作用なし: 変更は新しいインスタンスを返す
class Money {
  private constructor(
    public readonly amount: number,
    public readonly currency: string
  ) {}

  static create(amount: number, currency: string): Money {
    if (amount < 0) throw new DomainError('Amount cannot be negative');
    return new Money(amount, currency);
  }

  // 変更ではなく、新しいインスタンスを返す
  add(other: Money): Money {
    if (this.currency !== other.currency) {
      throw new DomainError('Currency mismatch');
    }
    return Money.create(this.amount + other.amount, this.currency);
  }
}
⚠️ レビュー観点

プリミティブ型を乱用していないか？
string, number をそのまま使わず、Email, Money, UserId のような 値オブジェクトでラップしているか確認。

3. 集約

🎯 このページのゴール

集約の概念と設計ルールを理解する

集約とは？

集約（Aggregate）とは、 一貫性を保つ必要があるオブジェクトの集まりです。
1つのトランザクションで扱う境界を定義します。

💡 たとえ話

「注文」は集約です。
注文には「注文明細」が含まれますが、注文明細だけを 独立して変更することはありません。
常に「注文」を通じて「注文明細」を操作します。

注文全体で整合性を保つ必要があるからです。
（合計金額と明細の合計が一致しているなど）

集約の構成

集約の設計ルール

ルール 説明
小さく保つ 1つのトランザクションで完結するサイズ
IDで参照 他の集約はIDで参照、直接参照しない
結果整合性 集約間は非同期で整合性を保つ
外部からのアクセス 集約ルートを通じてのみ

巨大な集約の問題

巨大な集約
class Order {
  constructor(
    public id: OrderId,
    // 顧客全体を含む（巨大）
    public customer: Customer,
    public items: OrderItem[],
    // 支払い履歴全部
    public payments: Payment[],
    // 配送履歴全部
    public shipments: Shipment[],
    // レビュー全部
    public reviews: Review[]
  ) {}
}

// 1つの注文を取得するだけで
// 大量のデータを読み込む
適切なサイズの集約
class Order {
  constructor(
    public readonly id: OrderId,
    // IDで参照
    public readonly customerId: CustomerId,
    private items: OrderItem[],
    private status: OrderStatus
  ) {}
}

// Payment は別の集約
class Payment {
  constructor(
    public readonly id: PaymentId,
    // IDで参照
    public readonly orderId: OrderId,
    private amount: Money,
    private status: PaymentStatus
  ) {}
}
⚠️ レビュー観点

集約が適切なサイズか？
1つの集約に関連オブジェクトをすべて含めていないか、 他の集約を直接参照（オブジェクト参照）していないか確認。

4. 集約ルート

🎯 このページのゴール

集約ルートの役割と実装方法を理解する

集約ルートとは？

集約ルート（Aggregate Root）とは、 集約への唯一の入口となるエンティティです。
外部からは集約ルートを通じてのみ、内部を操作します。

💡 たとえ話

会社で言えば、集約ルートは「受付窓口」です。
外部の人は受付を通じて社内の人と連絡を取ります。
直接、社員の席に行って話しかけることはしません。

受付が来客の対応を一元管理することで、セキュリティが保たれます。

集約ルートの責務

  • 一貫性の維持: 集約内の整合性ルールを守る
  • アクセス制御: 内部エンティティへの直接アクセスを防ぐ
  • ビジネスルール: ドメインロジックを内包する
  • トランザクション境界: 永続化の単位となる

実装例

内部エンティティを直接操作
class OrderService {
  async updateItemQuantity(
    orderId: string,
    itemId: string,
    quantity: number
  ): Promise<void> {
    const order = await this.orderRepo
      .findById(orderId);

    // 内部のOrderItemを直接変更！
    const item = order.items
      .find(i => i.id === itemId);
    item.quantity = quantity;  // カプセル化違反

    await this.orderRepo.save(order);
  }
}
集約ルートを通じて操作
class Order {
  private items: OrderItem[];

  // 集約ルートがメソッドを提供
  updateItemQuantity(
    itemId: OrderItemId,
    quantity: Quantity
  ): void {
    const item = this.items
      .find(i => i.id.equals(itemId));

    if (!item) {
      throw new DomainError('Item not found');
    }

    // ビジネスルールをチェック
    if (quantity.value > 100) {
      throw new DomainError('Max 100 items');
    }

    item.updateQuantity(quantity);
    this.recalculateTotal();
  }
}

class OrderService {
  async updateItemQuantity(...): Promise<void> {
    const order = await this.orderRepo
      .findById(orderId);

    // 集約ルートを通じて操作
    order.updateItemQuantity(itemId, quantity);

    await this.orderRepo.save(order);
  }
}

集約ルートの設計原則

原則 説明
内部を公開しない 内部エンティティのゲッターは最小限に
ビジネスメソッドを提供 setterではなく、意味のある操作
整合性を保証 不変条件を常にチェック
リポジトリの単位 集約ルート単位で保存/取得
⚠️ レビュー観点

集約ルートを通じて操作しているか？
内部エンティティを直接取得して変更していないか、 order.items[0].quantity = 10 のような操作がないか確認。

5. リポジトリ

🎯 このページのゴール

リポジトリの役割と設計方法を理解する

リポジトリとは？

リポジトリ（Repository）とは、 集約の永続化と取得を抽象化するパターンです。
ドメイン層はデータベースの詳細を知る必要がありません。

💡 たとえ話

リポジトリは「図書館の司書」のようなものです。
「この本が欲しい」と言えば、書庫から取ってきてくれます。
どの棚のどの位置にあるかは、利用者は知る必要がありません。

リポジトリの設計

CRUDの羅列
interface OrderRepository {
  findById(id: string): Promise<Order | null>;
  findAll(): Promise<Order[]>;
  findByCustomerId(customerId: string): Promise<Order[]>;
  findByStatus(status: string): Promise<Order[]>;
  findByDateRange(start: Date, end: Date): Promise<Order[]>;
  save(order: Order): Promise<void>;
  update(order: Order): Promise<void>;
  delete(id: string): Promise<void>;
}

// 汎用的すぎて、ドメインの意図が見えない
集約の保存と取得に集中
interface OrderRepository {
  // 基本操作
  findById(id: OrderId): Promise<Order | null>;
  save(order: Order): Promise<void>;

  // ビジネス要件に基づくクエリ
  findPendingOrdersForCustomer(
    customerId: CustomerId
  ): Promise<Order[]>;

  findOrdersToShipToday(): Promise<Order[]>;
}

// 複雑な検索はCQRSのQuery側で
interface OrderQueryService {
  searchOrders(criteria: OrderSearchCriteria)
    : Promise<OrderSummary[]>;
}

リポジトリの原則

原則 説明
集約単位 集約ルートごとに1つのリポジトリ
インターフェース ドメイン層はインターフェースのみ知る
コレクションの抽象化 メモリ上のコレクションのように見せる
ビジネス用語 メソッド名はビジネス要件を反映

実装例

// ドメイン層: インターフェース
interface OrderRepository {
  findById(id: OrderId): Promise<Order | null>;
  save(order: Order): Promise<void>;
}

// インフラ層: 実装
class PrismaOrderRepository implements OrderRepository {
  constructor(private prisma: PrismaClient) {}

  async findById(id: OrderId): Promise<Order | null> {
    const data = await this.prisma.order.findUnique({
      where: { id: id.value },
      include: { items: true }
    });

    if (!data) return null;

    // ORMのデータをドメインオブジェクトに変換
    return this.toDomain(data);
  }

  async save(order: Order): Promise<void> {
    // ドメインオブジェクトをORMのデータに変換
    const data = this.toRecord(order);
    await this.prisma.order.upsert({
      where: { id: order.id.value },
      create: data,
      update: data
    });
  }

  private toDomain(data: PrismaOrder): Order { ... }
  private toRecord(order: Order): PrismaOrderData { ... }
}

6. ドメインサービス

🎯 このページのゴール

ドメインサービスの役割と使いどころを理解する

ドメインサービスとは？

ドメインサービス（Domain Service）とは、 特定のエンティティに属さないドメインロジックを表現するものです。
複数の集約にまたがる操作や、概念として独立した操作を担当します。

💡 たとえ話

「送金」を考えてみましょう。
AさんからBさんへ送金する場合、これはAさんのメソッド？Bさんのメソッド？
どちらにも属さない「送金サービス」が必要です。

ドメインサービスが必要な場面

  • 複数の集約にまたがる操作: 送金、在庫引当
  • 外部システムとの連携ロジック: 価格計算API
  • ステートレスな計算: 税金計算、割引計算
  • ドメインルールの検証: 重複チェック

実装例

無理にエンティティに入れる
class Account {
  // 送金は自分の責務？
  transferTo(target: Account, amount: Money): void {
    this.balance = this.balance.subtract(amount);
    target.balance = target.balance.add(amount);
    // 2つの集約を同時に変更...
    // トランザクション境界が曖昧
  }
}
ドメインサービスで分離
// ドメインサービス
class TransferService {
  transfer(
    from: Account,
    to: Account,
    amount: Money
  ): TransferResult {
    // ビジネスルールのチェック
    if (from.balance.lessThan(amount)) {
      throw new InsufficientFundsError();
    }

    // 各集約の操作
    from.withdraw(amount);
    to.deposit(amount);

    // ドメインイベントを返す
    return TransferResult.success(
      new MoneyTransferredEvent(
        from.id, to.id, amount
      )
    );
  }
}

ドメインサービス vs アプリケーションサービス

観点 ドメインサービス アプリケーションサービス
層 ドメイン層 アプリケーション層
責務 ビジネスロジック ユースケースの調整
依存 ドメインオブジェクトのみ リポジトリ、外部サービス
例 送金計算、価格計算 注文処理フロー
⚠️ レビュー観点

ドメインサービスが肥大化していないか？
本来エンティティに属すべきロジックまでサービスに入れていないか、 「〜Manager」「〜Helper」という名前になっていないか確認。

7. ファクトリ

🎯 このページのゴール

ファクトリの役割と実装パターンを理解する

ファクトリとは？

ファクトリ（Factory）とは、 複雑なオブジェクトの生成をカプセル化するパターンです。
生成ロジックが複雑な場合、コンストラクタではなくファクトリを使います。

💡 たとえ話

ファクトリは「工場」です。
自動車を買うとき、部品を自分で組み立てますか？
工場が部品を組み立てて、完成品を届けてくれます。

同様に、ファクトリが複雑な初期化を行い、 正しく構築されたオブジェクトを返します。

ファクトリが必要な場面

  • 生成ロジックが複雑: 多数の依存関係、初期化処理
  • バリデーションが必要: 不正なオブジェクトを作らせない
  • ID生成が必要: UUIDの生成など
  • 集約の再構築: DBから取得したデータをドメインオブジェクトに

実装パターン

パターン1: staticファクトリメソッド

class Order {
  // コンストラクタはprivate
  private constructor(
    public readonly id: OrderId,
    private customerId: CustomerId,
    private items: OrderItem[],
    private status: OrderStatus
  ) {}

  // ファクトリメソッド
  static create(
    customerId: CustomerId,
    items: CreateOrderItem[]
  ): Order {
    // IDを生成
    const orderId = OrderId.generate();

    // アイテムを変換
    const orderItems = items.map(item =>
      OrderItem.create(
        OrderItemId.generate(),
        item.productId,
        item.quantity,
        item.price
      )
    );

    // バリデーション
    if (orderItems.length === 0) {
      throw new DomainError('Order must have items');
    }

    return new Order(
      orderId,
      customerId,
      orderItems,
      OrderStatus.Draft
    );
  }
}

パターン2: ファクトリクラス

class OrderFactory {
  constructor(
    private productRepository: ProductRepository,
    private pricingService: PricingService
  ) {}

  async create(
    customerId: CustomerId,
    items: CreateOrderItem[]
  ): Promise<Order> {
    // 商品情報を取得
    const products = await this.productRepository
      .findByIds(items.map(i => i.productId));

    // 価格を計算
    const pricedItems = await Promise.all(
      items.map(async item => {
        const product = products.find(
          p => p.id.equals(item.productId)
        );
        const price = await this.pricingService
          .calculate(product, item.quantity);
        return { ...item, price };
      })
    );

    return Order.create(customerId, pricedItems);
  }
}

コンストラクタが肥大化していないか？
10個以上の引数や複雑な初期化ロジックがコンストラクタにある場合、 ファクトリへの分離を検討すべき。

8. ドメインイベント

🎯 このページのゴール

ドメインイベントの役割と実装方法を理解する

ドメインイベントとは？

ドメインイベント（Domain Event）とは、 ドメインで何か重要なことが起きたことを表すオブジェクトです。
「〜された」という過去形で表現します。

💡 たとえ話

ドメインイベントは「ニュース速報」のようなものです。
「注文が確定されました」というニュースが流れると、 関係者（在庫、決済、配送）がそれぞれ対応します。

誰かが直接指示するのではなく、ニュースを見て各自が動きます。

ドメインイベントの例

  • OrderPlacedEvent - 注文が確定された
  • PaymentCompletedEvent - 支払いが完了した
  • InventoryReservedEvent - 在庫が引き当てられた
  • UserRegisteredEvent - ユーザーが登録された

直接呼び出し vs イベント駆動

直接呼び出しの連鎖
class OrderService {
  async confirmOrder(orderId: OrderId) {
    const order = await this.orderRepo.findById(orderId);
    order.confirm();
    await this.orderRepo.save(order);

    // 直接呼び出しの連鎖（密結合）
    await this.inventoryService.reserve(order.items);
    await this.paymentService.capture(order.payment);
    await this.emailService.sendConfirmation(order);
    await this.analyticsService.track('order_confirmed');
    // 依存が増えるたびに修正が必要
  }
}
イベント駆動で疎結合
class Order {
  private domainEvents: DomainEvent[] = [];

  confirm(): void {
    if (this.items.length === 0) {
      throw new DomainError('Cannot confirm');
    }
    this.status = OrderStatus.Confirmed;

    // イベントを発行
    this.domainEvents.push(
      new OrderConfirmedEvent(
        this.id,
        this.customerId,
        this.items
      )
    );
  }

  pullDomainEvents(): DomainEvent[] {
    const events = [...this.domainEvents];
    this.domainEvents = [];
    return events;
  }
}

// 各サービスは独立してイベントを購読
class InventoryEventHandler {
  @OnEvent('OrderConfirmed')
  async handle(event: OrderConfirmedEvent) {
    await this.inventoryService.reserve(event.items);
  }
}

ドメインイベントの構造

// ドメインイベントの基底クラス
abstract class DomainEvent {
  readonly occurredOn: Date;
  readonly eventId: string;

  constructor() {
    this.occurredOn = new Date();

9. 仕様パターン

🎯 このページのゴール

仕様パターンで複雑な条件をカプセル化する方法を理解する

仕様パターンとは？

仕様パターン（Specification Pattern）とは、 ビジネスルール（条件判定）をオブジェクトとしてカプセル化するパターンです。
複雑な条件を再利用可能で組み合わせ可能にします。

💡 たとえ話

仕様は「チェックリスト」のようなものです。
「プレミアム会員の条件」というチェックリストがあれば、 誰でも同じ基準で判定できます。

チェックリストを組み合わせることもできます。
「プレミアム会員」かつ「30日以内に購入」など。

仕様パターン
// 仕様の基底
interface Specification<T> {
  isSatisfiedBy(candidate: T): boolean;
  and(other: Specification<T>): Specification<T>;
  or(other: Specification<T>): Specification<T>;
}

// 各条件を仕様として定義（同じ型に対する仕様）
class HighValueOrderSpec implements Specification<Order> {
  isSatisfiedBy(order: Order): boolean {
    return order.total.greaterThan(Money.of(5000, 'JPY'));
  }
}

class BulkOrderSpec implements Specification<Order> {
  constructor(private minQuantity: number) {}
  isSatisfiedBy(order: Order): boolean {
    return order.itemCount >= this.minQuantity;
  }
}

class PromotionCodeSpec implements Specification<Order> {
  constructor(private code: string) {}
  isSatisfiedBy(order: Order): boolean {
    return order.promotionCode === this.code;
  }
}

// 組み合わせて使用（同じ型の仕様のみ結合可能）
const freeShippingSpec = new HighValueOrderSpec()
  .or(new BulkOrderSpec(10))           // 10個以上の注文
  .or(new PromotionCodeSpec('FREESHIP'));

// 判定
if (freeShippingSpec.isSatisfiedBy(order)) {
  order.applyFreeShipping();
}

仕様パターンの実装

// 基底クラス
abstract class CompositeSpecification<T> implements Specification<T> {
  abstract isSatisfiedBy(candidate: T): boolean;

  and(other: Specification<T>): Specification<T> {
    return new AndSpecification(this, other);
  }

  or(other: Specification<T>): Specification<T> {
    return new OrSpecification(this, other);
  }

  not(): Specification<T> {
    return new NotSpecification(this);
  }
}

// AND仕様
class AndSpecification<T> extends CompositeSpecification<T> {
  constructor(
    private left: Specification<T>,
    private right: Specification<T>
  ) { super(); }

  isSatisfiedBy(candidate: T): boolean {
    return this.left.isSatisfiedBy(candidate)
        && this.right.isSatisfiedBy(candidate);
  }
}

// 使用例
const eligibleForDiscount = new PremiumCustomerSpec()
  .and(new RecentPurchaseSpec(30))  // 30日以内に購入
  .and(new MinPurchaseAmountSpec(10000));

if (eligibleForDiscount.isSatisfiedBy(customer)) {
  applyDiscount(order);
}

仕様パターンの利点

  • 再利用性: 同じ条件を複数箇所で使える
  • 組み合わせ: and/or/notで柔軟に組み合わせ
  • テスト容易性: 各仕様を独立してテスト
  • 命名: ビジネスルールに名前がつく
⚠️ レビュー観点

複雑な条件判定がif文の羅列になっていないか？
同じ条件が複数箇所で重複している場合、仕様パターンでの カプセル化を検討すべき。

class Email {
  private constructor(public readonly value: string) {}
  static create(value: string): Email {
    if (!/.+@.+\..+/.test(value)) throw new Error('Invalid email');
    return new Email(value.toLowerCase());
  }
  equals(other: Email): boolean { return this.value === other.value; }
}

class User {
  constructor(
    public readonly id: UserId,
    private email: Email,
    private name: UserName
  ) {}

  changeEmail(newEmail: Email): void {
    // ビジネスルール
    this.email = newEmail;
  }

  equals(other: User): boolean { return this.id.equals(other.id); }
}

class Order {
  private domainEvents: DomainEvent[] = [];

  private constructor(
    public readonly id: OrderId,
    public readonly customerId: CustomerId,
    private items: OrderItem[],
    private status: OrderStatus
  ) {}

  static create(customerId: CustomerId, items: CreateOrderItem[]): Order {
    // ファクトリメソッド
  }

  addItem(item: OrderItem): void {
    // 集約ルートを通じて操作
    if (this.status !== OrderStatus.Draft) {
      throw new DomainError('Cannot modify confirmed order');
    }
    this.items.push(item);
  }

  confirm(): void {
    this.status = OrderStatus.Confirmed;
    this.domainEvents.push(new OrderConfirmedEvent(this.id));
  }

  pullDomainEvents(): DomainEvent[] {
    const events = [...this.domainEvents];
    this.domainEvents = [];
    return events;
  }
}
