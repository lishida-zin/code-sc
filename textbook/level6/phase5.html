1. アーキテクチャとは？

* このページのゴール

ソフトウェアアーキテクチャの目的と重要性を説明できる

アーキテクチャを一言で

ソフトウェアアーキテクチャとは、 システムの大きな構造と設計判断のことです。

* たとえ話

家を建てるとき、間取りを決めますよね。
「リビングは1階、寝室は2階」「キッチンとダイニングは近くに」
これが建築のアーキテクチャです。

ソフトウェアも同じです。
「どの機能をどこに配置するか」「どのように通信するか」
これがソフトウェアアーキテクチャです。

なぜアーキテクチャが重要？

アーキテクチャの選択は、後から変更が難しい決定です。
家の間取りを後から変えるのが大変なのと同じです。

品質特性 アーキテクチャの影響
保守性 変更のしやすさ、新機能追加のコスト
スケーラビリティ 負荷増加への対応能力
パフォーマンス 応答速度、スループット
信頼性 障害への耐性、回復力

トレードオフの考え方

完璧なアーキテクチャは存在しません。
何を優先し、何を妥協するかを判断するのがアーキテクチャ設計です。

* シニアの視点

「なぜこのアーキテクチャを選んだのか」を説明できないのは危険信号です。
流行りだから、他社がやっているから、ではなく、 自分たちの状況に合った理由が必要です。

2. レイヤードアーキテクチャ

* このページのゴール

レイヤードアーキテクチャの構造と各層の役割を説明できる

レイヤードアーキテクチャとは？

レイヤードアーキテクチャ（層状アーキテクチャ）は、 最も伝統的で広く使われている構造です。
システムを水平な層（レイヤー）に分割します。

* たとえ話

会社の組織に例えると分かりやすいです。
社長 → 部長 → 課長 → 一般社員
指示は上から下へ流れ、報告は下から上へ流れます。

典型的な3層/N層構造

┌─────────────────────────────────────┐
│      プレゼンテーション層            │  ← UI、API
│      (Presentation Layer)           │
├─────────────────────────────────────┤
│      ビジネスロジック層              │  ← ビジネスルール
│      (Business Logic Layer)         │
├─────────────────────────────────────┤
│      データアクセス層                │  ← DB操作
│      (Data Access Layer)            │
├─────────────────────────────────────┤
│      データベース                    │  ← データ保存
│      (Database)                     │
└─────────────────────────────────────┘

依存の方向: 上 → 下（上位層は下位層に依存）

各層の責務

層 責務 例
プレゼンテーション ユーザーとのやり取り Controller, View, API
ビジネスロジック 業務ルールの実装 Service, UseCase
データアクセス データの永続化 Repository, DAO

コード例

// プレゼンテーション層（Controller）
class UserController {
  constructor(private userService: UserService) {}

  async createUser(req: Request, res: Response) {
    const user = await this.userService.create(req.body);
    res.status(201).json(user);
  }
}

// ビジネスロジック層（Service）
class UserService {
  constructor(private userRepository: UserRepository) {}

  async create(data: CreateUserDto): Promise<User> {
    // ビジネスルールのチェック
    if (await this.userRepository.existsByEmail(data.email)) {
      throw new Error('Email already exists');
    }
    return this.userRepository.save(data);
  }
}

// データアクセス層（Repository）
class UserRepository {
  async save(data: CreateUserDto): Promise<User> {
    return await db.user.create({ data });
  }
}

3. レイヤードの問題点

* このページのゴール

レイヤードアーキテクチャの限界と問題点を指摘できる

問題1: DB駆動設計になりがち

レイヤードアーキテクチャでは、ドメイン（ビジネスロジック）がDBに依存してしまいがちです。

問題: ドメインがORMに依存
// domain/User.ts
import { Entity, Column } from 'typeorm';

@Entity()  // ORMのデコレータ！
export class User {
  @Column()
  email: string;
}

ドメインがインフラ（ORM）を知っている

理想: ドメインは純粋
// domain/User.ts
export class User {
  constructor(
    public readonly id: UserId,
    private email: Email
  ) {}
}
// ORMの知識は一切なし

ドメインはビジネスロジックのみ

問題2: テストが困難

下位層（DB）に依存しているため、上位層のテストでDBが必要になります。

問題: DBなしでテストできない
// Serviceのテストで本物のDBが必要
const service = new UserService(
  new UserRepository(db)  // 実際のDB接続
);
理想: モックで置き換え可能
// インターフェースに依存
const service = new UserService(
  mockUserRepository  // モックを注入
);

問題3: 変更の波及

DBスキーマの変更が上位層まで波及してしまいます。 

// DBカラム名を変更すると...
// 1. Repository を修正
// 2. Service を修正
// 3. Controller を修正
// 4. レスポンスを修正
// → 全層に影響！
* レビュー観点
  • ドメイン層にORMのimportがないか
  • Entityに @Column や @Entity があったら要注意
  • ビジネスロジックがDBの都合で書かれていないか

4. モノリス

* このページのゴール

モノリスアーキテクチャの特徴と適用場面を説明できる

モノリスとは？

モノリス（Monolith）は、すべての機能が 1つのアプリケーションとして動作するアーキテクチャです。

* たとえ話

モノリスは1棟のビルのようなものです。
すべての部署が同じビルにあり、エレベーターで移動できます。
管理はシンプルですが、ビル全体を建て替えないと大きな変更ができません。

モノリスの構造

モノリスの利点と欠点

利点
  • 開発がシンプル
  • デプロイが容易（1つのアプリ）
  • デバッグが容易（1プロセス）
  • トランザクション管理が容易
  • 初期コストが低い
欠点
  • コードベースが肥大化
  • スケーリングは全体単位
  • 1つの障害で全体停止
  • 技術選択の自由度が低い
  • デプロイに時間がかかる

モノリスが適している場面

状況 理由
チーム規模が小さい（1-10人） 複雑な分散システムの運用コストが見合わない
MVP/スタートアップ 素早くリリースして検証することが優先
ドメインが明確でない 最初から分割すると間違える可能性が高い
* 2026年のトレンド

Amazon Prime Videoが「マイクロサービスからモノリスに戻した」事例が話題になりました。
「マイクロサービス = 正解」ではないという認識が広まっています。

5. モジュラーモノリス

* このページのゴール

モジュラーモノリスの構造と利点を説明できる

モジュラーモノリスとは？

モジュラーモノリスは、モノリスの内部を明確なモジュールに分割したアーキテクチャです。
デプロイは1つのアプリ、でも内部は整理されています。

* たとえ話

オフィスフロアの区画分けに例えられます。
同じビルの中ですが、「営業部」「開発部」「人事部」は壁で仕切られています。
必要なときだけ受付を通じてやり取りします。

モジュラーモノリスの構造

モジュール間の境界

NG: 直接参照（密結合）
// order/OrderService.ts
import { UserRepository }
  from '../user/UserRepository';

// 他モジュールの内部に直接依存
OK: 公開APIのみ参照
// user/index.ts（公開API）
export interface UserModule {
  findById(id: string): UserDTO;
}

// order/OrderService.ts
import { UserModule } from '../user';
// 公開インターフェースのみ依存

モジュラーモノリスの利点

利点 説明
デプロイの単純さ モノリスと同様、1つのアプリとしてデプロイ
境界の明確化 モジュール間の依存が整理され、理解しやすい
将来の分割が容易 必要に応じてマイクロサービスに移行しやすい
チーム分割が可能 各モジュールを別チームが担当できる
* レビュー観点

モジュール間で直接importしていないか確認。
import { UserRepository } from '../user/repositories'はNG。
公開APIのみを使うべきです。

6. マイクロサービス

* このページのゴール

マイクロサービスの特徴と複雑さを説明できる

マイクロサービスとは？

マイクロサービスは、システムを独立してデプロイ可能な小さなサービスに分割するアーキテクチャです。

* たとえ話

専門店が集まった商店街に例えられます。
「パン屋」「肉屋」「八百屋」がそれぞれ独立した店舗として運営。
1つの店が休みでも他の店は営業できます。

マイクロサービスの構造

マイクロサービスの特徴

特徴 説明
独立デプロイ 各サービスを個別にデプロイできる
技術選択の自由 サービスごとに異なる言語/DBを使える
部分的スケーリング 負荷の高いサービスだけ増やせる
障害の隔離 1つのサービスの障害が全体に波及しにくい

マイクロサービスの複雑さ

* 分散システムの課題
  • ネットワーク障害: サービス間通信が失敗する可能性
  • データ整合性: 分散トランザクションの難しさ
  • デバッグの困難さ: リクエストが複数サービスを跨ぐ
  • 運用コスト: 監視、ログ収集、デプロイの複雑化

7. サービス境界の決め方

* このページのゴール

適切なサービス分割の基準を説明できる

サービス境界とは？

マイクロサービスで最も重要な設計判断は、「どこでサービスを分けるか」です。
間違った分割は、後で大きな問題を引き起こします。

アンチパターン: 技術的分割

NG: 技術レイヤーで分割
services/
  api-gateway/       # 全API
  business-logic/    # 全ビジネスロジック
  database-service/  # 全DB操作

すべてのサービスが密結合になる

OK: ビジネス機能で分割
services/
  user-service/      # ユーザー管理
  order-service/     # 注文管理
  inventory-service/ # 在庫管理
  payment-service/   # 決済

各サービスが独立して動作可能

分割の基準

基準 説明
ビジネスドメイン 業務の境界に沿って分割（DDDの境界づけられたコンテキスト）
チーム構成 1チーム = 1サービス（コンウェイの法則）
変更の頻度 よく一緒に変更される機能は同じサービスに
スケーリング要件 異なるスケール要件を持つ機能は分離

コンウェイの法則

「システムを設計する組織は、その組織のコミュニケーション構造をコピーした構造を持つ設計を生み出す」

つまり、チーム構成がアーキテクチャに影響するということです。
3チームあれば、自然と3つのサービスになりがちです。

* レビュー観点
  • サービス分割が「技術レイヤー」ではなく「ビジネス機能」になっているか
  • 1つのビジネス機能が複数サービスに分散していないか
  • 過度に細かく分割されていないか（ナノサービス問題）

8. 通信パターン

* このページのゴール

同期/非同期通信の違いと使い分けを説明できる

通信パターンの種類

パターン 特徴 用途
同期（HTTP/gRPC） 呼び出し元が応答を待つ 即座に結果が必要な場合
非同期（メッセージキュー） 呼び出し元は待たない 時間のかかる処理、疎結合
イベント駆動 イベントを発行、購読者が処理 複数サービスへの通知

同期通信の問題

問題: 同期呼び出しの連鎖
// 1サービスが遅いと全体が遅くなる
async createOrder(data) {
  await userService.getUser();     // 100ms
  await inventoryService.check();  // 200ms
  await paymentService.process();  // 500ms
  // 合計: 800ms + ネットワーク遅延
}

1つでも障害があると全体が止まる

解決: イベント駆動
// 即座に応答し、後続処理は非同期
async createOrder(data) {
  const order = Order.create(data);
  await orderRepo.save(order);

  // イベントを発行して終了
  await eventBus.publish(
    new OrderCreatedEvent(order)
  );
  return order;  // 即座に応答
}

各サービスは独立して処理

イベント駆動アーキテクチャ

┌──────────────┐     OrderCreated     ┌──────────────┐
│ Order Service│────────────────────► │ Message Queue│
└──────────────┘                      └───────┬──────┘
                                              │
            ┌─────────────────────────────────┼─────────────┐
            │                                 │             │
            ▼                                 ▼             ▼
   ┌──────────────┐              ┌──────────────┐  ┌──────────────┐
   │   Inventory  │              │   Payment    │  │ Notification │
   │   Service    │              │   Service    │  │   Service    │
   └──────────────┘              └──────────────┘  └──────────────┘
   在庫を予約                     決済を処理        メール送信
* レビュー観点
  • 同期呼び出しが連鎖していないか
  • タイムアウト、リトライが設定されているか
  • サーキットブレーカーが実装されているか

9. データ管理

* このページのゴール

マイクロサービスでのデータ管理パターンを説明できる

データベースの所有権

マイクロサービスでは、各サービスが自分のDBを持つのが原則です。
共有DBは避けるべきです。

NG: 共有データベース
User Service ──┐
               │
Order Service ─┼──► 共有DB
               │
Inventory ─────┘

スキーマ変更が全サービスに影響

OK: サービスごとのDB
User Service ──► User DB
Order Service ──► Order DB
Inventory ──► Inventory DB

各サービスが独立して進化可能

分散トランザクションの問題

複数サービスにまたがるトランザクションは、従来のACIDトランザクションが使えません。 

// 問題: 注文作成で複数サービスを更新
// 1. 在庫を減らす（Inventory Service）
// 2. 注文を保存（Order Service）
// 3. 決済を実行（Payment Service）

// もし決済が失敗したら、在庫はどうする？
// → 分散トランザクションの問題

Sagaパターン

Sagaは、長いトランザクションを小さなローカルトランザクションの連鎖として実装するパターンです。 

// Sagaの流れ
1. 在庫予約 → 成功
2. 注文作成 → 成功
3. 決済実行 → 失敗!

// 補償トランザクション（ロールバック相当）
3'. 注文キャンセル
2'. 在庫予約解除
* レビュー観点
  • 複数サービスにまたがる処理で整合性が考慮されているか
  • 失敗時の補償処理が実装されているか
  • 結果整合性（Eventual Consistency）を許容できる設計か

10. アーキテクチャ選択

* このページのゴール

状況に応じたアーキテクチャを選択できる

選択の基準

状況 推奨アーキテクチャ 理由
チーム1-10人、MVP モノリス シンプルさ、スピード優先
チーム10-50人、成長フェーズ モジュラーモノリス 境界を明確にしつつ運用コスト抑制
チーム50人以上、大規模 マイクロサービス 独立デプロイ、チーム自律性

よくある間違い

* オーバーエンジニアリング

「将来のため」にマイクロサービスを選ぶのは危険です。
まだ必要のない複雑さを抱え込み、開発速度が落ちます。

YAGNI（You Aren't Gonna Need It）の原則。
今必要なものだけを作り、将来必要になったら拡張しましょう。

進化的アーキテクチャ

最初から完璧なアーキテクチャを選ぶ必要はありません。
モノリス → モジュラーモノリス → マイクロサービスと 段階的に進化させることができます。 

Phase 1: モノリス（MVP、検証）
    ↓ ユーザー増加、チーム拡大
Phase 2: モジュラーモノリス（境界明確化）
    ↓ 特定機能のスケール要件
Phase 3: 一部をマイクロサービスに切り出し
    ↓ 必要に応じて段階的に分割

コンウェイの法則とは

1968年、メルヴィン・コンウェイが提唱した法則です。

💡 コンウェイの法則

「システムを設計する組織は、その組織のコミュニケーション構造を反映した設計を生み出す」

たとえ話

「4つのチームでコンパイラを作ると、4パスのコンパイラになる」
チームの数や構造が、そのままソフトウェアの構造に反映されるのです。

📊 チーム構造 → システム構造

逆コンウェイ戦略

コンウェイの法則を逆手に取る戦略です。
望ましいアーキテクチャに合わせて、チーム構造を設計するのです。

💡 実例

マイクロサービスアーキテクチャを目指すなら、
大きな1チームではなく、小さな自律チームに分ける。
各チームが1つのサービスを端から端まで担当する。

⚠️ 重要な気づき

技術的な議論だけでは足りません。
組織変革もアーキテクチャ設計の一部です。
チーム構造を変えずにアーキテクチャだけ変えても、元に戻ってしまいます。

Team Topologiesの4チームタイプ

チームタイプ 役割
Stream-aligned ビジネス価値を直接届ける主要チーム
Platform 共通基盤を提供（CI/CD、インフラなど）
Enabling 他チームの能力向上を支援
Complicated-subsystem 高度な専門知識が必要なサブシステム

12. レガシーシステムの改善戦略

📚このページで学ぶこと

なぜ「全面書き換え」は危険か

「古いシステムを全部捨てて、ゼロから作り直そう」
この誘惑は強力ですが、多くのプロジェクトで失敗しています。

  • 既存の暗黙知やエッジケース処理が失われる
  • 新システム完成まで長期間、保守が二重になる
  • ビジネス要件は待ってくれない（移行中も変更は続く）

Strangler Figパターン

イチジクの木（Strangler Fig）の比喩です。
熱帯のイチジクは宿主の木に巻き付きながら成長し、やがて宿主を完全に置き換えます。
同様に、既存システムを徐々に新システムで置き換える手法です。

📊 Strangler Figパターンの段階的移行

実装ステップ

  1. ファサード/プロキシの導入：全リクエストを受けるゲートウェイを配置
  2. 新機能は新システムに実装：新しいコードはレガシーに書かない
  3. 既存機能を段階的に移行：リスクの低い機能から順に
  4. 旧システムの廃止：全機能の移行完了後に停止

Anti-Corruption Layer（ACL）

新旧システム間に変換層（ACL）を置き、
レガシーの複雑な設計が新システムに侵食するのを防ぎます。 

// Anti-Corruption Layer の例
// レガシーAPIのレスポンスを新システムのモデルに変換
class LegacyUserAdapter {
  static toNewModel(legacyUser) {
    return {
      id: legacyUser.USER_ID,        // レガシー: 大文字スネーク
      name: legacyUser.FULL_NM,      // レガシー: 略語
      email: legacyUser.EMAIL_ADDR,
      isActive: legacyUser.STATUS_FLG === '1'
    };
  }
}
NG: ビッグバン移行
  • 全機能を一度に書き換え
  • リリースまで長期間かかる
  • 失敗時のロールバックが困難
  • ビジネス価値の提供が停止
OK: 段階的移行（Strangler Fig）
  • 機能単位で順次移行
  • 各段階で価値を提供
  • 問題発生時は該当部分のみ戻せる
  • 学びながら進められる
❌ ビッグバンリライトの現実

ビッグバンリライトの失敗率は非常に高いです。
Netscapeのブラウザ書き直し（3年間の遅延で市場シェア喪失）は有名な事例です。
「動いているコードには価値がある」ことを忘れないでください。
