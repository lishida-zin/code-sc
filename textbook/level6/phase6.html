1. なぜアーキテクチャが必要か

* このページのゴール

クリーンアーキテクチャの目的と価値を説明できる

アーキテクチャの目的

クリーンアーキテクチャやヘキサゴナルアーキテクチャの目的は、 ビジネスロジックを技術的な詳細から守ることです。

* たとえ話

家の設計で考えてみましょう。
「リビングで家族がくつろぐ」という目的（ビジネスロジック）は、 電気配線やエアコンの機種（技術的詳細）とは関係ありません。
エアコンを買い替えても、リビングの使い方は変わりませんよね。

技術に依存しないビジネスロジック

DBをPostgreSQLからMongoDBに変えても、
WebフレームワークをExpressからFastifyに変えても、
ビジネスロジックは変更不要であるべきです。

変更容易性とテスト容易性

目標 実現方法
変更容易性 技術的詳細の変更がビジネスロジックに影響しない
テスト容易性 DB/APIなしでビジネスロジックをテストできる
理解容易性 ビジネスルールがコードから明確に読み取れる

2. クリーンアーキテクチャ概要

* このページのゴール

クリーンアーキテクチャの同心円構造と依存ルールを説明できる

クリーンアーキテクチャとは？

Robert C. Martin（Uncle Bob）が提唱したアーキテクチャパターンです。
同心円の形で表現され、中心ほど重要（ビジネスルール）、外側ほど詳細（技術）です。

同心円の構造

内側ほど重要（ビジネス）、外側ほど詳細（技術）

依存ルール（The Dependency Rule）

最も重要なルール:
「ソースコードの依存性は、内側に向かってのみ向けることができる」

OK: 外側が内側に依存
// Controller → UseCase（OK）
class UserController {
  constructor(
    private createUser: CreateUserUseCase
  ) {}
}
NG: 内側が外側に依存
// Entity → ORM（NG！）
import { Entity } from 'typeorm';

@Entity()
class User { ... }
* レビュー観点

依存の方向を常にチェック。
内側の層（Entity, UseCase）から外側の層（DB, Framework）への importがあったら要注意です。

3. ドメイン層

* このページのゴール

ドメイン層の責務と実装方法を説明できる

ドメイン層とは？

ドメイン層（Enterprise Business Rules / Entities）は、 ビジネスの本質的なルールを表現する最も重要な層です。

* たとえ話

ECサイトの「注文」で考えましょう。
「在庫がない商品は注文できない」「合計金額は商品価格の合計」
これらはビジネスルールであり、
DBがPostgreSQLでもMongoDBでも変わりません。

ドメイン層の特徴

  • フレームワーク非依存: ORMのデコレータなし
  • 純粋なビジネスロジック: DBや外部APIを知らない
  • テスト容易: モックなしでテスト可能

コード例

NG: フレームワークに依存
// domain/User.ts
import { Entity, Column } from 'typeorm';

@Entity()
export class User {
  @Column()
  email: string;

  // ORMに依存している！
}
OK: 純粋なドメインモデル
// domain/User.ts
export class User {
  constructor(
    public readonly id: UserId,
    private email: Email,
    private name: UserName
  ) {}

  changeName(newName: UserName): void {
    if (newName.isEmpty()) {
      throw new DomainError('Name empty');
    }
    this.name = newName;
  }
}

値オブジェクト

ドメイン層では、プリミティブ型の代わりに値オブジェクトを使います。 

// 値オブジェクト: Email
class Email {
  private constructor(
    public readonly value: string
  ) {}

  static create(value: string): Email {
    if (!value.includes('@')) {
      throw new DomainError('Invalid email');
    }
    return new Email(value.toLowerCase());
  }

  equals(other: Email): boolean {
    return this.value === other.value;
  }
}

4. ユースケース層

* このページのゴール

ユースケース層の責務とドメイン層との違いを説明できる

ユースケース層とは？

ユースケース層（Application Business Rules）は、 アプリケーション固有のビジネスルールを実装する層です。
「ユーザーがシステムで何をするか」を表現します。

* ドメイン層との違い
層 責務 例
ドメイン層 ビジネスの本質的ルール 「在庫がない商品は注文できない」
ユースケース層 アプリケーションの操作フロー 「注文作成→在庫確認→メール送信」

ユースケースの実装

// application/CreateUserUseCase.ts
interface CreateUserInput {
  email: string;
  name: string;
}

interface CreateUserOutput {
  userId: string;
}

class CreateUserUseCase {
  constructor(
    private userRepository: UserRepository,  // 出力ポート
    private emailSender: EmailSender          // 出力ポート
  ) {}

  async execute(input: CreateUserInput): Promise<CreateUserOutput> {
    // 1. ドメインオブジェクトを生成
    const user = User.create(
      UserId.generate(),
      Email.create(input.email),
      UserName.create(input.name)
    );

    // 2. ポートを通じて永続化
    await this.userRepository.save(user);

    // 3. ポートを通じてメール送信
    await this.emailSender.sendWelcome(user.email);

    return { userId: user.id.value };
  }
}

ユースケース層のルール

  • ドメインオブジェクトを使ってビジネスフローを実装
  • インフラの詳細を知らない（インターフェース経由）
  • 入力/出力はDTOで、ドメインオブジェクトを直接返さない
NG: インフラに直接依存
class CreateUserUseCase {
  async execute(input) {
    // Prismaに直接依存！
    const prisma = new PrismaClient();
    await prisma.user.create({...});

    // SMTPの詳細を知っている！
    const transport = nodemailer
      .createTransport({...});
  }
}
OK: ポート経由
class CreateUserUseCase {
  constructor(
    private userRepo: UserRepository,
    private emailSender: EmailSender
  ) {}

  async execute(input) {
    // インターフェース経由
    await this.userRepo.save(user);
    await this.emailSender.send(email);
  }
}

5. インターフェース層

* このページのゴール

インターフェース層（アダプター層）の責務を説明できる

インターフェース層とは？

インターフェース層（Interface Adapters）は、 外部と内部を橋渡しする層です。
Controller、Presenter、Gatewayなどが含まれます。

Controllerの責務

Controllerは入力の変換とユースケースの呼び出しのみを担当します。
ビジネスロジックを含めてはいけません。

NG: ビジネスロジックが混入
class UserController {
  async createUser(req, res) {
    // バリデーション（OK）
    if (!req.body.email) {
      return res.status(400).json({});
    }

    // ビジネスロジックがここに！
    if (await db.user.findByEmail(
      req.body.email)) {
      return res.status(409).json({});
    }

    // 直接DBアクセス！
    const user = await db.user.create({
      data: req.body
    });

    res.status(201).json(user);
  }
}
OK: 変換と呼び出しのみ
class UserController {
  constructor(
    private createUser: CreateUserUseCase
  ) {}

  async create(req, res) {
    // 入力バリデーション
    const result = CreateUserSchema
      .safeParse(req.body);
    if (!result.success) {
      return res.status(400).json({});
    }

    // ユースケースを呼び出すだけ
    const output = await this.createUser
      .execute(result.data);

    res.status(201).json(output);
  }
}

インターフェース層の役割

コンポーネント 責務
Controller HTTPリクエストをUseCaseの入力に変換
Presenter UseCaseの出力をHTTPレスポンスに変換
Gateway 外部APIとの通信をドメインに変換

6. インフラ層

* このページのゴール

インフラ層の責務と実装方法を説明できる

インフラ層とは？

インフラ層（Frameworks & Drivers）は、 技術的な詳細を実装する最も外側の層です。
DB、外部API、フレームワークなどが含まれます。

インフラ層に含まれるもの

  • データベース: ORM、クエリ実装
  • 外部API: HTTP通信、SDKラッパー
  • Webフレームワーク: Express, Fastify等
  • メッセージキュー: RabbitMQ, SQS等

リポジトリの実装

// application/ports/UserRepository.ts（インターフェース）
interface UserRepository {
  save(user: User): Promise<void>;
  findById(id: UserId): Promise<User | null>;
}

// infrastructure/PrismaUserRepository.ts（実装）
class PrismaUserRepository implements UserRepository {
  constructor(private prisma: PrismaClient) {}

  async save(user: User): Promise<void> {
    await this.prisma.user.upsert({
      where: { id: user.id.value },
      create: this.toRecord(user),
      update: this.toRecord(user)
    });
  }

  async findById(id: UserId): Promise<User | null> {
    const record = await this.prisma.user.findUnique({
      where: { id: id.value }
    });
    return record ? this.toDomain(record) : null;
  }

  // ドメインとDBレコードの変換
  private toRecord(user: User): UserRecord { ... }
  private toDomain(record: UserRecord): User { ... }
}

7. ヘキサゴナル概要

* このページのゴール

ヘキサゴナルアーキテクチャ（Ports & Adapters）の概念を説明できる

ヘキサゴナルアーキテクチャとは？

Alistair Cockburnが提唱したPorts & Adaptersパターンです。
六角形（ヘキサゴン）で図示されることから、この名前がついています。

* たとえ話

電源コンセントで考えてみましょう。
日本のコンセント（ポート）に、海外の家電（アダプター）を繋ぐには 変換プラグ（アダプター）が必要ですよね。
アプリケーションも同じです。ポートとアダプターで外部と繋がります。

ヘキサゴナルの構造

クリーンアーキテクチャとの関係

ヘキサゴナル クリーンアーキテクチャ
Application Domain + Use Cases
Input Ports Use Case Interfaces
Output Ports Gateway Interfaces
Adapters Interface Adapters + Infrastructure

本質は同じで、ビジネスロジックを中心に据え、技術的詳細を外側に押し出す考え方です。

8. ポート（Port）

* このページのゴール

入力ポートと出力ポートの役割を説明できる

ポートとは？

ポートは、アプリケーションと外部世界の境界を定義するインターフェースです。
「何ができるか」を定義し、「どうやるか」は定義しません。

入力ポート（Input Port / Driving Port）

外部からアプリケーションを駆動するためのインターフェースです。
ユースケースのインターフェースとも言えます。 

// ports/input/CreateUserUseCase.ts（入力ポート）
interface CreateUserUseCase {
  execute(input: CreateUserInput): Promise<CreateUserOutput>;
}

interface CreateUserInput {
  email: string;
  name: string;
}

interface CreateUserOutput {
  userId: string;
}

出力ポート（Output Port / Driven Port）

アプリケーションが外部リソースを利用するためのインターフェースです。
リポジトリや外部サービスのインターフェースです。 

// ports/output/UserRepository.ts（出力ポート）
interface UserRepository {
  save(user: User): Promise<void>;
  findById(id: UserId): Promise<User | null>;
  findByEmail(email: Email): Promise<User | null>;
}

// ports/output/EmailSender.ts（出力ポート）
interface EmailSender {
  sendWelcome(to: Email): Promise<void>;
  sendPasswordReset(to: Email, token: string): Promise<void>;
}

ポートの利点

利点 説明
テスト容易性 モックを差し替えてテストできる
交換可能性 実装を変更してもアプリは影響なし
ドキュメント効果 システムの境界が明確になる

9. アダプター（Adapter）

* このページのゴール

Primary AdapterとSecondary Adapterの違いを説明できる

アダプターとは？

アダプターは、ポートの具体的な実装です。
外部の技術とアプリケーションを繋ぎます。

Primary Adapter（駆動側アダプター）

外部からアプリケーションを呼び出す側の実装です。 

// adapters/primary/ExpressUserController.ts
class ExpressUserController {
  constructor(
    private createUserUseCase: CreateUserUseCase  // 入力ポート
  ) {}

  // HTTPリクエストを入力ポートの形式に変換
  async create(req: Request, res: Response) {
    const input: CreateUserInput = {
      email: req.body.email,
      name: req.body.name
    };

    const output = await this.createUserUseCase.execute(input);
    res.status(201).json(output);
  }
}

Secondary Adapter（被駆動側アダプター）

アプリケーションから呼び出される側の実装です。 

// adapters/secondary/PrismaUserRepository.ts
class PrismaUserRepository implements UserRepository {  // 出力ポートを実装
  constructor(private prisma: PrismaClient) {}

  async save(user: User): Promise<void> {
    // ドメインオブジェクトをDBの形式に変換
    await this.prisma.user.create({
      data: {
        id: user.id.value,
        email: user.email.value,
        name: user.name.value
      }
    });
  }
}

// adapters/secondary/NodemailerEmailSender.ts
class NodemailerEmailSender implements EmailSender {  // 出力ポートを実装
  async sendWelcome(to: Email): Promise<void> {
    // nodemailerの詳細はここに閉じ込める
    await this.transporter.sendMail({
      to: to.value,
      subject: 'Welcome!',
      text: '...'
    });
  }
}

アダプターの種類

種類 方向 例
Primary 外部 → アプリ Controller, CLI, テスト
Secondary アプリ → 外部 Repository, API Client, EmailSender
* レビュー観点

アダプターにビジネスロジックが含まれていないか確認。
アダプターは「変換」のみを担当し、判断はアプリケーション層で行うべきです。

トレードオフ

利点

11. テスト戦略とアーキテクチャの統合

📚このページで学ぶこと
  • テスタブルなアーキテクチャの設計
  • ポートとアダプタでのテスト戦略
  • テストピラミッドとアーキテクチャ層の対応

クリーンアーキテクチャがテストを容易にする理由

クリーンアーキテクチャでは、依存関係が内側に向かうため、 外側の技術的詳細をモックに差し替えてテストできます。
つまり、ビジネスロジックをDB接続やHTTP通信なしでテストできるのです。

ヘキサゴナルアーキテクチャでのテスト戦略

レイヤー テスト種類 特徴
ドメイン層 純粋な単体テスト 外部依存なし、高速、決定的
アプリケーション層 モック利用の統合テスト ポートのモックでユースケース検証
インフラ層 実環境に近い結合テスト 実DB・外部サービスへの接続テスト
📊 テストピラミッドとアーキテクチャ層

依存性注入（DI）がテストを可能にする

ポート（インターフェース）を定義し、 テスト時にはモックを注入することで、外部依存なしにテストできます。 

// ポート（インターフェース）の定義
class UserRepository {
  async findById(id) { throw new Error('Not implemented'); }
  async save(user) { throw new Error('Not implemented'); }
}

// 本番用アダプタ
class PostgresUserRepository extends UserRepository {
  async findById(id) {
    return await db.query('SELECT * FROM users WHERE id = $1', [id]);
  }
}

// テスト用モック
class MockUserRepository extends UserRepository {
  constructor() { this.users = new Map(); }
  async findById(id) { return this.users.get(id) || null; }
  async save(user) { this.users.set(user.id, user); }
}

// ユースケースのテスト（外部依存なし！）
describe('CreateUserUseCase', () => {
  it('should create a user', async () => {
    const repo = new MockUserRepository();
    const useCase = new CreateUserUseCase(repo);

    await useCase.execute({ name: 'Alice', email: 'alice@test.com' });

    const saved = await repo.findById(1);
    expect(saved.name).toBe('Alice');
  });
});
✓ 良いアーキテクチャ = テストしやすいアーキテクチャ

テストが書きにくいと感じたら、それはアーキテクチャの問題かもしれません。
依存関係の方向を見直し、ポートとアダプタで分離することで、 テスタビリティは劇的に向上します。
