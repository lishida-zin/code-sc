プログラミングパラダイムの進化

プログラミングの歴史は複雑さとの戦いです。

🏠 たとえ話：工場の進化

手工業時代 = 命令型プログラミング
一人が全部やる。小さな作業なら効率的だが、規模が大きくなると限界。

分業制工場 = 手続き型プログラミング
作業を関数に分割。再利用できるが、データと処理がバラバラ。

チーム制工場 = オブジェクト指向プログラミング
データと処理を「チーム（オブジェクト）」としてまとめる。
各チームは自分の責務を持ち、他チームと協力する。

OOPが解決する問題

1960年代、プログラムが大規模化すると2つの問題が顕在化しました。

問題1：スパゲッティコード

グローバル変数を多数の関数が触る。
どこで何が変わるか追えない。 

// グローバル変数
let userData = { name: "", age: 0 };
let orderData = [];

// どの関数がどのデータを触るか不明
function processA() { userData.age++; }
function processB() { orderData.push({}); }
function processC() { userData = null; }
問題2：変更の波及

1箇所を変えると、全体に影響。
「何が壊れるか分からない」恐怖。 

// userDataの構造を変えると...
// → processA, processB, processC全部修正
// → テスト全部やり直し
// → 予期しないバグ発生

OOPの4つの柱

OOPは4つの原則でこれらの問題を解決します。

📊 OOPの4つの柱の関係

4つの柱が連携して「複雑さとの戦い」に挑む

原則 意味 解決する問題
カプセル化 データと処理をまとめ、内部を隠す グローバル変数の乱用
抽象化 複雑な詳細を隠し、本質だけを公開 複雑さの軽減
継承 既存クラスの機能を引き継ぐ コードの重複
ポリモーフィズム 同じ操作で異なる振る舞い 条件分岐の複雑さ

OOPの歴史

📜 知っておきたい歴史
  • 1967年：Simula（OOP最初の言語）
  • 1972年：Smalltalk（「オブジェクト指向」命名）
  • 1983年：C++（C言語にOOP追加）
  • 1995年：Java（OOPを主流に）
  • 2012年：TypeScript登場（JavaScriptに静的型付けを追加）

「オブジェクト指向」はAlan Kayが名付けました。
彼の理想は「メッセージ送信」でしたが、
現代のOOPは「クラスとメソッド」に進化しています。

カプセル化

カプセル化とは

カプセル化 = データと処理をまとめ、内部を隠すこと

🏠 たとえ話：薬のカプセル

薬のカプセルは中身を隠している。
利用者は「飲む」だけでよく、中の成分を直接触らない。

同様に、オブジェクトも内部データを隠し、
メソッドを通じてのみ操作させる。

なぜカプセル化が必要か

カプセル化なし
class User {
  public id: string;
  public email: string;
  public password: string;  // 丸見え！
}

const user = new User();
user.password = "";  // 空にできてしまう
user.email = "invalid";  // バリデーションなし

誰でも好きなように変更できる
= 不正なデータが入り込む

カプセル化あり
class User {
  private email: string;
  private passwordHash: string;

  changeEmail(newEmail: string): void {
    if (!this.isValidEmail(newEmail)) {
      throw new Error('Invalid email');
    }
    this.email = newEmail;
  }

  private isValidEmail(email: string): boolean {
    return email.includes('@');
  }
}

メソッドを通じてのみ変更
= バリデーションを強制できる

アクセス修飾子

修飾子 アクセス範囲 使いどころ
public どこからでも 外部に公開するメソッド
private クラス内のみ 内部データ、ヘルパー関数
protected クラス内 + 子クラス 継承で使う内部メソッド

getter / setter の役割

getter/setterは読み書きにロジックを挟むためのもの。 

class Temperature {
  private _celsius: number = 0;

  // getter: 読み取り時に計算
  get fahrenheit(): number {
    return this._celsius * 9/5 + 32;
  }

  // setter: 書き込み時にバリデーション
  set celsius(value: number) {
    if (value < -273.15) {
      throw new Error('絶対零度以下は不可');
    }
    this._celsius = value;
  }
}

const temp = new Temperature();
temp.celsius = 25;
console.log(temp.fahrenheit);  // 77
⚠️ getter/setterの注意点

単にprivateフィールドを公開するだけのgetter/setterは無意味です。 

// ❌ 無意味なgetter/setter
class User {
  private _name: string;

  get name(): string { return this._name; }
  set name(value: string) { this._name = value; }
}
// これならpublicと同じ

バリデーションや計算がある場合にのみ使いましょう。

🔍 コードレビューの観点

以下を見つけたら指摘しましょう：

  • 全フィールドがpublic：カプセル化違反
  • パスワードがpublic：セキュリティ問題
  • 意味のないgetter/setter：冗長なコード

抽象化

📚 このページで学ぶこと

抽象化とは

抽象化 = 複雑な詳細を隠し、本質的な機能だけを公開すること

🏠 たとえ話：車の運転

車を運転するとき、エンジンの仕組みを知る必要はない。
アクセル、ブレーキ、ハンドルだけ知っていればいい。

内部の複雑さ（燃焼、変速機、ABS）は隠されている。
これが抽象化です。

インターフェース

インターフェースは「何ができるか」を定義します。
「どうやるか」は定義しません。 

// 「何ができるか」だけ定義
interface PaymentMethod {
  pay(amount: number): Promise<PaymentResult>;
  refund(transactionId: string): Promise<void>;
}

// 「どうやるか」は実装クラスが決める
class CreditCard implements PaymentMethod {
  async pay(amount: number): Promise<PaymentResult> {
    // クレジットカード固有の処理
    return { success: true, transactionId: "cc_123" };
  }

  async refund(transactionId: string): Promise<void> {
    // クレジットカード固有の返金処理
  }
}

class PayPal implements PaymentMethod {
  async pay(amount: number): Promise<PaymentResult> {
    // PayPal固有の処理
    return { success: true, transactionId: "pp_456" };
  }

  async refund(transactionId: string): Promise<void> {
    // PayPal固有の返金処理
  }
}

抽象クラス

抽象クラスは「一部の実装を共有」しつつ、
「一部をサブクラスに任せる」ことができます。 

abstract class Animal {
  // 共通の実装
  sleep(): void {
    console.log("Zzz...");
  }

  // サブクラスに実装を任せる
  abstract makeSound(): void;
}

class Dog extends Animal {
  makeSound(): void {
    console.log("ワン！");
  }
}

class Cat extends Animal {
  makeSound(): void {
    console.log("ニャー");
  }
}

// 両方ともsleep()は使える
const dog = new Dog();
dog.sleep();      // "Zzz..."
dog.makeSound();  // "ワン！"

インターフェース vs 抽象クラス

インターフェース
  • 「契約」のみ定義
  • 複数実装できる（多重継承OK）
  • 状態を持てない
  • 使いどころ：異なるクラス間の共通機能
抽象クラス
  • 「契約 + 一部実装」を定義
  • 1つしか継承できない
  • 状態（フィールド）を持てる
  • 使いどころ：似たクラスの共通処理
🔍 コードレビューの観点

実装詳細の露出を見つけたら指摘しましょう：

// ❌ 実装詳細が露出している
class UserRepository {
  // MySQLの接続オブジェクトが公開されている
  public connection: MySQLConnection;

  getUser(id: string): User {
    // 呼び出し側がconnectionを直接触れてしまう
  }
}

// ⭕ 抽象化されている
interface UserRepository {
  getUser(id: string): Promise<User | null>;
  save(user: User): Promise<void>;
}
// 内部でMySQL/PostgreSQL/Mongoのどれを使うか隠されている

継承

継承とは

継承 = 既存クラスの機能を引き継いで新しいクラスを作ること

🏠 たとえ話：家系図

子供は親の特徴を受け継ぐ。
でも、子供独自の特徴も持つ。

プログラムでも同じ。
親クラスの機能を継承しつつ、
子クラス独自の機能を追加できる。

is-a関係

継承は「AはBである（is-a）」関係を表します。 

// 「犬は動物である」
class Animal {
  move(): void {
    console.log("移動する");
  }
}

class Dog extends Animal {
  bark(): void {
    console.log("ワン！");
  }
}

const dog = new Dog();
dog.move();  // 親クラスのメソッドが使える
dog.bark();  // 子クラス独自のメソッド

// 「DogはAnimalである」が成り立つ
const animal: Animal = new Dog();  // OK

オーバーライド

子クラスで親クラスのメソッドを上書きできます。 

class Animal {
  speak(): void {
    console.log("...");
  }
}

class Dog extends Animal {
  // 親のspeak()を上書き
  speak(): void {
    console.log("ワン！");
  }
}

class Cat extends Animal {
  speak(): void {
    console.log("ニャー");
  }
}

const animals: Animal[] = [new Dog(), new Cat()];
animals.forEach(a => a.speak());
// "ワン！"
// "ニャー"

superキーワード

superで親クラスのメソッドを呼び出せます。 

class Animal {
  constructor(protected name: string) {}

  describe(): string {
    return `名前: ${this.name}`;
  }
}

class Dog extends Animal {
  constructor(name: string, private breed: string) {
    super(name);  // 親のコンストラクタを呼ぶ
  }

  describe(): string {
    // 親のメソッドを呼び出して拡張
    return super.describe() + `, 犬種: ${this.breed}`;
  }
}

const dog = new Dog("ポチ", "柴犬");
console.log(dog.describe());
// "名前: ポチ, 犬種: 柴犬"
🔍 コードレビューの観点：深い継承階層 
// ❌ 深い継承階層（Fragile Base Class問題）
class Animal {}
class Mammal extends Animal {}
class Carnivore extends Mammal {}
class Feline extends Carnivore {}
class DomesticCat extends Feline {}  // 5階層！

// 親クラスの変更が全子クラスに波及
// 理解・テストが困難になる

3階層以上の継承は危険信号です。
コンポジションへの書き換えを検討しましょう。

ポリモーフィズム

ポリモーフィズムとは

ポリモーフィズム = 同じ操作で異なる振る舞いをすること

🏠 たとえ話：リモコンの「再生」ボタン

テレビ、DVDプレーヤー、スマホ...
どれも「再生」ボタンがあるが、やることは違う。

「再生」という同じ操作で、
異なる動作が実行される。
これがポリモーフィズムです。

ポリモーフィズムなしの世界

switch文だらけ
function calculateArea(shape: Shape): number {
  switch (shape.type) {
    case 'circle':
      return Math.PI * shape.radius ** 2;
    case 'rectangle':
      return shape.width * shape.height;
    case 'triangle':
      return shape.base * shape.height / 2;
    // 新しい図形が増えるたびに修正が必要
    default:
      throw new Error('Unknown shape');
  }
}

図形が増えるたびにswitch文を修正

ポリモーフィズムを活用
interface Shape {
  calculateArea(): number;
}

class Circle implements Shape {
  constructor(private radius: number) {}
  calculateArea(): number {
    return Math.PI * this.radius ** 2;
  }
}

class Rectangle implements Shape {
  constructor(private w: number, private h: number) {}
  calculateArea(): number {
    return this.w * this.h;
  }
}

// どんな図形でも同じように扱える
function printArea(shape: Shape): void {
  console.log(shape.calculateArea());
}

新しい図形は新クラスを追加するだけ

ダックタイピング

「アヒルのように歩き、アヒルのように鳴くなら、それはアヒルだ」 

// TypeScriptは「構造」で型を判断する
interface Printable {
  print(): void;
}

class Document {
  print(): void {
    console.log("文書を印刷");
  }
}

class Photo {
  print(): void {
    console.log("写真を印刷");
  }
}

// どちらもPrintableとして扱える
function printAll(items: Printable[]): void {
  items.forEach(item => item.print());
}

printAll([new Document(), new Photo()]);
// "文書を印刷"
// "写真を印刷"

implements Printableを書かなくても、
print()メソッドがあればPrintableとして扱える。

🔍 コードレビューの観点：switch文での型判定 
// ❌ 型をswitch文で判定している
function process(item: Dog | Cat | Bird): void {
  switch (item.type) {
    case 'dog':
      item.bark();
      break;
    case 'cat':
      item.meow();
      break;
    case 'bird':
      item.chirp();
      break;
  }
}

// ⭕ ポリモーフィズムで解決
interface Animal {
  speak(): void;
}

function process(animal: Animal): void {
  animal.speak();  // 各クラスが適切な実装を持つ
}

型によるswitch/if文を見つけたら、
ポリモーフィズムで書き換えられないか検討しましょう。

継承 vs コンポジション

📚 このページで学ぶこと
  • has-a関係（コンポジション）とは
  • 継承の問題点
  • 「継承よりコンポジションを優先」の原則

is-a vs has-a

is-a（継承）

「AはBである」

// 犬は動物である
class Dog extends Animal {}
has-a（コンポジション）

「AはBを持っている」

// 車はエンジンを持っている
class Car {
  private engine: Engine;
}

継承の問題点

⚠️ 継承の3つの問題
  • 脆い基底クラス問題：親を変えると子が壊れる
  • 柔軟性の欠如：実行時に振る舞いを変えられない
  • 不要な機能の継承：使わないメソッドも継承される
// ❌ 継承の問題：不要な機能まで継承
class Bird {
  fly(): void { console.log("飛ぶ"); }
  eat(): void { console.log("食べる"); }
}

class Penguin extends Bird {
  fly(): void {
    throw new Error("ペンギンは飛べません");  // 継承したけど使えない
  }
}

// ペンギンはBirdだが、fly()は使えない → LSP違反

コンポジションで解決

継承で実装
// 深い継承階層
class Animal {}
class Mammal extends Animal {}
class Carnivore extends Mammal {}
class Cat extends Carnivore {}

// 柔軟性がない
// 「草食の猫」は作れない
コンポジションで実装
interface Behavior {
  act(): void;
}

class HuntingBehavior implements Behavior {
  act(): void { console.log("狩りをする"); }
}

class GrazingBehavior implements Behavior {
  act(): void { console.log("草を食べる"); }
}

class Cat {
  constructor(private behavior: Behavior) {}

  performBehavior(): void {
    this.behavior.act();
  }
}

// 柔軟に振る舞いを変えられる
const hunter = new Cat(new HuntingBehavior());
const grazer = new Cat(new GrazingBehavior());

「継承よりコンポジションを優先」

✓ 設計の原則

「継承よりコンポジションを優先せよ」
（Effective Java / Design Patterns）

  • 継承：「何であるか」を決める（静的）
  • コンポジション：「何ができるか」を決める（動的）

コンポジションを使えば、実行時に振る舞いを変更できる。
継承は明確なis-a関係がある場合のみ使う。

🔍 コードレビューの観点

以下を見つけたら、コンポジションへの書き換えを検討：

  • 3階層以上の継承
  • オーバーライドで例外をthrow（使えないメソッドの継承）
  • 「〜を持っている」関係での継承（Car extends Engine）

凝集度と結合度

📚 このページで学ぶこと
  • 凝集度（Cohesion）とは
  • 結合度（Coupling）とは
  • 「高凝集・疎結合」の原則

凝集度とは

凝集度 = クラス内の要素がどれだけ関連しているか

🏠 たとえ話：工具箱

高凝集：ドライバーセット（関連する工具だけ）
低凝集：何でも入ってるガラクタ箱

高凝集なクラスは1つの目的に集中している。

低凝集（神クラス）
// ❌ 責務が多すぎる
class UserManager {
  createUser() {}
  deleteUser() {}
  sendEmail() {}        // メール？
  generateReport() {}   // レポート？
  validateInput() {}    // バリデーション？
  connectDatabase() {}  // DB接続？
}

// 何でもやる「神クラス」
// 変更理由が多すぎる
高凝集
// ⭕ 責務を分離
class UserRepository {
  create(user: User): void {}
  delete(id: string): void {}
  findById(id: string): User {}
}

class EmailService {
  send(to: string, subject: string): void {}
}

class UserReportGenerator {
  generate(users: User[]): Report {}
}

// 各クラスは1つの責務に集中

結合度とは

結合度 = クラス間の依存の強さ

🏠 たとえ話：レゴブロック

疎結合：レゴブロック（簡単に組み替え可能）
密結合：接着剤で固めたブロック（分離困難）

疎結合なら、1つを変えても他への影響が少ない。

密結合
// ❌ 具象クラスに直接依存
class OrderService {
  private emailSender = new GmailSender();
  private repository = new MySQLRepository();

  createOrder(data: OrderData): void {
    // GmailとMySQLに密結合
    // 変更が困難
  }
}
疎結合
// ⭕ インターフェースに依存
class OrderService {
  constructor(
    private emailSender: EmailSender,
    private repository: OrderRepository
  ) {}

  createOrder(data: OrderData): void {
    // 具体的な実装を知らない
    // 差し替え可能
  }
}

「高凝集・疎結合」

✓ 良い設計の目標
目標 意味 メリット
高凝集 クラス内の要素が密接に関連 理解しやすい、変更が局所的
疎結合 クラス間の依存が弱い 変更の影響が少ない、テストしやすい
🔍 コードレビューの観点

神クラスの兆候：

  • クラスが500行を超える
  • メソッドが20個以上ある
  • 「〜Manager」「〜Handler」「〜Util」という名前
  • 複数の理由で変更される

OOPの限界

OOPは万能ではありません。苦手な領域があります。

⚠️ OOPが苦手なこと
  • 並行処理：状態の共有が問題を引き起こす
  • データ変換：単純なデータ加工にクラスは大げさ
  • 横断的関心事：ログ、認証などが複数クラスに散らばる
  • パフォーマンス：オブジェクト生成のオーバーヘッド

関数型プログラミングとの融合

現代のTypeScriptではOOPと関数型を組み合わせるのが一般的です。

OOPスタイル
class UserService {
  private users: User[] = [];

  addUser(user: User): void {
    this.users.push(user);  // 状態を変更
  }

  getAdults(): User[] {
    return this.users.filter(u => u.age >= 18);
  }
}
関数型スタイル
// 純粋関数：入力から出力を計算するだけ
const addUser = (users: User[], user: User): User[] =>
  [...users, user];  // 新しい配列を返す

const getAdults = (users: User[]): User[] =>
  users.filter(u => u.age >= 18);

// 状態を変更しない（イミュータブル）

現代的なアプローチ

場面 アプローチ 理由
ビジネスロジック OOP（エンティティ、集約） 状態と振る舞いをカプセル化
データ変換 関数型（map, filter, reduce） シンプルで読みやすい
UI状態管理 関数型（Redux, イミュータブル） 予測可能、デバッグしやすい
インフラ層 OOP（リポジトリ、サービス） 依存性注入、テスト容易性

OOP原理主義の危険

🔍 コードレビューの観点

過度なOOPの兆候：

// ❌ 単純な処理にクラスは過剰
class StringUppercaser {
  private value: string;

  constructor(value: string) {
    this.value = value;
  }

  uppercase(): string {
    return this.value.toUpperCase();
  }
}

// ⭕ 関数で十分
const uppercase = (s: string): string => s.toUpperCase();

「すべてをオブジェクトに」は間違い。
問題に応じて適切なパラダイムを選びましょう。
