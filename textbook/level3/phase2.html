Reactとは何か

Reactは、Facebookが開発したUIライブラリです。

「ライブラリ」とは、特定の機能を提供するコードの集まりです。
ReactはUIを作ることに特化しています。

💡 Reactの3つの特徴
  1. 宣言的（Declarative）: 「こう見せたい」を宣言する
  2. コンポーネント指向: UIを部品に分けて組み立てる
  3. 仮想DOM: 効率的にUIを更新する仕組み

宣言的UI vs 命令的UI

Reactを理解する上で最も重要な概念が「宣言的」という考え方です。

命令的UI（従来のやり方）

「どうやって変えるか」を指示する方法です。

❌ 命令的UI（DOM操作） 
// 手順を1つ1つ指示する
const button = document.getElementById("btn");
const counter = document.getElementById("counter");

let count = 0;

button.addEventListener("click", () => {
  count++;
  counter.textContent = count;  // DOM を直接操作
});

問題点: 状態（count）とUI（counter.textContent）を手動で同期する必要がある。

宣言的UI（Reactのやり方）

「どう見えるべきか」を宣言する方法です。

✓ 宣言的UI（React） 
function Counter() {
  const [count, setCount] = useState(0);

  return (
    <div>
      <p>{count}</p>  {/* countが変われば自動で更新 */}
      <button onClick={() => setCount(count + 1)}>
        +1
      </button>
    </div>
  );
}

ポイント: 「countの値をUIに表示する」と宣言するだけ。
countが変わると、Reactが自動でUIを更新してくれる。

🍳 たとえ話

命令的: 「卵を割って、フライパンで焼いて、皿に盛って」（手順を指示）
宣言的: 「目玉焼きください」（結果を宣言）

仮想DOM（Virtual DOM）

Reactの高速化の仕組みです。

DOM操作は遅い: ブラウザのDOMを直接変更すると、再描画が発生して遅い。

仮想DOM: JavaScriptのメモリ上に「仮のDOM」を作り、
変更があった部分だけを本物のDOMに反映する。

仮想DOMの流れ
  1. 状態が変化する
  2. 新しい仮想DOMを作成
  3. 前の仮想DOMと比較（差分検出）
  4. 変更部分だけ本物のDOMを更新

コンポーネント指向

コンポーネント = UIの部品

Webページを部品に分けて考えます。 

// Headerコンポーネント
function Header() {
  return <header>サイトタイトル</header>;
}

// Buttonコンポーネント
function Button() {
  return <button>クリック</button>;
}

// Appコンポーネント（他のコンポーネントを組み合わせる）
function App() {
  return (
    <div>
      <Header />
      <Button />
      <Button />
    </div>
  );
}

利点:

  • 再利用: 同じ部品を何度も使える
  • 保守性: 部品ごとに修正できる
  • テスト: 部品単位でテストできる

JSXの仕組み

📚 このページで学ぶこと
  • JSXとは何か
  • JSXがJavaScriptに変換される仕組み
  • JSX内での式の埋め込み

JSXとは

JSX（JavaScript XML）は、JavaScript内にHTMLっぽく書ける構文です。 

// これがJSX
const element = <h1>Hello, World!</h1>;

見た目はHTMLですが、これはJavaScriptの一部です。

JSXはJavaScriptに変換される

JSXはブラウザが直接理解できません。
ビルド時にReact.createElement()の呼び出しに変換されます。

変換の例
// JSX（書くコード）
const element = <h1 className="title">Hello</h1>;

// 変換後（実際に実行されるコード）
const element = React.createElement(
  'h1',
  { className: 'title' },
  'Hello'
);

React.createElement(タグ名, 属性, 子要素)という関数呼び出しになります。

💡 なぜJSXを使う？

createElement()を直接書くのは大変。
JSXなら直感的にUIを書ける。

JSXのルール

1. classではなくclassName

// ❌ HTMLのclass属性は使えない
<div class="container"></div>

// ⭕ classNameを使う
<div className="container"></div>

理由: classはJavaScriptの予約語（クラス定義に使う）だから。

2. 単一のルート要素が必要

// ❌ 複数のルート要素は不可
return (
  <h1>タイトル</h1>
  <p>本文</p>
);

// ⭕ 1つの要素で囲む
return (
  <div>
    <h1>タイトル</h1>
    <p>本文</p>
  </div>
);

// ⭕ Fragment(<></>)でも可（余分なDOMを作らない）
return (
  <>
    <h1>タイトル</h1>
    <p>本文</p>
  </>
);

3. タグは必ず閉じる

// ❌ 自己終了タグがない
<img src="image.png">
<input type="text">

// ⭕ 自己終了タグが必要
<img src="image.png" />
<input type="text" />

式の埋め込み

{ }の中にJavaScriptの式を書けます。 

const name = "田中";
const age = 25;

// 変数を埋め込む
<p>名前: {name}</p>

// 計算を埋め込む
<p>来年の年齢: {age + 1}</p>

// 関数呼び出しを埋め込む
<p>大文字: {name.toUpperCase()}</p>

// 三項演算子（条件分岐）
<p>{age >= 20 ? "成人" : "未成年"}</p>
⚠️ { }の中に書けないもの

文（statement）は書けません。式（expression）のみ。 

// ❌ if文は書けない
<p>{if (age >= 20) { "成人" }}</p>

// ⭕ 三項演算子（式）なら書ける
<p>{age >= 20 ? "成人" : "未成年"}</p>

コンポーネントとProps

📚 このページで学ぶこと
  • 関数コンポーネントの書き方
  • Props（親から子へのデータ渡し）
  • TypeScriptでのProps型定義

関数コンポーネント

コンポーネントはJSXを返す関数です。 

// 最もシンプルなコンポーネント
function Greeting() {
  return <h1>こんにちは！</h1>;
}

// 使い方
function App() {
  return (
    <div>
      <Greeting />
    </div>
  );
}

ルール: コンポーネント名は大文字で始める（PascalCase）

コンポーネントツリーとデータの流れ（図解）

Reactアプリはコンポーネントのツリー構造で構成されます。データは親から子へ一方向に流れます。

重要：データは常に上から下へ流れます（単方向データフロー）。子から親へ直接データを渡すことはできません。

Props（プロップス）

Props = 親コンポーネントから子コンポーネントに渡すデータ 

// 子コンポーネント: propsを受け取る
function Greeting({ name }) {
  return <h1>こんにちは、{name}さん！</h1>;
}

// 親コンポーネント: propsを渡す
function App() {
  return (
    <div>
      <Greeting name="田中" />
      <Greeting name="佐藤" />
    </div>
  );
}

// 結果:
// こんにちは、田中さん！
// こんにちは、佐藤さん！

Propsは読み取り専用

🔴 最重要ルール

Propsを直接変更してはいけない

❌ 絶対にやってはいけない 
function UserCard({ user }) {
  // ❌ Propsを直接変更（Reactのルール違反）
  user.name = "変更された名前";  // 絶対ダメ！

  return <p>{user.name}</p>;
}

理由: Propsの変更は予測不能なバグを引き起こす。
親から渡されたデータを勝手に変えると、他の部分にも影響する。

✓ 正しい方法: 親に変更を依頼する 
// 子コンポーネント
function UserCard({ user, onUpdate }) {
  const handleClick = () => {
    // 親に変更を依頼（新しいオブジェクトを渡す）
    onUpdate({ ...user, name: "新しい名前" });
  };

  return (
    <div>
      <p>{user.name}</p>
      <button onClick={handleClick}>名前変更</button>
    </div>
  );
}

// 親コンポーネント
function App() {
  const [user, setUser] = useState({ name: "田中" });

  return <UserCard user={user} onUpdate={setUser} />;
}

TypeScriptでのProps型定義

TypeScriptではPropsの型を定義します。

✓ 推奨: interfaceでProps型を定義 
// Propsの型を定義
interface ButtonProps {
  label: string;
  onClick: () => void;
  disabled?: boolean;  // ?は省略可能
}

// 型を適用
function Button({ label, onClick, disabled = false }: ButtonProps) {
  return (
    <button onClick={onClick} disabled={disabled}>
      {label}
    </button>
  );
}
⚠️ レビューで指摘: Props型定義なし 
// ❌ 型定義なし（何が渡されるかわからない）
function Button({ label, onClick, disabled }) {
  // ...
}

// ⭕ 型定義あり（明確）
function Button({ label, onClick, disabled }: ButtonProps) {
  // ...
}

childrenプロパティ

タグの中身はchildrenというPropsで受け取れます。 

interface CardProps {
  title: string;

}

function Card({ title, children }: CardProps) {
  return (
    <div className="card">

// 使い方

  <p>ここがchildrenになる</p>
  <p>複数の要素もOK</p>

useState

📚 このページで学ぶこと
  • stateとは何か
  • useStateの使い方

stateとは

state（状態）= コンポーネントが持つ「変更可能なデータ」

Propsは親から渡されて変更不可。
stateは自分で持ち、自分で変更できる。

Props vs State
- Props State
データの出所 親から渡される 自分で持つ
変更 できない（読み取り専用） できる（setXxxで更新）

useStateの基本

import { useState } from 'react';

function Counter() {
  // [現在の値, 更新関数] = useState(初期値)
  const [count, setCount] = useState(0);

  return (
    <div>
      <p>カウント: {count}</p>
      <button onClick={() => setCount(count + 1)}>
        +1
      </button>
    </div>
  );
}

useState(初期値)は配列を返す:

  1. count: 現在の値
  2. setCount: 値を更新する関数

TypeScriptでの型指定

// 型推論が効く場合（初期値から推論）
const [count, setCount] = useState(0);  // number型と推論

// 明示的に型を指定
const [name, setName] = useState<string>("");

// nullを含む場合
const [user, setUser] = useState<User | null>(null);

// 配列の場合
const [items, setItems] = useState<string[]>([]);

状態更新の重要ルール

1. 更新は非同期

⚠️ よくある間違い 
function Counter() {
  const [count, setCount] = useState(0);

  const handleClick = () => {
    setCount(count + 1);
    console.log(count);  // まだ0のまま！（更新は非同期）
  };
}

setCountを呼んでも、その時点ではcountは更新されていない。

2. 直接変更してはいけない

❌ 絶対にやってはいけない 
const [items, setItems] = useState(["a", "b"]);

// ❌ 配列を直接変更（Reactが変更を検知できない）
items.push("c");  // ダメ！

// ❌ オブジェクトを直接変更
const [user, setUser] = useState({ name: "田中" });
user.name = "佐藤";  // ダメ！
✓ 正しい方法: 新しい配列/オブジェクトを作る 
// ⭕ スプレッド構文で新しい配列を作る
setItems([...items, "c"]);

// ⭕ スプレッド構文で新しいオブジェクトを作る
setUser({ ...user, name: "佐藤" });

3. 前の値を使う場合は関数形式

✓ 推奨: 関数形式のセッター 
// ❌ 古い値を参照する可能性
setCount(count + 1);

// ⭕ 前の値を確実に使える
setCount(prev => prev + 1);

// 連続で呼ぶ場合の違い
// ❌ これは1しか増えない
setCount(count + 1);
setCount(count + 1);

// ⭕ これは2増える
setCount(prev => prev + 1);
setCount(prev => prev + 1);

イベントハンドリング

📚 このページで学ぶこと

  • onClick, onChange, onSubmit
  • よくある間違い

基本的なイベント処理

function Button() {
  const handleClick = () => {
    console.log("クリックされました");
  };

  return (
    <button onClick={handleClick}>
      クリック
    </button>
  );
}

ポイント: イベント名はcamelCase（onClick, onChangeなど）

よく使うイベント

// クリック
<button onClick={handleClick}>ボタン</button>

// 入力変更
<input onChange={handleChange} />

// フォーム送信
<form onSubmit={handleSubmit}>...</form>

// フォーカス
<input onFocus={handleFocus} onBlur={handleBlur} />

// キー入力
<input onKeyDown={handleKeyDown} />

イベントオブジェクト

function Form() {
  const [value, setValue] = useState("");

  // event（イベントオブジェクト）を受け取る
  const handleChange = (e: React.ChangeEvent<HTMLInputElement>) => {
    setValue(e.target.value);  // 入力値を取得
  };

  const handleSubmit = (e: React.FormEvent<HTMLFormElement>) => {
    e.preventDefault();  // デフォルト動作（ページ遷移）を防ぐ
    console.log("送信:", value);
  };

  return (
    <form onSubmit={handleSubmit}>
      <input value={value} onChange={handleChange} />
      <button type="submit">送信</button>
    </form>
  );
}

よくある間違い

🔴 最重要: 関数を渡す vs 関数を呼び出す 
// ❌ 関数を呼び出している（即座に実行される！）
<button onClick={handleClick()}>クリック</button>

// ⭕ 関数を渡している（クリック時に実行）
<button onClick={handleClick}>クリック</button>

違い:

  • handleClick: 関数そのものを渡す
  • handleClick(): 関数を今すぐ実行して、その結果を渡す

引数を渡したい場合

// 引数を渡す場合はアロー関数で包む
<button onClick={() => handleDelete(item.id)}>
  削除
</button>

// ❌ これは即座に実行される
<button onClick={handleDelete(item.id)}>
  削除
</button>

TypeScriptでのイベント型

📝 よく使うイベント型 
// クリックイベント
React.MouseEvent<HTMLButtonElement>

// 入力変更
React.ChangeEvent<HTMLInputElement>

// フォーム送信
React.FormEvent<HTMLFormElement>

// キーボード
React.KeyboardEvent<HTMLInputElement>

条件付きレンダリングとは

条件によって表示するUIを変えることです。

例: ログイン状態によって表示を切り替える

&& 演算子

「条件がtrueの場合だけ表示」という場合に使います。 

function Notification({ count }: { count: number }) {
  return (
    <div>
      {/* countが0より大きい場合だけ表示 */}
      {count > 0 && <span>{count}件の通知</span>}
    </div>
  );
}

// count = 3 の場合: "3件の通知" が表示
// count = 0 の場合: 何も表示されない
⚠️ 注意: 0 は falsy だが表示される 
// ❌ countが0の場合、"0" が表示されてしまう
{count && <span>{count}件</span>}

// ⭕ 明示的に比較する
{count > 0 && <span>{count}件</span>}

三項演算子

「条件によって2つのUIを切り替える」場合に使います。 

function LoginStatus({ isLoggedIn }: { isLoggedIn: boolean }) {
  return (
    <div>
      {isLoggedIn ? (
        <button>ログアウト</button>
      ) : (
        <button>ログイン</button>
      )}
    </div>
  );
}

early return

条件に合わない場合は早めにreturnするパターンです。

✓ 推奨: early return 
function UserProfile({ user }: { user: User | null }) {
  // nullの場合は早めにreturn
  if (!user) {
    return <p>ユーザーが見つかりません</p>;
  }

  // ここからはuserが必ず存在する
  return (
    <div>
      <h1>{user.name}</h1>
      <p>{user.email}</p>
    </div>
  );
}

利点:

  • ネストが深くならない
  • コードが読みやすい
  • TypeScriptの型絞り込みが効く

使い分け

パターン 使う場面
&& 表示する/しないの2択
三項演算子 AかBかの2択
early return 異常系を先に処理

リストとkey

📚 このページで学ぶこと
  • map()でリスト描画
  • keyの役割
  • key={index}が危険な理由

map()でリスト描画

配列のデータをmap()でJSXに変換します。 

interface Todo {
  id: string;
  text: string;
}

function TodoList({ todos }: { todos: Todo[] }) {
  return (
    <ul>
      {todos.map(todo => (
        <li key={todo.id}>{todo.text}</li>
      ))}
    </ul>
  );
}

keyとは

keyは、Reactがどの要素が変わったかを識別するための属性です。

💡 なぜkeyが必要？

Reactは仮想DOMの差分を計算して効率的に更新します。
keyがあると、どの要素が追加/削除/移動されたかを正確に判断できます。

key={index}は危険

🔴 レビューで必ず指摘: key={index} 
// ❌ indexをkeyにする（危険！）
{todos.map((todo, index) => (
  <li key={index}>{todo.text}</li>
))}

// ⭕ 一意のIDをkeyにする
{todos.map(todo => (
  <li key={todo.id}>{todo.text}</li>
))}

なぜ危険か？

index をkeyにした場合の問題

リストの先頭に要素を追加した場合: 

// 追加前
["A", "B", "C"]  // key: 0, 1, 2

// 先頭に "X" を追加
["X", "A", "B", "C"]  // key: 0, 1, 2, 3

// Reactの解釈（indexがkey）:
// key=0 が "A" → "X" に変わった（更新）
// key=1 が "B" → "A" に変わった（更新）
// key=2 が "C" → "B" に変わった（更新）
// key=3 が新規追加（"C"）

// 本当は "X" だけ追加すればいいのに、全部更新される！

問題点:

  • パフォーマンス低下（全要素が再レンダリング）
  • 入力値やフォーカスが失われる
  • アニメーションが正しく動かない

正しいkeyの選び方

✓ keyにすべきもの
  • データベースのID（最も推奨）
  • uuid などで生成した一意の値
  • データの中で一意な値（メールアドレスなど）
⚠️ indexを使っていい場合（限定的）
  • リストが固定で変更されない
  • 要素の並び替えがない
  • 要素の追加・削除がない

→ 実務では一意のIDを使う方が安全

  // 200行以上のコード...

// ⭕ 責務ごとにコンポーネントを分割
function UserPage() {

}

function UserProfile() { /* ユーザー情報のみ */ }
function PostList() { /* 投稿一覧のみ */ }
function CommentSection() { /* コメント機能のみ */ }

コンポーネントを分割する基準

分割を検討すべきとき
  • 100行を超えた: 大きすぎる
  • 複数の責務がある: 表示と入力処理が混在など
  • 再利用したい: ボタン、カードなど
  • 条件分岐が複雑: 早期returnで分けられる

props drilling問題

props drilling = 深いコンポーネント階層でpropsをバケツリレーすること

⚠️ 問題: バケツリレーが深い 
// App → Header → UserMenu → UserIcon と渡していく
function App() {
  const user = { name: "田中", avatar: "..." };
  return <Header user={user} />;
}

function Header({ user }) {
  return <UserMenu user={user} />;  // 中継するだけ
}

function UserMenu({ user }) {
  return <UserIcon user={user} />;  // 中継するだけ
}

function UserIcon({ user }) {
  return <img src={user.avatar} />;  // やっと使う
}

問題点:

  • 中間のコンポーネントが不要なpropsを受け取る
  • コードが冗長になる
  • propsの追加/変更が大変
✓ 解決策
  • Context: グローバルに共有したいデータに使う
  • 状態管理ライブラリ: Zustand, Jotaiなど
  • コンポーネント構造の見直し: 必要な場所で直接データを取得

まとめ: コンポーネント設計の指針

✓ 設計のチェックリスト
  • 1コンポーネント1責務になっているか
  • 100行を大きく超えていないか
  • Propsの型が定義されているか
  • props drillingが深くなりすぎていないか
  • 再利用可能な部品として設計されているか
