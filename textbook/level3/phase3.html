useEffect基礎

副作用（Side Effect）とは、コンポーネントの「レンダリング以外の処理」のことです。 データ取得、DOM操作、タイマー設定など。useEffectはこれらを安全に実行するためのHooksです。

副作用とは何か

純粋関数（Pure Function）= 同じ入力には常に同じ出力を返す関数

副作用（Side Effect）= 関数の外部に影響を与える処理

純粋関数と副作用の例
// 純粋関数：外部に影響しない
function add(a, b) {
  return a + b;
}

// 副作用を持つ関数：外部に影響する
function logAndAdd(a, b) {
  console.log(`計算中: ${a} + ${b}`);  // 副作用: コンソール出力
  fetch('/api/log', { method: 'POST' }); // 副作用: ネットワーク通信
  return a + b;
}

Reactコンポーネントでの副作用の例：

  • API呼び出し（データフェッチ）
  • イベントリスナーの登録
  • タイマーの設定（setTimeout, setInterval）
  • ローカルストレージの読み書き
  • DOM要素への直接アクセス

useEffectの基本構文

useEffectの構文
import { useEffect } from 'react';

function Component() {
  useEffect(() => {
    // 副作用の処理
    console.log('コンポーネントがレンダリングされた');

    // クリーンアップ関数（省略可）
    return () => {
      console.log('クリーンアップ実行');
    };
  }, [依存配列]); // 依存配列

  return <div>...</div>;
}

3つの要素：

  1. 副作用関数：実行したい処理
  2. クリーンアップ関数：副作用を解除する処理（return文）
  3. 依存配列：いつ再実行するかを指定

実行タイミング（依存配列の違い）

依存配列による実行タイミングの違い
// パターン1: 毎回実行（依存配列なし）
useEffect(() => {
  console.log('毎回のレンダリング後に実行');
});

// パターン2: マウント時のみ（空配列）
useEffect(() => {
  console.log('最初の1回だけ実行');
}, []);

// パターン3: 特定の値が変わったとき
useEffect(() => {
  console.log(`countが${count}に変わった`);
}, [count]);

// パターン4: 複数の値のどれかが変わったとき
useEffect(() => {
  console.log('countまたはnameが変わった');
}, [count, name]);
依存配列 実行タイミング 使用例
なし（省略） 毎回のレンダリング後 ほぼ使わない（パフォーマンス問題）
[]（空配列） マウント時のみ 初期化処理、API初回呼び出し
[value] valueが変わったとき 値に応じたデータ取得

useEffect実践

useEffectの実践的なパターンを学びます。 データフェッチ、イベント購読、タイマーの3大ユースケースを押さえましょう。

データフェッチの例

userIdに応じてデータを取得
function UserProfile({ userId }) {
  const [user, setUser] = useState(null);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState(null);

  useEffect(() => {
    // フラグでマウント状態を追跡
    let isMounted = true;

    async function fetchUser() {
      setLoading(true);
      setError(null);

      try {
        const response = await fetch(`/api/users/${userId}`);
        const data = await response.json();

        // アンマウント後にsetStateしない
        if (isMounted) {
          setUser(data);
        }
      } catch (err) {
        if (isMounted) {
          setError(err.message);
        }
      } finally {
        if (isMounted) {
          setLoading(false);
        }
      }
    }

    fetchUser();

    // クリーンアップ：フラグをfalseに
    return () => {
      isMounted = false;
    };
  }, [userId]); // userIdが変わったら再取得

  if (loading) return <p>読み込み中...</p>;
  if (error) return <p>エラー: {error}</p>;
  return <p>{user?.name}</p>;
}

2026年の推奨：TanStack Query

実務ではuseEffectで直接fetchせず、TanStack Query（旧React Query）を使うことが推奨されます。

理由：キャッシュ、再取得、ローディング状態の管理が自動化される

購読（Subscription）の例

ウィンドウリサイズの購読
function WindowSize() {
  const [size, setSize] = useState({
    width: window.innerWidth,
    height: window.innerHeight,
  });

  useEffect(() => {
    // イベントハンドラを定義
    function handleResize() {
      setSize({
        width: window.innerWidth,
        height: window.innerHeight,
      });
    }

    // イベントリスナーを登録
    window.addEventListener('resize', handleResize);

    // クリーンアップ：リスナーを解除
    return () => {
      window.removeEventListener('resize', handleResize);
    };
  }, []); // マウント時に1回だけ登録

  return <p>{size.width} x {size.height}</p>;
}

タイマーの例

カウントダウンタイマー
function Countdown({ initialSeconds }) {
  const [seconds, setSeconds] = useState(initialSeconds);

  useEffect(() => {
    // 0以下なら何もしない
    if (seconds <= 0) return;

    // 1秒ごとにカウントダウン
    const timerId = setInterval(() => {
      setSeconds(prev => prev - 1);
    }, 1000);

    // クリーンアップ：タイマーをクリア
    return () => {
      clearInterval(timerId);
    };
  }, [seconds]); // secondsが変わるたびに再設定

  return <p>残り: {seconds}秒</p>;
}

注意：setIntervalの罠

上の例は正しいですが、依存配列にsecondsを入れると毎秒クリア＆再設定されます。

より効率的な実装はuseRefを使う方法（後述）です。

useEffectの競合状態（Race Condition）

非同期処理を伴うuseEffectでは、レスポンスの到着順序が保証されないため、古いデータが新しいデータを上書きしてしまう問題が起こります。

❌ よくある間違い
// レスポンスの順序を考慮しない
useEffect(() => {
  fetch(`/api/users/${userId}`)
    .then(res => res.json())
    .then(data => setUser(data));
  // userId=1のレスポンスが遅延し
  // userId=2の後に届くと古いデータで上書き
}, [userId]);
⭕ 正しい方法
// AbortControllerでクリーンアップ
useEffect(() => {
  const controller = new AbortController();

  fetch(`/api/users/${userId}`, {
    signal: controller.signal
  })
    .then(res => res.json())
    .then(data => setUser(data))
    .catch(err => {
      if (err.name !== 'AbortError') throw err;
    });

  return () => controller.abort();
}, [userId]);
🔍 コードレビューの観点
  • isMountedフラグなし → アンマウント後のsetStateでWarning
  • クリーンアップなし → イベントリスナー、タイマーの蓄積（メモリリーク）
  • useEffect内で直接async → 非推奨（内部で関数定義すべき）
  • 競合状態の未対策 → AbortControllerまたはstale closureチェックがない
  • Hooksルール違反 → 条件分岐やループの中でHooksを呼んでいる
  • 依存配列の欠落 → ESLint react-hooks/exhaustive-deps の警告を無視している
  • Stale closure問題 → useEffect内で古い値を参照し続けている
よくある間違い：useEffectを直接asyncにする
// ❌ useEffectにasyncを直接つけるのはNG
useEffect(async () => {
  const data = await fetch('/api/data');
  // ...
}, []);

// ⭕ 内部で関数を定義して呼び出す
useEffect(() => {
  async function fetchData() {
    const data = await fetch('/api/data');
    // ...
  }
  fetchData();
}, []);
❓ 確認クイズ

イベントリスナーを登録するuseEffectで、クリーンアップ関数を書かないと何が起こりますか？

useEffectの罠（★最重要）

useEffectは最もバグを生みやすいHooksです。 レビューで最も指摘が多い問題を徹底的に学びます。

罠1：依存配列の欠落（最も多いバグ）

依存配列の欠落の例
// ❌ 依存配列が空：userIdが変わっても再実行されない
function UserProfile({ userId }) {
  const [user, setUser] = useState(null);

  useEffect(() => {
    fetchUser(userId).then(setUser);
  }, []); // ← userIdが欠落！

  return <p>{user?.name}</p>;
}

// ⭕ 依存配列にuserIdを追加
useEffect(() => {
  fetchUser(userId).then(setUser);
}, [userId]); // ← userIdが変わったら再実行

結果：userIdが「1」から「2」に変わっても、古いuser（ID=1）が表示されたまま

発見方法：ESLintのreact-hooks/exhaustive-depsルールを有効にする

罠2：無限ループ（オブジェクトを依存配列に入れる）

無限ループの例
// ❌ 毎回新しいオブジェクトが生成される
function Parent() {
  const options = { sortBy: 'name' }; // 毎レンダリングで新しい参照

  return <Child options={options} />;
}

function Child({ options }) {
  const [data, setData] = useState([]);

  useEffect(() => {
    fetchData(options).then(setData);
  }, [options]); // ← optionsが毎回「違う」と判定される

  return <ul>{data.map(...)}</ul>;
}
// 結果：レンダリング → useEffect → setData → 再レンダリング → 無限ループ
解決策：useMemoで参照を安定させる
// ⭕ useMemoでオブジェクトの参照を安定させる
function Parent() {
  const options = useMemo(() => ({ sortBy: 'name' }), []);
  return <Child options={options} />;
}

// または、個別のプリミティブ値を依存配列に
useEffect(() => {
  fetchData({ sortBy: options.sortBy });
}, [options.sortBy]); // プリミティブ値なら安定

なぜ起こる？JavaScriptでは{} !== {}（オブジェクトは参照で比較）

罠3：クリーンアップ忘れ（メモリリーク）

クリーンアップ忘れの例
// ❌ クリーンアップなし：タイマーが残り続ける
function Timer() {
  const [count, setCount] = useState(0);

  useEffect(() => {
    const id = setInterval(() => {
      setCount(c => c + 1);
    }, 1000);
    // return がない！
  }, []);

  return <p>{count}</p>;
}

// ⭕ クリーンアップでタイマーを解除
useEffect(() => {
  const id = setInterval(() => {
    setCount(c => c + 1);
  }, 1000);

  return () => clearInterval(id); // クリーンアップ
}, []);

結果：コンポーネントがアンマウントされてもタイマーが動き続ける（メモリリーク）

クリーンアップが必要なケース：

  • イベントリスナー（addEventListener）
  • タイマー（setInterval, setTimeout）
  • WebSocket接続
  • 購読（subscription）

Hooksのルール違反

条件の中でHooksを呼ぶ（NG）
// ❌ 条件の中でHooks（Reactのルール違反）
function Component({ isLoggedIn }) {
  if (isLoggedIn) {
    useEffect(() => {
      // ...
    }, []);
  }
  // Reactはエラーを出すか、予測不能な動作に
}

// ⭕ Hooksはトップレベルで呼び、条件は内部で
function Component({ isLoggedIn }) {
  useEffect(() => {
    if (isLoggedIn) {
      // ...
    }
  }, [isLoggedIn]);
}

なぜNG？ReactはHooksの呼び出し順で状態を管理している。条件分岐で順序が変わると壊れる。

レビューで必ず確認すべきポイント

問題 指摘例 危険度
依存配列の欠落 「〇〇を依存配列に追加すべき」 🔴 最高
クリーンアップなし 「return文でクリーンアップすべき」 🔴 最高
条件内でHooks 「Hooksはトップレベルで呼ぶべき」 🔴 最高
オブジェクトを依存配列に 「useMemoで参照を安定させるべき」 高
🔍 コードレビューの観点：Stale Closure（古いクロージャ）

useEffect内のコールバックが、古い変数の値を掴んだままになる問題です。

❌ よくある間違い
function Counter() {
  const [count, setCount] = useState(0);

  useEffect(() => {
    const id = setInterval(() => {
      // countは常に0（古い値）
      console.log(count);
      setCount(count + 1); // 常に1になる
    }, 1000);
    return () => clearInterval(id);
  }, []); // countが依存配列にない
}
⭕ 正しい方法
function Counter() {
  const [count, setCount] = useState(0);

  useEffect(() => {
    const id = setInterval(() => {
      // 関数形式で最新の値を取得
      setCount(prev => prev + 1);
    }, 1000);
    return () => clearInterval(id);
  }, []); // setCountの関数形式なら安全
}

useRef

useRefは「再レンダリングを引き起こさない」値を保持するためのHooksです。 DOM要素への参照や、レンダリング間で保持したい値に使います。

useRefの基本

useRefの構文
import { useRef } from 'react';

function Component() {
  // 初期値を設定
  const countRef = useRef(0);

  // .current プロパティで値にアクセス
  console.log(countRef.current); // 0

  // 値を更新（再レンダリングは起こらない）
  countRef.current = 1;

  return <div>...</div>;
}

useStateとの違い：

特性 useState useRef
値の更新 再レンダリングを引き起こす 再レンダリングしない
用途 UIに反映する値 UIに反映しない値、DOM参照
アクセス方法 直接（value） .current経由

ユースケース1：DOM要素へのアクセス

input要素にフォーカスを当てる
function TextInput() {
  const inputRef = useRef<HTMLInputElement>(null);

  const handleClick = () => {
    // DOM要素に直接アクセス
    inputRef.current?.focus();
  };

  return (
    <>
      <input ref={inputRef} type="text" />
      <button onClick={handleClick}>フォーカス</button>
    </>
  );
}

TypeScriptでの型：

  • useRef<HTMLInputElement>(null) - input要素
  • useRef<HTMLDivElement>(null) - div要素
  • useRef<HTMLButtonElement>(null) - button要素

ユースケース2：値の保持（再レンダリングなし）

前回の値を保持する
function Counter() {
  const [count, setCount] = useState(0);
  const prevCountRef = useRef<number>();

  useEffect(() => {
    // レンダリング後に前回の値を保存
    prevCountRef.current = count;
  });

  return (
    <div>
      <p>現在: {count}</p>
      <p>前回: {prevCountRef.current}</p>
      <button onClick={() => setCount(c => c + 1)}>
        増やす
      </button>
    </div>
  );
}
タイマーIDを保持する
function Stopwatch() {
  const [time, setTime] = useState(0);
  const timerRef = useRef<number | null>(null);

  const start = () => {
    // すでに動いていたら何もしない
    if (timerRef.current !== null) return;

    timerRef.current = setInterval(() => {
      setTime(t => t + 1);
    }, 1000);
  };

  const stop = () => {
    if (timerRef.current !== null) {
      clearInterval(timerRef.current);
      timerRef.current = null;
    }
  };

  return (
    <div>
      <p>{time}秒</p>
      <button onClick={start}>開始</button>
      <button onClick={stop}>停止</button>
    </div>
  );
}

レビューで指摘すべきポイント

  • UIに反映する値にuseRef → useStateを使うべき
  • .currentの初期値null忘れ → DOM参照は初期値nullにする
  • ref.currentを依存配列に入れる → 意味がない（変更を検知しない）
間違い例：UIに反映する値にuseRef
// ❌ UIに表示する値にuseRefは不適切
function Counter() {
  const countRef = useRef(0);

  const increment = () => {
    countRef.current += 1;
    // UIは更新されない！
  };

  return <p>{countRef.current}</p>; // 常に初期値0
}

// ⭕ UIに反映するならuseState
function Counter() {
  const [count, setCount] = useState(0);
  return <p>{count}</p>;
}

useRefとuseStateの違いとして正しいのはどれですか？

useContext

useContextは、コンポーネントツリー全体でデータを共有するためのHooksです。 「Props drilling」（深いバケツリレー）を解消します。

Contextとは（グローバル状態共有）

Props drilling の問題：

Props drilling の例
// ❌ 深いバケツリレー
function App() {
  const [theme, setTheme] = useState('light');
  return <Header theme={theme} />;
}

function Header({ theme }) {
  return <Nav theme={theme} />; // 使わないのに渡す
}

function Nav({ theme }) {
  return <Button theme={theme} />; // 使わないのに渡す
}

function Button({ theme }) {
  return <button className={theme}>Click</button>; // ここで使う
}

Contextで解決：

Context を使った例
// ⭕ Contextで直接アクセス
const ThemeContext = createContext('light');

function App() {
  const [theme, setTheme] = useState('light');
  return (
    <ThemeContext.Provider value={theme}>
      <Header /> {/* themeを渡さない */}
    </ThemeContext.Provider>
  );
}

function Button() {
  const theme = useContext(ThemeContext); // 直接取得
  return <button className={theme}>Click</button>;
}

Context の3ステップ

Step 1: createContext で作成
import { createContext } from 'react';

// 初期値を設定（型推論のため）
interface User {
  id: number;
  name: string;
}

const UserContext = createContext<User | null>(null);
Step 2: Provider で値を提供
function App() {
  const [user, setUser] = useState<User | null>({
    id: 1,
    name: 'Alice'
  });

  return (
    <UserContext.Provider value={user}>
      <Dashboard />
    </UserContext.Provider>
  );
}
Step 3: useContext で取得
function UserProfile() {
  const user = useContext(UserContext);

  if (!user) return <p>ログインしてください</p>;

  return <p>{user.name}さん、こんにちは</p>;
}

Context の注意点（パフォーマンス）

問題：Context の値が変わると、useContext を使っている全てのコンポーネントが再レンダリングされる

パフォーマンス問題の例
// ❌ 全ての値を1つのContextに入れる
const AppContext = createContext({
  user: null,
  theme: 'light',
  notifications: [],
  // ...大量の状態
});

// themeだけ変わっても、user や notifications を使うコンポーネントも再レンダリング
解決策：Contextを分割する
// ⭕ 関連する状態ごとにContextを分ける
const UserContext = createContext(null);
const ThemeContext = createContext('light');
const NotificationContext = createContext([]);

// themeが変わっても、UserContextを使うコンポーネントは再レンダリングされない

実務では：高頻度で更新される状態は、ZustandやJotaiなどの状態管理ライブラリを使う

レビューで指摘すべきポイント

  • 巨大なContext → 分割を検討すべき
  • 高頻度更新をContextで → Zustand等を検討すべき
  • Provider外でuseContext → undefinedになる

Contextのパフォーマンス問題を軽減する方法として適切なのは？

useReducer

useReducerは、複雑な状態更新ロジックを管理するためのHooksです。 Reduxパターンに基づいた「action」と「reducer」を使います。

複雑な状態更新の問題

useStateで複雑な状態を扱う問題
// ❌ 複数のsetStateが散らばる
function ShoppingCart() {
  const [items, setItems] = useState([]);
  const [total, setTotal] = useState(0);
  const [discount, setDiscount] = useState(0);

  const addItem = (item) => {
    setItems([...items, item]);
    setTotal(total + item.price);
    // discountも再計算...
  };

  const removeItem = (id) => {
    setItems(items.filter(i => i.id !== id));
    // totalも再計算...
  };

  // 状態更新ロジックがバラバラで管理しづらい
}

useReducerの構文

useReducerの基本形
import { useReducer } from 'react';

// 状態の型
interface State {
  count: number;
}

// アクションの型
type Action =
  | { type: 'increment' }
  | { type: 'decrement' }
  | { type: 'reset'; payload: number };

// reducer関数：現在の状態とアクションから新しい状態を返す
function reducer(state: State, action: Action): State {
  switch (action.type) {
    case 'increment':
      return { count: state.count + 1 };
    case 'decrement':
      return { count: state.count - 1 };
    case 'reset':
      return { count: action.payload };
    default:
      return state;
  }
}

function Counter() {
  // useReducer(reducer関数, 初期状態)
  const [state, dispatch] = useReducer(reducer, { count: 0 });

  return (
    <div>
      <p>{state.count}</p>
      <button onClick={() => dispatch({ type: 'increment' })}>
        +1
      </button>
      <button onClick={() => dispatch({ type: 'decrement' })}>
        -1
      </button>
      <button onClick={() => dispatch({ type: 'reset', payload: 0 })}>
        リセット
      </button>
    </div>
  );
}

3つの要素：

  1. state：現在の状態
  2. dispatch：アクションを発行する関数
  3. reducer：状態の更新ロジックをまとめた関数

useStateとの使い分け

状況 推奨
単純な値（数値、文字列、真偽値） useState
オブジェクト・配列（少数のプロパティ） useState
複数の状態が連動して更新される useReducer
更新ロジックが複雑（複数のswitch分岐） useReducer
状態更新を別ファイルでテストしたい useReducer

実務での判断：「3つ以上のsetStateが連動する」or「更新パターンが3種類以上」ならuseReducer検討

useMemo / useCallback

useMemoとuseCallbackは、パフォーマンス最適化のためのHooksです。 計算結果や関数を「メモ化」して、不要な再計算・再生成を防ぎます。

メモ化（Memoization）とは

メモ化 = 計算結果をキャッシュして、同じ入力なら再計算せずに返す

メモ化の概念
// メモ化なし：毎回計算
function slowCalculation(n) {
  // 重い処理...
  return result;
}

// メモ化あり：同じnなら前回の結果を返す
const cache = new Map();
function memoizedCalculation(n) {
  if (cache.has(n)) {
    return cache.get(n); // キャッシュから返す
  }
  const result = slowCalculation(n);
  cache.set(n, result);
  return result;
}

useMemo：計算結果のメモ化

useMemoの例
import { useMemo } from 'react';

function FilteredList({ items, filter }) {
  // ❌ 毎回フィルタリングが実行される
  // const filteredItems = items.filter(item => item.includes(filter));

  // ⭕ items または filter が変わったときだけ再計算
  const filteredItems = useMemo(() => {
    console.log('フィルタリング実行');
    return items.filter(item => item.includes(filter));
  }, [items, filter]);

  return (
    <ul>
      {filteredItems.map(item => <li key={item}>{item}</li>)}
    </ul>
  );
}

いつ使う？

  • 計算コストが高い処理（大量のデータのフィルタリング・ソート）
  • オブジェクト・配列の参照を安定させたいとき

useCallback：関数のメモ化

useCallbackの例
import { useCallback } from 'react';

function Parent() {
  const [count, setCount] = useState(0);

  // ❌ 毎回新しい関数が生成される
  // const handleClick = () => setCount(c => c + 1);

  // ⭕ 依存配列の値が変わらない限り同じ関数を返す
  const handleClick = useCallback(() => {
    setCount(c => c + 1);
  }, []); // setCountは安定しているので依存不要

  return <ExpensiveChild onClick={handleClick} />;
}

// memo()でラップされた子コンポーネント
const ExpensiveChild = memo(function ExpensiveChild({ onClick }) {
  console.log('ExpensiveChild レンダリング');
  return <button onClick={onClick}>Click</button>;
});

いつ使う？

  • memo()でラップした子コンポーネントに関数を渡すとき
  • useEffectの依存配列に関数を入れるとき

2026年の豆知識：React Compiler

React Compiler（旧React Forget）が正式リリースされ、 useMemo/useCallbackを自動的に挿入してくれるようになりました。

つまり：

  • 新規プロジェクトでは手動のメモ化は不要になりつつある
  • 既存コードでは、過剰なuseMemo/useCallbackを削除してシンプルに
  • ただし「いつメモ化が必要か」を理解することは依然として重要

レビューで指摘すべきポイント

  • 過剰なメモ化 → シンプルな計算には不要（オーバーヘッドになる）
  • 依存配列の欠落 → 古い値を参照してバグに
  • memo()なしでuseCallback → 子が毎回レンダリングされるなら意味なし
過剰なメモ化の例
// ❌ シンプルな計算にuseMemoは不要
const doubled = useMemo(() => count * 2, [count]);

// ⭕ 直接計算で十分
const doubled = count * 2;

カスタムHooks

カスタムHooksは、再利用可能なロジックを抽出するためのパターンです。 「use」から始まる名前で、他のHooksを組み合わせて作ります。

カスタムHooksとは

問題：同じロジックが複数のコンポーネントで重複する

ロジックの重複
// ComponentA.tsx
function ComponentA() {
  const [data, setData] = useState(null);
  const [loading, setLoading] = useState(true);

  useEffect(() => {
    fetch('/api/dataA').then(res => res.json()).then(setData);
    setLoading(false);
  }, []);
  // ...
}

// ComponentB.tsx
function ComponentB() {
  const [data, setData] = useState(null);
  const [loading, setLoading] = useState(true);

  useEffect(() => {
    fetch('/api/dataB').then(res => res.json()).then(setData);
    setLoading(false);
  }, []);
  // ... 同じパターンの繰り返し
}

解決：カスタムHooksでロジックを抽出

カスタムHooksで抽出
// useFetch.ts（カスタムHooks）
function useFetch<T>(url: string) {
  const [data, setData] = useState<T | null>(null);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState<Error | null>(null);

  useEffect(() => {
    let isMounted = true;
    setLoading(true);

    fetch(url)
      .then(res => res.json())
      .then(data => {
        if (isMounted) setData(data);
      })
      .catch(err => {
        if (isMounted) setError(err);
      })
      .finally(() => {
        if (isMounted) setLoading(false);
      });

    return () => { isMounted = false; };
  }, [url]);

  return { data, loading, error };
}

// 使用する側
function ComponentA() {
  const { data, loading, error } = useFetch('/api/dataA');
  if (loading) return <p>読み込み中...</p>;
  return <p>{data?.name}</p>;
}

命名規則：「use」から始める

必須ルール：カスタムHooksはuseから始まる名前にする

命名の例
// ⭕ 正しい命名
function useLocalStorage(key) { ... }
function useWindowSize() { ... }
function useDebounce(value, delay) { ... }
function useOnClickOutside(ref, handler) { ... }

// ❌ 間違った命名（Hooksと認識されない）
function getLocalStorage(key) { ... }
function windowSizeHook() { ... }

なぜ重要？

  • ESLintがHooksのルール違反を検出できる
  • 他の開発者が「これはHooksだ」と認識できる
  • 内部でuseState等を使っていることが分かる

よく使われるカスタムHooksの例

useLocalStorage
function useLocalStorage<T>(key: string, initialValue: T) {
  const [value, setValue] = useState<T>(() => {
    const stored = localStorage.getItem(key);
    return stored ? JSON.parse(stored) : initialValue;
  });

  useEffect(() => {
    localStorage.setItem(key, JSON.stringify(value));
  }, [key, value]);

  return [value, setValue] as const;
}

// 使用例
function Settings() {
  const [theme, setTheme] = useLocalStorage('theme', 'light');
  return <button onClick={() => setTheme('dark')}>ダークモード</button>;
}
useDebounce
function useDebounce<T>(value: T, delay: number): T {
  const [debouncedValue, setDebouncedValue] = useState(value);

  useEffect(() => {
    const timer = setTimeout(() => {
      setDebouncedValue(value);
    }, delay);

    return () => clearTimeout(timer);
  }, [value, delay]);

  return debouncedValue;
}

// 使用例：検索入力の遅延
function Search() {
  const [query, setQuery] = useState('');
  const debouncedQuery = useDebounce(query, 300);
  // debouncedQueryが変わったときだけAPI呼び出し
}

レビューで指摘すべきポイント

  • useで始まらない名前 → Hooksの命名規則違反
  • コンポーネント内で定義 → ファイル外に抽出すべき
  • 過度に複雑なカスタムHooks → 分割を検討
  • 同じロジックが複数箇所に → カスタムHooksに抽出すべき

useState → サーバーサイドの状態管理

ReactのuseStateは「UIの状態を管理する仕組み」でした。 バックエンドにも「状態」があります。ただし管理方法が異なります。

概念の対比
// フロントエンド: useState でUIの状態管理
const [user, setUser] = useState(null);
const [cart, setCart] = useState([]);

// バックエンド: 状態はDB・セッション・キャッシュに保持
// Express + セッション
app.use(session({ secret: 'key', resave: false }));
app.get('/api/user', (req, res) => {
  const user = req.session.user; // セッションから状態取得
  res.json(user);
});

// DBに永続化された状態
const user = await db.users.findById(userId);
// Redisキャッシュに一時保存された状態
const cached = await redis.get(`user:${userId}`);

共通点：どちらも「現在の状態を保持し、変更を検知して処理する」仕組み

違い：フロントはメモリ上（リロードで消える）、バックエンドはDB/セッション/キャッシュ（永続化可能）

useEffect → サーバーサイドのライフサイクル

useEffectは「マウント時の初期化」と「アンマウント時のクリーンアップ」を管理しました。 バックエンドのサーバーにも同じライフサイクルがあります。

ライフサイクルの対比
// フロントエンド: useEffect のライフサイクル
useEffect(() => {
  // マウント時: 初期化処理
  const ws = new WebSocket('ws://localhost:3001');

  return () => {
    // アンマウント時: クリーンアップ
    ws.close();
  };
}, []);

// バックエンド: サーバーのライフサイクル
const server = app.listen(3000, () => {
  // 起動時: 初期化処理（DB接続、キャッシュウォームアップ）
  console.log('Server started');
  connectDatabase();
  initializeCache();
});

// Graceful Shutdown: クリーンアップ
process.on('SIGTERM', async () => {
  console.log('Shutting down gracefully...');
  await closeDatabase();       // DB接続を閉じる
  await flushCache();          // キャッシュを書き出す
  server.close();              // サーバーを停止
});

共通点：「開始時に初期化、終了時にクリーンアップ」という考え方は同じ

バックエンドでクリーンアップが重要な理由：DB接続の解放漏れ、ファイルハンドルの残存、未完了トランザクションの放置はサーバー障害につながる

カスタムHooks → バックエンドのサービス層

カスタムHooksは「再利用可能なロジックを分離する」パターンでした。 バックエンドではサービス層（Service Layer）が同じ役割を果たします。

ロジック分離の対比
// フロントエンド: カスタムHooksでロジック分離
function useAuth() {
  const [user, setUser] = useState(null);
  const login = async (email, password) => { /* ... */ };
  const logout = async () => { /* ... */ };
  return { user, login, logout };
}

// バックエンド: サービス層でロジック分離
// services/authService.ts
class AuthService {
  async login(email: string, password: string) { /* ... */ }
  async logout(userId: string) { /* ... */ }
  async validateToken(token: string) { /* ... */ }
}

// routes/auth.ts（ルーティング層はサービスを呼ぶだけ）
router.post('/login', async (req, res) => {
  const result = await authService.login(req.body.email, req.body.password);
  res.json(result);
});

共通の設計原則：

  • 関心の分離 — UI/ルーティングとビジネスロジックを分ける
  • 再利用性 — 同じロジックを複数箇所から呼び出せる
  • テスタビリティ — ロジック単体でテストできる

データフェッチ → REST API / GraphQLの設計

フロントエンドではfetchやTanStack QueryでAPIを「呼ぶ側」でした。 Level 4では「呼ばれる側」（APIを設計・実装する側）を学びます。

呼ぶ側 → 作る側
// フロントエンド: APIを呼ぶ側（Level 3で学んだ）
const { data, loading } = useFetch('/api/users/1');

// バックエンド: APIを作る側（Level 4で学ぶ）
// REST API
app.get('/api/users/:id', async (req, res) => {
  try {
    const user = await UserService.findById(req.params.id);
    if (!user) {
      return res.status(404).json({ error: 'User not found' });
    }
    res.json(user);
  } catch (error) {
    res.status(500).json({ error: 'Internal server error' });
  }
});

フロントの知識が活きるポイント：

  • 「どんなレスポンスが使いやすいか」をフロント視点で設計できる
  • ローディング状態やエラーハンドリングの必要性を理解している
  • 非同期処理の基本（async/await、Promise）を既に習得済み

エラーハンドリング → バックエンドのエラー戦略

フロントエンドではtry-catchやError Boundaryでエラーを処理しました。 バックエンドではこれがミドルウェアパターンに進化します。

エラーハンドリングの対比
// フロントエンド: コンポーネント単位のエラー処理
useEffect(() => {
  try {
    const data = await fetchData();
    setData(data);
  } catch (err) {
    setError(err.message); // UIにエラー表示
  }
}, []);

// バックエンド: Express エラーミドルウェア（一元管理）
// 各ルートでエラーを投げる
app.get('/api/users/:id', async (req, res, next) => {
  try {
    const user = await UserService.findById(req.params.id);
    if (!user) throw new NotFoundError('User not found');
    res.json(user);
  } catch (error) {
    next(error); // エラーミドルウェアに委譲
  }
});

// エラーミドルウェアで一元処理
app.use((err, req, res, next) => {
  const status = err.statusCode || 500;
  res.status(status).json({
    error: err.message,
    code: err.code,
  });
});

共通の考え方：「エラーを握りつぶさず、適切な粒度でハンドリングする」

バックエンドの進化ポイント：ミドルウェアパターンでエラー処理を一元化し、ルートハンドラをシンプルに保つ

対応表：Hooks概念 → バックエンド概念

Hooks概念 バックエンド対応概念 具体例
