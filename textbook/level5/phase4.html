1. IaCとは？

🎯 このページのゴール

Infrastructure as Code（IaC）の概念と手動管理の問題点を説明できる

IaCを一言で

Infrastructure as Code（IaC）とは、 サーバーやネットワークなどのインフラをコードで定義・管理する手法です。

💡 たとえ話

IaCは「設計図」のようなものです。
家を建てるとき、職人が記憶で作るのではなく、設計図に従って正確に建てますよね。
同様に、インフラも「コードという設計図」に従って構築します。

なぜIaCが必要？

手動管理の問題
  • 「前と同じ設定」が再現できない
  • 誰がいつ何を変えたか追跡困難
  • ヒューマンエラーが避けられない
  • 100台のサーバーに同じ設定は地獄
IaCの利点
  • 同じコードで同じ環境を何度でも構築
  • Gitで変更履歴を完全追跡
  • PRでレビュー、CIで検証
  • 1台でも1000台でも同じコマンド

主要なIaCツール

ツール 提供元 特徴
Terraform HashiCorp マルチクラウド対応、宣言的、最も普及
AWS CDK AWS プログラミング言語で記述、AWS専用
Pulumi Pulumi プログラミング言語、マルチクラウド
CloudFormation AWS AWS純正、YAML/JSON、AWS専用

2. Terraform基礎

🎯 このページのゴール

Terraformの基本概念（provider、resource、data）を理解する

Terraformとは？

Terraformは、HashiCorp社が開発したIaCツールです。
2026年現在、最も広く使われているIaCツールであり、 AWS、Azure、GCPなど3000以上のプロバイダに対応しています。

基本的な流れ

3つの基本概念

1. Provider（プロバイダ）

どのクラウド/サービスを使うかを指定します。

# AWSプロバイダを使用
terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
}

provider "aws" {
  region = "ap-northeast-1"  # 東京リージョン
}

2. Resource（リソース）

作成したいインフラの「宣言」です。「こういうものが欲しい」を書きます。

# EC2インスタンスを作成
resource "aws_instance" "web" {
  ami           = "ami-0123456789abcdef0"
  instance_type = "t3.micro"

  tags = {
    Name = "WebServer"
  }
}

3. Data Source（データソース）

既存のリソースを参照します（作成はしない）。

# 最新のAmazon Linux 2023 AMIを取得
data "aws_ami" "amazon_linux" {
  most_recent = true
  owners      = ["amazon"]

  filter {
    name   = "name"
    values = ["al2023-ami-*-x86_64"]
  }
}

# データソースを参照
resource "aws_instance" "web" {
  ami           = data.aws_ami.amazon_linux.id  # 動的に取得
  instance_type = "t3.micro"
}
概念 役割 例
provider どのサービスを使うか AWS, GCP, Azure
resource 作成するもの EC2, S3, VPC
data 参照するもの 既存AMI, VPC

3. HCL構文

🎯 このページのゴール

HCL（HashiCorp Configuration Language）の基本構文を理解する

HCLとは？

HCL（HashiCorp Configuration Language）は、 Terraform用の設定言語です。
JSONより読みやすく、YAMLより構造化されています。

変数（Variable）

値を外部から注入できるようにします。ハードコードを避けるために必須。

# 変数定義 (variables.tf)
variable "environment" {
  description = "環境名（dev/stg/prod）"
  type        = string
  default     = "dev"
}

variable "instance_type" {
  description = "EC2インスタンスタイプ"
  type        = string
  default     = "t3.micro"
}

variable "allowed_ips" {
  description = "許可するIPアドレスリスト"
  type        = list(string)
  default     = ["10.0.0.0/8"]
}

# 変数の使用 (main.tf)
resource "aws_instance" "web" {
  instance_type = var.instance_type

  tags = {
    Environment = var.environment
  }
}

ローカル値（Locals）

計算結果や繰り返し使う値に名前をつけます。

locals {
  # 共通タグ
  common_tags = {
    Project     = "MyApp"
    Environment = var.environment
    ManagedBy   = "Terraform"
  }

  # 名前の命名規則
  name_prefix = "${var.project}-${var.environment}"
}

resource "aws_instance" "web" {
  # ...
  tags = merge(local.common_tags, {
    Name = "${local.name_prefix}-web"
  })
}

出力（Output）

作成したリソースの情報を出力します。他のモジュールで参照できます。

# 出力定義 (outputs.tf)
output "instance_id" {
  description = "EC2インスタンスID"
  value       = aws_instance.web.id
}

output "public_ip" {
  description = "パブリックIPアドレス"
  value       = aws_instance.web.public_ip
}

# terraform applyの結果
# Outputs:
# instance_id = "i-0123456789abcdef0"
# public_ip = "54.123.45.67"

条件式とループ

# 条件式: 本番のみMulti-AZ
resource "aws_db_instance" "main" {
  multi_az = var.environment == "prod" ? true : false
}

# countでループ
resource "aws_instance" "web" {
  count         = var.instance_count
  instance_type = var.instance_type

  tags = {
    Name = "web-${count.index + 1}"
  }
}

# for_eachで柔軟なループ
variable "instances" {
  default = {
    web = "t3.micro"
    api = "t3.small"
    db  = "t3.medium"
  }
}

resource "aws_instance" "servers" {
  for_each      = var.instances
  instance_type = each.value

  tags = {
    Name = each.key
  }
}
ハードコード（レビューNG）
resource "aws_instance" "web" {
  ami           = "ami-12345678"
  instance_type = "t3.micro"
  subnet_id     = "subnet-abc123"
}

値が直書き。環境ごとの切り替え不可

変数化（レビューOK）
resource "aws_instance" "web" {
  ami           = data.aws_ami.latest.id
  instance_type = var.instance_type
  subnet_id     = var.subnet_id
}

4. 状態管理

🎯 このページのゴール

Terraform状態ファイル（tfstate）の役割とリモートバックエンドを理解する

状態ファイルとは？

Terraformは「コードで宣言した理想の状態」と 「現在の実際のインフラ」の差分を計算して適用します。
この「現在の状態」を記録するのがterraform.tfstateです。

ローカル状態の問題

⚠️ レビュー観点: ローカル状態は危険

デフォルトではterraform.tfstateはローカルに保存されます。
これには重大な問題があります：

  • チームメンバーと共有できない
  • 同時実行で状態ファイルが壊れる
  • PCが壊れるとインフラの状態がわからなくなる
  • シークレットが平文で保存される

リモートバックエンド

状態ファイルをS3などのリモートストレージに保存します。

# backend.tf - リモートバックエンド設定
terraform {
  backend "s3" {
    bucket         = "my-terraform-state"      # S3バケット名
    key            = "prod/terraform.tfstate"  # 状態ファイルのパス
    region         = "ap-northeast-1"
    encrypt        = true                      # 暗号化必須
    dynamodb_table = "terraform-locks"         # 状態ロック（後述）
  }
}
ローカル状態（チーム開発不可）
# バックエンド設定なし
# → terraform.tfstate がローカルに作成される

個人開発でも本番環境では避けるべき

リモートバックエンド（推奨）
terraform {
  backend "s3" {
    bucket         = "terraform-state"
    key            = "state.tfstate"
    region         = "ap-northeast-1"
    encrypt        = true
    dynamodb_table = "terraform-locks"
  }
}

暗号化 + 状態ロックで安全

状態ファイルの中身

状態ファイルには機密情報が含まれることがあります。

// terraform.tfstate の例（抜粋）
{
  "resources": [{
    "type": "aws_db_instance",
    "instances": [{
      "attributes": {
        "password": "MySecretPassword123",  // 平文で保存される！
        "endpoint": "mydb.xxx.ap-northeast-1.rds.amazonaws.com"
      }
    }]
  }]
}
⚠️ 重要: 状態ファイルをGitにコミットしない

.gitignoreに必ず追加してください： 

# .gitignore
*.tfstate
*.tfstate.*
.terraform/

5. 状態ロック

🎯 このページのゴール

状態ロックの仕組みと同時実行防止の重要性を理解する

なぜ状態ロックが必要？

複数人が同時にterraform applyを実行すると、 状態ファイルが矛盾してインフラが壊れます。

DynamoDBによる状態ロック

AWSではDynamoDBを使ってロックを実現します。

# DynamoDBテーブルの作成（これもTerraformで）
resource "aws_dynamodb_table" "terraform_locks" {
  name         = "terraform-locks"
  billing_mode = "PAY_PER_REQUEST"
  hash_key     = "LockID"

  attribute {
    name = "LockID"
    type = "S"
  }
}

# バックエンドでロックテーブルを指定
terraform {
  backend "s3" {
    bucket         = "my-terraform-state"
    key            = "prod/terraform.tfstate"
    region         = "ap-northeast-1"
    encrypt        = true
    dynamodb_table = "terraform-locks"  # ← これ！
  }
}

ロックの動作

# Aさんがapply実行中
$ terraform apply
Acquiring state lock. This may take a few moments...
# → DynamoDBにロックレコードが作成される

# Bさんが同時にapply
$ terraform apply
Error: Error acquiring the state lock
Error message: ConditionalCheckFailedException: The conditional request failed
Lock Info:
  ID:        xxxx-xxxx-xxxx
  Path:      prod/terraform.tfstate
  Operation: OperationTypeApply
  Who:       userA@hostname
  Created:   2026-02-04 10:00:00.000000 +0000 UTC

# Aさんが完了すると自動でロック解除
Apply complete!
Releasing state lock. This may take a few moments...
⚠️ レビュー観点: ロックなしは危険

リモートバックエンドを設定していても、dynamodb_tableがないとロックが効きません。
チーム開発では必ず状態ロックを設定してください。

6. モジュール

🎯 このページのゴール

Terraformモジュールによる再利用可能なコード設計を理解する

モジュールとは？

モジュールは、Terraformコードを 再利用可能な「部品」としてパッケージ化したものです。
関数やクラスのように、設定値を渡して使い回せます。

💡 たとえ話

モジュールは「LEGOブロック」のようなものです。
同じブロック（モジュール）を使って、異なる建物（環境）を組み立てられます。

モジュールの構造

# ディレクトリ構造
modules/
└── vpc/
    ├── main.tf      # リソース定義
    ├── variables.tf # 入力変数
    └── outputs.tf   # 出力値

# modules/vpc/variables.tf
variable "name" {
  description = "VPCの名前"
  type        = string
}

variable "cidr_block" {
  description = "VPCのCIDR"
  type        = string
  default     = "10.0.0.0/16"
}

# modules/vpc/main.tf
resource "aws_vpc" "main" {
  cidr_block = var.cidr_block

  tags = {
    Name = var.name
  }
}

resource "aws_subnet" "public" {
  vpc_id     = aws_vpc.main.id
  cidr_block = cidrsubnet(var.cidr_block, 8, 1)
}

# modules/vpc/outputs.tf
output "vpc_id" {
  value = aws_vpc.main.id
}

output "public_subnet_id" {
  value = aws_subnet.public.id
}

モジュールの使用

# 環境ごとにモジュールを呼び出す
module "vpc_dev" {
  source     = "./modules/vpc"
  name       = "dev-vpc"
  cidr_block = "10.1.0.0/16"
}

module "vpc_prod" {
  source     = "./modules/vpc"
  name       = "prod-vpc"
  cidr_block = "10.2.0.0/16"
}

# モジュールの出力を使う
resource "aws_instance" "web" {
  subnet_id = module.vpc_prod.public_subnet_id
}

Terraform Registry

Terraform Registryには、 AWSやコミュニティが作成した公式モジュールがあります。 

# AWS公式VPCモジュールを使用
module "vpc" {
  source  = "terraform-aws-modules/vpc/aws"
  version = "5.0.0"

  name = "my-vpc"
  cidr = "10.0.0.0/16"

  azs             = ["ap-northeast-1a", "ap-northeast-1c"]
  private_subnets = ["10.0.1.0/24", "10.0.2.0/24"]
  public_subnets  = ["10.0.101.0/24", "10.0.102.0/24"]

  enable_nat_gateway = true
}
コピペ（レビューNG）
# dev/main.tf
resource "aws_vpc" "main" {...}
resource "aws_subnet" "public" {...}

# prod/main.tf（同じコードをコピペ）
resource "aws_vpc" "main" {...}
resource "aws_subnet" "public" {...}

修正時に全箇所を直す必要あり

モジュール化（レビューOK）
# 共通モジュール
module "vpc_dev" {
  source = "./modules/vpc"
  name   = "dev"
}

module "vpc_prod" {
  source = "./modules/vpc"
  name   = "prod"
}

モジュールを1箇所直せばOK

7. ワークスペース

🎯 このページのゴール

Terraformワークスペースによる環境分離（dev/stg/prod）を理解する

なぜ環境分離が必要？

開発（dev）、ステージング（stg）、本番（prod）で 同じコードだが異なる設定を使いたい場面は多いです。

環境分離の方法

方法 特徴 適した場面
Workspace 同じコード、状態ファイルを分離 環境差が少ない場合
ディレクトリ分離 環境ごとにフォルダを分ける 環境差が大きい場合
tfvars 変数ファイルで切り替え 設定値のみ異なる場合

Workspaceの使い方

# ワークスペース一覧
$ terraform workspace list
* default
  dev
  stg
  prod

# 新しいワークスペース作成
$ terraform workspace new dev
Created and switched to workspace "dev"!

# ワークスペース切り替え
$ terraform workspace select prod
Switched to workspace "prod".

# 現在のワークスペースを確認
$ terraform workspace show
prod

コードでワークスペースを参照

locals {
  # ワークスペース名に応じた設定
  env_config = {
    dev = {
      instance_type = "t3.micro"
      min_size      = 1
      max_size      = 2
    }
    stg = {
      instance_type = "t3.small"
      min_size      = 2
      max_size      = 4
    }
    prod = {
      instance_type = "t3.medium"
      min_size      = 3
      max_size      = 10
    }
  }

  # 現在のワークスペースの設定を取得
  config = local.env_config[terraform.workspace]
}

resource "aws_instance" "web" {
  instance_type = local.config.instance_type

  tags = {
    Environment = terraform.workspace
  }
}

ディレクトリ分離（大規模向け）

# ディレクトリ構造
infrastructure/
├── modules/           # 共通モジュール
│   └── vpc/
├── environments/
│   ├── dev/
│   │   ├── main.tf
│   │   ├── variables.tf
│   │   └── terraform.tfvars
│   ├── stg/
│   │   └── ...
│   └── prod/
│       └── ...

# environments/prod/main.tf
module "vpc" {
  source = "../../modules/vpc"
  # prod固有の設定
}

# environments/prod/terraform.tfvars
environment   = "prod"
instance_type = "t3.medium"
min_size      = 3
⚠️ レビュー観点: 環境混在は危険

1つの状態ファイルでdev/prod両方を管理すると、 terraform destroyで本番が消える可能性があります。
環境ごとに状態ファイルを分離してください。

8. シークレット管理

🎯 このページのゴール

Terraformでシークレット（機密情報）を安全に扱う方法を理解する

シークレット管理の課題

データベースパスワード、APIキーなどの機密情報を どう扱うかは、IaCの最大の課題の1つです。

⚠️ 絶対にやってはいけないこと
  • シークレットをコードにハードコード
  • シークレットをGitにコミット
  • 状態ファイル（tfstate）の平文保存

方法1: 環境変数

最もシンプルな方法。CIパイプラインで設定します。

# 変数定義
variable "db_password" {
  description = "Database password"
  type        = string
  sensitive   = true  # ← 重要：ログに出力されない
}

# 環境変数から自動的に読み込まれる
# TF_VAR_db_password=xxx terraform apply

# 使用
resource "aws_db_instance" "main" {
  password = var.db_password
}

方法2: AWS Secrets Manager

シークレットを専用サービスで管理し、dataソースで参照します。

# Secrets Managerからシークレットを取得
data "aws_secretsmanager_secret_version" "db_password" {
  secret_id = "prod/db/password"
}

resource "aws_db_instance" "main" {
  password = data.aws_secretsmanager_secret_version.db_password.secret_string
}

方法3: HashiCorp Vault

エンタープライズ向けのシークレット管理ツール。

provider "vault" {
  address = "https://vault.example.com"
}

data "vault_generic_secret" "db" {
  path = "secret/prod/database"
}

resource "aws_db_instance" "main" {
  password = data.vault_generic_secret.db.data["password"]
}

sensitive属性

sensitive = trueを設定すると、 plan/apply時のログに値が表示されなくなります。 

variable "api_key" {
  type      = string
  sensitive = true
}

output "api_endpoint" {
  value     = "https://api.example.com?key=${var.api_key}"
  sensitive = true  # 出力も隠す
}
平文保存（絶対NG）
resource "aws_db_instance" "db" {
  password = "MySecretPassword123"
}

# terraform.tfvars（Gitにコミット）
db_password = "MySecretPassword123"

Gitリポジトリに平文で残る

安全な管理（推奨）
variable "db_password" {
  type      = string
  sensitive = true
}

# CI/CDで環境変数として設定
# TF_VAR_db_password=$DB_PASSWORD

# または Secrets Manager
data "aws_secretsmanager_secret_version" "db" {
  secret_id = "prod/db/password"
}

9. 静的解析

🎯 このページのゴール

Terraformコードの静的解析ツール（tfsec、checkov、tflint）を理解する

なぜ静的解析が必要？

terraform planは「何が変わるか」を見せますが、 セキュリティ問題やベストプラクティス違反は検出できません。

主要な静的解析ツール

tfsec Aqua Security製、高速 セキュリティチェック
checkov Bridgecrew製、多機能 セキュリティ + コンプライアンス
tflint Linter、プラグイン拡張 構文・命名規則チェック

10. CI/CD統合

🎯 このページのゴール

Terraformのplan/applyをCI/CDで自動化し、承認フローを構築する方法を理解する

なぜCI/CD統合が必要？

手動でterraform applyを実行するのは危険です。
CI/CDで自動化し、レビューと承認を経てからapplyすべきです。

GitHub Actions ワークフロー例

name: Terraform

on:
  pull_request:
    paths:
      - 'terraform/**'
  push:
    branches:
      - main
    paths:
      - 'terraform/**'

permissions:
  id-token: write   # OIDC認証用
  contents: read
  pull-requests: write  # PRにコメント

jobs:
  plan:
    runs-on: ubuntu-latest
    if: github.event_name == 'pull_request'
    steps:
      - uses: actions/checkout@v4

      - name: Configure AWS (OIDC)
        uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789:role/terraform
          aws-region: ap-northeast-1

      - name: Setup Terraform
        uses: hashicorp/setup-terraform@v3
        with:
          terraform_version: 1.7.0

      - name: Terraform Init
        run: terraform init
        working-directory: terraform/

      - name: Terraform Plan
        id: plan
        run: terraform plan -no-color -out=tfplan
        working-directory: terraform/
        continue-on-error: true

      - name: Comment Plan on PR
        uses: actions/github-script@v7
        with:
          script: |
            const output = `#### Terraform Plan
            \`\`\`
            ${{ steps.plan.outputs.stdout }}
            \`\`\`
            `;
            github.rest.issues.createComment({
              issue_number: context.issue.number,
              owner: context.repo.owner,
              repo: context.repo.repo,
              body: output
            })

  apply:
    runs-on: ubuntu-latest
    if: github.ref == 'refs/heads/main' && github.event_name == 'push'
    environment:
      name: production  # 承認が必要
    steps:
      - uses: actions/checkout@v4

      - name: Configure AWS (OIDC)
        uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789:role/terraform
          aws-region: ap-northeast-1

      - name: Setup Terraform
        uses: hashicorp/setup-terraform@v3

      - name: Terraform Init
        run: terraform init
        working-directory: terraform/

      - name: Terraform Apply
        run: terraform apply -auto-approve
        working-directory: terraform/

承認フロー（Environment Protection Rules）

GitHubのEnvironment機能で、本番applyに承認を必須にできます。 

# Settings > Environments > production
# - Required reviewers: チームメンバーを指定
# - Wait timer: 5分の待機時間（オプション）

# ワークフローで environment を指定
apply:
  environment:
    name: production  # ← この環境に承認ルールを設定
  steps:
    - run: terraform apply -auto-approve
手動apply（危険）
# 開発者のローカルPCから直接
$ terraform apply

# 問題点
# - レビューなしで本番変更
# - 誰が何を変えたか追跡困難
# - 間違いに気づきにくい
CI/CD統合（推奨）
# PR作成 → 自動plan → レビュー → 承認 → apply

# メリット
# - Plan結果をチームで確認
# - 承認後のみ適用
# - 全変更がGitに記録
⚠️ レビュー観点: 手動applyは禁止

本番環境への手動applyは事故のもとです。
CI/CDパイプラインを通し、承認フローを経てからapplyしてください。

Phase 4 まとめ: Terraformレビューチェックリスト

✅ コードレビューで確認すべきポイント
  • 状態管理: リモートバックエンド + 状態ロックを使用しているか
  • ハードコード: 値が変数化されているか、AMI IDなどが直書きでないか
  • シークレット: パスワード等がコードに平文で書かれていないか、sensitive=trueか
  • モジュール化: 重複コードがコピペでなくモジュールで再利用されているか
  • 環境分離: dev/stg/prodの状態ファイルが分離されているか
  • 静的解析: tfsec/checkovがCI/CDに組み込まれているか
  • 承認フロー: 本番applyに承認が必要な設定になっているか
