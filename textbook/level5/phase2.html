1. Kubernetesとは？

🎯 このページのゴール

Kubernetesが必要な理由を説明できる

コンテナオーケストレーションとは

Kubernetes（クバネティス、K8s）は、 コンテナオーケストレーションのためのプラットフォームです。

💡 たとえ話

Dockerが「船（コンテナ）」だとすると、
Kubernetesは「港の管理システム」です。
どの船をどの港に停めるか、船が壊れたら代わりを用意する、
荷物（トラフィック）を適切に振り分ける。
これらを自動でやってくれます。

なぜKubernetesが必要？

コンテナが1〜2個なら手動で管理できます。しかし本番環境では...

コンテナ手動管理の問題
  • 数十〜数百のコンテナを管理できない
  • 1台のサーバーがダウンしたら？
  • アクセス増加時のスケーリングは？
  • 新バージョンへの更新をどうする？
  • コンテナ間のネットワークは？
Kubernetesが解決
  • 宣言的に「3台動かして」と書くだけ
  • ダウンしたら自動で別サーバーに再配置
  • 負荷に応じて自動スケーリング
  • ローリングアップデートで無停止更新
  • サービスディスカバリで自動接続

Kubernetesの主な機能

機能 説明
自己修復 コンテナが落ちたら自動で再起動・再配置
水平スケーリング CPU/メモリ使用率に応じて自動でPod数を増減
ローリングアップデート サービス無停止で新バージョンに更新
サービスディスカバリ DNS名でコンテナ間通信、自動ロードバランス
設定/シークレット管理 環境変数や機密情報を安全に注入

K8s = Kubernetes の名前の由来

「K8s」は、Kubernetesの略称です。
「K」と「s」の間に8文字あるので「K8s」。
（internationalization → i18n と同じ発想）

Kubernetesはギリシャ語で「舵取り」「操舵士」という意味。
コンテナという「船」を操縦する存在、というわけです。

2. Kubernetesアーキテクチャ

🎯 このページのゴール

Control Plane と Worker Node の役割を説明できる

クラスターの構成

Kubernetesはクラスターという単位で動作します。
クラスターは、Control Plane（管理側）と Worker Node（実行側）で構成されます。

コンポーネント詳細

Control Plane（マスター）

コンポーネント 役割
API Server すべての操作の窓口。kubectlやkubeletはここと通信
etcd クラスターの状態を保存する分散KVストア
Scheduler 新しいPodをどのNodeに配置するか決定
Controller Manager 「あるべき状態」と「現在の状態」を比較し調整

Worker Node

コンポーネント 役割
kubelet 各Nodeで動くエージェント。Podの起動・監視を担当
kube-proxy ネットワークルールを管理。Service経由の通信を実現
Container Runtime 実際にコンテナを動かす（containerd、CRI-O等）
⚠️ 重要: etcdの役割

etcdはクラスターの「真実の源（Source of Truth）」です。
すべての設定、状態がここに保存されます。
etcdが壊れるとクラスター全体が機能しなくなるため、 本番環境では必ずバックアップと冗長化が必要です。

3. Pod（ポッド）

🎯 このページのゴール

Podの概念とライフサイクルを理解する

Podとは？

Podは、Kubernetesの最小デプロイ単位です。
1つ以上のコンテナをまとめたグループで、 同じネットワークとストレージを共有します。

💡 たとえ話

Podは「一緒に暮らす家族」のようなものです。
同じ家（Pod）に住み、同じ住所（IPアドレス）を持ち、
同じ冷蔵庫（ストレージ）を共有します。
引っ越す時は家族全員で一緒に移動します。

Podのライフサイクル

状態 説明
Pending スケジュール待ち、またはイメージダウンロード中
Running 少なくとも1つのコンテナが実行中
Succeeded すべてのコンテナが正常終了
Failed 少なくとも1つのコンテナが異常終了
Unknown Podの状態を取得できない

マルチコンテナパターン

パターン 用途 例
Sidecar メインコンテナを補助 ログ収集、プロキシ
Ambassador 外部通信をプロキシ DB接続プール
Adapter 出力形式を変換 メトリクス変換

Podのマニフェスト例

# pod.yaml
apiVersion: v1
kind: Pod
metadata:
  name: my-app
  labels:
    app: my-app
spec:
  containers:
  - name: app
    image: my-app:1.0.0
    ports:
    - containerPort: 3000
    resources:
      requests:
        memory: "256Mi"
        cpu: "250m"
      limits:
        memory: "512Mi"
        cpu: "500m"
⚠️ レビュー観点: 直接Podを作成していないか

本番環境で直接Podを作成するのはアンチパターンです。
Podが落ちても自動で再作成されません。
必ずDeploymentやStatefulSet経由で管理しましょう。

直接Pod作成（非推奨）
apiVersion: v1
kind: Pod
metadata:
  name: my-app
spec:
  containers:
  - name: app
    image: my-app:1.0.0

Podが落ちたら手動で再作成が必要

Deployment経由（推奨）
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
spec:
  replicas: 3
  # ...

Podが落ちても自動で再作成される

4. Deployment

🎯 このページのゴール

Deploymentによるレプリカ管理とローリングアップデートを理解する

Deploymentとは？

Deploymentは、Podのあるべき状態を宣言し、 その状態を維持するリソースです。
「このPodを3つ動かしてほしい」と宣言すると、常に3つを維持します。

Deploymentの階層構造

Deployment
  └── ReplicaSet（バージョン管理）
        └── Pod（実際のコンテナ）

ReplicaSetは裏で自動的に作成されます。
直接ReplicaSetを操作する必要はありません。

基本的なDeploymentマニフェスト

apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
spec:
  replicas: 3                    # Podを3つ維持
  selector:
    matchLabels:
      app: my-app                # 管理対象のPodを選択
  template:
    metadata:
      labels:
        app: my-app              # Podにつけるラベル
    spec:
      containers:
      - name: app
        image: my-app:1.0.0      # 明示的なバージョン！
        ports:
        - containerPort: 3000
        resources:
          requests:
            memory: "256Mi"
            cpu: "250m"
          limits:
            memory: "512Mi"
            cpu: "500m"

ローリングアップデート

Deploymentは無停止でアプリを更新できます。
古いPodを1つずつ新しいPodに置き換えていきます。 

# イメージを更新
kubectl set image deployment/my-app app=my-app:2.0.0

# または、マニフェストを編集して適用
kubectl apply -f deployment.yaml

# 更新状況を確認
kubectl rollout status deployment/my-app

# 問題があればロールバック
kubectl rollout undo deployment/my-app

更新戦略の設定

spec:
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1        # 一時的に増やせるPod数
      maxUnavailable: 0  # 同時に停止できるPod数
⚠️ レビュー観点
  • replicas: 1 は本番環境ではNG（冗長性なし）
  • image: latest は追跡不可（明示的バージョンを使う）
  • resourcesなし はノード枯渇リスク
問題のあるDeployment
spec:
  replicas: 1          # 冗長性なし
  template:
    spec:
      containers:
      - image: my-app:latest  # 追跡不可
        # resourcesなし
本番向けDeployment
spec:
  replicas: 3          # 冗長性あり
  template:
    spec:
      containers:
      - image: my-app:1.0.0   # 明示的バージョン
        resources:
          requests:
            memory: "256Mi"
            cpu: "250m"
          limits:
            memory: "512Mi"
            cpu: "500m"

5. Service

🎯 このページのゴール

ServiceによるPodへのアクセス方法を理解する

なぜServiceが必要？

Podは一時的な存在です。
再起動するとIPアドレスが変わります。
Serviceは、変わらないエンドポイントを提供します。

Serviceの種類

種類 用途 アクセス範囲
ClusterIP クラスター内部通信（デフォルト） クラスター内のみ
NodePort 各Nodeのポートで公開 クラスター外から可
LoadBalancer クラウドのLBを使用 インターネット公開
ExternalName 外部サービスへのエイリアス DNS転送

Serviceマニフェスト例

apiVersion: v1
kind: Service
metadata:
  name: my-app-svc
spec:
  type: ClusterIP           # デフォルト
  selector:
    app: my-app             # このラベルのPodにルーティング
  ports:
  - port: 80                # Serviceのポート
    targetPort: 3000        # Podのポート
    protocol: TCP

サービスディスカバリ（DNS）

KubernetesはCoreDNSを使って、 Service名をDNSで解決できます。 

# 同じNamespace内からアクセス
curl http://my-app-svc

# 別のNamespaceからアクセス
curl http://my-app-svc.production.svc.cluster.local

# FQDN形式: {service}.{namespace}.svc.cluster.local
⚠️ レビュー観点: Pod IPを直接参照していないか

コード内でPodのIPアドレスを直接指定するのはアンチパターンです。
PodのIPは再起動で変わります。
必ずService名を使いましょう。

Pod IPを直接参照（NG）
DATABASE_URL=postgres://10.244.1.5:5432/db
# PodのIPは変わる！
Service名で参照（OK）
DATABASE_URL=postgres://db-svc:5432/db
# Service名は固定

6. Ingress

🎯 このページのゴール

IngressによるHTTPルーティングとTLS終端を理解する

Ingressとは？

Ingressは、HTTPレベルでトラフィックを振り分けるリソースです。
1つのロードバランサーで、複数のServiceにルーティングできます。

Ingressマニフェスト例

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: my-ingress
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
spec:
  ingressClassName: nginx
  tls:
  - hosts:
    - example.com
    secretName: tls-secret      # TLS証明書
  rules:
  - host: example.com
    http:
      paths:
      - path: /api
        pathType: Prefix
        backend:
          service:
            name: api-svc
            port:
              number: 80
      - path: /
        pathType: Prefix
        backend:
          service:
            name: web-svc
            port:
              number: 80

Ingress Controller

Ingressリソースだけでは動きません。
Ingress Controller（NGINX、Traefik等）を事前にインストールする必要があります。

Controller 特徴
NGINX Ingress 最も普及、安定、高機能
Traefik 自動証明書、動的設定
AWS ALB Controller AWS ALBとネイティブ統合
⚠️ レビュー観点: Serviceを直接公開していないか

NodePortやLoadBalancerで 各Serviceを直接公開するのは非効率です。
Ingressで1つのエントリーポイントにまとめましょう。

Service直接公開（非効率）
# 各ServiceにLoadBalancer
api-svc: LB1 ($0.025/hour)
web-svc: LB2 ($0.025/hour)
admin-svc: LB3 ($0.025/hour)
# コスト: 3個分
Ingress経由（効率的）
# 1つのIngressでルーティング
/api → api-svc
/web → web-svc
/admin → admin-svc
# コスト: 1個分

7. ConfigMap と Secret

🎯 このページのゴール

設定と機密情報の外部化方法を理解する

なぜ設定を外部化？

設定をコンテナイメージに埋め込むと、
環境ごと（dev/stg/prod）にイメージを作り直す必要があります。
ConfigMapとSecretで設定を外部化しましょう。

ConfigMap vs Secret

項目 ConfigMap Secret
用途 一般的な設定 機密情報
データ形式 平文 Base64エンコード
Git管理 OK NG（暗号化必須）
サイズ制限 1MB 1MB

ConfigMapの作成と使用

# ConfigMapマニフェスト
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  LOG_LEVEL: "info"
  API_ENDPOINT: "https://api.example.com"
  # ファイルとして
  nginx.conf: |
    server {
      listen 80;
      ...
    }

---
# Podで使用（環境変数）
spec:
  containers:
  - name: app
    envFrom:
    - configMapRef:
        name: app-config

# または個別に
    env:
    - name: LOG_LEVEL
      valueFrom:
        configMapKeyRef:
          name: app-config
          key: LOG_LEVEL

Secretの作成と使用

# Secretマニフェスト
apiVersion: v1
kind: Secret
metadata:
  name: db-secret
type: Opaque
data:
  # Base64エンコードが必要
  password: cGFzc3dvcmQxMjM=  # "password123"

# stringDataを使うと自動でBase64化
stringData:
  password: password123

---
# Podで使用
spec:
  containers:
  - name: app
    env:
    - name: DB_PASSWORD
      valueFrom:
        secretKeyRef:
          name: db-secret
          key: password
⚠️ レビュー観点: 設定がハードコードされていないか

環境変数や機密情報がDeploymentのマニフェストに
直接書かれていないかチェック。
ConfigMap/Secretで外部化しましょう。

ハードコード（NG）
spec:
  containers:
  - name: app
    env:
    - name: DATABASE_URL
      value: "postgres://user:pass@db:5432"
    - name: API_KEY
      value: "sk-123456789"
Secret参照（OK）
spec:
  containers:
  - name: app
    env:
    - name: DATABASE_URL
      valueFrom:
        secretKeyRef:
          name: db-secret
          key: url
    - name: API_KEY
      valueFrom:
        secretKeyRef:
          name: api-secret
          key: key

8. ストレージ（PV/PVC）

🎯 このページのゴール

PersistentVolumeとPersistentVolumeClaimの関係を理解する

なぜ永続ストレージが必要？

Podは一時的な存在です。
Pod内のデータは、Podが削除されると消えます。
データベースなど永続化が必要なデータは、PersistentVolumeを使います。

アクセスモード

モード 説明 用途
ReadWriteOnce (RWO) 1つのNodeからのみR/W 一般的なDB
ReadOnlyMany (ROX) 複数Nodeから読み取り 静的コンテンツ
ReadWriteMany (RWX) 複数Nodeから読み書き 共有ストレージ（NFS）

PVCマニフェスト例

apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: postgres-pvc
spec:
  accessModes:
    - ReadWriteOnce
  storageClassName: standard     # StorageClassを指定
  resources:
    requests:
      storage: 10Gi

---
# Podで使用
apiVersion: apps/v1
kind: Deployment
metadata:
  name: postgres
spec:
  template:
    spec:
      containers:
      - name: postgres
        image: postgres:16-alpine
        volumeMounts:
        - name: data
          mountPath: /var/lib/postgresql/data
      volumes:
      - name: data
        persistentVolumeClaim:
          claimName: postgres-pvc
⚠️ レビュー観点: emptyDirをデータベースに使っていないか

emptyDirはPodと一緒に消える一時ストレージです。
データベースに使うと、Podが再起動するたびにデータが消失します。
本番環境では必ずPersistentVolumeClaimを使いましょう。

emptyDir（データ消失リスク）
volumes:
- name: data
  emptyDir: {}  # Podと一緒に消える
PVC（永続化）
volumes:
- name: data
  persistentVolumeClaim:
    claimName: postgres-pvc  # Pod削除後も残る

9. RBAC（権限管理）

🎯 このページのゴール

Role/RoleBindingによる最小権限の原則を理解する

RBACとは？

RBAC（Role-Based Access Control）は、
「誰が」「何に対して」「何ができるか」を制御する仕組みです。

💡 たとえ話

会社のオフィスと同じです。
「一般社員」は自分のデスク周辺にしかアクセスできない。
「経理部長」は経理室の金庫にもアクセスできる。
「社長」は全フロアにアクセスできる。
これが「ロールベースのアクセス制御」です。

RBACリソースの種類

リソース スコープ 用途
Role Namespace内 特定Namespaceの権限
ClusterRole クラスター全体 クラスター全体の権限
RoleBinding Namespace内 RoleをUserに紐付け
ClusterRoleBinding クラスター全体 ClusterRoleをUserに紐付け

Roleの例

# 特定NamespaceでPodの参照のみ許可
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: development
rules:
- apiGroups: [""]           # コアAPI
  resources: ["pods"]
  verbs: ["get", "list", "watch"]

---
# RoleBinding
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: read-pods
  namespace: development
subjects:
- kind: User
  name: dev-user
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io

よく使うverbs

Verb 説明 kubectl相当
get 単一リソースの取得 kubectl get pod my-pod
list リソース一覧の取得 kubectl get pods
watch リソースの変更監視 kubectl get pods -w
create リソースの作成 kubectl create
delete リソースの削除 kubectl delete
⚠️ レビュー観点: cluster-adminを多用していないか

cluster-adminはすべての権限を持つ最強のClusterRoleです。
本番環境で安易に付与するのはセキュリティリスクです。
最小権限の原則に従い、必要な権限だけを付与しましょう。

過剰な権限（NG）
roleRef:
  kind: ClusterRole
  name: cluster-admin  # 全権限！危険
最小権限（OK）
roleRef:
  kind: Role
  name: pod-reader  # 必要な権限のみ

10. ヘルスチェック（Probe）

🎯 このページのゴール

liveness/readiness/startup Probeの違いと使い方を理解する

なぜヘルスチェックが必要？

アプリケーションは、プロセスが起動していても
正常に動作しているとは限りません。
デッドロック、DB接続切れ、メモリ不足などで応答しなくなることがあります。

Probeを設定することで、Kubernetesが
アプリケーションの健全性を監視し、問題があれば自動で対処します。

3種類のProbe

Probe 目的 失敗時の動作
Liveness コンテナが正常か コンテナ再起動
Readiness トラフィックを受けられるか Serviceから除外
Startup 起動が完了したか 他のProbeを遅延

Probeの設定方法

apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
spec:
  template:
    spec:
      containers:
      - name: app
        image: my-app:1.0.0
        ports:
        - containerPort: 3000

        # 起動完了チェック
        startupProbe:
          httpGet:
            path: /health
            port: 3000
          failureThreshold: 30   # 30回失敗まで待つ
          periodSeconds: 10       # 10秒ごとにチェック

        # 生存チェック
        livenessProbe:
          httpGet:
            path: /health
            port: 3000
          initialDelaySeconds: 10 # 起動後10秒待ってから開始
          periodSeconds: 10       # 10秒ごとにチェック
          timeoutSeconds: 3       # 3秒でタイムアウト
          failureThreshold: 3     # 3回失敗で再起動

        # 受付可能チェック
        readinessProbe:
          httpGet:
            path: /ready
            port: 3000
          initialDelaySeconds: 5
          periodSeconds: 5
          failureThreshold: 3

Probeの種類（チェック方法）

方法 用途
httpGet HTTP GETリクエスト（200-399で成功）
tcpSocket TCPポート接続チェック
exec コマンド実行（exit 0で成功）
grpc gRPCヘルスチェック
⚠️ レビュー観点: Probeが設定されているか

本番環境でProbeなしは危険です。
アプリがハングしても検知・復旧できません。
少なくともlivenessとreadinessは設定しましょう。

Probeなし（NG）
spec:
  containers:
  - name: app
    image: my-app:1.0.0
    # Probeなし → ハング検知できない
Probe設定（OK）
spec:
  containers:
  - name: app

// Node.js Express
app.get('/health', (req, res) => {
  // 単純な生存確認
  res.status(200).json({ status: 'ok' });
});

app.get('/ready', async (req, res) => {
  try {
    // DB接続チェック
    await db.query('SELECT 1');
    // 外部サービスチェック
    await fetch('https://api.example.com/health');
    res.status(200).json({ status: 'ready' });
  } catch (error) {
    res.status(503).json({ status: 'not ready', error: error.message });
  }
});

Phase 2 まとめ: Kubernetesレビューチェックリスト

✓ コードレビューで確認すべきポイント
  • Deployment経由で管理しているか（直接Pod作成NG）
  • replicas: 3以上で冗長性を確保しているか
  • 明示的バージョンを使っているか（latestタグNG）
  • resources（requests/limits）が設定されているか
  • liveness/readiness Probeが設定されているか
  • ConfigMap/Secretで設定を外部化しているか
  • PVCでデータを永続化しているか（emptyDirNG）
  • 最小権限のRBACを設定しているか（cluster-admin多用NG）
  • Service名で通信しているか（Pod IP直接参照NG）
  • IngressでHTTPルーティングしているか（Service直接公開NG）
