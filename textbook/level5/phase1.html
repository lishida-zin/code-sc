1. コンテナとは？

🎯 このページのゴール

コンテナと仮想マシン（VM）の違いを説明できる

コンテナを一言で

コンテナとは、アプリケーションとその実行環境を 「箱」にまとめて持ち運べる技術です。

💡 たとえ話

コンテナは「お弁当箱」のようなものです。
お弁当箱には、ご飯、おかず、お箸がすべて入っている。
どこに持っていっても、同じご飯が食べられます。

同様に、コンテナにはアプリと必要なライブラリがすべて入っている。
どのサーバーでも、同じように動きます。

なぜコンテナが必要？

開発者の永遠の悩み「自分のPCでは動くのに...」を解決します。

コンテナなしの問題
  • 開発環境と本番環境で動作が違う
  • 「Node 18で動かない」「ライブラリが古い」
  • 環境構築に何時間もかかる
  • チームメンバー間で環境がバラバラ
コンテナありの解決
  • どこでも同じ環境で動く
  • 必要なものがすべてコンテナ内に
  • 環境構築はdocker runだけ
  • チーム全員が同じ環境

コンテナ vs 仮想マシン（VM）

観点 仮想マシン（VM） コンテナ
OS 各VMに専用OS（ゲストOS） ホストOSを共有
サイズ 数GB〜数十GB 数MB〜数百MB
起動時間 数分 数秒
リソース 重い（OS分のオーバーヘッド） 軽い（OSを共有）
隔離レベル 強い（完全なOS分離） やや弱い（カーネル共有）

2. Dockerの仕組み

🎯 このページのゴール

イメージ・コンテナ・レジストリの関係を説明できる

Docker = コンテナ技術の標準

Dockerは2013年に登場したコンテナプラットフォームです。
2026年現在、92%のIT専門家がDockerを使用しています。

3つの重要概念

概念 説明 たとえ
イメージ コンテナの設計図。読み取り専用。 料理のレシピ
コンテナ イメージから作られた実行環境。 レシピから作った料理
レジストリ イメージの保管場所（Docker Hub等） レシピ本の図書館

レイヤー構造

Dockerイメージはレイヤー（層）で構成されています。
各レイヤーは差分のみを保存するため、効率的です。 

# 各行が1レイヤーになる
FROM node:22-alpine     # レイヤー1: Node.js基盤
WORKDIR /app            # レイヤー2: 作業ディレクトリ
COPY package*.json ./   # レイヤー3: 依存定義
RUN npm ci              # レイヤー4: 依存インストール
COPY . .                # レイヤー5: アプリコード
⚠️ 重要：キャッシュの仕組み

レイヤーは上から順に実行され、変更があったレイヤー以降は再ビルドされます。
そのため、変更頻度が低いもの（依存）を先に、 変更頻度が高いもの（コード）を後に書くのがベストプラクティスです。

3. Dockerfile基礎

🎯 このページのゴール

Dockerfileの主要な命令を理解し、読めるようになる

Dockerfileとは？

Dockerfileは、イメージの作り方を記述したテキストファイルです。
「このイメージをベースに、これをインストールして、これを実行する」という手順を書きます。

主要な命令

命令 説明 例
FROM ベースイメージを指定 FROM node:22-alpine
WORKDIR 作業ディレクトリを設定 WORKDIR /app
COPY ファイルをコピー COPY . .
RUN コマンドを実行（ビルド時） RUN npm install
CMD コンテナ起動時のコマンド CMD ["node", "index.js"]
EXPOSE 公開ポートを宣言 EXPOSE 3000
ENV 環境変数を設定 ENV NODE_ENV=production

基本的なDockerfile

# ベースイメージ（Node.js 22のAlpine版）
FROM node:22-alpine

# 作業ディレクトリを設定
WORKDIR /app

# 依存関係ファイルをコピー
COPY package*.json ./

# 依存関係をインストール
RUN npm ci --only=production

# アプリケーションコードをコピー
COPY . .

# ポート3000を公開
EXPOSE 3000

# アプリケーションを起動
CMD ["node", "index.js"]

CMD vs ENTRYPOINT

CMD

コンテナ起動時のデフォルトコマンド。
docker runで上書き可能。

CMD ["node", "index.js"]
# docker run myapp npm test で上書き可能
ENTRYPOINT

必ず実行されるコマンド。
CMDは引数として渡される。

ENTRYPOINT ["node"]
CMD ["index.js"]
# docker run myapp test.js で引数変更

4. イメージ最適化

🎯 このページのゴール

レイヤーキャッシュを活かす書き方を理解する

なぜ最適化が必要？

最適化されていないDockerfileは、ビルド時間が長く、 イメージサイズが大きくなります。

キャッシュを活かす順序

非効率（キャッシュ無効化）
FROM node:22
COPY . .
RUN npm install

コード変更のたびにnpm installが再実行される

効率的（キャッシュ活用）
FROM node:22
COPY package*.json ./
RUN npm install
COPY . .

package.jsonが変わらなければキャッシュ利用

.dockerignoreファイル

.dockerignoreは、イメージに含めないファイルを指定します。
.gitignoreのDocker版です。 

# .dockerignore
node_modules
.git
.gitignore
*.md
.env
.env.*
dist
coverage
.DS_Store
⚠️ レビュー観点

node_modulesをイメージにコピーするのはアンチパターンです。
OS間の互換性問題が発生し、イメージサイズも肥大化します。

RUN命令の最適化

レイヤーが増える
RUN apt-get update
RUN apt-get install -y curl
RUN apt-get clean

3つのレイヤーが作成される

1つのレイヤーにまとめる
RUN apt-get update && \
    apt-get install -y curl && \
    apt-get clean && \
    rm -rf /var/lib/apt/lists/*

1つのレイヤーで完結

5. マルチステージビルド

🎯 このページのゴール

マルチステージビルドで軽量イメージを作る方法を理解する

マルチステージビルドとは？

マルチステージビルドは、複数のFROMを使って、 ビルド環境と実行環境を分離する手法です。

実際のマルチステージDockerfile

# ========== ビルドステージ ==========
FROM node:22-alpine AS builder
WORKDIR /app

# 依存関係をインストール
COPY package*.json ./
RUN npm ci

# ソースコードをコピーしてビルド
COPY . .
RUN npm run build

# ========== 実行ステージ ==========
FROM gcr.io/distroless/nodejs22-debian12
WORKDIR /app

# ビルド成果物のみをコピー
COPY --from=builder /app/dist ./dist
COPY --from=builder /app/node_modules ./node_modules

# 実行
CMD ["dist/index.js"]

ベースイメージの選択

イメージ サイズ 用途
node:22 〜1GB 開発環境、フル機能が必要な場合
node:22-alpine 〜50MB 軽量、ほとんどの本番環境
node:22-slim 〜200MB alpineで動かない場合のバランス
distroless 〜30MB 最小構成、セキュリティ重視
⚠️ レビュー観点

本番イメージにdevDependenciesや ビルドツールが含まれていないかチェック。
マルチステージビルドを使わない場合、これらが残り、 セキュリティリスクとサイズ増加の原因になります。

6. Docker Compose V2

🎯 このページのゴール

Docker Composeで複数コンテナを管理する方法を理解する

Docker Composeとは？

Docker Composeは、複数のコンテナをまとめて管理するツールです。
アプリ + DB + Redis のような構成を1コマンドで起動できます。

⚠️ V1 vs V2

旧: docker-compose up（V1、ハイフンあり）
新: docker compose up（V2、スペース）
2026年現在、V1は非推奨です。V2を使いましょう。

compose.yaml の例

# compose.yaml（旧 docker-compose.yml）
services:
  app:
    build: .
    ports:
      - "3000:3000"
    environment:
      - DATABASE_URL=postgres://user:pass@db:5432/myapp
    depends_on:
      - db
    volumes:
      - .:/app
      - /app/node_modules

  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: user
      POSTGRES_PASSWORD: pass
      POSTGRES_DB: myapp
    volumes:
      - postgres_data:/var/lib/postgresql/data
    ports:
      - "5432:5432"

volumes:
  postgres_data:

主要な設定

設定 説明
build Dockerfileからビルド
image 既存イメージを使用
ports ポートマッピング（ホスト:コンテナ）
environment 環境変数
volumes データ永続化、ホストマウント
depends_on 起動順序の依存関係

よく使うコマンド

# 起動（バックグラウンド）
docker compose up -d

# ログを見る
docker compose logs -f app

# 停止
docker compose down

# 停止してボリュームも削除
docker compose down -v

# 再ビルドして起動
docker compose up -d --build

7. ボリュームとネットワーク

🎯 このページのゴール

データ永続化とコンテナ間通信の仕組みを理解する

ボリューム（Volume）

コンテナは一時的です。停止・削除するとデータも消えます。
ボリュームを使うと、データをコンテナ外に永続化できます。

ボリュームの種類

種類 書き方 用途
名前付きボリューム postgres_data:/var/lib/postgresql 本番環境、データ永続化
バインドマウント ./src:/app/src 開発環境、ホットリロード
匿名ボリューム /app/node_modules 一時データ、キャッシュ

ネットワーク

Docker Composeでは、サービス名でコンテナ間通信ができます。 

# appコンテナからdbコンテナへ接続
# IPアドレスではなくサービス名「db」を使う
DATABASE_URL=postgres://user:pass@db:5432/myapp
#                             ↑ サービス名

8. セキュリティ基礎

🎯 このページのゴール

コンテナセキュリティの基本原則を理解する

コンテナセキュリティの原則

  1. 最小権限の原則: 必要最小限の権限で実行
  2. 最小イメージの原則: 必要最小限のものだけ含める
  3. 不変性の原則: イメージは変更せず、新しいバージョンを作る

非rootユーザーで実行

危険: rootで実行
FROM node:22-alpine
# USER指定なし = root
CMD ["node", "index.js"]

脆弱性があると、ホストに影響する可能性

安全: 非rootユーザー
FROM node:22-alpine
RUN addgroup -S app && \
    adduser -S app -G app
USER app
CMD ["node", "index.js"]

権限が制限され、被害を最小化

読み取り専用ファイルシステム

# docker run で読み取り専用にする
docker run --read-only --tmpfs /tmp myapp

# compose.yaml で設定
services:
  app:
    image: myapp
    read_only: true
    tmpfs:
      - /tmp

シークレット管理

危険: イメージに埋め込み
ENV DATABASE_PASSWORD=secret123
# イメージに残り続ける
安全: 実行時に渡す
# .envファイルを使用
docker compose --env-file .env up

# または環境変数で渡す
docker run -e DATABASE_PASSWORD myapp
⚠️ レビュー観点: セキュリティチェックリスト
  • rootユーザーで実行していないか
  • シークレットがDockerfileに含まれていないか
  • 不要なパッケージがインストールされていないか
  • ベースイメージは信頼できるものか
  • リソース制限（CPU/メモリ）が設定されているか
🔍 コードレビューの観点
  • マルチステージビルドの未使用：本番イメージにdevDependencies、TypeScript、ESLintなどビルドツールが残っている。イメージサイズが肥大化し、攻撃対象面が広がる
  • .dockerignore の不足：node_modules、.git、.envがイメージに含まれていないか。特に.envはシークレット漏洩の原因になる
  • ROOTユーザーでの実行：USER命令がないDockerfileはroot実行。コンテナが侵害された場合、ホストにも影響が及ぶ可能性がある

9. 脆弱性スキャン

🎯 このページのゴール

コンテナイメージの脆弱性スキャン方法を理解する

なぜスキャンが必要？

2026年の調査によると、約87%のコンテナイメージに 高/重大な脆弱性が存在しています。
定期的なスキャンは必須です。

主要なスキャンツール

ツール 特徴 使い方
Trivy OSS、高速、包括的 trivy image myapp:latest
Docker Scout Docker公式、Docker Desktop統合 docker scout cves myapp:latest
Grype OSS、Anchore製、SBOM対応 grype myapp:latest

Trivyの使い方

# イメージをスキャン
trivy image node:22-alpine

# 高・重大な脆弱性のみ表示
trivy image --severity HIGH,CRITICAL myapp:latest

# CI/CDで使う（脆弱性があれば失敗）
trivy image --exit-code 1 --severity HIGH,CRITICAL myapp:latest

CI/CD統合の例（GitHub Actions）

name: Security Scan

on: push

jobs:
  scan:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Build image
        run: docker build -t myapp:${{ github.sha }} .

      - name: Run Trivy vulnerability scanner
        uses: aquasecurity/trivy-action@0.33.1
        with:
          image-ref: myapp:${{ github.sha }}
          severity: 'HIGH,CRITICAL'
          exit-code: '1'
⚠️ レビュー観点

CI/CDパイプラインに脆弱性スキャンが組み込まれているか確認。
スキャンなしで本番デプロイされているのはリスクです。

10. 本番運用

🎯 このページのゴール

本番環境でのコンテナ運用ベストプラクティスを理解する

ヘルスチェック

HEALTHCHECK命令で、コンテナの健全性を監視できます。
異常を検知すると、オーケストレーターが自動で再起動します。 

FROM node:22-alpine
# ... 省略 ...

HEALTHCHECK --interval=30s --timeout=3s --start-period=5s --retries=3 \
  CMD wget --no-verbose --tries=1 --spider http://localhost:3000/health || exit 1

CMD ["node", "index.js"]

リソース制限

リソース制限がないと、1つのコンテナがホストの全リソースを消費する可能性があります。 

# docker run でリソース制限
docker run --memory=512m --cpus=0.5 myapp

# compose.yaml で設定
services:
  app:
    image: myapp
    deploy:
      resources:
        limits:
          memory: 512M
          cpus: '0.5'
        reservations:
          memory: 256M
          cpus: '0.25'

ログ管理

アンチパターン
// ファイルにログ出力
fs.appendFileSync('/app/logs/app.log', msg);

コンテナ内のファイルはコンテナと共に消える

ベストプラクティス
// 標準出力にログ出力
console.log(JSON.stringify({
  level: 'info',
  message: 'Request received',
  timestamp: new Date().toISOString()
}));

Docker/K8sがログを収集・転送
