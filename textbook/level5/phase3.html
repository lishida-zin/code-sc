1. AWSの全体像

🎯 このページのゴール

AWSのリージョン/AZ構成と主要サービスの分類を理解する

AWS（Amazon Web Services）とは？

AWSは、Amazonが提供する世界最大のクラウドプラットフォームです。
2006年にサービス開始し、2026年現在世界シェア約32%でトップを維持しています。

💡 たとえ話

AWSは「巨大なレンタルサーバー倉庫」のようなものです。
自分でサーバーを買って管理する代わりに、必要な分だけ借りて使います。
電気代・冷房・セキュリティはAmazonが管理してくれます。

リージョンとアベイラビリティゾーン（AZ）

主要サービスの分類

カテゴリ サービス 用途
コンピューティング EC2, Lambda, ECS, Fargate サーバー、コンテナ、サーバーレス
ストレージ S3, EBS, EFS オブジェクト、ブロック、ファイル
データベース RDS, Aurora, DynamoDB リレーショナル、NoSQL
ネットワーク VPC, Route 53, CloudFront 仮想ネットワーク、DNS、CDN
セキュリティ IAM, KMS, WAF 認証認可、暗号化、ファイアウォール

2. IAM基礎

🎯 このページのゴール

IAMのユーザー/グループ/ロール/ポリシーの関係を理解する

IAM（Identity and Access Management）とは？

IAMは、「誰が」「何を」「どこで」できるかを管理するサービスです。
AWSセキュリティの最も重要な基盤です。

💡 たとえ話

IAMは「会社のセキュリティカードシステム」のようなものです。
社員証（ユーザー）を持っていても、すべての部屋に入れるわけではない。
部署（グループ）によって入れる部屋（権限）が違います。

IAMの4つの要素

ユーザー vs ロール

IAMユーザー
  • 人間がAWSを操作する時に使う
  • パスワードやアクセスキーで認証
  • 長期的な認証情報
  • 例: 開発者、運用担当者
IAMロール
  • サービスやアプリが使う
  • 一時的な認証情報を自動発行
  • アクセスキー不要でセキュア
  • 例: EC2、Lambda、外部サービス
⚠️ レビュー観点: rootユーザー使用

rootユーザー（AWSアカウント作成時のユーザー）を 日常業務で使っているコードや設定は即座にNGです。
rootには全権限があり、誤操作や漏洩時の被害が甚大です。

3. IAMベストプラクティス

🎯 このページのゴール

最小権限の原則とIAMセキュリティのベストプラクティスを理解する

最小権限の原則（Principle of Least Privilege）

必要最小限の権限のみを付与するというセキュリティの基本原則です。
「念のため全部許可」は最大のアンチパターンです。

危険: 過剰な権限
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": "*",
    "Resource": "*"
  }]
}

全サービス全操作を許可 = 管理者権限と同等

安全: 最小権限
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": [
      "s3:GetObject",
      "s3:PutObject"
    ],
    "Resource": "arn:aws:s3:::my-bucket/*"
  }]
}

特定バケットの読み書きのみ許可

IAMセキュリティベストプラクティス

項目 推奨事項 理由
rootユーザー 日常使用禁止、MFA必須 全権限があり被害が甚大
MFA 全IAMユーザーに設定 パスワード漏洩時の防御
アクセスキー ロールで代替、定期ローテーション 長期キーは漏洩リスク高
ポリシー AWS管理ポリシー優先 AWSが最新のベストプラクティスを反映
グループ ユーザーに直接権限付与しない 管理が煩雑になる

MFA（多要素認証）の重要性

アクセスキーの管理

危険: アクセスキーをコードに埋め込み
// 絶対NG！
const AWS = require('aws-sdk');
AWS.config.update({
  accessKeyId: 'AKIAIOSFODNN7EXAMPLE',
  secretAccessKey: 'wJalrXUtnFEMI...'
});
安全: 環境変数 or IAMロール
// EC2/Lambda: IAMロールを使用（推奨）
const AWS = require('aws-sdk');
// 自動的にロールの認証情報を使用

// ローカル開発: 環境変数
// AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY
// を環境変数に設定（コードに書かない）

4. EC2基礎

🎯 このページのゴール

EC2のインスタンスタイプ、AMI、セキュリティグループを理解する

EC2（Elastic Compute Cloud）とは？

EC2は、AWSで仮想サーバーを起動できるサービスです。
数分でサーバーを起動し、使った分だけ課金されます。

💡 たとえ話

EC2は「レンタルパソコン」のようなものです。
必要なスペックのPCを必要な時間だけ借りられます。
使い終わったら返却（停止/終了）すれば料金が止まります。

インスタンスタイプ

ファミリー 用途 例
t系（汎用バースト） 開発環境、小規模サイト t3.micro, t3.small
m系（汎用） Webサーバー、アプリサーバー m6i.large, m7g.xlarge
c系（コンピューティング最適化） CPU負荷の高い処理 c6i.xlarge
r系（メモリ最適化） データベース、キャッシュ r6i.large
g/p系（GPU） 機械学習、動画処理 g5.xlarge, p4d.24xlarge

AMI（Amazon Machine Image）

AMIは、EC2の「テンプレート」です。
OS + 必要なソフトウェアがインストール済みの状態を保存したものです。 

# よく使うAMI
Amazon Linux 2023    # AWS推奨、軽量、無料
Ubuntu 22.04 LTS     # 人気のLinuxディストリビューション
Windows Server 2022  # Windows環境が必要な場合

セキュリティグループ

セキュリティグループは、EC2の仮想ファイアウォールです。
許可するトラフィック（ポート、IPアドレス）を定義します。

危険: 全ポート全世界開放
# セキュリティグループ（インバウンド）
Type: All traffic
Source: 0.0.0.0/0   # 全世界からアクセス可能

攻撃者が任意のポートにアクセス可能

安全: 必要最小限のポート
# セキュリティグループ（インバウンド）
Type: HTTPS (443)
Source: 0.0.0.0/0   # Webは全世界OK

Type: SSH (22)
Source: 10.0.0.0/8  # SSHは社内ネットワークのみ
⚠️ レビュー観点: セキュリティグループ
  • 0.0.0.0/0（全世界）からSSH(22)やRDP(3389)を許可していないか
  • 全ポート開放（-1 または 0-65535）していないか
  • 不要なポートが開いていないか

5. VPC基礎

🎯 このページのゴール

VPCのサブネット、ルートテーブル、NAT Gatewayを理解する

VPC（Virtual Private Cloud）とは？

VPCは、AWS上に作成する自分専用の仮想ネットワークです。
IPアドレス範囲、サブネット、ルーティングを自由に設計できます。

💡 たとえ話

VPCは「自社ビル」のようなものです。
パブリックサブネット = 1階の受付（外部からアクセス可能）
プライベートサブネット = 上階のオフィス（関係者のみ）
NAT Gateway = 社員が外出するための出口

VPC構成の基本

サブネットの種類

種類 インターネット接続 用途 配置するもの
パブリックサブネット 直接可能（IGW経由） 外部公開が必要なリソース ALB, NAT Gateway, 踏み台
プライベートサブネット NAT経由で外向きのみ 外部から隠すリソース EC2, RDS, Lambda

NAT Gateway

NAT Gatewayは、プライベートサブネットのリソースが インターネットにアクセスするための出口です。
外からの接続は受け付けず、内からの接続のみ許可します。

危険: DBをパブリックサブネットに配置
# RDSをパブリックサブネットに配置
# インターネットから直接アクセス可能
Publicly accessible: Yes

DBが攻撃対象になる

安全: DBはプライベートサブネット
# RDSをプライベートサブネットに配置
# EC2経由でのみアクセス可能
Publicly accessible: No
Subnet: private-subnet-a, private-subnet-c
⚠️ レビュー観点: VPCセキュリティ
  • RDSがパブリックサブネットにないか
  • EC2に不必要にパブリックIPが付与されていないか
  • 複数AZに分散されているか（高可用性）

6. S3（Simple Storage Service）

🎯 このページのゴール

S3のバケット、アクセス制御、暗号化を理解する

S3とは？

S3は、AWSのオブジェクトストレージサービスです。
ファイル（画像、動画、バックアップなど）を保存し、 99.999999999%（イレブンナイン）の耐久性を提供します。

💡 たとえ話

S3は「無限に拡張できるクラウドのUSBメモリ」です。
バケット = フォルダ（ファイルを入れる箱）
オブジェクト = ファイル
キー = ファイルパス（ファイル名）

S3の基本概念

アクセス制御

S3のアクセス制御は複数のレイヤーがあります。

レイヤー 説明 優先度
ブロックパブリックアクセス バケット全体のパブリックアクセスを一括ブロック 最優先（推奨ON）
バケットポリシー バケット単位のJSON形式ポリシー 高
IAMポリシー IAMユーザー/ロールへの権限付与 中
ACL（非推奨） レガシーなアクセス制御リスト 低（使わない）
危険: パブリックバケット
# ブロックパブリックアクセスが無効
Block all public access: OFF

# バケットポリシーで全世界に公開
{
  "Effect": "Allow",
  "Principal": "*",
  "Action": "s3:GetObject",
  "Resource": "arn:aws:s3:::my-bucket/*"
}

機密データが全世界に公開される

安全: プライベートバケット
# ブロックパブリックアクセスが有効
Block all public access: ON

# IAMロール経由でのみアクセス
{
  "Effect": "Allow",
  "Principal": {
    "AWS": "arn:aws:iam::123456789:role/AppRole"
  },
  "Action": ["s3:GetObject", "s3:PutObject"],
  "Resource": "arn:aws:s3:::my-bucket/*"
}

暗号化

種類 説明 用途
SSE-S3 S3管理キーで暗号化（デフォルト） 一般的な用途
SSE-KMS KMSキーで暗号化、監査ログ取得可能 コンプライアンス要件
SSE-C 顧客管理キーで暗号化 独自キー管理が必要な場合
⚠️ レビュー観点: S3セキュリティ
  • ブロックパブリックアクセスが有効か
  • バケットポリシーに"Principal": "*"がないか
  • 暗号化が有効か（2023年以降デフォルトON）
  • バージョニングが有効か（誤削除対策）

7. RDS / Aurora

🎯 このページのゴール

マネージドDBのRDS/Aurora、Multi-AZ、リードレプリカを理解する

RDS（Relational Database Service）とは？

RDSは、AWSのマネージドリレーショナルデータベースサービスです。
バックアップ、パッチ適用、レプリケーションをAWSが自動管理します。

対応エンジン

エンジン 特徴
Amazon Aurora AWS独自開発、MySQL/PostgreSQL互換、高性能
PostgreSQL 高機能、拡張性が高い
MySQL 最も普及、情報が多い
MariaDB MySQLからフォーク、オープンソース
SQL Server Microsoft製、Windows環境向け
Oracle エンタープライズ向け、ライセンス持ち込み可

Multi-AZ（高可用性）

リードレプリカ（読み取り性能向上）

リードレプリカは、読み取り専用のコピーです。
読み取り処理を分散し、プライマリの負荷を軽減します。 

// アプリケーションでの使い分け
// 書き込み → プライマリ
const primary = 'db-primary.xxx.rds.amazonaws.com';
await primary.query('INSERT INTO users VALUES (...)');

// 読み取り → リードレプリカ
const replica = 'db-replica.xxx.rds.amazonaws.com';
await replica.query('SELECT * FROM users WHERE ...');

RDS vs Aurora

観点 RDS Aurora
性能 標準 MySQL比5倍、PostgreSQL比3倍
ストレージ 手動拡張（最大64TB） 自動拡張（最大128TB）
レプリカ 最大5台 最大15台
コスト 安い 約20%高い
推奨用途 小〜中規模、コスト重視 大規模、性能重視
⚠️ レビュー観点: RDS/Aurora
  • 本番環境でMulti-AZが無効になっていないか（Single-AZ = 単一障害点）
  • 自動バックアップが有効か、保持期間は適切か
  • 暗号化が有効か（作成後は変更不可）
  • パブリックアクセスが無効か

8. Lambda（サーバーレス）

🎯 このページのゴール

サーバーレスの概念とLambdaの制限事項を理解する

Lambdaとは？

Lambdaは、サーバーを管理せずにコードを実行できるサービスです。
イベント（HTTPリクエスト、S3アップロードなど）をトリガーに実行されます。

💡 たとえ話

Lambdaは「タクシー」のようなものです。
自分で車（サーバー）を持つ必要がなく、必要な時だけ呼んで使います。
使った距離（実行時間）だけ料金が発生します。

サーバーレス vs サーバーあり

Lambdaのイベントソース

イベントソース 用途例
API Gateway REST API、WebSocket
S3 ファイルアップロード時の処理（リサイズ等）
DynamoDB Streams データ変更時のトリガー
SQS メッセージキュー処理
EventBridge（CloudWatch Events） スケジュール実行（cron）

Lambdaの制限事項（重要）

⚠️ Lambdaの主な制限
項目 制限 注意点
実行時間 最大15分 長時間処理には不向き
メモリ 128MB〜10GB メモリに応じてCPUも増加
同時実行数 デフォルト1000/リージョン 引き上げ申請可能
デプロイパッケージ 50MB（直接）/ 250MB（S3経由） レイヤーで分割可能
/tmp領域 512MB〜10GB 一時ファイル用

コールドスタート

コールドスタートとは、しばらく実行されていないLambdaが 初めて呼び出される際に発生する遅延（数百ms〜数秒）です。

コールドスタートが問題になるケース
  • レイテンシに厳しいAPI
  • 大きなデプロイパッケージ
  • VPC内Lambda（ENI作成に時間）
対策
  • Provisioned Concurrency: 事前にウォーム状態を維持
  • パッケージサイズの最小化
  • 定期的なウォームアップ呼び出し

9. ECS / Fargate

🎯 このページのゴール

ECS/Fargateでのコンテナオーケストレーションとタスク定義を理解する

ECS（Elastic Container Service）とは？

ECSは、AWSのコンテナオーケストレーションサービスです。
Dockerコンテナを簡単にデプロイ、管理、スケールできます。

起動タイプ: EC2 vs Fargate

観点 EC2起動タイプ Fargate
サーバー管理 必要（パッチ、スケーリング等） 不要（AWS管理）
コスト 安い（大規模時） やや高い
柔軟性 高い（GPU等特殊要件対応） 制限あり
推奨用途 大規模、特殊要件 一般的なWebアプリ（推奨）

ECSの主要概念

概念 説明 K8sとの対応
クラスター タスクを実行する論理的なグループ Cluster
タスク定義 コンテナの設計図（イメージ、CPU、メモリ等） Pod定義
タスク タスク定義から起動された実行インスタンス Pod
サービス タスクの実行数を維持、ロードバランサー連携 Deployment + Service

        }

        {

10. コスト管理

🎯 このページのゴール

AWSの料金モデル、Cost Explorer、予算アラートを理解する

AWSの料金モデル

AWSは基本的に従量課金です。
使った分だけ支払いますが、放置すると予想外の請求が来ることも。

💡 たとえ話

AWSの料金は「電気代」のようなものです。
使った分だけ請求されますが、エアコンを消し忘れると大変なことに。
AWSでも、リソースを消し忘れると高額請求のリスクがあります。

主なコスト要因

サービス 課金要素 注意点
EC2 インスタンス稼働時間 停止忘れ、不要なインスタンス
RDS インスタンス稼働時間、ストレージ Multi-AZは2倍、スナップショット
S3 ストレージ量、リクエスト数、転送量 古いバージョンの蓄積
Lambda 実行回数、実行時間、メモリ 無限ループ、過剰なメモリ設定
NAT Gateway 稼働時間、転送量 意外と高額（約4,000円/月〜）
データ転送 アウトバウンド転送量 リージョン間、インターネット転送

購入オプション（EC2/RDS）

コスト管理ツール

ツール 用途
Cost Explorer コストの可視化、分析、予測
AWS Budgets 予算設定、アラート通知
Cost Anomaly Detection 異常なコスト増加の自動検出
Trusted Advisor 未使用リソースの検出、最適化提案

予算アラートの設定（必須）

# AWS CLIで予算アラートを作成
aws budgets create-budget \
  --account-id 123456789012 \
  --budget '{
    "BudgetName": "Monthly-Budget",
    "BudgetLimit": {
      "Amount": "100",
      "Unit": "USD"
    },
    "BudgetType": "COST",
    "TimeUnit": "MONTHLY"
  }' \
  --notifications-with-subscribers '[{
    "Notification": {
      "NotificationType": "ACTUAL",
      "ComparisonOperator": "GREATER_THAN",
      "Threshold": 80
    },
    "Subscribers": [{
      "SubscriptionType": "EMAIL",
      "Address": "your-email@example.com"
    }]
  }]'
⚠️ レビュー観点: コスト管理
  • 予算アラートが設定されているか（設定なし = 野放し）
