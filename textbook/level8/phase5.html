同値分割法とは

同値分割法（Equivalence Partitioning）とは、入力データを「同じ振る舞いをするグループ」に分け、各グループから代表値を1つ選んでテストする技法です。

🏠 たとえ話：りんごの品質検査

1000個のりんごを検査するとき、全部調べますか？

実際には「大きさ」「色」「産地」でグループ分けし、
各グループから数個だけ抜き取り検査します。

同値分割も同じ。同じ結果になるはずの入力をグループ化し、代表を1つテストします。

📊 同値クラスの分類イメージ

同値分割の手順

📝 実践手順
  1. 仕様を確認：有効な入力範囲を特定
  2. 同値クラスを分類：有効クラス・無効クラスに分ける
  3. 代表値を選択：各クラスから1つずつ選ぶ
  4. テストケース作成：代表値でテストを実行

実践例：ユーザー登録フォーム

💻 仕様：ユーザー名（3〜20文字の英数字）
同値クラス 説明 代表値 期待結果
有効クラス 3〜20文字の英数字 "user123" 成功
無効クラス1 2文字以下 "ab" エラー
無効クラス2 21文字以上 "abcdefghijklmnopqrstu" エラー
無効クラス3 特殊文字を含む "user@123" エラー
無効クラス4 空文字 "" エラー
効率的なテスト
// 5つのテストケースで網羅
test("有効: 通常の入力", () => {
  expect(validate("user123")).toBe(true);
});

test("無効: 短すぎる", () => {
  expect(validate("ab")).toBe(false);
});

test("無効: 長すぎる", () => {
  expect(validate("a".repeat(21))).toBe(false);
});

test("無効: 特殊文字", () => {
  expect(validate("user@123")).toBe(false);
});

test("無効: 空文字", () => {
  expect(validate("")).toBe(false);
});
非効率なテスト
// ❌ 同じクラスを何度もテスト
test("3文字", () => {...});
test("4文字", () => {...});
test("5文字", () => {...});
test("6文字", () => {...});
// ...延々と続く

// 同値クラス内の値は
// 同じ結果になるはずなので無駄
🔍 コードレビューの観点
  • 同値クラスが網羅されているか：有効・無効の両方をテストしているか
  • 無駄な重複がないか：同じクラス内で複数テストしていないか
  • 特殊な無効クラスを見落としていないか：null、空文字、型違いなど
🤖 AIがやりがちな間違い
  • 有効クラスだけテスト：正常系ばかりで異常系を忘れる
  • 同値クラス内で複数テスト：「念のため」と無駄なテストを追加
  • 境界値との混同：同値分割は「代表値」、境界値は「端の値」

境界値分析

📚 このページで学ぶこと

  • 境界の両側をテストする方法
  • off-by-oneエラーの発見

境界値分析とは

境界値分析（Boundary Value Analysis）とは、同値クラスの「境界」に着目してテストする技法です。バグは境界付近に集中する傾向があります。

🏠 たとえ話：国境の警備

国の内部より国境でトラブルが起きやすい。

プログラムも同じ。「ちょうど18歳」「ちょうど0円」のような境界でバグが発生しやすいのです。

なぜ境界でバグが起きるのか

⚠️ off-by-oneエラー

「1つずれる」エラーは最も多いバグの一つです。 

// ❌ off-by-oneエラーの例
if (age > 18) {  // 18歳は成人？未成年？
  return "成人";
}

// ⭕ 正しい実装
if (age >= 18) {  // 18歳以上が成人
  return "成人";
}

境界値の選び方

📊 境界値テストのポイント
📝 テストすべき境界値（2値分析 vs 3値分析）
手法 テスト値 説明
2値分析 0, 1, 100, 101 境界の両側だけテスト（最小限）
3値分析 0, 1, 2, 99, 100, 101 境界とその隣もテスト（より確実）

実践例：配列のインデックス

バグのあるコード
function getElement(arr, index) {
  // ❌ 境界チェックが不完全
  if (index > arr.length) {
    throw new Error("範囲外");
  }
  return arr[index];
}

// index = arr.length でエラーにならない
// → 実際にはundefinedが返る
正しいコード
function getElement(arr, index) {
  // ⭕ 正しい境界チェック
  if (index < 0 || index >= arr.length) {
    throw new Error("範囲外");
  }
  return arr[index];
}

// 境界値テスト
// index = -1 → エラー
// index = 0 → OK
// index = length-1 → OK
// index = length → エラー
✓ 境界値テストのテンプレート 
describe("境界値テスト: 1〜100の範囲", () => {
  // 下限の境界
  test("0は無効（境界外）", () => {
    expect(validate(0)).toBe(false);
  });

  test("1は有効（最小境界値）", () => {
    expect(validate(1)).toBe(true);
  });

  // 上限の境界
  test("100は有効（最大境界値）", () => {
    expect(validate(100)).toBe(true);
  });

  test("101は無効（境界外）", () => {
    expect(validate(101)).toBe(false);
  });
});
🔍 コードレビューの観点
  • < と <= の使い分け：off-by-oneエラーの温床
  • 配列アクセスの境界：0始まりのインデックスを意識しているか
  • ループの終了条件：< length か <= length か
🤖 AIがやりがちな間違い 
// AIが書きがちな曖昧な境界チェック
if (value > 0 && value < 100) {
  // 0と100は含まれる？含まれない？
  // 仕様を確認せずに書いている
}

→ 仕様を明確にし、境界を含むか含まないかを明示的に

デシジョンテーブルとは

デシジョンテーブル（Decision Table）とは、複数の条件とその結果を表形式で整理し、全ての組み合わせを網羅するテスト技法です。

🏠 たとえ話：料金表

電車の料金は「大人/子供」「平日/休日」「普通/特急」などの条件の組み合わせで決まります。

デシジョンテーブルは、このような条件と結果の対応表を作る技法です。

デシジョンテーブルの構造

📊 デシジョンテーブルの構造

実践例：割引計算

💻 仕様：ECサイトの割引ルール
  • 会員は10%割引
  • 5000円以上で送料無料
  • 会員かつ5000円以上でさらに5%割引
R1 R2 R3 R4
条件：会員 Y Y N N
条件：5000円以上 Y N Y N
結果：割引率 15% 10% 0% 0%
結果：送料 無料 有料 無料 有料
✓ テストコードへの変換 
describe("割引計算", () => {
  // R1: 会員 + 5000円以上
  test("会員で5000円以上は15%割引+送料無料", () => {
    const result = calculate(true, 6000);
    expect(result.discount).toBe(0.15);
    expect(result.shipping).toBe(0);
  });

  // R2: 会員 + 5000円未満
  test("会員で5000円未満は10%割引+送料有料", () => {
    const result = calculate(true, 3000);
    expect(result.discount).toBe(0.10);
    expect(result.shipping).toBe(500);
  });

  // R3: 非会員 + 5000円以上
  test("非会員で5000円以上は割引なし+送料無料", () => {
    const result = calculate(false, 6000);
    expect(result.discount).toBe(0);
    expect(result.shipping).toBe(0);
  });

  // R4: 非会員 + 5000円未満
  test("非会員で5000円未満は割引なし+送料有料", () => {
    const result = calculate(false, 3000);
    expect(result.discount).toBe(0);
    expect(result.shipping).toBe(500);
  });
});
🔍 コードレビューの観点
  • 全ての組み合わせをカバーしているか：条件がN個なら2^N通り
  • 矛盾するルールがないか：同じ条件で異なる結果になっていないか
  • 抜け漏れがないか：特に「どちらでもない」ケース

状態遷移テストとは

状態遷移テスト（State Transition Testing）とは、システムの「状態」と「状態間の遷移」に着目してテストを設計する技法です。

🏠 たとえ話：信号機

信号機は「赤」→「青」→「黄」→「赤」と状態が変化します。

「赤から直接黄になる」のは無効な遷移。これをテストで検出します。

状態遷移図の例

📊 ログイン機能の状態遷移図

テストケースの導出

📝 状態遷移からテストケースを作成
No 初期状態 イベント 期待する遷移先
1 未ログイン 正しい認証情報でログイン ログイン済み
2 未ログイン 間違った認証情報で3回失敗 ロック
3 ログイン済み ログアウト 未ログイン
4 ロック 管理者が解除 未ログイン
5 ロック ログイン試行 遷移しない（無効）
⚠️ 無効な遷移をテストする重要性

無効な遷移とは、許可されていない状態変化のことです。 

// ロック状態からログインできてはいけない
test("ロック状態ではログインできない", () => {
  user.state = "locked";

  const result = user.login("correct", "password");

  expect(result.success).toBe(false);
  expect(user.state).toBe("locked"); // 状態は変わらない
});
🔍 コードレビューの観点
  • 全ての状態遷移がテストされているか
  • 無効な遷移が適切にブロックされているか
  • 状態の初期化・リセットが正しいか
  • 並行処理での状態不整合がないか
🤖 AIがやりがちな間違い
  • 正常系の遷移だけテスト：無効な遷移を見落とす
  • 状態の前提条件を無視：「ログイン済み」でないと使えない機能をテストしない
  • 状態リセットを忘れる：前のテストの状態が残ってしまう

組み合わせ爆発の問題

複数のパラメータがある場合、全ての組み合わせをテストすると爆発的にケース数が増加します。

⚠️ 組み合わせ爆発の例
パラメータ 選択肢数
OS3（Windows, Mac, Linux）
ブラウザ4（Chrome, Firefox, Safari, Edge）
解像度3（HD, FHD, 4K）
言語5（日本語, 英語, 中国語, 韓国語, スペイン語）

全組み合わせ：3 × 4 × 3 × 5 = 180ケース
ペアワイズ：約20ケースで2因子間の組み合わせを網羅

ペアワイズ法とは

ペアワイズ法（All-Pairs Testing）とは、全ての2因子の組み合わせを最小のテストケース数で網羅する技法です。

📊 ペアワイズの考え方
💡 なぜペアワイズで十分なのか

研究によると、ソフトウェアの不具合の70〜90%は1〜2因子の組み合わせで発見できます。

3因子以上の複雑な相互作用によるバグは稀です。

PICTツールの使い方

🔧 PICT（Pairwise Independent Combinatorial Testing）

Microsoftが開発したペアワイズテストケース生成ツールです。

# model.txt
OS: Windows, Mac, Linux
Browser: Chrome, Firefox, Safari, Edge
Resolution: HD, FHD, 4K
Language: Japanese, English, Chinese

# コマンド実行
$ pict model.txt

# 出力例（約15-20ケース）
OS       Browser  Resolution  Language
Windows  Chrome   HD          Japanese
Mac      Firefox  FHD         English
Linux    Safari   4K          Chinese
Windows  Edge     FHD         Chinese
...
✓ PICTの便利な機能 
# 制約条件の指定
IF [OS] = "Mac" THEN [Browser] <> "Edge";

# 重み付け（重要な組み合わせを優先）
OS: Windows (2), Mac, Linux
# Windowsが2倍の頻度で出現

# 負の値（無効な値）のテスト
Resolution: HD, FHD, 4K, ~Invalid
🔍 コードレビューの観点
  • 組み合わせテストが必要な箇所を見落としていないか
  • 全組み合わせを愚直にテストしていないか（非効率）
  • 制約条件（無効な組み合わせ）を考慮しているか

探索的テストとは

探索的テスト（Exploratory Testing）とは、テスト設計・実行・学習を同時に行うテスト手法です。事前に詳細なテストケースを作らず、テスターの経験と直感を活かします。

🏠 たとえ話：探検家

地図（テストケース）に従って歩くのではなく、
実際に歩きながら地図を作るのが探索的テスト。

「この道は怪しい」「ここに何かありそう」という直感を大切にします。

スクリプトテスト vs 探索的テスト

スクリプトテスト
  • 事前にテストケースを詳細に設計
  • 手順通りに実行
  • 再現性が高い
  • 自動化しやすい

向いている場面：回帰テスト、コンプライアンス

探索的テスト
  • テスト中に設計・実行・学習
  • テスターの判断で柔軟に進行
  • 予想外のバグを発見しやすい
  • 人間の直感を活用

向いている場面：新機能、複雑なUI、セキュリティ

ユースケーステストとは

ユースケーステストとは、ユーザーが実際にシステムを使うシナリオに基づいてテストを設計する技法です。

🏠 たとえ話：ロールプレイング

「私は会社員の田中さん。朝の通勤電車で、スマホからこのアプリを使って...」

ユーザーになりきって、実際の利用シーンを想像しながらテストします。

ユースケース図からテストを導出

📊 ECサイトのユースケース例

シナリオの作成

📝 基本フロー（正常系） 
【ユースケース】商品を購入する

【前提条件】
- ユーザーはログイン済み
- カートに商品が1つ以上ある

【基本フロー】
1. ユーザーが「購入手続きへ」をクリック
2. システムが配送先選択画面を表示

4. システムが支払い方法選択画面を表示
5. ユーザーが支払い方法を選択
6. システムが注文確認画面を表示
7. ユーザーが「注文を確定」をクリック
8. システムが注文完了画面を表示

【代替フロー】新しい配送先を追加

3d. 基本フローのステップ4に戻る

【例外フロー】在庫切れ
4a. システムが在庫不足を検出
4b. システムがエラーメッセージを表示

  • 実際のユーザー行動を反映しているか

エラー推測とは

エラー推測（Error Guessing）とは、テスターの経験と直感に基づいて「バグが潜んでいそうな場所」を予測してテストする技法です。

🏠 たとえ話：ベテラン医師の勘

ベテラン医師は症状を見ただけで「この病気かも」と推測できます。

同様に、経験豊富なテスターは「ここにバグがありそう」と勘が働くのです。

よくあるバグパターン

ミューテーションテスト

ミューテーションテストとは

ミューテーションテストとは、意図的にコードにバグを埋め込み、テストがそのバグを検出できるかを確認する技法です。「テストのテスト」とも呼ばれます。

🏠 たとえ話：煙感知器のテスト

煙感知器が本当に動くか確認するには、実際に煙を出してみるのが一番確実。

ミューテーションテストも同じ。意図的にバグを入れて、テストが検出できるか確認します。

ミューテーションの仕組み

📊 ミューテーションテストの流れ

ミューテーションの種類

📝 代表的なミューテーション演算子
演算子 元のコード ミュータント
関係演算子 a > b a >= b, a < b, a == b
算術演算子 a + b a - b, a * b, a / b
論理演算子 a && b a || b, !a && b
定数 return 0; return 1; return -1;
削除 if (cond) {...} （条件文を削除）

⚠️ 生存したミュータント（Survived）の対処

ミュータントが「生存」した = テストがそのバグを検出できていない 

// 元のコード
function isAdult(age) {
  return age >= 18;  // ← age > 18 に変異されても検出できない？
}

// 不十分なテスト
test("20歳は成人", () => {
  expect(isAdult(20)).toBe(true);  // 両方trueになる
});

// 改善したテスト
test("18歳は成人", () => {
  expect(isAdult(18)).toBe(true);  // これで >= と > を区別できる
});

test("17歳は未成年", () => {
  expect(isAdult(17)).toBe(false);
});
🔍 コードレビューの観点
  • ミューテーションスコアが低い箇所：テストが不十分
  • 境界条件のテスト：>= と > を区別できているか
  • 条件分岐のテスト：全てのブランチをカバーしているか

リスクベーステスト

📚 このページで学ぶこと

  • リスクの評価方法（影響度 × 発生確率）

リスクベーステストとは

リスクベーステストとは、リスクの高い箇所に優先的にテストリソースを割り当てる戦略的なテスト手法です。

🏠 たとえ話：防犯対策

全ての窓に同じセキュリティをかけますか？
普通は玄関や1階の窓を重点的に守ります。

テストも同じ。リスクが高い機能に重点を置きます。

リスクの評価方法

📊 リスク = 影響度 × 発生確率

リスク分析の実践

📝 リスク分析表の例
機能 影響度 発生確率 リスク テスト優先度
決済処理 高（金銭損失） 中 高 1（最優先）
認証・ログイン 高（セキュリティ） 中 高 1（最優先）
商品検索 中（利便性） 高 中 2
FAQ表示 低（情報のみ） 低 低 3（後回し）
✓ リスク要因の洗い出し
  • ビジネスリスク：金銭、法規制、ブランド毀損
  • 技術リスク：複雑な機能、新技術、外部連携
  • 変更リスク：頻繁に変更される箇所、リファクタリング
  • 過去の障害：以前バグがあった機能

限られた時間でのテスト戦略

💡 時間がないときの優先順位 
【リリースまで残り1日】
1. 決済・認証（高リスク）→ 必ずテスト
2. 今回変更した機能 → スモークテスト
3. その他 → リスクに応じて取捨選択

【テストタイプの優先順位】
1. スモークテスト（基本動作確認）
2. リグレッションテスト（既存機能の確認）
3. 探索的テスト（新機能の深掘り）
4. 非機能テスト（パフォーマンス等）
🔍 コードレビューの観点
  • 高リスク機能のテストが十分か
  • 変更の影響範囲を考慮しているか
  • テストリソースの配分が適切か
🤖 AIがやりがちな間違い
  • 全ての機能を均等にテスト：リスクを考慮していない
  • コードカバレッジだけを追求：ビジネスリスクを無視
  • 変更の影響範囲を見落とす：関連機能のテストを忘れる
