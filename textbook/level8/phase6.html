TDD（テスト駆動開発）とは何か

TDD（Test-Driven Development）とは、
テストを先に書いてから実装する開発手法です。

🏠 たとえ話：試験問題と解答

普通は「解答を作ってから採点」しますが、
TDDは「採点基準（テスト）を先に作ってから解答（実装）を作る」ようなものです。

採点基準が明確だから、「何を作るべきか」がブレません。

Red-Green-Refactorサイクル

TDDは3つのステップを繰り返します。

📊 TDDサイクル
ステップ やること ポイント
1. Red 失敗するテストを書く まだ実装がないので必ず失敗する
2. Green テストを通す最小限のコードを書く 綺麗さは気にしない。動けばOK
3. Refactor コードを綺麗にする テストが通る状態を維持しながら改善

TDDの具体例

💻 例：足し算関数をTDDで作る 
// === Step 1: Red（テストを書く）===
test('add(1, 2)は3を返す', () => {
  expect(add(1, 2)).toBe(3);
});
// → テスト失敗（add関数がない）

// === Step 2: Green（最小実装）===
function add(a, b) {
  return 3; // ハードコード！でもテストは通る
}
// → テスト成功

// === Step 3: 次のテストを追加（Red）===
test('add(2, 3)は5を返す', () => {
  expect(add(2, 3)).toBe(5);
});
// → テスト失敗（3を返すから）

// === Step 4: Green（一般化）===
function add(a, b) {
  return a + b; // 正しい実装
}
// → 両方のテスト成功

// === Step 5: Refactor ===
// この場合、リファクタ不要（既にシンプル）

TDDの利点

✓ TDDのメリット
  • 設計の改善：テストしやすい設計 = 良い設計になる
  • 仕様の明確化：テストが仕様書になる
  • リグレッション防止：変更時に壊れたらすぐ分かる
  • 自信を持ってリファクタ：テストが守ってくれる
  • 過剰実装の防止：必要なものだけ作る（YAGNI）
🔍 コードレビューの観点

以下を見つけたら指摘しましょう：

  • テストなしの実装PR：TDDでなくても、テストは必須
  • テストが後付け感：実装に引きずられたテスト
  • Refactorステップの省略：動くだけで満足していないか

小さなステップの重要性

TDDの核心は「小さなステップで進む」ことです。

🏠 たとえ話：階段を上る

3階に行きたい時、一気にジャンプしようとせず、
一段ずつ階段を上る方が確実です。

TDDも同じ。大きな機能を一気に作らず、小さなテストを一つずつ通していく。

大きすぎるステップ
// ❌ いきなり全機能をテスト
test('ユーザー登録が完全に動作する', () => {
  const result = registerUser({
    email: 'test@example.com',
    password: 'Pass123!',
    name: '田中太郎',
    age: 25,
    address: '東京都...'
  });
  expect(result.success).toBe(true);
  expect(result.user.id).toBeDefined();
  expect(result.emailSent).toBe(true);
  expect(result.dbRecord).toBeDefined();
});
// → 失敗しても原因特定が困難
小さなステップ
// ⭕ 一つずつテスト
test('メール形式を検証できる', () => {
  expect(isValidEmail('test@example.com')).toBe(true);
  expect(isValidEmail('invalid')).toBe(false);
});

test('パスワード強度を検証できる', () => {
  expect(isStrongPassword('Pass123!')).toBe(true);
  expect(isStrongPassword('weak')).toBe(false);
});

test('ユーザーオブジェクトを作成できる', () => {
  const user = createUser({ email: 'test@example.com' });
  expect(user.email).toBe('test@example.com');
});
// → 一つずつ確実に進む

最小実装のテクニック

Green（テストを通す）段階では、最小限の実装でOKです。

💡 3つの実装アプローチ
手法 説明 使いどころ
Fake it ハードコードで通す 最初の一歩、様子見
Obvious 明らかな実装をそのまま書く 簡単で自信がある時
Triangulation 複数テストで一般化を強制 正しい抽象化が分からない時
💻 Triangulationの例 
// テスト1
test('1の階乗は1', () => {
  expect(factorial(1)).toBe(1);
});

// Fake it: ハードコード
function factorial(n) {
  return 1;
}

// テスト2を追加（Triangulation）
test('3の階乗は6', () => {
  expect(factorial(3)).toBe(6);
});

// → ハードコードでは通らない。一般化が必要
function factorial(n) {
  if (n <= 1) return 1;
  return n * factorial(n - 1);
}

リファクタリングのタイミング

⚠️ Refactorステップのルール
  • テストが緑の時だけリファクタする
  • テストを変えずに実装だけ変える
  • 小さな変更を繰り返す（大きな変更は危険）
  • リファクタ後もテストが通ることを確認
💻 リファクタリングの例 
// Before: 動くけど汚い
function calculatePrice(items) {
  let total = 0;
  for (let i = 0; i < items.length; i++) {
    total = total + items[i].price * items[i].quantity;
    if (items[i].discount) {
      total = total - items[i].discount;
    }
  }
  return total;
}

// After: リファクタ後
function calculatePrice(items) {
  return items.reduce((total, item) => {
    const itemTotal = item.price * item.quantity;
    const discount = item.discount || 0;
    return total + itemTotal - discount;
  }, 0);
}
// テストは変更なし → 同じ結果が保証される

// ❌ AIは一気に「完璧な」コードを書きがち

TDDのデメリット

📚 このページで学ぶこと
  • TDDの学習コストと習熟の壁
  • TDDが適さない場面
  • 過度なTDD信仰の危険性

TDDは万能ではない

TDDは強力な手法ですが、全ての場面に適しているわけではありません。

⚠️ TDDの主なデメリット
  • 学習コストが高い：慣れるまで時間がかかる
  • 初期の開発速度低下：最初はテストなしより遅い
  • 設計変更時のテスト書き直し：大きな方針変更に弱い
  • 過剰なテストのリスク：テスト自体が負債になることも

TDDが適さない場面

📊 TDDの適用判断

過度なTDD信仰の危険性

❌ TDD原理主義の問題
  • 「TDDでなければダメ」という思考停止
  • テストカバレッジ100%への執着（価値のないテストが増える）
  • 探索的な開発の阻害（試行錯誤がしにくい）
  • テストのためのテスト（本末転倒）
TDD原理主義
// ❌ 無理にTDDで書いた結果
// getterにまでテストを書く...

test('getNameはnameを返す', () => {
  const user = new User('田中');
  expect(user.getName()).toBe('田中');
});

test('setNameはnameを設定する', () => {
  const user = new User('田中');
  user.setName('鈴木');
  expect(user.getName()).toBe('鈴木');
});
// → 価値が低いテスト
現実的なアプローチ
// ⭕ 価値のあるテストに集中

test('ユーザー名は空にできない', () => {
  const user = new User('田中');
  expect(() => user.setName('')).toThrow();
});

test('ユーザー名は50文字以内', () => {
  const user = new User('田中');
  const longName = 'a'.repeat(51);
  expect(() => user.setName(longName)).toThrow();
});
// → ビジネスルールをテスト

バランスの取れたアプローチ

✓ シニアエンジニアの判断基準
  • コアロジックにはTDD：お金、認証、計算など
  • UIは後からテスト：見た目は試行錯誤が必要
  • プロトタイプはテストなし：検証後に書く
  • チームの習熟度を考慮：無理強いしない
  • ROIを意識：テストのコストと価値を比較
🔍 コードレビューの観点

以下を見つけたら議論しましょう：

  • 価値の低いテストの量産：getter/setterのテストなど
  • 実装の詳細をテスト：privateメソッドのテスト
  • テストのためだけのコード変更：本末転倒

BDD（振る舞い駆動開発）とは何か

BDD（Behavior-Driven Development）とは、
「振る舞い」を自然言語で記述し、それをテストにする開発手法です。

🏠 たとえ話：説明書を先に書く

製品を作る前に、「ユーザーへの説明書」を先に書くイメージです。

「このボタンを押すと、こうなります」という振る舞いの説明が、
そのままテストになります。

TDDとBDDの違い

📊 TDD vs BDD
TDDのテスト
// 開発者向けの技術的なテスト
test('calculateTax returns 10% of price', () => {
  expect(calculateTax(1000)).toBe(100);
});

test('throws error for negative price', () => {
  expect(() => calculateTax(-1)).toThrow();
});
BDDのテスト
// 誰でも読める自然言語
Feature: 消費税計算

  Scenario: 商品に消費税を加算する
    Given 商品価格が1000円のとき
    When 消費税を計算すると
    Then 消費税は100円になる

  Scenario: 不正な価格はエラーになる
    Given 商品価格がマイナスのとき
    When 消費税を計算すると
    Then エラーが発生する

BDDの三者協働

BDDでは「3つの役割」が協力してシナリオを作ります。

👥 Three Amigos（三銃士）
役割 貢献 質問例
ビジネス
（PO/BA）		 「何を」達成したいか 「この機能の価値は？」
開発
（Developer）		 「どう」実現するか 「技術的に可能？」
テスト
（QA）		 「何が」壊れうるか 「エッジケースは？」
✓ BDDのメリット
  • 共通言語：技術者と非技術者が同じ言葉で話せる
  • 生きたドキュメント：テストが仕様書になる
  • 認識のズレ防止：早い段階で誤解を発見
  • 受け入れ基準の明確化：完了条件が明確
🔍 コードレビューの観点：BDDの形骸化

以下を見つけたら指摘しましょう：

  • 開発者だけでシナリオを書いている：三者協働になっていない
  • 技術用語だらけのシナリオ：非技術者が読めない
  • シナリオと実装の乖離：シナリオが更新されていない

Gherkin記法とは

Gherkinとは、BDDでシナリオを書くための構造化された自然言語です。

🏠 たとえ話：レシピの書き方

料理のレシピには決まった形式があります。
「材料」「手順」「完成図」のように、誰が見ても分かる形式です。

Gherkinも同じ。Given（前提）、When（操作）、Then（結果）という
決まった形式でシナリオを書きます。

Gherkinの基本構造

📊 Gherkinの階層構造

Given-When-Thenパターン

キーワード 意味 例
Given 前提条件・初期状態 ユーザーがログイン済みのとき
When アクション・操作 商品をカートに追加すると
Then 期待される結果 カートに商品が表示される
And / But 追加条件・結果 And 合計金額が更新される
💻 Gherkinの実例 
# language: ja

Feature: ショッピングカート
  オンラインショップの顧客として
  商品をカートに追加したい
  購入前に商品を確認するために

  Background:
    Given ユーザーがログインしている
    And カートが空の状態

  Scenario: 商品をカートに追加する
    Given 商品「TypeScript入門」が在庫にある
    When 「カートに追加」ボタンをクリックする
    Then カートに「TypeScript入門」が表示される
    And カート内の商品数が「1」になる

  Scenario: 在庫切れ商品は追加できない
    Given 商品「限定版」が在庫切れ
    When 「カートに追加」ボタンをクリックする
    Then 「在庫切れです」メッセージが表示される
    And カートは空のまま

  Scenario Outline: 複数個追加
    Given 商品「ノート」が在庫にある
    When <数量>個をカートに追加する
    Then カートの合計金額は<合計>円になる

    Examples:
      | 数量 | 合計  |
      | 1    | 100   |
      | 3    | 300   |
      | 10   | 1000  |

BDDツールとは

Gherkinで書いたシナリオを実際のテストコードに変換するツールです。

🏠 たとえ話：翻訳者

Gherkinは「日本語のシナリオ」、テストコードは「プログラムの言葉」。
CucumberやJest-Cucumberは、この2つをつなぐ翻訳者です。

ツール 言語/環境 特徴

Jest-Cucumber JavaScript/TypeScript Jest統合、導入が簡単

ステップ定義とは

Gherkinの各行を実際のコードに紐づけるのがステップ定義です。

📊 ステップ定義の流れ

Jest-Cucumberの実例

💻 1. Featureファイル（login.feature） 
# features/login.feature
Feature: ログイン機能

  Scenario: 正しい認証情報でログインできる
    Given ユーザー "tanaka@example.com" が登録されている
    When パスワード "Password123" でログインする
    Then ログイン成功のメッセージが表示される

  Scenario: 間違ったパスワードではログインできない
    Given ユーザー "tanaka@example.com" が登録されている
    When パスワード "WrongPassword" でログインする
    Then "パスワードが間違っています" エラーが表示される
💻 2. ステップ定義（login.steps.ts） 
// steps/login.steps.ts
import { defineFeature, loadFeature } from 'jest-cucumber';
import { login, createUser } from '../src/auth';

const feature = loadFeature('features/login.feature');

defineFeature(feature, (test) => {
  let result: { success: boolean; message: string };
  let userEmail: string;

  // Given のステップ定義
  const givenUserExists = (given) => {
    given(/^ユーザー "(.+)" が登録されている$/, (email: string) => {
      userEmail = email;
      createUser({ email, password: 'Password123' });
    });
  };

  // When のステップ定義
  const whenLogin = (when) => {
    when(/^パスワード "(.+)" でログインする$/, (password: string) => {
      result = login(userEmail, password);
    });
  };

  test('正しい認証情報でログインできる', ({ given, when, then }) => {
    givenUserExists(given);
    whenLogin(when);

    then('ログイン成功のメッセージが表示される', () => {
      expect(result.success).toBe(true);
      expect(result.message).toBe('ログイン成功');
    });
  });

  test('間違ったパスワードではログインできない', ({ given, when, then }) => {
    givenUserExists(given);
    whenLogin(when);

    then(/^"(.+)" エラーが表示される$/, (errorMessage: string) => {
      expect(result.success).toBe(false);
      expect(result.message).toBe(errorMessage);
    });
  });
});
⚠️ ステップ定義の注意点
  • 正規表現のパターン：引数は正規表現で抽出
  • ステップの再利用：同じステップは共通化する
  • 状態の管理：ステップ間でデータを共有する方法を決める
  • 非同期処理：async/awaitを適切に使う
🔍 コードレビューの観点

以下を見つけたら指摘しましょう：

  • ステップ定義の重複：同じ処理を複数箇所に書いている
  • 巨大なステップ定義：1つのステップに処理を詰め込みすぎ
  • Gherkinとステップの乖離：更新されていない

ATDD（受入テスト駆動開発）とは何か

ATDD（Acceptance Test-Driven Development）とは、
受入テストを先に定義してから開発する手法です。

🏠 たとえ話：合格基準を先に決める

試験を作る時、「何ができたら合格か」を先に決めるのと同じです。

「この機能が完了した」と言える基準（受入条件）を、
開発前にステークホルダー全員で合意します。

TDD/BDD/ATDDの関係

📊 3つの手法の位置づけ
手法 スコープ 主な参加者 成果物
ATDD ユーザーストーリー全体 PO、開発、QA、顧客 受入テスト
BDD 機能の振る舞い PO、開発、QA シナリオテスト
TDD 関数・メソッド 開発者 単体テスト

ATDDのプロセス

💡 ATDDの4ステップ
  1. 議論（Discuss）：ストーリーの意図と受入条件を話し合う
  2. 蒸留（Distill）：受入テストを具体的に書き出す
  3. 開発（Develop）：テストを通すように実装
  4. デモ（Demo）：ステークホルダーに動作を見せる
💻 受入条件の例 
ユーザーストーリー:
「顧客として、過去の注文履歴を見たい。再注文しやすくするために。」

受入条件（Acceptance Criteria）:
1. ログイン済みユーザーは注文履歴ページにアクセスできる
2. 未ログインユーザーはログインページにリダイレクトされる
3. 注文履歴は新しい順に表示される
4. 各注文には日付、商品名、金額、ステータスが表示される
5. 注文がない場合は「注文履歴がありません」と表示される
6. 「再注文」ボタンで同じ商品をカートに追加できる

  • 受入条件がない：何をもって完了か不明
  • 曖昧な受入条件：「使いやすい」など検証不能
  • 実装と受入条件の乖離：条件を満たしていない

テストファースト vs テストラスト

📚 このページで学ぶこと
  • テストファーストとテストラストの違い
  • それぞれのメリット・デメリット
  • 適用場面の判断基準

2つのアプローチ

テストファースト

テストを先に書いてから実装

  • TDD/BDD/ATDDのアプローチ
  • Red → Green → Refactor
  • 仕様を先に確定させる
// 1. テストを書く
test('add(1,2) = 3', () => {
  expect(add(1,2)).toBe(3);
});

// 2. 実装する
function add(a, b) {
  return a + b;
}
テストラスト

実装してからテストを書く

  • 従来型のアプローチ
  • 実装 → テスト追加
  • 動作確認としてのテスト
// 1. 実装する
function add(a, b) {
  return a + b;
}

// 2. テストを書く
test('add(1,2) = 3', () => {
  expect(add(1,2)).toBe(3);
});

メリット・デメリット比較

観点 テストファースト テストラスト
設計品質 高い（テスタブルな設計が自然にできる） 低くなりがち（テスト困難な設計になることも）
初期速度 遅い（テスト作成のオーバーヘッド） 速い（すぐ実装に入れる）
仕様の明確さ 高い（テストが仕様になる） 曖昧になりがち
テスト漏れ 少ない（テスト必須） 起きやすい（後回しにされる）
探索的開発 難しい（仕様確定が必要） やりやすい（試行錯誤しやすい）

適用場面の判断基準

📊 判断フローチャート
✓ シニアエンジニアの判断

テストファーストを選ぶ場面：

  • 金融・医療などバグが許されない領域
  • 仕様が明確に定義されている場合
  • 長期保守が必要なシステム
  • チームにTDDの経験者がいる場合

テストラストでもOKな場面：

  • プロトタイプやスパイク（調査目的）
  • 仕様が頻繁に変わる初期フェーズ
  • スクリプトや使い捨てツール
🤖 AIがやりがちな間違い 
// ❌ AIは実装を先に出力し、テストを後回しにしがち
// さらに、テストが実装に引きずられる

// AIの出力例（テストラスト）
function calculateDiscount(price, discountRate) {
  return price * (1 - discountRate);  // 実装
}

// 後から書いたテスト（実装をなぞっただけ）
test('discount works', () => {
  expect(calculateDiscount(100, 0.1)).toBe(90);
});
// → エッジケース（負の値、100%超え）がテストされない

// ⭕ テストファーストなら
test('割引率0%なら価格そのまま', () => {...});
test('割引率100%なら0円', () => {...});
test('割引率が負の値ならエラー', () => {...});
test('割引率が100%超えならエラー', () => {...});
// → 先にエッジケースを考える

レガシーコードのテスト

📚 このページで学ぶこと
  • レガシーコードとは何か
  • 特性テスト（Characterization Test）
  • スプラウト/ラップ手法

レガシーコードとは

Michael Feathersの定義：
「テストのないコードはレガシーコード」

🏠 たとえ話：古い家のリフォーム

古い家をリフォームする時、構造を理解せずに壁を壊すと大変なことに。

レガシーコードも同じ。テストという安全網なしに変更すると、
思わぬところが壊れます。

⚠️ レガシーコードの特徴
  • テストがないまたは不十分
  • 依存関係が複雑（グローバル変数、密結合）
  • ドキュメントがないまたは古い
  • 動作が仕様（誰も正しい動作を知らない）
  • 変更が怖い（壊れるかもしれない）

特性テスト（Characterization Test）

特性テストとは、現在の動作をそのまま記録するテストです。

💡 特性テストの目的

「正しい動作」ではなく、「今の動作」をテストで固定します。

  • リファクタリング時に動作が変わったことを検知
  • コードを読まなくても動作を理解できる
  • 変更の安全網になる
💻 特性テストの書き方 
// レガシーコード（何をしているか不明）
function mysteryFunction(input) {
  // 複雑な処理...
  return result;
}

// 特性テスト：現在の動作を記録
describe('mysteryFunction の特性テスト', () => {
  test('入力が空配列のとき', () => {
    // 1. 実際に動かして結果を見る
    const result = mysteryFunction([]);
    // 2. その結果をそのままテストにする
    expect(result).toBe(null); // 実際の出力
  });

  test('入力が[1,2,3]のとき', () => {
    const result = mysteryFunction([1, 2, 3]);
    expect(result).toBe(6); // 実際の出力
  });

  test('入力にnullが含まれるとき', () => {
    const result = mysteryFunction([1, null, 3]);
    expect(result).toBe(4); // nullはスキップされる？
  });
});
// これでリファクタリングの準備完了

スプラウト/ラップ手法

レガシーコードに安全に新機能を追加するテクニックです。

スプラウト（Sprout）

新しい機能を別のメソッドとして「芽生えさせる」

// Before: レガシーコード
function processOrder(order) {
  // 複雑な処理...
  // ここに割引計算を追加したい
}

// After: スプラウト
function processOrder(order) {
  // 複雑な処理...
  const discount = calculateDiscount(order);
  // ↑ 新機能は別メソッドに（テスト可能）
}

// 新しいメソッド（テスト付き）
function calculateDiscount(order) {
  // テスト駆動で開発できる
}
ラップ（Wrap）

既存コードを新しいメソッドで「包む」

// Before: レガシーコード
function sendEmail(to, subject, body) {
  // メール送信ロジック
}

// After: ラップ
function sendEmailWithLogging(to, subject, body) {
  logEmailAttempt(to, subject);  // 新機能
  sendEmail(to, subject, body);  // 既存コードを呼ぶ
  logEmailSuccess(to);           // 新機能
}

// 既存コードは変更なし
// 新機能部分だけテスト可能
📊 スプラウト vs ラップ
🔍 コードレビューの観点

以下を見つけたら指摘しましょう：

  • テストなしでレガシーコードを変更：まず特性テストを書くべき
  • 「動いているから触らない」：技術的負債の放置
  • 大規模リファクタリングの一発勝負：小さなステップで進めるべき

リファクタリングとテスト

📚 このページで学ぶこと
  • リファクタリングの定義と重要性
  • テストが守る安全なリファクタリング
  • リファクタリング中のテスト維持

リファクタリングとは

リファクタリングとは、
外部から見た振る舞いを変えずに、内部構造を改善することです。

🏠 たとえ話：部屋の模様替え

部屋を模様替えしても、「寝室」という機能は変わらない。
でも、使いやすく、整理整頓された状態になる。

リファクタリングも同じ。外から見た動きは同じだけど、
中は読みやすく、変更しやすくなる。

テストがリファクタリングを守る

📊 安全なリファクタリングの流れ
⚠️ テストなしリファクタリングの危険 
// テストなしでリファクタリング → 知らぬ間にバグ混入

// Before
function getFullName(user) {
  return user.firstName + ' ' + user.lastName;
}

// After（リファクタリングのつもりが...）
function getFullName(user) {
  return `${user.firstName}${user.lastName}`;  // スペースが消えた！
}

// テストがあれば即座に検知
test('フルネームにスペースが入る', () => {
  const user = { firstName: '田中', lastName: '太郎' };
  expect(getFullName(user)).toBe('田中 太郎');
  // → テスト失敗！バグ発見
});

リファクタリング中のテスト維持

✓ 安全なリファクタリングのルール
  1. テストが全て通っている状態から始める
  2. 小さな変更を1つずつ（大きな変更は分割）
  3. 変更のたびにテスト実行（IDEの自動実行が便利）
  4. テストが落ちたらすぐ戻す（git checkoutなど）
  5. 振る舞いを変えるならテストも変える（別のコミット）
危険なリファクタリング
// ❌ 一度に大きく変更
git commit -m "大規模リファクタリング"
// 変更ファイル: 50個
// テスト: 10個失敗
// → 原因特定が困難
安全なリファクタリング
// ⭕ 小さく刻んで変更
git commit -m "変数名をuserIdに統一"
// テスト: 全パス

git commit -m "calculateTotal関数を抽出"
// テスト: 全パス

git commit -m "マジックナンバーを定数化"
// テスト: 全パス

テスト自体のリファクタリング

💡 テストコードも保守対象

テストコードもリファクタリングが必要です。
ただし、プロダクションコードと同時には変更しない。 

// ❌ 同時に変更（危険）
git commit -m "計算ロジックとテストを両方リファクタ"
// → どちらに問題があるか分からない

// ⭕ 別々に変更（安全）
git commit -m "テストのヘルパー関数を追加"
// テスト: 全パス（テストの動作は同じ）

git commit -m "計算ロジックをリファクタ"
// テスト: 全パス（テストが保護）
🤖 AIがやりがちな間違い 
// ❌ AIにリファクタリングを頼むと一気に変更しがち

// Before（AI入力）
function processData(data) {
  // 100行の複雑なコード
}

// AIの出力（一気に変更）
function processData(data) {
  // 完全に書き換えられた50行
}
// → 振る舞いが変わっていないか不明
// → テストなしでは検証不能

// ⭕ AIへの正しい依頼
「この関数から calculateSum を抽出してください。
 他の部分は変更しないでください。」
// → 小さなステップで依頼
🔍 コードレビューの観点

以下を見つけたら指摘しましょう：

  • テストなしの大規模リファクタリング：まずテストを書く
  • リファクタリングと機能追加が混在：コミットを分ける
  • テストとプロダクションコードの同時変更：別コミットに
