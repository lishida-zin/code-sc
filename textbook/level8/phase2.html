FIRST原則とは

FIRST原則は、良い単体テストの5つの特性です。

📊 FIRST原則

各原則の詳細

原則 意味 違反例
Fast 高速に実行できる DBアクセスで遅い
Isolated 他のテストに依存しない テスト順序に依存
Repeatable 何度実行しても同じ結果 乱数や日時に依存
Self-validating 自動で成功/失敗を判定 目視確認が必要
Timely 適切なタイミングで書く リリース後にテスト

💀 コードレビューの観点

  • Isolated違反：テスト間で変数やDBの状態を共有していないか。beforeEachでリセットしているか確認
  • Repeatable違反：new Date()やMath.random()を直接使っていないか。日時や乱数はDI（依存性注入）で制御可能にする
  • Fast違反：テスト全体が1分以上かかる場合、遅いテストを特定して改善。DB接続をモックに置き換えられないか検討

❌ FIRST原則違反

let counter = 0; // 共有状態！

test('increment', () => {
  counter++; // Isolated違反
  expect(counter).toBe(1);
});

test('check value', () => {
  // 前のテストに依存
  expect(counter).toBe(1); // Isolated違反
});

⭕ FIRST原則遵守

test('increment', () => {
  let counter = 0; // テスト内で独立
  counter++;
  expect(counter).toBe(1);
});

test('starts at zero', () => {
  let counter = 0; // 各テスト独立
  expect(counter).toBe(0);
});

AAAパターン

📋 Arrange - Act - Assert 
test('ユーザーを作成できる', () => {
  // Arrange（準備）
  const userData = { name: '太郎', email: 'taro@example.com' };

  // Act（実行）
  const user = createUser(userData);

  // Assert（検証）
  expect(user.id).toBeDefined();
  expect(user.name).toBe('太郎');
});

Given-When-Then

📋 BDDスタイル 
describe('ユーザー作成', () => {
  test('有効なデータが与えられたとき、ユーザーが作成される', () => {
    // Given（前提条件）
    const userData = { name: '太郎', email: 'taro@example.com' };

    // When（操作）
    const user = createUser(userData);

    // Then（期待結果）
    expect(user.id).toBeDefined();
    expect(user.name).toBe('太郎');
  });
});

💀 コードレビューの観点

  • AAA構造の欠如：テスト内にArrange/Act/Assertの区別がなく、セットアップとアサーションが混在していないか
  • Actが複数回：1つのテストで複数のActを実行していないか。各Actは別テストに分割すべき
  • Arrangeの重複：同じセットアップが複数テストに重複している場合、beforeEachに共通化を検討
構造化されていない
test('test', () => {
  const x = func(1);
  expect(x).toBe(2);
  const y = func(x);
  expect(y).toBe(4);
  // 何がArrange? Act? Assert?
});
構造化されている
test('2倍にする', () => {
  // Arrange
  const input = 1;
  // Act
  const result = double(input);
  // Assert
  expect(result).toBe(2);
});

アサーションとは

アサーションとは、テストの期待値を検証する文です。

🔧 Jestのアサーション例 
// 等価
expect(value).toBe(1);           // 厳密等価（===）
expect(value).toEqual({a: 1});   // 深い等価

// 真偽値
expect(value).toBeTruthy();      // 真っぽい値
expect(value).toBeFalsy();       // 偽っぽい値
expect(value).toBeNull();        // null

// 数値
expect(value).toBeGreaterThan(3);
expect(value).toBeLessThanOrEqual(5);

// 配列・文字列
expect(array).toContain('item');
expect(string).toMatch(/pattern/);

// エラー
expect(() => func()).toThrow();
expect(() => func()).toThrow('message');

アサーションの注意点

❌ AIがやりがちな間違い 
// ❌ 甘いアサーション
test('ユーザーを取得', async () => {
  const user = await getUser(1);
  expect(user).toBeTruthy(); // 存在だけ確認
});

// ⭕ 適切なアサーション
test('ユーザーを取得', async () => {
  const user = await getUser(1);
  expect(user.id).toBe(1);
  expect(user.name).toBe('太郎');
  expect(user.email).toMatch(/@/);
});

💀 コードレビューの観点

  • アサーションなしのテスト：expectがないテストは必ず成功する。テストとしての意味がない
  • toBeTruthy()の多用：0、""、nullが正当な戻り値の場合に誤検出する。具体的な値で検証する
  • toBeとtoEqualの混同：オブジェクトをtoBeで比較すると参照比較になり失敗する。オブジェクト比較にはtoEqualを使う

❌ アサーションが甘い

test('ユーザー取得', async () => {
  const user = await getUser(1);
  // 存在だけ確認 → 中身が間違っていても通る
  expect(user).toBeTruthy();
  expect(user).toBeDefined();
});

⭕ 具体的に検証

test('ID=1のユーザーを取得', async () => {
  const user = await getUser(1);
  expect(user).toEqual({
    id: 1,
    name: '太郎',
    email: 'taro@example.com',
    role: 'user'
  });
});

テストダブルとは

テストダブルとは、テストで本物の依存オブジェクトの代わりに使う偽物です。
映画のスタントダブル（代役）が語源。

📊 5種類のテストダブル
種類 目的 例
Dummy 引数を埋めるだけ 使わない引数にnull
Stub 固定値を返す APIが常に成功を返す
Spy 呼び出しを記録 何回呼ばれたか確認
Mock 期待値を事前に設定 特定の引数で呼ばれることを検証
Fake 簡易的な実装 インメモリDB

💀 コードレビューの観点

  • テストダブルの種類が不適切：戻り値の検証で十分なのにMockを使っていないか。Stubで済む場面でMockを使うとテストが壊れやすくなる
  • テストダブルと本物の乖離：Stubが返す値が本物のAPIレスポンスと異なる形式になっていないか
  • 過度な複雑さ：テストダブルのセットアップが本番コードより長い場合、テスト設計に問題がある

❌ 不要なMock

// 戻り値を検証するだけなのにMock
const mock = jest.fn()
  .mockReturnValue({ id: 1 });
service.setRepository(mock);
service.getUser(1);
expect(mock).toHaveBeenCalledWith(1);
// → Stubで十分

⭕ 適切なStub

// 戻り値を検証 → Stubで十分
jest.spyOn(repo, 'findById')
  .mockResolvedValue({ id: 1 });
const user = await service.getUser(1);
expect(user.id).toBe(1);
// → シンプルで意図が明確
❓ 確認クイズ

Mockとは

Mockは、期待する呼び出しを事前に設定し、検証するテストダブルです。

🔧 Jestでのモック 
// モジュール全体をモック
jest.mock('./api');

// 関数をモック
const mockFn = jest.fn();
mockFn.mockReturnValue('hello');

// 呼び出しを検証
expect(mockFn).toHaveBeenCalled();
expect(mockFn).toHaveBeenCalledWith('arg');
expect(mockFn).toHaveBeenCalledTimes(2);

過剰なモックの問題

⚠️ モックの罠
  • 実装詳細への依存：内部実装が変わるとテストが壊れる
  • 本番との乖離：モックと本物の動作が違う可能性
  • 過信：モックは成功するが本番で失敗
過剰なモック
// ❌ 内部実装をモック
test('process', () => {
  const spy = jest.spyOn(
    service, '_internalHelper'
  );
  service.process();
  expect(spy).toHaveBeenCalled();
});
振る舞いをテスト
// ⭕ 外部から見た振る舞い
test('process', () => {
  const result = service.process();
  expect(result.status).toBe('ok');
});

Stub

📚 このページで学ぶこと
  • Stubの使い方
  • 外部依存の置き換え

Stubとは

Stubは、固定の戻り値を返すテストダブルです。外部依存を排除できます。

🔧 Stubの例 
// API呼び出しをスタブ
jest.spyOn(api, 'fetchUser').mockResolvedValue({
  id: 1,
  name: '太郎'
});

// テスト
test('ユーザー情報を表示', async () => {
  const result = await displayUser(1);
  expect(result).toContain('太郎');
});

Stubの注意点

⚠️ 本番との乖離

Stubは常に期待通りの値を返しますが、本番のAPIは：

  • エラーを返すかもしれない
  • タイムアウトするかもしれない
  • 予期しないデータ形式かもしれない

→ 異常系のStubも用意する

💀 コードレビューの観点

  • 正常系Stubのみ：APIのStubが常に200 OKを返す設定のみ。エラーレスポンスのStubがあるか確認
  • Stubの形状と実APIの乖離：Stubが返すオブジェクトの型が実APIと一致しているか。TypeScriptの型定義と照合する
  • Stubのリセット漏れ：afterEachでjest.restoreAllMocks()を呼んでいるか。前のテストのStubが残ると予期しない結果になる

❌ 正常系のみのStub

// 常に成功を返すStubだけ
jest.spyOn(api, 'fetchUser')
  .mockResolvedValue({ id: 1 });

test('ユーザー表示', async () => {
  const result = await showUser(1);
  expect(result).toContain('太郎');
  // エラー時の挙動は未テスト！
});

⭕ 異常系もStub

test('正常: ユーザー表示', async () => {
  jest.spyOn(api, 'fetchUser')
    .mockResolvedValue({ id: 1 });
  // ...
});

test('異常: API失敗時', async () => {
  jest.spyOn(api, 'fetchUser')
    .mockRejectedValue(new Error('500'));
  await expect(showUser(1))
    .rejects.toThrow();
});

基本的なテスト構造

🔧 Jestの基本 
// describe: テストをグループ化
describe('Calculator', () => {
  // テストケース
  test('足し算ができる', () => {
    expect(add(1, 2)).toBe(3);
  });

  test('引き算ができる', () => {
    expect(subtract(5, 3)).toBe(2);
  });
});

// ネストも可能
describe('Calculator', () => {
  describe('add', () => {
    test('正の数', () => { ... });
    test('負の数', () => { ... });
  });
});

セットアップとティアダウン

🔧 ライフサイクル 
describe('Database', () => {
  // 全テスト前に1回
  beforeAll(async () => {
    await db.connect();
  });

  // 各テスト前
  beforeEach(() => {
    db.clear();
  });

  // 各テスト後
  afterEach(() => {
    db.rollback();
  });

  // 全テスト後に1回
  afterAll(async () => {
    await db.disconnect();
  });
});

💀 コードレビューの観点

  • beforeAllとbeforeEachの混同：DB接続はbeforeAll、データリセットはbeforeEachが適切。逆にすると毎テストでDB再接続してしまい遅い
  • afterEachでのクリーンアップ漏れ：jest.restoreAllMocks()やjest.clearAllMocks()がafterEachにあるか確認
  • describeの乱用：1階層で十分なのに3段4段のネストは可読性を下げる。2階層までを推奨

❌ ライフサイクルの誤用

describe('User', () => {
  // 毎テストでDB再接続（遅い!）
  beforeEach(async () => {
    await db.connect();
    await db.clear();
  });
  afterEach(async () => {
    await db.disconnect();
  });
});

⭕ 適切なライフサイクル

describe('User', () => {
  // 接続は1回だけ
  beforeAll(() => db.connect());
  afterAll(() => db.disconnect());
  // データクリアは毎回
  beforeEach(() => db.clear());
  afterEach(() => jest.restoreAllMocks());
});

async/awaitでテスト

🔧 非同期テストの書き方 
// async/await
test('ユーザーを取得できる', async () => {
  const user = await fetchUser(1);
  expect(user.name).toBe('太郎');
});

// Promiseを返す
test('ユーザーを取得できる', () => {
  return fetchUser(1).then(user => {
    expect(user.name).toBe('太郎');
  });
});

// resolves/rejects マッチャー
test('成功を返す', async () => {
  await expect(fetchUser(1)).resolves.toHaveProperty('name');
});

test('エラーを返す', async () => {
  await expect(fetchUser(-1)).rejects.toThrow('Invalid ID');
});

タイマーのテスト

⏱️ Fake Timers 
// タイマーをモック
jest.useFakeTimers();

test('1秒後にコールバックが呼ばれる', () => {
  const callback = jest.fn();
  setTimeout(callback, 1000);

  // 1秒進める
  jest.advanceTimersByTime(1000);

  expect(callback).toHaveBeenCalled();
});

// 元に戻す
afterEach(() => {
  jest.useRealTimers();
});

💀 コードレビューの観点

  • awaitの付け忘れ：非同期テストでawaitを付け忘れるとテストがアサーション前に完了し、常にパスする。async関数内の全Promiseにawaitがあるか確認
  • Fake Timersの戻し忘れ：jest.useFakeTimers()を使った後にjest.useRealTimers()で戻さないと後続テストに影響する
  • タイムアウトの設定：長時間かかる非同期テストに適切なtimeoutが設定されているか

❌ await忘れ（常にパス！）

test('ユーザー取得', () => {
  // asyncキーワードがない！
  // awaitできない → アサーション前に終了
  const user = fetchUser(1);
  expect(user.name).toBe('太郎');
  // → Promiseとundefinedの比較
  // → テストは「成功」するが実際はバグ
});

⭕ 正しい非同期テスト

test('ユーザー取得', async () => {
  // asyncを付けて
  const user = await fetchUser(1);
  // awaitで待ってからアサーション
  expect(user.name).toBe('太郎');
});

// エラーの場合
test('不正ID', async () => {
  await expect(fetchUser(-1))
    .rejects.toThrow('Invalid');
});

カバレッジ

📚 このページで学ぶこと
  • コードカバレッジとは
  • カバレッジの種類
  • カバレッジの罠

カバレッジとは

コードカバレッジは、テストがコードのどれだけを実行したかを示す指標です。

種類 意味
行カバレッジ 実行された行の割合
分岐カバレッジ if/elseの全分岐を通過した割合
関数カバレッジ 呼び出された関数の割合
文カバレッジ 実行された文の割合

カバレッジの罠

⚠️ カバレッジ100%の落とし穴 
// カバレッジ100%でもバグがある例
function divide(a, b) {
  return a / b;  // b=0 でInfinityになる
}

test('割り算', () => {
  expect(divide(10, 2)).toBe(5);
  // カバレッジ100%だが、b=0のテストがない
});

カバレッジは「テストされていない箇所」を見つけるツールであり、
「テストの品質」を保証するものではない。

❌ カバレッジだけ追求

// カバレッジのためだけのテスト
test('divide', () => {
  divide(10, 2);
  // アサーションなし！
  // → カバレッジは上がるが無意味
});

test('validate', () => {
  validate('test');
  // → 何も検証していない
});

⭕ 品質重視のテスト

test('正常: 割り算', () => {
  expect(divide(10, 2)).toBe(5);
});
test('異常: ゼロ除算', () => {
  expect(() => divide(10, 0))
    .toThrow('Division by zero');
});
test('境界: 小数点', () => {
  expect(divide(1, 3)).toBeCloseTo(0.333);
});

テストしにくいコード

❌ テスト困難な例 
// ❌ 直接依存
function getUser(id) {
  const db = new Database();  // 直接生成
  return db.query(`SELECT * FROM users WHERE id = ${id}`);
}

// テストでDBを差し替えられない

依存性注入（DI）

✅ テスト可能な設計 
// ⭕ 依存性注入
function getUser(id, db) {
  return db.query(`SELECT * FROM users WHERE id = ${id}`);
}

// テストでモックを注入できる
test('ユーザーを取得', () => {
  const mockDb = {
    query: jest.fn().mockReturnValue({ id: 1, name: '太郎' })
  };
  const user = getUser(1, mockDb);
  expect(user.name).toBe('太郎');
});
