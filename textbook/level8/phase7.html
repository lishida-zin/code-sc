CI/CDパイプラインとテスト

CI/CD（継続的インテグレーション/継続的デリバリー）では、 コード変更のたびに自動テストを実行し、品質を担保します。

🏠 たとえ話：工場の品質検査

工場で製品がベルトコンベアを流れる途中で品質検査を行うように、
CI/CDではコードが本番に届く前にテストという検査を通過させます。

検査に不合格なら、製品（コード）は出荷（デプロイ）されません。

GitHub Actionsでのテスト設定

# .github/workflows/test.yml
name: Test

on:
  push:
    branches: [main, develop]
  pull_request:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest

    steps:
      - uses: actions/checkout@v4

      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'npm'

      - name: Install dependencies
        run: npm ci

      - name: Run linter
        run: npm run lint

      - name: Run unit tests
        run: npm test -- --coverage

      - name: Run integration tests
        run: npm run test:integration

      - name: Upload coverage
        uses: codecov/codecov-action@v4
        with:
          token: ${{ secrets.CODECOV_TOKEN }}

品質ゲートの設定

品質ゲートとは、テストやカバレッジが基準を満たさないと 次のステージに進めない仕組みです。

✓ 品質ゲートの例
  • テスト成功率：100%（全テスト合格必須）
  • カバレッジ：80%以上
  • 静的解析：エラー0件
  • セキュリティスキャン：Critical脆弱性0件
AIがやりがちな間違い
# ❌ テスト失敗を無視する設定
- name: Run tests
  run: npm test
  continue-on-error: true  # 失敗しても続行

# ❌ 失敗時にexit 0で握りつぶす
- name: Run tests
  run: npm test || exit 0

テスト失敗を無視するとバグが本番に流出

正しい設定
# ⭕ テスト失敗で即座に停止
- name: Run tests
  run: npm test

# ⭕ 明示的に失敗を検知
- name: Run tests
  run: |
    npm test
    if [ $? -ne 0 ]; then
      echo "Tests failed!"
      exit 1
    fi

  • テストなしでデプロイできるワークフロー
  • 品質ゲートがないパイプライン
  • main直接プッシュが許可されている

テストの並列化

📚 このページで学ぶこと
  • テスト並列実行の仕組み

  • 並列化による高速化の実践

なぜ並列化が必要か

テストスイートが大きくなると、実行時間が数十分〜数時間になることも。 並列化で劇的に短縮できます。

🏠 たとえ話：レジの行列

スーパーで1つのレジに100人並んでいると時間がかかります。
レジを5台に増やせば、待ち時間は1/5に。

テストも同じ。複数のマシンで分担すれば速くなります。

並列化の基本戦略

📊 並列実行のイメージ

GitHub Actionsでの並列化

⚙️ マトリックス戦略による並列化 
# .github/workflows/test-parallel.yml
name: Parallel Tests

on: [push, pull_request]

jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        shard: [1, 2, 3, 4, 5]  # 5分割
      fail-fast: false  # 1つ失敗しても他を継続

    steps:
      - uses: actions/checkout@v4

      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'npm'

      - name: Install dependencies
        run: npm ci

      - name: Run tests (shard ${{ matrix.shard }}/5)
        run: |
          npx jest --shard=${{ matrix.shard }}/5

シャーディングの仕組み

💡 Jestのシャーディング 
# 5分割の2番目のシャードを実行
npx jest --shard=2/5

# テストファイルがこう分配される：
# Shard 1/5: test1.js, test6.js, test11.js...
# Shard 2/5: test2.js, test7.js, test12.js...
# Shard 3/5: test3.js, test8.js, test13.js...
# ...

ポイント：テストファイル単位で分割され、各シャードが独立して実行されます。

⚙️ Playwright（E2Eテスト）の並列化 
# playwright.config.ts
export default defineConfig({
  // 並列ワーカー数
  workers: process.env.CI ? 4 : undefined,

  // シャーディング設定（CI用）
  shard: process.env.SHARD
    ? { current: parseInt(process.env.SHARD), total: 5 }
    : undefined,
});

# GitHub Actionsで実行
- name: Run E2E tests
  run: npx playwright test
  env:
    SHARD: ${{ matrix.shard }}
⚠️ 並列化の注意点
  • テストの独立性：テスト間で状態を共有しないこと
  • データベース：各シャードで独立したDBが必要
  • ポート競合：同じポートを使うテストは失敗する
  • コスト：ランナー数が増えると課金も増える
🔍 コードレビューの観点

以下を見つけたら指摘しましょう：

  • fail-fast: trueのまま（1つ失敗で全停止）
  • テスト間でグローバル状態を共有している
  • ハードコードされたポート番号
  • シャード数が多すぎる（オーバーヘッドで逆効果）

テストの順序と依存

📚 このページで学ぶこと
  • テストの独立性の重要さ
  • 順序依存の検出と排除
  • テスト間の状態汚染の防止

テストの独立性とは

独立したテストとは、他のテストの実行結果に影響されず、 単独でも、どの順序でも同じ結果になるテストです。

🏠 たとえ話：試験問題

良い試験は、問1の答えがわからなくても問2は解けます。
「問1の答えを使って問2を解く」設計は悪い設計。

テストも同じ。テストAの結果がテストBに影響するのは危険です。

順序依存の問題

順序依存のあるテスト
// ❌ グローバル状態に依存
let userId;

test('ユーザー作成', async () => {
  const user = await createUser('test@example.com');
  userId = user.id;  // グローバルに保存
  expect(user).toBeDefined();
});

test('ユーザー取得', async () => {
  // 上のテストで設定されたuserIdに依存
  const user = await getUser(userId);
  expect(user.email).toBe('test@example.com');
});

// テスト順序が変わると失敗！
独立したテスト
// ⭕ 各テストが独立
test('ユーザー作成', async () => {
  const user = await createUser('test1@example.com');
  expect(user).toBeDefined();
});

test('ユーザー取得', async () => {
  // このテスト用に新たにユーザー作成
  const user = await createUser('test2@example.com');
  const fetched = await getUser(user.id);
  expect(fetched.email).toBe('test2@example.com');
});

// どの順序でも成功！

順序依存の検出方法

💡 ランダム実行で検出 
# Jest: ランダム順序で実行
npx jest --randomize

# Vitest: シャッフルモード
npx vitest --sequence.shuffle

# RSpec (Ruby): ランダムシード指定
rspec --order random

# pytest (Python): pytest-random-order
pip install pytest-random-order
pytest --random-order

ランダム実行で失敗が発生したら、順序依存がある証拠です。

状態汚染の防止

✓ 各テストでクリーンな状態を作る 
describe('User API', () => {
  // 各テスト前にDBをリセット
  beforeEach(async () => {
    await db.query('TRUNCATE users CASCADE');
  });

  // 各テスト後にクリーンアップ
  afterEach(async () => {
    await cleanup();
  });

  test('ユーザー作成', async () => {
    // クリーンな状態から開始
    const user = await createUser('test@example.com');
    expect(user).toBeDefined();
  });

  test('ユーザー一覧', async () => {
    // このテストもクリーンな状態から開始
    await createUser('user1@example.com');
    await createUser('user2@example.com');
    const users = await listUsers();
    expect(users).toHaveLength(2);
  });
});
🔍 コードレビューの観点

以下を見つけたら指摘しましょう：

  • テストファイル外のlet/var変数を複数テストで使用
  • beforeAllで作成したデータを複数テストで参照
  • afterEachがないのにDBや外部リソースを使用
  • テスト名に「その後」「続いて」などの表現

Flakyテストとは

Flaky（フレーキー）テストとは、コード変更なしに 成功したり失敗したりする不安定なテストです。

🏠 たとえ話：壊れかけの信号機

時々赤になったり青になったりする信号機は信用できません。
ドライバーは「本当に青か？」と疑い、交通が混乱します。

Flakyテストも同じ。開発者は「本当に失敗？」と疑い、 テスト結果を無視する悪習慣が生まれます。

Flakyテストの主な原因

📊 Flakyテストの原因分類

Flakyテストの検出

⚙️ 複数回実行で検出 
# Jest: 同じテストを複数回実行
npx jest --repeat=5

# Vitest: 繰り返し実行
npx vitest --retry=3

# Playwright: 繰り返し実行
npx playwright test --repeat-each=5

# GitHub Actionsで定期検出
name: Flaky Test Detection
on:
  schedule:
    - cron: '0 3 * * *'  # 毎日3時

jobs:
  detect-flaky:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci
      - name: Run tests multiple times
        run: |
          for i in {1..10}; do
            npm test 2>&1 | tee -a results.txt
          done
      - name: Check for flaky tests
        run: |
          if grep -q "FAIL" results.txt && grep -q "PASS" results.txt; then
            echo "Flaky tests detected!"
            exit 1
          fi

Flakyテストの対処法

✓ 原因別の修正方法
原因 修正方法
タイミング 明示的なwaitFor、ポーリング、適切なawait
外部依存 モック化、スタブ化、フェイク実装
順序依存 beforeEach/afterEachで状態リセット
リソース競合 動的ポート割当、一意なファイル名
Flakyになりやすいコード
// ❌ 固定の待機時間
test('データ読み込み', async () => {
  render(<DataList />);
  await sleep(1000);  // 環境により不足する
  expect(screen.getByText('Item 1')).toBeVisible();
});

// ❌ リトライで誤魔化す
test('不安定なテスト', async () => {
  for (let i = 0; i < 3; i++) {
    try {
      await unstableOperation();
      break;
    } catch (e) {
      if (i === 2) throw e;
    }
  }
});
安定したコード
// ⭕ 条件を待つ
test('データ読み込み', async () => {
  render(<DataList />);
  await waitFor(() => {
    expect(screen.getByText('Item 1')).toBeVisible();
  });
});

// ⭕ 根本原因を修正
test('安定したテスト', async () => {
  // 外部依存をモック化
  mockApi.get.mockResolvedValue({ data: 'test' });
  const result = await stableOperation();
  expect(result).toBe('test');
});
🔍 コードレビューの観点

以下を見つけたら指摘しましょう：

  • sleep/waitを固定時間で使用
  • Date.now()やMath.random()を直接使用
  • リトライでテストを通すアプローチ
  • .skip()されたまま放置されたテスト

なぜテストレポートが重要か

テスト結果を見やすく可視化することで、 問題の発見と分析が格段に速くなります。

🏠 たとえ話：健康診断結果

健康診断で数値だけ渡されても何が問題かわかりません。
グラフや正常範囲との比較があると一目で異常がわかる。

テストレポートも同じ。どこで何が失敗したか視覚的にわかることが大切です。

JUnit XMLは、CI/CDツール共通のテスト結果フォーマットです。 ほぼすべてのCIサービスがサポートしています。

npx jest --reporters=default --reporters=jest-junit
# jest.config.js で設定も可能

# Vitest
npx vitest --reporter=junit --outputFile=test-results.xml

# Playwright
npx playwright test --reporter=junit

# pytest (Python)

# Go
go test -v ./... 2>&1 | go-junit-report > test-results.xml

    runs-on: ubuntu-latest

          path: './reports/*.xml'

コードカバレッジとは

コードカバレッジとは、テストがコードのどの程度を 実行したかを示す指標です。

🏠 たとえ話：家の点検

家の点検で「全体の80%を確認しました」と言われたら、
「残り20%は大丈夫？」と心配になります。

カバレッジ80%は「20%は未テスト」という意味。
高ければ良いわけではないが、低すぎると不安。

カバレッジの種類

種類 説明 例
行カバレッジ 実行された行の割合 100行中80行実行 = 80%
分岐カバレッジ if/elseの全分岐を通過 if文のtrue/false両方テスト
関数カバレッジ 呼び出された関数の割合 10関数中8関数呼び出し = 80%
ステートメント 実行された文の割合 行カバレッジに近い

カバレッジの計測と出力

カバレッジゲート

✓ codecov.ymlでの設定 
# codecov.yml
coverage:
  status:
    project:
      default:
        target: 80%          # 全体で80%以上
        threshold: 2%        # 2%までの低下は許容
    patch:
      default:
        target: 90%          # 新規コードは90%以上

comment:
  layout: "reach,diff,flags,files"
  behavior: default
  require_changes: true
⚠️ カバレッジの罠
  • 100%を目指さない：現実的には80-90%で十分
  • カバレッジ≠品質：通っただけでは正しさは保証されない
  • 重要な箇所を重点的に：ビジネスロジックを優先
  • 生成コードは除外：自動生成ファイルは計測対象外に
カバレッジだけ上げる悪例
// ❌ 意味のないテスト
test('covers the function', () => {
  calculate(1, 2);  // 結果を検証しない！
});

// これでもカバレッジは上がるが
// バグは検出できない
意味のあるテスト
// ⭕ 結果を検証する
test('calculates correctly', () => {
  expect(calculate(1, 2)).toBe(3);
  expect(calculate(-1, 1)).toBe(0);
  expect(calculate(0, 0)).toBe(0);
});

// カバレッジも上がり、バグも検出できる
🔍 コードレビューの観点

以下を見つけたら指摘しましょう：

  • expect/assertがないテスト（カバレッジ稼ぎ）
  • カバレッジ除外（istanbul ignore）の乱用
  • テストなしで追加された新規コード
  • 閾値が低すぎるカバレッジ設定

キャッシュによる高速化

⚙️ 依存関係のキャッシュ 
# GitHub Actionsでのキャッシュ設定
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Setup Node.js with cache
        uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'npm'  # npm ciの結果をキャッシュ

      # または明示的にキャッシュ
      - name: Cache node_modules
        uses: actions/cache@v4
        with:
          path: node_modules
          key: ${{ runner.os }}-node-${{ hashFiles('**/package-lock.json') }}
          restore-keys: |
            ${{ runner.os }}-node-

      - run: npm ci
      - run: npm test

差分テスト（Affected Tests）

差分テストとは、変更されたコードに関連するテストだけを実行する手法です。

⚙️ Jestの差分テスト 
# 前回コミットからの変更に関連するテストのみ実行
npx jest --onlyChanged

# 特定のコミット以降の変更に関連
npx jest --changedSince=main

# GitHub Actionsでの設定
- name: Run affected tests
  run: |
    if [ "${{ github.event_name }}" == "pull_request" ]; then
      npx jest --changedSince=origin/${{ github.base_ref }}
    else
      npx jest
    fi
⚙️ Nxを使った差分テスト（モノレポ） 
# 影響を受けるプロジェクトのみテスト
npx nx affected:test --base=main

# GitHub Actions
- name: Run affected tests
  run: npx nx affected:test --base=${{ github.event.pull_request.base.sha }}

ブランチとテストの関係

ブランチによって実行すべきテストの範囲が異なります。 適切な設計で効率とセキュリティを両立します。

📊 ブランチ別テスト戦略

PRでのテスト設定

⚙️ PRトリガーのワークフロー 
# .github/workflows/pr-check.yml
name: PR Check

on:
  pull_request:
    branches: [main, develop]

jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci
      - run: npm run lint
      - run: npm run type-check

  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci
      - run: npm test -- --coverage
      - uses: codecov/codecov-action@v4

  e2e:
    runs-on: ubuntu-latest
    needs: [lint, test]  # lint, testが通ってから
    steps:
      - uses: actions/checkout@v4
      - run: npm ci
      - run: npx playwright install --with-deps
      - run: npm run test:e2e

mainブランチの保護

✓ ブランチ保護ルール 
# GitHubの設定（Settings > Branches > Branch protection rules）

Protected branch: main

✓ Require a pull request before merging
  ✓ Require approvals: 1
  ✓ Dismiss stale pull request approvals when new commits are pushed

✓ Require status checks to pass before merging
  Required checks:
  - lint
  - test
  - e2e

✓ Require branches to be up to date before merging

✓ Do not allow bypassing the above settings
⚙️ GitHub ActionsでのRequired Status Checks 
# ジョブ名がStatus Checkとして登録される
jobs:
  lint:        # ← "lint" がチェック名になる
    runs-on: ubuntu-latest
    ...

  test:        # ← "test" がチェック名になる
    runs-on: ubuntu-latest
    ...

  # 複数ジョブの結果を1つにまとめる場合
  all-checks:
    runs-on: ubuntu-latest
    needs: [lint, test, e2e]
    steps:
      - run: echo "All checks passed!"

  • mainへの直接プッシュが許可されている
  • Required status checksが設定されていない
  • PRなしでマージ可能な設定
  • Force pushが許可されている

テストも負債になる

テストは資産ですが、メンテナンスしないと負債になります。 壊れたテスト、古いテストは開発速度を下げます。

🏠 たとえ話：庭の手入れ

庭を放置すると雑草だらけになり、美しい花も埋もれてしまいます。
定期的な手入れで、庭（テストスイート）を健全に保つ必要があります。

壊れたテストの対処

⚠️ 放置してはいけない

壊れたテストを放置すると...

  • 「また失敗してる」とテスト結果を無視する習慣が生まれる
  • 本当のバグを見逃す
  • 新しいテストを書く意欲が下がる
悪い対処法
// ❌ とりあえずスキップ
test.skip('壊れてるテスト', () => {
  // TODO: 直す
});

// ❌ 無意味なコメントアウト
// test('古いテスト', () => {
//   ...
// });

// ❌ 常にtrueにする
test('動かないテスト', () => {
  expect(true).toBe(true);  // 元のコードを削除
});
正しい対処法
// ⭕ 原因を特定して修正
test('修正したテスト', () => {
  // 仕様変更に合わせてテストを更新
  expect(newBehavior()).toBe(expected);
});

// ⭕ 不要なら削除（履歴はGitにある）
// テストごと削除

// ⭕ 一時的なスキップは期限付きで
test.skip('一時スキップ: Issue #123で対応', () => {
  // 2024-02-01までに対応
});

テスト負債の可視化

⚙️ スキップされたテストの検出 
# Jest: スキップされたテストを一覧
npx jest --listTests | xargs grep -l "\.skip\|xit\|xdescribe"

# ESLintルールで検出
// .eslintrc.js
module.exports = {
  rules: {
    'jest/no-disabled-tests': 'warn',
    'jest/no-focused-tests': 'error',
  },
};

# GitHub Actionsで定期チェック
- name: Check for skipped tests
  run: |
    SKIPPED=$(grep -r "\.skip\|xit\|xdescribe" --include="*.test.*" . | wc -l)
    echo "Skipped tests: $SKIPPED"
    if [ $SKIPPED -gt 10 ]; then
      echo "Too many skipped tests!"
      exit 1
    fi

テストの整理基準

✓ 削除を検討すべきテスト
  • 実装と乖離：仕様変更で意味をなさなくなったテスト
  • 重複テスト：同じことを複数箇所でテスト
  • 価値の低いテスト：ゲッター/セッターの単純テスト
  • Flakyのまま放置：修正できないなら削除
  • 削除された機能：もう存在しない機能のテスト
💡 定期メンテナンスの習慣 
# 月次でテスト健全性をチェック
チェックリスト:
□ スキップされたテストを確認（10件以下が目標）
□ Flakyテストを特定・修正
□ カバレッジの低下がないか確認
□ テスト実行時間のトレンド確認
□ 古いスナップショットの更新
🔍 コードレビューの観点

以下を見つけたら指摘しましょう：

  • .skip()が理由なく追加されている
  • テストが削除されるが代替テストがない
  • expect(true).toBe(true)のような無意味なテスト
  • コメントアウトされたテストコード

なぜ環境の自動化が必要か

「ローカルでは動くのにCIで失敗する」問題を解決するため、 環境を統一することが重要です。

🏠 たとえ話：レシピと調理環境

同じレシピでも、使うオーブンが違えば焼き加減が変わります。
テストも同じ。環境が違えば結果が変わる可能性があります。

Dockerで「同じ調理環境」を用意すれば、誰がやっても同じ結果に。

Dockerでのテスト環境

⚙️ テスト用Dockerfile 
# Dockerfile.test
FROM node:20-slim

WORKDIR /app

# 依存関係のみ先にコピー（キャッシュ活用）
COPY package*.json ./
RUN npm ci

# ソースコードをコピー
COPY . .

# テスト実行
CMD ["npm", "test"]
⚙️ docker-compose.test.yml 
# docker-compose.test.yml
version: '3.8'

services:
  app:
    build:
      context: .
      dockerfile: Dockerfile.test
    environment:
      - NODE_ENV=test
      - DATABASE_URL=postgres://test:test@db:5432/testdb
    depends_on:
      db:
        condition: service_healthy

  db:
    image: postgres:15
    environment:
      POSTGRES_USER: test
      POSTGRES_PASSWORD: test
      POSTGRES_DB: testdb
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U test"]
      interval: 5s
      timeout: 5s
      retries: 5

Testcontainersの活用

Testcontainersは、テストコードから直接Dockerコンテナを 起動・管理できるライブラリです。

⚙️ Testcontainersの例（Node.js） 
// tests/db.test.ts
import { PostgreSqlContainer } from '@testcontainers/postgresql';

describe('Database tests', () => {
  let container;
  let connectionUrl;

  beforeAll(async () => {
    // PostgreSQLコンテナを起動
    container = await new PostgreSqlContainer()
      .withDatabase('testdb')
      .withUsername('test')
      .withPassword('test')
      .start();

    connectionUrl = container.getConnectionUri();
  }, 60000);  // タイムアウト60秒

  afterAll(async () => {
    await container.stop();
  });

  test('connects to database', async () => {
    const client = new Client({ connectionString: connectionUrl });
    await client.connect();
    const result = await client.query('SELECT 1');
    expect(result.rows[0]).toEqual({ '?column?': 1 });
    await client.end();
  });
});

# .github/workflows/test.yml
jobs:
  test:
    runs-on: ubuntu-latest

    services:
      postgres:
        image: postgres:15
        env:
          POSTGRES_USER: test
          POSTGRES_PASSWORD: test
          POSTGRES_DB: testdb
        ports:
          - 5432:5432
        options: >-
          --health-cmd pg_isready
          --health-interval 10s
          --health-timeout 5s
          --health-retries 5

        image: redis:7
        ports:
          - 6379:6379
