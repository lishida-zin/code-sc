E2Eテストとは

E2E（End-to-End）テストとは、実際のユーザー操作をシミュレートし、 システム全体が正しく動作することを検証するテストです。

🏠 たとえ話：車の完成検査

車を製造するとき、エンジン単体のテスト（ユニットテスト）、 エンジンとトランスミッションの結合テスト（統合テスト）だけでは不十分です。

最終的に実際に道路を走って、ハンドル操作、ブレーキ、 エアコンなどすべてが連携して動くことを確認します。 これがE2Eテストです。

テストピラミッド

📊 テストピラミッドにおけるE2Eの位置
テスト種別 検証対象 実行速度 推奨割合
E2E ユーザーフロー全体 遅い（秒〜分） 10%
統合 コンポーネント間連携 中程度 20%
ユニット 関数・クラス単体 速い（ミリ秒） 70%

E2Eテストで検証すること

✓ E2Eテストの検証範囲
  • クリティカルパス：ログイン → 商品選択 → 購入 → 決済完了
  • ユーザーシナリオ：実際のユーザーが行う一連の操作
  • システム統合：フロントエンド + バックエンド + DB + 外部API
  • ブラウザ動作：JavaScript、CSS、画面遷移
E2Eでテストすべきこと
  • ユーザー登録〜ログインフロー
  • 購入完了までの一連の流れ
  • 重要な業務フロー
  • 決済処理の成功確認
E2Eでテストすべきでないこと
  • 個別の関数の境界値テスト
  • エラーメッセージの文言確認
  • すべての入力バリデーション
  • APIの個別エンドポイント

E2Eテストの価値

💡 なぜE2Eテストが必要か

ユニットテストと統合テストだけでは見つからないバグがあります。

  • 設定ミス：環境変数、CORS、認証設定
  • 統合の問題：APIの型不一致、タイムアウト
  • UIの問題：ボタンが押せない、画面遷移の失敗
  • リグレッション：以前動いていた機能が壊れている
🔍 コードレビューの観点

E2Eテストのレビューで確認すべきこと：

  • ユーザー視点か：実装詳細ではなくユーザー操作をテストしているか
  • クリティカルパスか：重要度の低い機能をE2Eで書いていないか
  • 適切な粒度か：1テストが長すぎないか（理想は1シナリオ）

E2Eテストの3大課題

⚠️ E2Eテストのデメリット

1. 実行速度が遅い

🐢 なぜ遅いのか
  • ブラウザ起動：実際のブラウザを立ち上げる
  • ネットワーク通信：サーバーとの実際の通信
  • DOM操作：画面描画の待機
  • アニメーション：CSS/JSアニメーションの完了待ち
テスト種別 1テストあたりの時間 1000テストの場合
ユニットテスト 1-10 ミリ秒 約10秒
統合テスト 100-500 ミリ秒 約5分
E2Eテスト 5-30 秒 数時間

2. 不安定（Flakyテスト）

Flakyテストとは、同じコードでも成功したり失敗したりする不安定なテストです。

🎲 Flakyテストの原因
  • タイミング問題：要素の表示待ちが不十分
  • テスト順序依存：他のテストの状態に依存
  • 外部依存：ネットワーク、外部API、時刻
  • 並列実行の競合：同じデータを複数テストが操作
Flakyテストの例
// ❌ タイミング問題が起きやすい
test('商品を購入できる', async () => {
  await page.click('#buy-button');
  // 即座に確認 → まだ処理中かも
  expect(await page.textContent('.message'))
    .toBe('購入完了');
});
安定したテスト
// ⭕ 明示的に待機
test('商品を購入できる', async () => {
  await page.click('#buy-button');
  // 要素が表示されるまで待機
  await page.waitForSelector('.message');
  expect(await page.textContent('.message'))
    .toBe('購入完了');
});

3. メンテナンスコストが高い

💰 なぜコストが高いのか
  • UI変更への脆弱性：ボタンのクラス名変更で壊れる
  • テストデータの管理：事前データの準備と後片付け
  • 環境依存：ローカル/CI/本番で動作が異なる
  • デバッグの困難さ：失敗原因の特定に時間がかかる
⚠️ AIがやりがちな間違い 
// ❌ AIが生成しがちな脆弱なセレクタ
await page.click('div.sc-abc123 > button:nth-child(2)');
await page.click('[class*="Button__StyledButton"]');

// ⭕ 変更に強いセレクタ
await page.click('[data-testid="submit-button"]');
await page.getByRole('button', { name: '送信' });

AIは自動生成されたクラス名やDOM構造に依存するセレクタを書きがちです。 これはUI変更で即座に壊れます。

制約への対処方針

✓ 実践的な対処法
制約 対処法
遅い 並列実行、テスト数を絞る、CI最適化
不安定 明示的待機、リトライ、テストの独立性確保
高コスト Page Object Model、安定したセレクタ
🔍 コードレビューの観点

E2Eテストのレビューで確認すべきこと：

  • ハードコードされた待機：sleep(5000)は避けているか
  • 脆弱なセレクタ：自動生成クラス名を使っていないか
  • テストの独立性：他のテストの状態に依存していないか
  • 適切なアサーション：何を検証しているか明確か

Playwrightとは

Playwrightは、Microsoftが開発したE2Eテストフレームワークです。 複数ブラウザ（Chromium、Firefox、WebKit）をサポートします。

✓ Playwrightの特徴
  • Auto-waiting：要素が操作可能になるまで自動待機
  • クロスブラウザ：Chrome、Firefox、Safari対応
  • 並列実行：高速なテスト実行
  • トレース機能：失敗時の詳細なデバッグ情報

基本的なテストの書き方

💻 Playwrightの基本構文 
// playwright.config.ts
import { defineConfig } from '@playwright/test';

export default defineConfig({
  testDir: './tests',
  use: {
    baseURL: 'http://localhost:3000',
    screenshot: 'only-on-failure',
    trace: 'on-first-retry',
  },
});

// tests/login.spec.ts
import { test, expect } from '@playwright/test';

test('ログインできる', async ({ page }) => {
  // 1. ページに移動
  await page.goto('/login');

  // 2. フォームに入力
  await page.fill('[data-testid="email"]', 'user@example.com');
  await page.fill('[data-testid="password"]', 'password123');

  // 3. ボタンをクリック
  await page.click('[data-testid="login-button"]');

  // 4. 結果を検証
  await expect(page).toHaveURL('/dashboard');
  await expect(page.locator('h1')).toHaveText('ダッシュボード');
});

セレクタの種類

📊 Playwrightのセレクタ優先順位
💻 セレクタの例 
// ロールベースセレクタ（最も推奨）
await page.getByRole('button', { name: '送信' }).click();
await page.getByRole('textbox', { name: 'メールアドレス' }).fill('test@example.com');
await page.getByRole('link', { name: 'ホーム' }).click();

// テキストベースセレクタ
await page.getByText('ログイン').click();
await page.getByLabel('パスワード').fill('secret');
await page.getByPlaceholder('検索...').fill('keyword');

// data-testid（実装詳細を隠したい場合）
await page.getByTestId('user-profile').click();

// CSSセレクタ（他の方法が使えない場合）
await page.locator('.product-card').first().click();
await page.locator('#main-content').isVisible();

待機戦略（Auto-waiting）

Playwrightは自動待機（Auto-waiting）機能を持ちます。 要素が操作可能になるまで自動で待機します。

避けるべき書き方
// ❌ 固定時間の待機
await page.waitForTimeout(5000);
await page.click('#button');

// ❌ 不要な手動待機
await page.waitForSelector('#button');
await page.click('#button');
推奨される書き方
// ⭕ 自動待機を活用
await page.click('#button');
// Playwrightが自動で待機してくれる

// ⭕ 特定の状態を待つ場合
await page.waitForURL('/dashboard');
await expect(page.locator('.loading'))
  .not.toBeVisible();
💡 明示的な待機が必要な場面 
// ネットワークリクエストの完了を待つ
await page.waitForResponse(
  response => response.url().includes('/api/users')
);

// 特定の状態を待つ
await expect(page.locator('.spinner')).not.toBeVisible();
await expect(page.locator('.content')).toBeVisible();

// ナビゲーションを待つ
await Promise.all([
  page.waitForNavigation(),
  page.click('a[href="/next-page"]'),
]);

アサーション

💻 Playwrightのアサーション 
import { expect } from '@playwright/test';

// ページレベルのアサーション
await expect(page).toHaveURL('/dashboard');

// 要素のアサーション

Cypressとは

Cypressは、フロントエンド向けに特化したE2Eテストフレームワークです。 開発者体験（DX）を重視した設計が特徴です。

✓ Cypressの特徴
  • リアルタイムリロード：コード変更で即座にテスト再実行
  • タイムトラベル：各ステップの状態をスナップショットで確認
  • 自動待機：要素が現れるまで自動で待機
  • スクリーンショット/動画：失敗時に自動記録

Cypress Test Runner

📊 Cypress Test Runnerの機能

基本的なテストの書き方

💻 Cypressの基本構文 
// cypress.config.js
const { defineConfig } = require('cypress');

module.exports = defineConfig({
  e2e: {
    baseUrl: 'http://localhost:3000',
    viewportWidth: 1280,
    viewportHeight: 720,
  },
});

// cypress/e2e/login.cy.js
describe('ログイン機能', () => {
  beforeEach(() => {
    cy.visit('/login');
  });

  it('正しい認証情報でログインできる', () => {
    // フォームに入力
    cy.get('[data-testid="email"]').type('user@example.com');
    cy.get('[data-testid="password"]').type('password123');

    // ボタンをクリック
    cy.get('[data-testid="login-button"]').click();

    // 結果を検証
    cy.url().should('include', '/dashboard');
    cy.get('h1').should('contain', 'ダッシュボード');
  });

  it('不正な認証情報でエラーが表示される', () => {
    cy.get('[data-testid="email"]').type('wrong@example.com');
    cy.get('[data-testid="password"]').type('wrongpass');
    cy.get('[data-testid="login-button"]').click();

    cy.get('.error-message').should('be.visible');
  });
});

Cypressのコマンドチェーン

CypressはチェーンベースのAPIを採用しています。 コマンドが順番に実行され、自動的に待機します。

💻 コマンドチェーンの例 
// チェーンで操作を連結
cy.get('.product-list')      // 要素を取得
  .find('.product-card')     // 子要素を検索
  .first()                   // 最初の要素
  .click()                   // クリック
  .should('have.class', 'selected');  // アサーション

// 親要素から検索
cy.get('.modal')
  .within(() => {
    cy.get('input[name="email"]').type('test@example.com');
    cy.get('button[type="submit"]').click();
  });

// カスタムコマンドの定義
// cypress/support/commands.js
Cypress.Commands.add('login', (email, password) => {
  cy.visit('/login');
  cy.get('[data-testid="email"]').type(email);
  cy.get('[data-testid="password"]').type(password);
  cy.get('[data-testid="login-button"]').click();
});

// 使用
cy.login('user@example.com', 'password123');

Page Object Modelとは

Page Object Model（POM）は、ページの要素と操作を クラスとしてカプセル化するデザインパターンです。

🏠 たとえ話：リモコン

テレビを操作するとき、内部の回路を直接触りません。 リモコンという「インターフェース」を使います。

Page Objectは「ページのリモコン」です。 テストコードはセレクタの詳細を知らず、操作だけを呼び出す。

Page Object Modelの構造

📊 POMのアーキテクチャ

POMの実装例（Playwright）

POMなし（直接セレクタを書く）
// ❌ テストコードにセレクタが散らばる
test('ログインできる', async ({ page }) => {
  await page.goto('/login');
  await page.fill('[data-testid="email"]', 'user@example.com');
  await page.fill('[data-testid="password"]', 'pass123');
  await page.click('[data-testid="submit-btn"]');
  await expect(page).toHaveURL('/dashboard');
});

test('ログアウトできる', async ({ page }) => {
  // 同じセレクタを再度書く必要がある
  await page.goto('/login');
  await page.fill('[data-testid="email"]', 'user@example.com');
  // ... 繰り返し
});
POMあり
// ⭕ Page Objectにカプセル化

// pages/LoginPage.ts
export class LoginPage {
  constructor(private page: Page) {}

  async goto() {
    await this.page.goto('/login');
  }

  async login(email: string, password: string) {
    await this.page.fill('[data-testid="email"]', email);
    await this.page.fill('[data-testid="password"]', password);
    await this.page.click('[data-testid="submit-btn"]');
  }
}

// tests/login.spec.ts
test('ログインできる', async ({ page }) => {
  const loginPage = new LoginPage(page);
  await loginPage.goto();
  await loginPage.login('user@example.com', 'pass123');
  await expect(page).toHaveURL('/dashboard');
});

POMの実装例（Cypress）

💻 CypressでのPage Object 
// cypress/pages/LoginPage.js
class LoginPage {
  // セレクタを定義
  elements = {
    emailInput: () => cy.get('[data-testid="email"]'),
    passwordInput: () => cy.get('[data-testid="password"]'),
    submitButton: () => cy.get('[data-testid="submit-btn"]'),
    errorMessage: () => cy.get('.error-message'),
  };

  // 操作をメソッド化
  visit() {
    cy.visit('/login');
    return this;
  }

  typeEmail(email) {
    this.elements.emailInput().type(email);
    return this;
  }

  typePassword(password) {
    this.elements.passwordInput().type(password);
    return this;
  }

  submit() {
    this.elements.submitButton().click();
    return this;
  }

  // 一連の操作をまとめる
  login(email, password) {
    this.typeEmail(email);
    this.typePassword(password);
    this.submit();
    return this;
  }
}

export default new LoginPage();

// cypress/e2e/login.cy.js
import loginPage from '../pages/LoginPage';

describe('ログイン', () => {
  it('正常にログインできる', () => {
    loginPage
      .visit()
      .login('user@example.com', 'password123');

    cy.url().should('include', '/dashboard');
  });
});

POMのベストプラクティス

✓ 良いPage Objectの特徴
  • 単一責任：1ページ = 1 Page Object
  • 操作の抽象化：「ログインする」のような高レベルのメソッド
  • アサーションはテストに：Page Objectでassertしない
  • メソッドチェーン：return thisで連続呼び出し可能に
⚠️ AIがやりがちな間違い 
// ❌ Page Objectでアサーションしている
class LoginPage {
  async login(email, password) {
    await this.page.fill('#email', email);
    await this.page.fill('#password', password);
    await this.page.click('#submit');
    // ❌ アサーションはPage Objectでやらない
    await expect(this.page).toHaveURL('/dashboard');
  }
}

// ⭕ アサーションはテストコードで行う
class LoginPage {
  async login(email, password) {
    await this.page.fill('#email', email);
    await this.page.fill('#password', password);
    await this.page.click('#submit');
    // アサーションは呼び出し側で
  }
}

// テストコード
await loginPage.login('user@example.com', 'pass');
await expect(page).toHaveURL('/dashboard'); // ここでアサート
🔍 コードレビューの観点
  • セレクタの露出：テストコードにセレクタが直書きされていないか
  • Page Objectの肥大化：1つのPage Objectが大きすぎないか
  • 命名の明確さ：メソッド名が操作内容を表しているか
  • 適切な粒度：低レベルすぎる（fillEmailInput）/高レベルすぎないか

Flakyテスト対策

📚 このページで学ぶこと
  • Flakyテストの原因と検出方法
  • 待機戦略とリトライ
  • テストの隔離と安定化

Flakyテストとは

Flakyテストとは、コードを変更していないのに、 成功したり失敗したりする不安定なテストです。

⚠️ Flakyテストの悪影響
  • 信頼性の低下：「またFlakyか」とテストを無視するようになる
  • CI/CDの阻害：無関係なテスト失敗でデプロイがブロック
  • デバッグ時間の浪費：原因特定に時間がかかる
  • 本物のバグの見逃し：Flakyに紛れて見落とす

Flakyテストの主な原因

📊 Flakyテストの原因分類

対策1：適切な待機戦略

避けるべき待機
// ❌ 固定時間の待機
await page.waitForTimeout(5000);
await page.click('#submit');

// ❌ 短すぎる待機
await page.waitForTimeout(100);
expect(await page.textContent('.result')).toBe('Success');
推奨される待機
// ⭕ 要素の状態を待つ
await page.waitForSelector('.result', { state: 'visible' });
await page.click('#submit');

// ⭕ ネットワークリクエストを待つ
await Promise.all([
  page.waitForResponse(resp => resp.url().includes('/api/data')),
  page.click('#submit'),
]);

// ⭕ アサーションに待機を組み込む（Playwright）

await expect(page.locator('.loading')).not.toBeVisible();

⚠️ リトライの注意点

リトライは対症療法です。 根本原因を解決せずにリトライに頼りすぎると、 テストスイート全体の実行時間が増加します。

対策3：テストの隔離

💻 テストの独立性を確保 
// ⭕ 各テストで独自のデータを使う

  });

    // testUserは他のテストと独立
  });
});

// ⭕ APIでテストデータをセットアップ
test.beforeEach(async ({ request }) => {
  // UIを経由せずAPIで直接データ作成

対策4：Flakyテストの検出

💻 Flakyテスト検出の方法 
# Playwright: 同じテストを複数回実行
npx playwright test --repeat-each=10

# 特定のテストファイルを繰り返し実行

✓ Flakyテスト対策チェックリスト
  • 固定時間待機を避ける：waitForTimeoutは使わない
  • 明示的な待機を使う：waitForSelector、expect().toBeVisible()
  • テストを独立させる：他のテストに依存しない
  • 外部依存をモック：不安定なAPIはモックする
  • リトライを適切に設定：CIでは2-3回
  • 定期的にFlaky検出：repeat-eachで検出
🔍 コードレビューの観点
  • waitForTimeout：固定時間待機がないか
  • テストの独立性：共有状態に依存していないか
  • データのクリーンアップ：afterEachで後片付けしているか
  • 過度なリトライ：リトライで誤魔化していないか

Visual Regressionテストとは

Visual Regressionテストは、UIの見た目が意図せず変わっていないかを スクリーンショット比較で検出するテストです。

🏠 たとえ話：間違い探し

2枚の絵を並べて「間違い探し」をするように、 前回のスクリーンショットと今回のスクリーンショットを比較します。

CSSの変更で意図せずレイアウトが崩れた場合、 機能テストでは検出できませんが、Visual Regressionなら検出できます。

クロスブラウザテストとは

クロスブラウザテストは、複数のブラウザでアプリケーションが 正しく動作することを確認するテストです。

⚠️ なぜ必要か

  • CSSの解釈の違い：Flexbox、Gridの挙動
  • ユーザーの多様性：特定ブラウザのみテストは危険

E2Eテストの選定基準

E2Eテストはコストが高いため、すべてをE2Eでテストするのは非効率です。 ROI（投資対効果）を考えて選定します。

📊 E2Eテストの選定マトリクス

E2Eテストすべきもの

✓ E2E必須のシナリオ
  • クリティカルパス：会員登録 → ログイン → 購入 → 決済完了
  • 収益に直結：カート追加、チェックアウト、サブスク登録
  • ユーザー影響大：パスワードリセット、アカウント削除
  • 統合ポイント：決済API、外部認証（OAuth）
✗ E2Eでテストすべきでないもの
  • エッジケース：境界値、異常系 → ユニットテストで
  • UIの細部：文言、色、位置 → Visual Regression/手動で
  • API単体：レスポンス形式 → APIテストで
  • 計算ロジック：税計算、割引 → ユニットテストで

ROIの計算

💡 E2EテストのROI計算 
// E2EテストのROI = (防いだ損失) / (テストコスト)

防いだ損失:
  - 障害発生時の売上損失
  - 障害対応の人件費
  - 顧客からの信頼低下

テストコスト:
  - テスト作成時間
  - メンテナンス時間
  - CI/CD実行時間
  - インフラコスト（デバイスファーム等）

例：決済フローのE2Eテスト
  - 障害時の損失: 100万円/時間 × 平均復旧2時間 = 200万円
  - 年間障害回数（テストなし）: 5回 → 1000万円の損失
  - テスト導入で障害を1回に削減 → 800万円の損失防止
  - テストコスト: 作成50万円 + 年間運用100万円 = 150万円
  - ROI = 800万円 / 150万円 = 約5.3倍

E2Eテストの運用

💻 CI/CD統合のベストプラクティス 
# .github/workflows/e2e.yml
name: E2E Tests

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  e2e:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: '20'

      - name: Install dependencies
        run: npm ci

      - name: Install Playwright browsers
        run: npx playwright install --with-deps

      - name: Run E2E tests
        run: npx playwright test
        env:
          CI: true

      - name: Upload test results
        if: failure()
        uses: actions/upload-artifact@v4
        with:
          name: playwright-report
          path: playwright-report/
