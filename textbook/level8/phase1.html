テストとは何か

テストとは、ソフトウェアが期待通りに動作するかを検証する活動です。

🏠 たとえ話：家の検査

家を建てたら、引き渡し前に検査をしますよね。
水道は出るか、電気は通るか、ドアは開くか...

ソフトウェアも同じ。リリース前に「ちゃんと動くか」を確認するのがテストです。

なぜテストするのか

📊 テストの目的

テストのROI（投資対効果）

テストなし
  • 本番でバグ発覚 → 緊急対応
  • 修正コストが10〜100倍
  • ユーザーの信頼を失う
  • リファクタリングが怖い
テストあり
  • 開発中にバグ発見 → 即修正
  • 修正コストが最小
  • 安心してリリース
  • 自信を持ってリファクタ
💰 バグ修正コストの法則

バグは発見が遅いほど修正コストが高くなる。

発見フェーズ 相対コスト
設計時 1倍
開発時（単体テスト） 5倍
結合テスト時 10倍
本番リリース後 30〜100倍
🔍 コードレビューの観点
  • テストがないPR：新機能やバグ修正にテストが含まれていないPRはリリース後のバグリスクが大きい。「テストは後で書く」は実現しないことが多い
  • テストカバレッジの数値だけに頼る危険：80%のカバレッジでも、重要なエッジケースが未テストなら意味がない。カバレッジは目安であり、テストの質（境界値、異常系）を必ず確認する
  • テストの可読性：テストコードも「ドキュメント」。何をテストしているか3秒で理解できるか？テスト名が test1、test2 ではなく should return 404 when user not found のように意図が明確か
  • テストが形骸化：常にパスするテスト、アサーションのないテストは無意味
  • テストなしのリファクタ：既存機能を壊すリスク
❓ 確認クイズ

本番リリース後にバグを発見した場合、開発時に発見した場合と比べてどのくらいの修正コストがかかる？

テストの分類

📊 テストの種類

各テストの詳細

種類 対象 目的 実行者
単体テスト 関数、メソッド 個々の部品が正しく動くか 開発者
結合テスト 複数コンポーネント 部品同士が連携できるか 開発者/QA
E2Eテスト システム全体 ユーザーフロー全体が動くか QA/自動化
受入テスト ビジネス要件 要件を満たしているか PO/顧客
回帰テスト 既存機能 変更で壊れていないか 自動化

テストの例

単体テスト
// 関数単体をテスト
test('合計を計算できる', () => {
  const result = sum(1, 2);
  expect(result).toBe(3);
});
E2Eテスト
// ユーザーフローをテスト
test('商品を購入できる', async () => {
  await page.goto('/products');
  await page.click('.add-to-cart');
  await page.click('.checkout');
  await expect(page).toHaveURL('/success');
});

💀 コードレビューの観点

  • テスト種類の混同：単体テストで外部API呼び出しをしている → 結合テストに分類すべき。テストの種類を正しく分けることで実行速度と安定性が向上する
  • E2Eテストの過剰：すべてをE2Eで検証しようとするとCI/CDが遅くなる。テストピラミッドを意識して適切な比率を保つ
  • 回帰テストの欠如：バグ修正時に再発防止のテストが追加されているか確認する

テストピラミッドとは

テストピラミッドは、テストの理想的な比率を示すモデルです。

📊 テストピラミッド

なぜピラミッド型なのか

テスト種類 実行速度 コスト 安定性 推奨比率
単体テスト 非常に速い 低い 高い 70%
結合テスト 普通 中程度 中程度 20%
E2Eテスト 遅い 高い 低い 10%

逆ピラミッド（アンチパターン）

⚠️ アイスクリームコーン

E2Eテストが多すぎる状態をアイスクリームコーンと呼びます。

  • テストが遅くてCI/CDが遅延
  • テストが不安定（Flaky）になりやすい
  • メンテナンスコストが高い
  • バグの原因特定が困難

❌ アイスクリームコーン型

// E2Eテストだらけのプロジェクト
// テスト実行: 45分
// Flakyテスト率: 20%
describe('全機能E2Eテスト', () => {
  test('ログインできる', async () => {...});
  test('商品一覧が表示される', async () => {...});
  test('検索できる', async () => {...});
  test('ソートできる', async () => {...});
  // ...E2Eだけで200件以上
});

⭕ ピラミッド型

// 単体テスト: 500件 (2秒)
test('合計計算', () => {...});
test('バリデーション', () => {...});

// 結合テスト: 100件 (30秒)
test('API経由でユーザー作成', () => {...});

// E2E: 20件 (5分)
test('購入フロー完了', () => {...});

開発者思考 vs QA思考

開発者思考

「正しく動くことを確認する」

  • ハッピーパスのみテスト
  • 自分のコードを信じる
  • 「普通はこう使う」と想定
QA思考

「どうしたら壊れるかを考える」

  • 異常系を積極的にテスト
  • ユーザーの予想外の行動を想定
  • 「もしこうしたら？」を問う

エッジケースの例

🎯 考えるべきエッジケース
入力タイプ エッジケース
文字列 空文字、null、超長い文字、特殊文字、絵文字
数値 0、負数、小数、MAX_VALUE、NaN
配列 空配列、1要素、重複要素、null含む
日付 うるう年、月末、タイムゾーン、過去日
❌ AIがやりがちな間違い 
// ❌ ハッピーパスのみ
test('ユーザー名を取得できる', () => {
  const user = getUser(1);
  expect(user.name).toBe('太郎');
});

// ⭕ 異常系もテスト
describe('ユーザー取得', () => {
  test('正常: ユーザーを取得できる', () => {
    const user = getUser(1);
    expect(user.name).toBe('太郎');
  });

  test('異常: 存在しないIDでnullを返す', () => {
    const user = getUser(999);
    expect(user).toBeNull();
  });

  test('異常: 負のIDでエラー', () => {
    expect(() => getUser(-1)).toThrow();
  });
});

テストの7原則

📚 このページで学ぶこと

ISTQB テストの7原則

📜 7つの原則
  1. テストは欠陥の存在を示す：欠陥がないことは証明できない
  2. 全数テストは不可能：すべての組み合わせはテストできない
  3. 早期テスト：早く始めるほど効果的
  4. 欠陥の偏在：バグは特定の場所に集中する
  5. 殺虫剤のパラドックス：同じテストではバグは見つからなくなる
  6. テストは状況次第：コンテキストによって最適なテストは異なる
  7. 「欠陥ゼロ」の落とし穴：欠陥がなくても使えないシステムはある

特に重要な原則

⚠️ 全数テストは不可能

例：3つの入力フィールドがあり、それぞれ100通りの値を取る場合
→ 100 × 100 × 100 = 100万通りの組み合わせ

だからリスクベースでテストを選択する必要がある。

🐛 欠陥の偏在（パレートの法則）

全体の20%のモジュールに80%のバグが存在する傾向がある。

→ バグが多い領域を特定し、重点的にテストする。

💀 コードレビューの観点

  • 殺虫剤のパラドックス：同じテストケースが長期間更新されていないか。新機能追加時にテストも更新しているか確認する
  • 欠陥ゼロへの過信：テストがすべてパスしていても、テストケース自体が不十分な可能性を常に疑う
  • 早期テストの実践：設計段階でテスト可能性を考慮しているか。テスト困難なコードは設計に問題がある

❌ 殺虫剤のパラドックス

// 2年前から変わらないテストケース
test('ユーザー登録', () => {
  // 正常系だけ
  const user = register('taro');
  expect(user).toBeDefined();
});
// → 新機能追加してもテスト更新なし
// → 見つかるバグがどんどん減る

⭕ テストを継続的に進化

// 新機能に合わせてテスト追加
test('2段階認証付きで登録', () => {
  const user = register('taro', {
    twoFactor: true
  });
  expect(user.twoFactorEnabled).toBe(true);
});
// → 機能追加ごとにテストも成長

ボックステスト

📚 このページで学ぶこと

3つのテストアプローチ

📊 ボックステストの分類
アプローチ 内部構造 主な用途 例
ホワイトボックス 知っている 単体テスト、分岐網羅 すべての条件分岐を通過
ブラックボックス 知らない 機能テスト、受入テスト 入力と出力のみ確認
グレーボックス 部分的 結合テスト、APIテスト APIの仕様は知るが実装は知らない

💀 コードレビューの観点

  • テストアプローチの偏り：ホワイトボックスのみだと仕様の漏れを見逃す。ブラックボックスのみだと内部ロジックの抜けを見逃す。両方を組み合わせているか確認
  • 内部実装への過度な依存：ホワイトボックスで内部メソッドの呼び出し順序をテストしていると、リファクタリングでテストが壊れる
  • APIテストのアプローチ：APIテストはグレーボックスが適切。レスポンス形式は知るが内部SQLは知らない前提でテスト設計する

❌ ホワイトボックスに偏りすぎ

// 内部実装を直接検証
test('処理の流れ', () => {
  const spy = jest.spyOn(service, '_validate');
  service.process(data);
  // 内部メソッドの呼び出しを検証
  expect(spy).toHaveBeenCalledBefore(
    otherSpy
  );
});

⭕ ブラックボックス観点

// 入力と出力で検証
test('有効なデータで成功する', () => {
  const result = service.process(validData);
  expect(result.status).toBe('success');
});

test('無効なデータでエラー', () => {
  expect(() => service.process(null))
    .toThrow('Invalid data');
});

静的テスト vs 動的テスト

静的テスト

コードを実行しない

  • コードレビュー
  • 静的解析（ESLint, TypeScript）
  • ドキュメントレビュー

バグを早期に発見できる

動的テスト

コードを実行する

  • 単体テスト
  • 結合テスト
  • E2Eテスト

実際の動作を確認できる

静的解析ツール

🔧 代表的なツール
ツール 目的
ESLint JavaScript/TypeScriptのコード品質
TypeScript 型チェック
Prettier コードフォーマット
SonarQube コード品質・セキュリティ

💀 コードレビューの観点

  • 静的解析の無視：ESLintの警告を // eslint-disable で無効化していないか。正当な理由なしにルールを無効化するPRは差し戻し
  • 型安全性の欠如：any型の多用はTypeScriptの静的型チェックを無効化する。as anyのキャストが含まれるPRは要注意
  • CI/CDでの静的テスト漏れ：lint、型チェック、フォーマットがCIに含まれているか確認

テスト計画とは

テスト計画とは、何を、いつ、どのようにテストするかを定義するドキュメントです。

📋 テスト計画に含める項目
  • スコープ：何をテストするか/しないか
  • テスト戦略：どのようなアプローチでテストするか
  • リソース：人員、ツール、環境
  • スケジュール：いつまでに完了するか
  • リスク：想定されるリスクと対策
  • 完了基準：テスト終了の判断基準

リソース配分の考え方

⚖️ リスクベースの配分

全機能を均等にテストするのではなく、リスクが高い機能に多くリソースを割く。

  • 決済機能 → 重点テスト
  • 認証機能 → 重点テスト
  • 管理画面の見た目 → 軽めでOK

❌ 均等配分のテスト計画

// すべての機能を同じ工数でテスト
テスト計画:
- ログイン機能: 2日
- 決済機能: 2日    ← 足りない！
- ヘルプページ: 2日 ← 多すぎる！
- 管理画面: 2日
// リスクを無視した均等配分

⭕ リスクベースのテスト計画

// リスクに応じて工数を配分
テスト計画:
- 決済機能: 5日（高リスク）
- ログイン/認証: 4日（高リスク）
- 検索・一覧: 2日（中リスク）
- ヘルプ/管理: 1日（低リスク）
// 重要な機能に重点配分

💀 コードレビューの観点

  • テスト計画の不在：テスト方針がないまま「とりあえずテストを書く」は非効率。最低限スコープと優先度を定義する
  • 完了基準の曖昧さ：「十分にテストした」の基準が不明確なまま進めていないか
  • テスト環境の未整備：テストDBやモックサーバーの準備が計画に含まれているか

テストケース設計

良いテストケースの条件

✅ 良いテストケースの特徴
  1. 再現性：何度実行しても同じ結果になる
  2. 独立性：他のテストに依存しない
  3. 明確な期待値：何が正しいか明確
  4. 単一の検証：1つのテストで1つのことを検証
  5. わかりやすい名前：何をテストしているかわかる

テストケースの例

悪い例
test('test1', () => {
  // 何をテストしている？
  const result = process(data);
  expect(result).toBeTruthy();
  // 期待値が曖昧
});
良い例
test('空の配列を渡すと空配列を返す', () => {
  // 明確な入力
  const input = [];
  // 明確な操作
  const result = filterActive(input);
  // 明確な期待値
  expect(result).toEqual([]);
});

💀 コードレビューの観点

  • テスト名が不明瞭：test('test1')やtest('works')のような名前は即座に差し戻し。何をテストしているか一目でわかる名前にする
  • 複数のことを検証：1つのテストで5個のexpectがある場合、テストを分割すべき。失敗時にどこが壊れたかわかりにくい
  • テスト間の依存：「テストAが先に実行されないとテストBが失敗する」は設計ミス。各テストが独立して実行できるか確認

テスト環境とは

テストを実行する環境。本番環境との差異がバグの見逃しにつながる。

⚠️ 本番との差異の例
  • OSが違う（Windows vs Linux）
  • データベースのバージョンが違う
  • 外部サービスがモックされている
  • データ量が違う（本番は100万件、テストは10件）
  • ネットワーク環境が違う

テストデータ管理

📊 テストデータの種類
種類 説明 用途
シードデータ テスト前に投入する固定データ 初期状態の再現
ファクトリ テスト内で動的に生成 柔軟なデータ作成
フィクスチャ JSONなどで定義した固定データ 複雑なデータ構造
🔍 コードレビューの観点
  • 本番データの使用：個人情報の漏洩リスク
  • 環境依存のテスト：他の環境で動かない
  • テストデータの汚染：テスト後にデータが残る

❌ 環境差異が大きい

// テスト: ローカルSQLite
// 本番: PostgreSQL
test('ユーザー検索', async () => {
  // SQLiteでは大文字小文字を区別しない
  const users = await search('TARO');
  expect(users).toHaveLength(1);
  // → 本番PostgreSQLでは0件！
});

⭕ 環境を統一

// Docker Composeで本番同等のDBを使用
// docker-compose.test.yml
// services:
//   db:
//     image: postgres:16
test('ユーザー検索', async () => {
  const users = await search('TARO');
  // 本番と同じDB → 結果も同じ
  expect(users).toHaveLength(0);
});
