テストとは何か

テストとは、ソフトウェアが期待通りに動作するかを検証する活動です。

🏠 たとえ話：家の検査

家を建てたら、引き渡し前に検査をしますよね。
水道は出るか、電気は通るか、ドアは開くか...

ソフトウェアも同じ。リリース前に「ちゃんと動くか」を確認するのがテストです。

なぜテストするのか

📊 テストの目的

テストのROI（投資対効果）

テストなし
  • 本番でバグ発覚 → 緊急対応
  • 修正コストが10〜100倍
  • ユーザーの信頼を失う
  • リファクタリングが怖い
テストあり
  • 開発中にバグ発見 → 即修正
  • 修正コストが最小
  • 安心してリリース
  • 自信を持ってリファクタ
💰 バグ修正コストの法則

バグは発見が遅いほど修正コストが高くなる。

発見フェーズ 相対コスト
設計時 1倍
開発時（単体テスト） 5倍
結合テスト時 10倍
本番リリース後 30〜100倍
🔍 コードレビューの観点
  • テストがない機能：リリース後のバグリスク大
  • テストが形骸化：常にパスするテストは無意味
  • テストなしのリファクタ：既存機能を壊すリスク

テストの分類

📊 テストの種類

各テストの詳細

種類 対象 目的 実行者
単体テスト 関数、メソッド 個々の部品が正しく動くか 開発者
結合テスト 複数コンポーネント 部品同士が連携できるか 開発者/QA
E2Eテスト システム全体 ユーザーフロー全体が動くか QA/自動化
受入テスト ビジネス要件 要件を満たしているか PO/顧客
回帰テスト 既存機能 変更で壊れていないか 自動化

テストの例

単体テスト
// 関数単体をテスト
test('合計を計算できる', () => {
  const result = sum(1, 2);
  expect(result).toBe(3);
});
E2Eテスト
// ユーザーフローをテスト
test('商品を購入できる', async () => {
  await page.goto('/products');
  await page.click('.add-to-cart');
  await page.click('.checkout');
  await expect(page).toHaveURL('/success');
});

開発者思考 vs QA思考

開発者思考

「正しく動くことを確認する」

  • ハッピーパスのみテスト
  • 自分のコードを信じる
  • 「普通はこう使う」と想定
QA思考

「どうしたら壊れるかを考える」

  • 異常系を積極的にテスト
  • ユーザーの予想外の行動を想定
  • 「もしこうしたら？」を問う

// ❌ ハッピーパスのみ
test('ユーザー名を取得できる', () => {
  const user = getUser(1);
  expect(user.name).toBe('太郎');
});

// ⭕ 異常系もテスト
describe('ユーザー取得', () => {
  test('正常: ユーザーを取得できる', () => {
    const user = getUser(1);
    expect(user.name).toBe('太郎');
  });

  test('異常: 存在しないIDでnullを返す', () => {
    const user = getUser(999);
    expect(user).toBeNull();
  });

  test('異常: 負のIDでエラー', () => {
    expect(() => getUser(-1)).toThrow();
  });
});

ISTQB テストの7原則

📜 7つの原則
  1. テストは欠陥の存在を示す：欠陥がないことは証明できない
  2. 全数テストは不可能：すべての組み合わせはテストできない
  3. 早期テスト：早く始めるほど効果的
  4. 欠陥の偏在：バグは特定の場所に集中する
  5. 殺虫剤のパラドックス：同じテストではバグは見つからなくなる
  6. テストは状況次第：コンテキストによって最適なテストは異なる
  7. 「欠陥ゼロ」の落とし穴：欠陥がなくても使えないシステムはある

特に重要な原則

⚠️ 全数テストは不可能

例：3つの入力フィールドがあり、それぞれ100通りの値を取る場合
→ 100 × 100 × 100 = 100万通りの組み合わせ

だからリスクベースでテストを選択する必要がある。

🐛 欠陥の偏在（パレートの法則）

全体の20%のモジュールに80%のバグが存在する傾向がある。

→ バグが多い領域を特定し、重点的にテストする。

テスト計画とは

テスト計画とは、何を、いつ、どのようにテストするかを定義するドキュメントです。

📋 テスト計画に含める項目
  • スコープ：何をテストするか/しないか
  • テスト戦略：どのようなアプローチでテストするか
  • リソース：人員、ツール、環境
  • スケジュール：いつまでに完了するか
  • リスク：想定されるリスクと対策
  • 完了基準：テスト終了の判断基準

リソース配分の考え方

⚖️ リスクベースの配分

全機能を均等にテストするのではなく、リスクが高い機能に多くリソースを割く。

  • 決済機能 → 重点テスト
  • 認証機能 → 重点テスト
  • 管理画面の見た目 → 軽めでOK

良いテストケースの条件

✅ 良いテストケースの特徴
  1. 再現性：何度実行しても同じ結果になる
  2. 独立性：他のテストに依存しない
  3. 明確な期待値：何が正しいか明確
  4. 単一の検証：1つのテストで1つのことを検証
  5. わかりやすい名前：何をテストしているかわかる

テストケースの例

悪い例
test('test1', () => {
  // 何をテストしている？
  const result = process(data);
  expect(result).toBeTruthy();
  // 期待値が曖昧
});
良い例
test('空の配列を渡すと空配列を返す', () => {
  // 明確な入力
  const input = [];
  // 明確な操作
  const result = filterActive(input);
  // 明確な期待値
  expect(result).toEqual([]);
});

テスト環境とは

テストを実行する環境。本番環境との差異がバグの見逃しにつながる。

⚠️ 本番との差異の例
  • OSが違う（Windows vs Linux）
  • データベースのバージョンが違う
  • 外部サービスがモックされている
  • データ量が違う（本番は100万件、テストは10件）
  • ネットワーク環境が違う

テストデータ管理

📊 テストデータの種類
種類 説明 用途
シードデータ テスト前に投入する固定データ 初期状態の再現
ファクトリ テスト内で動的に生成 柔軟なデータ作成
フィクスチャ JSONなどで定義した固定データ 複雑なデータ構造
🔍 コードレビューの観点
  • 本番データの使用：個人情報の漏洩リスク
  • 環境依存のテスト：他の環境で動かない
  • テストデータの汚染：テスト後にデータが残る
