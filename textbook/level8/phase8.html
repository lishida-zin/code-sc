パフォーマンステストの種類

種類 目的 シナリオ
負荷テスト 通常負荷での性能 想定ユーザー数で動作確認
ストレステスト 限界性能の確認 限界まで負荷をかける
スパイクテスト 急激な負荷への対応 突然のアクセス増加
耐久テスト 長時間稼働の安定性 24時間以上の連続稼働

k6の例

🔧 k6スクリプト 
import http from 'k6/http';
import { check, sleep } from 'k6';

export const options = {
  vus: 100,  // 仮想ユーザー数
  duration: '30s',  // テスト時間
};

export default function() {
  const res = http.get('https://api.example.com/users');

  check(res, {
    'status is 200': (r) => r.status === 200,
    'response time < 200ms': (r) => r.timings.duration < 200,
  });

  sleep(1);
}

OWASP ZAP

🔧 ZAPでできること
  • 自動スキャン：よくある脆弱性を自動検出
  • 手動テスト：プロキシとして動作し、リクエストを改変
  • CI/CD統合：パイプラインでセキュリティテスト
⚠️ よく見つかる脆弱性
  • XSS：クロスサイトスクリプティング
  • SQLインジェクション：SQLの不正実行
  • CSRF：クロスサイトリクエストフォージェリ
  • 認証の欠陥：セッション管理の不備

axeによる自動テスト

🔧 axe-core + Playwright 
import { test, expect } from '@playwright/test';
import AxeBuilder from '@axe-core/playwright';

test('ホームページのa11yチェック', async ({ page }) => {
  await page.goto('/');

  const results = await new AxeBuilder({ page }).analyze();

  expect(results.violations).toEqual([]);
});
⚠️ 自動テストの限界

自動テストで検出できるのは約30%の問題のみ。
手動テスト（スクリーンリーダー使用など）も必要。

重要なメトリクス

テスト実行率 実行テスト / 計画テスト テスト進捗

メトリクスの罠

⚠️ グッドハートの法則

「指標が目標になると、良い指標でなくなる」

  • バグ数を目標にすると → 報告されなくなる
  • カバレッジを目標にすると → 無意味なテストが増える
  • テスト数を目標にすると → 質が下がる

ダッシュボードに含めるもの

📊 品質ダッシュボードの要素
  • テスト実行状況：成功/失敗/スキップ
  • カバレッジ：行/分岐カバレッジの推移
  • バグ状況：新規/解決/残存
  • パフォーマンス：レスポンスタイム推移
  • Flakyテスト：不安定なテストのリスト

トレンド分析

📈 注目すべきトレンド
  • カバレッジが下がっている → テストが追いついていない
  • テスト時間が増えている → パフォーマンス問題
  • Flakyテストが増えている → テスト環境の問題
  • バグ逃げ率が上がっている → テスト戦略の見直し

AIテストの注意点

⚠️ AIテストの限界

  • ビジネスロジック：AIは要件を完全に理解しない

  • コスト：AIツールは高価なものが多い

品質はQAチームだけの責任ではない

⚠️ アンチパターン
  • 「QAがテストするから大丈夫」
  • 「バグを見つけるのはQAの仕事」
  • 「開発者はコードを書くだけ」

→ 品質はチーム全体の責任

DevQAOps

🔄 DevQAOpsの原則
  • 開発者がテストを書く：単体テストは開発者の責務
  • QAが戦略を立てる：テスト全体の設計
  • Opsが監視する：本番環境での品質監視
  • 全員が品質に責任を持つ

品質文化の構築

🏗️ 品質文化を作るには
  1. 経営層のコミットメント：品質への投資を認める
  2. 自動化への投資：CI/CD、自動テスト
  3. 学習の機会：テスト技術の教育
  4. 失敗から学ぶ：ポストモーテムの実施
  5. 品質の可視化：ダッシュボードで共有
