結合テストとは

結合テスト（Integration Test）とは、複数のコンポーネントを組み合わせて正しく連携するかを検証するテストです。

🏠 たとえ話：オーケストラのリハーサル

各楽器奏者が個別に練習する = 単体テスト
全員で合わせて演奏する = 結合テスト

個人が完璧でも、タイミングが合わなければ音楽にならない。
結合テストは「ちゃんと合奏できるか」を確認します。

単体テストとの違い

コンポーネント連携の検証

結合テストで検証すべき連携ポイントは以下です。

🔗 検証すべき連携
  • API呼び出し：Controller → Service → Repository
  • データベース連携：アプリ → DB への読み書き
  • 外部サービス連携：自システム → 外部API
  • メッセージング：Producer → Queue → Consumer

境界（バウンダリ）の確認

境界とは、異なるコンポーネント間の接点です。
ここが結合テストの最重要ポイントです。

⚠️ 境界で起きやすい問題
  • データ形式の不一致：Date型 vs 文字列、タイムゾーン
  • null/undefinedの扱い：送信側と受信側で認識が違う
  • エラーハンドリング：例外が正しく伝播しない
  • トランザクション境界：ロールバックが効かない
💻 結合テストの例（Node.js） 
// 結合テスト：Controller + Service + Repository
describe('UserController Integration', () => {
  let app: Express;
  let db: Database;

  beforeAll(async () => {
    // 実際のDBに接続（テスト用）
    db = await Database.connect(TEST_DB_URL);
    app = createApp(db);
  });

  afterAll(async () => {
    await db.close();
  });

  it('ユーザー作成からDB保存まで連携する', async () => {
    const response = await request(app)
      .post('/users')
      .send({ name: '田中', email: 'tanaka@example.com' });

    expect(response.status).toBe(201);

    // DBに実際に保存されたか確認
    const user = await db.query(
      'SELECT * FROM users WHERE email = $1',
      ['tanaka@example.com']
    );
    expect(user.rows[0].name).toBe('田中');
  });
});
🔍 コードレビューの観点
  • モックばかりの結合テスト：全部モックなら単体テストと変わらない
  • テスト後のクリーンアップ漏れ：テストデータが残る
  • 境界条件のテスト不足：正常系だけでは不十分

結合テスト戦略

📚 このページで学ぶこと

3つの結合テスト戦略

結合テストを行う順番には3つの戦略があります。

トップダウンアプローチ

⬇️ トップダウン

上位モジュール（UI、Controller）から先にテストし、
下位モジュールはスタブ（Stub）で代用します。 

// トップダウン：Controllerを先にテスト、Serviceはスタブ
describe('UserController', () => {
  it('ユーザー一覧を取得', async () => {
    // Serviceをスタブ化
    const mockService = {
      findAll: jest.fn().mockResolvedValue([
        { id: 1, name: 'テストユーザー' }
      ])
    };

    const controller = new UserController(mockService);
    const result = await controller.list();

    expect(result).toHaveLength(1);
  });
});

スタブ：呼び出されたら固定値を返すダミー実装

ボトムアップアプローチ

⬆️ ボトムアップ

下位モジュール（Repository、DB層）から先にテストし、
上位モジュールはドライバ（Driver）で呼び出します。 

// ボトムアップ：Repositoryを先にテスト
describe('UserRepository', () => {
  let repository: UserRepository;
  let db: TestDatabase;

  beforeAll(async () => {
    db = await TestDatabase.create();
    repository = new UserRepository(db);
  });

  it('ユーザーを保存できる', async () => {
    // テストドライバとして直接Repositoryを呼び出す
    const user = await repository.save({
      name: '田中',
      email: 'tanaka@example.com'
    });

    expect(user.id).toBeDefined();
    expect(user.name).toBe('田中');
  });
});

ドライバ：テスト対象を呼び出すためのテストコード

サンドイッチアプローチ

🥪 サンドイッチ（ハイブリッド）

上位と下位を同時並行でテストし、
中間層で合流させます。

  • チームを分けて並列開発する大規模プロジェクト向け
  • UIチーム：トップダウンでController層まで
  • バックエンドチーム：ボトムアップでService層まで
  • 最後にService層で結合
✓ 実務での選択基準
状況 推奨アプローチ
UIを早く見せたい トップダウン
DB設計が固まっている ボトムアップ
大規模・並列開発 サンドイッチ
小規模・アジャイル 柔軟に組み合わせ
🔍 コードレビューの観点
  • 戦略なき結合テスト：場当たり的で網羅性がない
  • スタブの過剰使用：実際の連携をテストしていない
  • ドライバの使い回し：本番コードに混入していないか

APIテストとは

APIテストとは、HTTP APIの動作を検証するテストです。
フロントエンドとバックエンドの契約が守られているかを確認します。

HTTPメソッド

📝 PUT vs PATCH
  • PUT：リソース全体を置き換える（全フィールド必須）
  • PATCH：リソースの一部を更新（変更フィールドのみ）
// PUT: 全フィールドを送信
PUT /users/123
{ "name": "田中", "email": "tanaka@example.com", "age": 30 }

// PATCH: 変更部分のみ送信
PATCH /users/123
{ "age": 31 }

ステータスコード

🔢 主要なステータスコード
コード 意味 使用場面
200 OK GET成功、PUT/PATCH成功
201 Created POST成功（リソース作成）
204 No Content DELETE成功（レスポンスボディなし）
400 Bad Request リクエスト形式エラー
401 Unauthorized 認証が必要
403 Forbidden 認可エラー（権限なし）
404 Not Found リソースが存在しない
500 Internal Server Error サーバー内部エラー

リクエスト/レスポンスのペイロード

📦 JSONペイロードの例 
// リクエスト
POST /api/users HTTP/1.1
Content-Type: application/json

{
  "name": "田中太郎",
  "email": "tanaka@example.com",
  "role": "user"
}

// レスポンス
HTTP/1.1 201 Created
Content-Type: application/json

{
  "id": 123,
  "name": "田中太郎",
  "email": "tanaka@example.com",
  "role": "user",
  "createdAt": "2026-02-04T10:30:00Z"
}
⚠️ AIがやりがちな間違い 
// ❌ POSTで200を返す
POST /users
→ 200 OK  // 201 Createdが正しい

// ❌ DELETEでボディを返す
DELETE /users/123
→ 200 OK { "message": "deleted" }
// 204 No Content（ボディなし）が一般的

// ❌ 認証エラーで403を返す
→ 403 Forbidden  // 認証切れは401、認可エラーは403
🔍 コードレビューの観点
  • 不適切なステータスコード：全部200で返していないか
  • HTTPメソッドの誤用：GETで更新、POSTで取得
  • レスポンス形式の不統一：エラー時とスキーマが違う

Supertest / REST Assured

📚 このページで学ぶこと

Supertestとは

Supertestは、Node.js/ExpressアプリケーションのHTTPテストライブラリです。
サーバーを起動せずにAPIをテストできます。

💻 Supertestの基本 
import request from 'supertest';
import app from '../src/app';

describe('User API', () => {
  describe('GET /users', () => {
    it('ユーザー一覧を取得できる', async () => {
      const response = await request(app)
        .get('/users')
        .expect('Content-Type', /json/)
        .expect(200);

      expect(response.body).toBeInstanceOf(Array);
    });
  });

  describe('POST /users', () => {
    it('新規ユーザーを作成できる', async () => {
      const newUser = {
        name: '田中太郎',
        email: 'tanaka@example.com'
      };

      const response = await request(app)
        .post('/users')
        .send(newUser)
        .expect('Content-Type', /json/)
        .expect(201);

      expect(response.body.id).toBeDefined();
      expect(response.body.name).toBe(newUser.name);
    });

    it('必須フィールドがない場合は400を返す', async () => {
      await request(app)
        .post('/users')
        .send({ name: '田中' }) // emailがない
        .expect(400);
    });
  });
});
🔧 認証付きリクエストのテスト 
describe('認証が必要なAPI', () => {
  let authToken: string;

  beforeAll(async () => {
    // ログインしてトークンを取得
    const loginResponse = await request(app)
      .post('/auth/login')
      .send({ email: 'admin@example.com', password: 'password' });

    authToken = loginResponse.body.token;
  });

  it('認証済みでプロフィールを取得できる', async () => {
    await request(app)
      .get('/profile')
      .set('Authorization', `Bearer ${authToken}`)
      .expect(200);
  });

  it('認証なしは401を返す', async () => {
    await request(app)
      .get('/profile')
      .expect(401);
  });
});

REST Assured（Java）

REST Assuredは、Java向けのAPIテストライブラリです。
流暢なAPIで読みやすいテストが書けます。

☕ REST Assuredの基本（Java） 
import static io.restassured.RestAssured.*;
import static org.hamcrest.Matchers.*;

public class UserApiTest {

    @BeforeAll
    static void setup() {
        RestAssured.baseURI = "http://localhost:8080";
    }

    @Test
    void ユーザー一覧を取得できる() {
        given()
            .contentType(ContentType.JSON)
        .when()
            .get("/users")
        .then()
            .statusCode(200)
            .body("$", hasSize(greaterThan(0)))
            .body("[0].name", notNullValue());
    }

    @Test
    void 新規ユーザーを作成できる() {
        String requestBody = """
            {
                "name": "田中太郎",
                "email": "tanaka@example.com"
            }
            """;

        given()
            .contentType(ContentType.JSON)
            .body(requestBody)
        .when()
            .post("/users")
        .then()
            .statusCode(201)
            .body("id", notNullValue())
            .body("name", equalTo("田中太郎"));
    }
}

比較：Supertest vs REST Assured

観点 Supertest (Node.js) REST Assured (Java)
言語 JavaScript/TypeScript Java/Kotlin
スタイル async/await + チェーン given/when/then (BDD)
サーバー起動 不要（インメモリ） 必要（実サーバー）
適用範囲 Express/Fastify等 任意のREST API
🔍 コードレビューの観点
  • ステータスコードのみの検証：ボディの内容も確認すべき
  • ハードコードされたURL：環境変数やbaseURIを使う
  • テスト間の依存：順番に依存しないよう独立させる

契約テスト

📚 このページで学ぶこと

契約テストとは

契約テストとは、サービス間の「約束事」が守られているかを検証するテストです。

🏠 たとえ話：賃貸契約

大家さん（プロバイダ）と借主（コンシューマ）は契約書で約束を交わします。

  • 大家：「毎月1日に家賃を受け取る」
  • 借主：「毎月1日に家賃を払う」

この「契約」が守られているかを自動でチェックするのが契約テストです。

Pactによる契約テスト

Pactは、最も広く使われている契約テストツールです。

📝 Consumer側のテスト（契約を定義） 
// consumer.spec.ts（フロントエンド側）
import { PactV3, MatchersV3 } from '@pact-foundation/pact';

const provider = new PactV3({
  consumer: 'Frontend',
  provider: 'UserAPI'
});

describe('User API Contract', () => {
  it('ユーザー取得の契約', async () => {
    // 期待するリクエスト/レスポンスを定義
    await provider
      .given('ユーザーID=123が存在する')
      .uponReceiving('GET /users/123')
      .withRequest({
        method: 'GET',
        path: '/users/123'
      })
      .willRespondWith({
        status: 200,
        headers: { 'Content-Type': 'application/json' },
        body: MatchersV3.like({
          id: 123,
          name: MatchersV3.string('田中太郎'),
          email: MatchersV3.email()
        })
      });

    await provider.executeTest(async (mockServer) => {
      // mockServerに対してリクエストを実行
      const response = await fetch(`${mockServer.url}/users/123`);
      const user = await response.json();

      expect(user.id).toBe(123);
    });
  });
});
🔧 Provider側のテスト（契約を検証） 
// provider.spec.ts（バックエンド側）
import { Verifier } from '@pact-foundation/pact';

describe('Provider Verification', () => {
  it('すべての契約を満たす', async () => {
    const verifier = new Verifier({
      providerBaseUrl: 'http://localhost:3000',
      pactBrokerUrl: 'https://your-broker.pact.io',
      provider: 'UserAPI',
      providerVersion: process.env.GIT_COMMIT,

      // 状態のセットアップ
      stateHandlers: {
        'ユーザーID=123が存在する': async () => {
          // テストデータをDBに投入
          await db.users.create({ id: 123, name: '田中太郎' });
        }
      }
    });

    await verifier.verifyProvider();
  });
});

契約テストのメリット

✓ なぜ契約テストが必要か
  • 独立したデプロイ：全サービスを同時にテストしなくていい
  • 早期発見：本番前にAPI仕様の不整合を検出
  • ドキュメント：契約がそのまま仕様書になる
  • 安心感：プロバイダの変更がコンシューマを壊さない
🔍 コードレビューの観点
  • マッチャーの誤用：exact matchよりlike/regexを使うべき場面
  • 状態のセットアップ漏れ：given()に対応するstateHandlersがない
  • 契約の肥大化：1契約に多すぎるシナリオ

DBテスト

📚 このページで学ぶこと

なぜDBテストが重要か

実際のDBを使ったテストは、モックでは検出できない問題を発見します。

⚠️ モックでは検出できない問題
  • SQL構文エラー：実行して初めてわかる
  • 制約違反：UNIQUE、NOT NULL、外部キー
  • N+1問題：クエリ数が爆発する
  • トランザクション境界：ロールバックの挙動

テスト用データベースの構築

🐳 Testcontainersの使用例 
// Node.js + Testcontainers
import { PostgreSqlContainer } from '@testcontainers/postgresql';

describe('UserRepository', () => {
  let container: StartedPostgreSqlContainer;
  let db: Database;

  beforeAll(async () => {
    // Dockerコンテナを起動
    container = await new PostgreSqlContainer()
      .withDatabase('testdb')
      .start();

    // 接続
    db = await Database.connect(container.getConnectionUri());

    // マイグレーション実行
    await db.migrate();
  }, 60000); // タイムアウトを長めに

  afterAll(async () => {
    await db.close();
    await container.stop();
  });

  it('ユーザーを保存して取得できる', async () => {
    const repo = new UserRepository(db);

    const created = await repo.create({
      name: '田中',
      email: 'tanaka@example.com'
    });

    const found = await repo.findById(created.id);
    expect(found.name).toBe('田中');
  });
});

トランザクションロールバック戦略

テスト後のデータクリーンアップには2つの戦略があります。

トランザクションロールバック
beforeEach(async () => {
  await db.query('BEGIN');
});

afterEach(async () => {
  await db.query('ROLLBACK');
});

it('テスト', async () => {
  // INSERT/UPDATE/DELETE
  // → ROLLBACKで元に戻る
});

利点: 高速、確実

欠点: トランザクション境界のテストが難しい

テーブルトランケート
afterEach(async () => {
  await db.query('TRUNCATE users CASCADE');
});

it('テスト', async () => {
  // INSERT/UPDATE/DELETE
  // → TRUNCATEで全削除
});

利点: 実際のコミットをテスト可能

欠点: やや遅い

🔍 コードレビューの観点
  • 本番DBに接続：テスト用DB URLが環境変数で分離されているか
  • クリーンアップ漏れ：テストデータが残っていないか
  • テスト間の依存：順番に依存していないか
  • 接続リーク：afterAllでconnection.close()しているか
⚠️ AIがやりがちな間違い 
// ❌ 本番DBのURLをハードコード
const db = new Database('postgresql://prod-server/maindb');

// ❌ クリーンアップなし
it('ユーザー作成', async () => {
  await repo.create({ name: 'テスト' });
  // afterEachでのクリーンアップがない
});

// ❌ 接続を閉じない
afterAll(() => {
  // db.close() を忘れている
});

外部サービスのテスト

📚 このページで学ぶこと

外部サービステストの課題

外部APIに依存するコードのテストには課題があります。

⚠️ 外部APIをそのままテストする問題
  • 不安定：外部サービスの障害でテストが失敗
  • 遅い：ネットワーク遅延
  • コスト：API呼び出し課金
  • 制御不能：エラーケースを再現できない

WireMockの使用

🔧 WireMock（Node.js版）の例 
import { WireMock } from 'wiremock-captain';

describe('PaymentService', () => {
  let wireMock: WireMock;

  beforeAll(async () => {
    wireMock = new WireMock('http://localhost:8080');
  });

  beforeEach(async () => {
    await wireMock.clearAll();
  });

  it('決済APIを呼び出せる', async () => {
    // モックの設定
    await wireMock.register({
      request: {
        method: 'POST',
        url: '/v1/payments'
      },
      response: {
        status: 200,
        body: JSON.stringify({
          id: 'pay_123',
          status: 'succeeded'
        }),
        headers: { 'Content-Type': 'application/json' }
      }
    });

    // テスト実行
    const service = new PaymentService('http://localhost:8080');
    const result = await service.charge({ amount: 1000 });

    expect(result.status).toBe('succeeded');
  });

  it('決済APIがエラーを返す場合', async () => {
    // エラーケースのモック
    await wireMock.register({
      request: {
        method: 'POST',
        url: '/v1/payments'
      },
      response: {
        status: 402,
        body: JSON.stringify({
          error: { message: 'Card declined' }
        })
      }
    });

    const service = new PaymentService('http://localhost:8080');

    await expect(service.charge({ amount: 1000 }))
      .rejects.toThrow('Card declined');
  });
});

レコード＆リプレイ

レコード＆リプレイは、実際のAPIレスポンスを記録して再利用するパターンです。

📼 Nockによるレコード＆リプレイ（Node.js） 
import nock from 'nock';

// レコードモード（初回実行時）
nock.recorder.rec({
  output_objects: true,
  dont_print: true
});

// API呼び出し
await callExternalAPI();

// 記録を保存
const recordings = nock.recorder.play();
fs.writeFileSync('fixtures/api-recordings.json', JSON.stringify(recordings));

// リプレイモード（2回目以降）

🔐 JWTトークンのテスト例 
import jwt from 'jsonwebtoken';
import request from 'supertest';

describe('JWT認証テスト', () => {
  const SECRET = 'test-secret';

  // テスト用トークン生成ヘルパー
  const createToken = (payload: object, options = {}) => {
    return jwt.sign(payload, SECRET, { expiresIn: '1h', ...options });
  };

  it('有効なトークンでアクセスできる', async () => {
    const token = createToken({ userId: 123, role: 'user' });

    await request(app)
      .get('/api/profile')
      .set('Authorization', `Bearer ${token}`)
      .expect(200);
  });

  it('トークンなしは401を返す', async () => {
    await request(app)
      .get('/api/profile')
      .expect(401);
  });

  it('期限切れトークンは401を返す', async () => {
    const expiredToken = createToken(
      { userId: 123 },
      { expiresIn: '-1h' } // 1時間前に期限切れ
    );

    await request(app)
      .get('/api/profile')
      .set('Authorization', `Bearer ${expiredToken}`)
      .expect(401);
  });

  it('改ざんされたトークンは401を返す', async () => {
    const validToken = createToken({ userId: 123 });
    // ペイロードを改ざん
    const tamperedToken = validToken.slice(0, -5) + 'XXXXX';

    await request(app)
      .get('/api/profile')
      .set('Authorization', `Bearer ${tamperedToken}`)
      .expect(401);
  });
});

describe('ロールベースアクセス制御', () => {
  const createUserToken = (role: string) => {
    return jwt.sign({ userId: 1, role }, SECRET);
  };

  describe('管理者専用エンドポイント', () => {
    it('adminロールはアクセス可能', async () => {
      const adminToken = createUserToken('admin');

      await request(app)
        .get('/api/admin/users')
        .set('Authorization', `Bearer ${adminToken}`)
        .expect(200);
    });

    it('userロールは403を返す', async () => {
      const userToken = createUserToken('user');

      await request(app)
        .get('/api/admin/users')
        .set('Authorization', `Bearer ${userToken}`)
        .expect(403);
    });

    it('guestロールは403を返す', async () => {
      const guestToken = createUserToken('guest');

      await request(app)
        .get('/api/admin/users')
        .set('Authorization', `Bearer ${guestToken}`)
        .expect(403);
    });
  });

  describe('リソース所有権', () => {
    it('自分のデータは取得できる', async () => {
      const token = createUserToken('user');

      await request(app)
        .get('/api/users/1/profile') // 自分のID
        .set('Authorization', `Bearer ${token}`)
        .expect(200);
    });

    it('他人のデータは403を返す', async () => {
      const token = createUserToken('user');

      await request(app)
        .get('/api/users/999/profile') // 他人のID
        .set('Authorization', `Bearer ${token}`)
        .expect(403);
    });
  });
});

なぜ異常系テストが重要か

本番環境では、正常系より異常系の方が多く発生します。

⚠️ 本番で起きる異常

  • 外部サービス障害：5xx エラー、レート制限
  • データ不整合：想定外の null、不正なフォーマット
  • リソース枯渇：メモリ不足、ディスク容量

リトライロジックのテスト

🔄 リトライテストの例 
describe('リトライロジック', () => {
  it('一時的エラーは3回までリトライする', async () => {
    let callCount = 0;

    // 最初の2回は失敗、3回目で成功
    jest.spyOn(httpClient, 'get').mockImplementation(() => {
      callCount++;
      if (callCount < 3) {
        return Promise.reject(new Error('503 Service Unavailable'));
      }
      return Promise.resolve({ data: 'success' });
    });

    const service = new ResilientService({ maxRetries: 3 });
    const result = await service.fetch('/api/data');

    expect(result.data).toBe('success');
    expect(callCount).toBe(3);
  });

  it('永続的エラーはリトライしない', async () => {
    let callCount = 0;

    jest.spyOn(httpClient, 'get').mockImplementation(() => {
      callCount++;
      return Promise.reject(new Error('404 Not Found'));
    });

    const service = new ResilientService({ maxRetries: 3 });

    await expect(service.fetch('/api/data'))
      .rejects.toThrow('404 Not Found');

    // 404はリトライしない（1回のみ）
    expect(callCount).toBe(1);
  });

  it('指数バックオフで待機時間が増える', async () => {
    const delays: number[] = [];
    jest.spyOn(global, 'setTimeout').mockImplementation((fn, delay) => {
      delays.push(delay as number);
      (fn as Function)();
      return 0 as any;
    });

    // 3回失敗するモック
    jest.spyOn(httpClient, 'get').mockRejectedValue(new Error('503'));

    const service = new ResilientService({
      maxRetries: 3,
      backoff: 'exponential',
      initialDelay: 100
    });

    try {
      await service.fetch('/api/data');
    } catch (e) {}

    // 100ms → 200ms → 400ms（指数的に増加）
    expect(delays).toEqual([100, 200, 400]);
  });
});
🔍 コードレビューの観点
  • リトライ対象の判断：4xx は即失敗、5xx はリトライが基本
  • 無限リトライ：必ず上限を設ける
  • バックオフなし：障害時にサーバーを殴り続けてしまう
  • タイムアウト設定なし：永遠に待ち続ける可能性

テストデータ管理の課題

⚠️ よくある問題
  • ハードコード地獄：全テストに同じデータがベタ書き
  • データの依存関係：テストAのデータがテストBに影響
  • メンテナンス困難：スキーマ変更時に大量修正
  • 現実離れしたデータ：「test@test.com」では本番のバグを見逃す

ファクトリパターン

ファクトリは、テストデータを生成する専用の関数/クラスです。

🏭 ファクトリの実装例

シードデータ

シードは、テスト実行前にDBに投入する初期データです。

🌱 シードファイルの例 
// seeds/test-seed.ts
import { createUser } from '../factories/user.factory';

export const seedTestData = async (db: Database) => {
  // 管理者（固定ID）
  await db.users.create({
    id: 1,
    ...createUser({ role: 'admin', email: 'admin@test.com' })
  });

  // 一般ユーザー10人
  const users = Array.from({ length: 10 }, (_, i) => ({
    id: i + 2,
    ...createUser()
  }));
  await db.users.createMany(users);

  // 注文データ
  const orders = users.slice(0, 5).map(user => ({
    userId: user.id,
    amount: faker.number.int({ min: 100, max: 10000 }),
    status: 'completed'
  }));
  await db.orders.createMany(orders);
};

// テストで使用
beforeAll(async () => {
  await db.truncateAll();
  await seedTestData(db);
});

クリーンアップ戦略

🧹 クリーンアップの実装例 
// test-utils.ts
export const setupTestDatabase = () => {
  let transaction: Transaction;

  beforeEach(async () => {
    // トランザクション開始
    transaction = await db.beginTransaction();

    // シードデータ投入
    await seedTestData(db);
  });

  afterEach(async () => {
    // ロールバック（データを元に戻す）
    await transaction.rollback();
  });

  return { db, transaction };
};

// テストファイルで使用
describe('OrderService', () => {
  const { db } = setupTestDatabase();

  it('注文を作成できる', async () => {
    const order = await orderService.create({
      userId: 1,
      amount: 1000
    });

    expect(order.id).toBeDefined();
    // afterEachでロールバックされる
  });
});
🔍 コードレビューの観点
  • ハードコードされたテストデータ：ファクトリを使うべき
  • 固定ID依存：id=1 に依存するテストは脆い
  • クリーンアップ漏れ：テスト後にデータが残る
  • テスト間の依存：順番に依存していないか
