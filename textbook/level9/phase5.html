Site Reliability Engineeringとは

SRE（Site Reliability Engineering）は、Googleが2003年頃に提唱した考え方で、「ソフトウェアエンジニアリングのアプローチでインフラ運用の課題を解決する」という哲学です。 従来の「運用チーム」が手作業で対応していた仕事を、ソフトウェアで自動化し、スケーラブルに運用する方法論です。

SREの生みの親であるBen Treynorは「SREとは、ソフトウェアエンジニアに運用の仕事を任せたときに生まれるもの」と定義しています。 つまり、運用の問題をコードで解決するエンジニアがSREです。

🏠 たとえ話：工場の生産管理

工場で製品の品質を保つために、昔は熟練工が目視で検査していました。
SREは「検査を自動化する装置を設計・導入するエンジニア」のようなものです。
手作業の検査ではなく、仕組みで品質を保証するのがSREの本質です。

SREの主な原則

原則 内容
自動化の推進 手作業（Toil）を減らし、エンジニアリングに時間を使う
SLOベースの運用 サービスレベル目標を定め、データ駆動で判断する
エラーバジェット 100%の信頼性を目指さず、許容できる障害量を管理する
Toilの削減 繰り返しの手作業は50%以下に抑える
ブレームレス文化 障害の原因を「人」ではなく「仕組み」に求める

SREとDevOpsの違い

SRE
  • Googleが発祥の具体的な実践方法
  • SLI/SLO/エラーバジェットなど明確な指標
  • ソフトウェアエンジニアが運用を担当
  • 「class SRE implements DevOps」
DevOps
  • 開発と運用の壁を壊すための文化・思想
  • 具体的な指標の定義は含まれない
  • 開発者と運用者の協力を重視
  • より広い概念で組織文化に焦点

よく使われる表現に「class SRE implements DevOps」があります。 DevOpsという「インターフェース（考え方）」を、SREが「具体的なクラス（実装）」として実現するという意味です。

Toil（トイル）とは

SREにとって最大の敵はToil（トイル）です。 Toilとは「手作業で、繰り返しで、自動化可能で、戦略的価値がなく、サービスの成長に比例して増える作業」のことです。

Toilの例 自動化後
手動でのサーバー再起動 自動回復スクリプト
手動でのデプロイ作業 CI/CDパイプライン
アラートへの手動対応 自動修復ランブック
容量の手動調整 オートスケーリング
⚠️ Toilが50%を超えたら危険信号

GoogleのSREでは、エンジニアの作業時間の50%以上がToilになってはいけないというルールがあります。
Toilが増えすぎると、改善のためのエンジニアリング時間がなくなり、悪循環に陥ります。

❌ SREアンチパターン
  • SREチームを「運用チームの名前を変えただけ」にする
  • SLO/SLIを設定せずに「雰囲気」で運用する
  • 自動化をせずに手動オペレーションを続ける
  • 開発チームが信頼性に無関心で、SREに丸投げする

SLI・SLO・SLAとは

SREにおける信頼性管理の基本は、測る → 目標を決める → 約束するの3段階です。 これがSLI・SLO・SLAに対応します。

用語 正式名称 意味 例
SLI Service Level Indicator サービスの品質を測る指標 リクエスト成功率、レイテンシ
SLO Service Level Objective SLIに対する目標値 成功率 99.9%、P99 200ms以下
SLA Service Level Agreement 顧客との契約（違反時にペナルティ） 稼働率99.9%を下回ったら返金
🏠 たとえ話：宅配サービス

SLI = 「翌日に届いた荷物の割合」（実測データ）
SLO = 「翌日配達率95%を目指す」（社内目標）
SLA = 「翌日届かなかったら送料無料」（顧客との約束）
SLOはSLAよりも厳しく設定し、SLAに違反する前に対処するのがポイントです。

代表的なSLI

SLIの種類 測定内容 計算式
可用性（Availability） サービスが利用可能な割合 成功リクエスト数 / 全リクエスト数
レイテンシ（Latency） レスポンスの速さ P50, P95, P99の応答時間
スループット（Throughput） 処理能力 単位時間あたりの処理数
エラー率（Error Rate） エラーの発生割合 エラー数 / 全リクエスト数

「ナインの数」を理解する

信頼性は「9がいくつ並ぶか」で表現します。 9が1つ増えるごとに、許容されるダウンタイムが10分の1になります。

可用性 ナイン数 年間ダウンタイム 月間ダウンタイム
99% 2ナイン 3.65日 7.3時間
99.9% 3ナイン 8.76時間 43.8分
99.99% 4ナイン 52.6分 4.38分
99.999% 5ナイン 5.26分 26.3秒

SLO設計テンプレート

# SLO定義テンプレート

サービス名: ユーザー認証API
SLOウィンドウ: 30日間ローリング

## SLI/SLO定義

### 可用性
- SLI: 成功レスポンス(2xx, 3xx) / 全リクエスト
- SLO: 99.9%（月間ダウンタイム上限: 約43分）
- 測定方法: ロードバランサーのアクセスログ

### レイテンシ
- SLI: レスポンスタイム
- SLO: P50 ≤ 100ms, P99 ≤ 500ms
- 測定方法: APMツール（Datadog/New Relic）

### エラー率
- SLI: 5xxレスポンス / 全リクエスト
- SLO: 0.1%以下
- 測定方法: アプリケーションログ

## アクション
- SLO違反時: 新機能開発を停止し信頼性改善に注力
- エラーバジェット消費75%: 警告アラート発火
- エラーバジェット消費100%: フリーズ期間開始
⚠️ SLO設定のよくある失敗
  • 「とりあえず99.99%」と根拠なく高い目標を設定する
  • SLIの測定ポイントがユーザー視点ではなくサーバー内部になっている
  • SLOを設定したが、誰も見ていない・判断に使っていない
  • SLAとSLOを同じ値にして、バッファがない
❌ 100%の信頼性を目指してはいけない

100%の信頼性は不可能であり、目指すべきでもありません。
100%を目指すと、リリース速度が極端に遅くなり、ユーザーにとっての価値（新機能）が届かなくなります。
「十分な信頼性」を定義して、残りのリスクを許容するのがSREの考え方です。

エラーバジェット

  • イノベーション（新機能開発）と信頼性のバランス

エラーバジェットとは

エラーバジェットとは、「SLOを満たしながら許容できる障害の量」のことです。 例えば、SLOが99.9%なら、残りの0.1%が「使っていいエラーの予算」です。

この仕組みのおかげで、開発チームとSREチームの間で「どれだけリスクを取っていいか」を定量的に議論できるようになります。

🏠 たとえ話：家計の予算管理

月収30万円のうち、生活費（信頼性維持）に25万円必要だとすると、残り5万円が「自由に使えるお金（エラーバジェット）」です。
この5万円で旅行（新機能リリース）に使える。でも使い過ぎたら来月は節約（リリース凍結）する必要があります。
予算が残っているときは積極的にチャレンジし、使い切ったら守りに入るのがエラーバジェットの発想です。

エラーバジェットの計算

# エラーバジェットの計算例

SLO: 99.9%（可用性）
測定期間: 30日間

## 計算
許容エラー率 = 100% - 99.9% = 0.1%

月間リクエスト数: 1,000,000
エラーバジェット = 1,000,000 × 0.001 = 1,000リクエスト

## つまり
- 月に1,000リクエストまでエラーを出して良い
- 月間ダウンタイム換算: 約43分まで許容

## 現在の消費状況
今月のエラー数: 400リクエスト
消費率: 400 / 1,000 = 40%
残りバジェット: 600リクエスト（60%）

エラーバジェットポリシー

バジェット残量 状態 アクション
75%以上 余裕あり 積極的にリリース、新機能開発を推進
50〜75% 注意 リリース頻度を維持しつつ、慎重に判断
25〜50% 警告 リスクの高いリリースを延期、信頼性改善を優先
25%未満 危険 新機能リリースを凍結、信頼性改善に全力
0%（枯渇） フリーズ バグ修正とインフラ改善のみ許可

エラーバジェットが生む対話

バジェットが余っている時
  • 開発チーム「リスクある機能だけどリリースしたい」
  • SRE「バジェット残ってるからGO。ただしロールバック手順は用意してね」
  • 結果: イノベーションが加速する
バジェットが枯渇している時
  • 開発チーム「この機能を今週リリースしたい」
  • SRE「バジェット使い切ったので、まず信頼性を改善しよう」
  • 結果: 感情論ではなくデータで判断できる
⚠️ エラーバジェットの落とし穴
  • バジェットが常に余っている → SLOが緩すぎる可能性がある
  • バジェットが常にゼロ → SLOが厳しすぎるか、根本的な品質問題がある
  • バジェット消費の原因分析をしない → 同じ問題が繰り返される
❌ エラーバジェットのアンチパターン
  • エラーバジェットを無視して、とにかくリリースを強行する
  • バジェットが枯渇しても誰も責任を持たない
  • SLOを意図的に下げて、バジェットを水増しする
  • エラーバジェットを「罰則の仕組み」として使い、チームを萎縮させる

障害対応フロー

📚 このページで学ぶこと
  • 障害対応の4フェーズ：検知→トリアージ→対応→復旧
  • 各フェーズで行うべきアクションと判断基準
  • 復旧優先（Mitigation First）の原則

障害対応の全体像

障害が発生した時、パニックにならず冷静に対応するために、あらかじめ決められたフローに従うことが重要です。 SREでは「検知 → トリアージ → 対応 → 復旧」の4段階で障害対応を行います。

🏠 たとえ話：消防署の出動

火災報知器が鳴る（検知）→ 火災の規模を確認（トリアージ）→ 消火活動（対応）→ 鎮火確認と安全確保（復旧）
消防士は「まず火を消す」ことに集中します。出火原因の調査は鎮火後です。
同じように、障害対応中は「まず復旧」が最優先です。原因調査は後で行います。

Phase 1: 検知（Detection）

検知方法 内容 特徴
監視アラート モニタリングツールが異常を検出 最速・自動的
ユーザー報告 ユーザーからの問い合わせやSNS投稿 検知が遅い・影響大
内部発見 開発者やQAが偶然発見 不定期・属人的

Phase 2: トリアージ（Triage）

検知した障害の影響範囲と緊急度を判断し、対応の優先度を決定します。 

# トリアージチェックリスト

□ 影響を受けているユーザー数は？
  - 全ユーザー / 特定地域 / 特定機能のユーザー

□ ビジネスへの影響は？
  - 売上に直結 / 代替手段あり / 影響軽微

□ 拡大の可能性は？
  - 時間とともに悪化 / 一定 / 収束傾向

□ 既知の問題か？
  - 過去のインシデントと類似 / 新しいタイプの障害

□ 対応可能なメンバーは？
  - 即座に対応可能 / エスカレーション必要

Phase 3: 対応（Mitigation）

最重要原則：まず復旧（Mitigation First）
原因調査より先に、ユーザーへの影響を止めることを最優先にします。

対応手段 内容 時間目安
ロールバック 直前の安定版に戻す 数分
フィーチャーフラグOFF 問題のある機能を無効化 即座
スケールアウト サーバー台数を増やす 数分〜
トラフィック制御 レートリミットや一部遮断 即座
ホットフィックス 最小限のコード修正をデプロイ 数十分〜

Phase 4: 復旧（Recovery）

# 復旧確認チェックリスト

□ サービスの正常稼働を確認
  - エラー率が通常レベルに戻った
  - レイテンシが正常範囲内
  - ユーザーからの報告が止まった

□ 再発防止の暫定措置
  - 一時的な制限事項の記録
  - 監視強化（閾値の一時的な引き下げ）

□ コミュニケーション
  - ステータスページの更新
  - 関係者への報告
  - ユーザーへの復旧告知

□ Post-mortem準備
  - タイムラインの記録
  - ログ・メトリクスの保全
  - Post-mortem会議のスケジュール設定
⚠️ 障害対応中にやりがちなミス
  • 原因調査に時間を使いすぎて、復旧が遅れる
  • 対応状況を共有せず、各自がバラバラに動く
  • 「もう少しで原因が分かる」と楽観視して判断が遅れる
  • エスカレーションを躊躇して、一人で抱え込む
❌ 絶対にやってはいけないこと
  • 障害中に原因と無関係な変更（新機能デプロイ等）を行う
  • ログを消す・証拠を隠す
  • 障害を報告せずに隠蔽しようとする
  • 「犯人探し」をして個人を責める

なぜインシデント指揮が必要か

大規模な障害が発生すると、多くのエンジニアが関与します。 指揮系統がないと「全員が原因調査をしていて、誰もユーザー対応をしていない」といった混乱が起きます。 インシデント指揮（Incident Command System）は、この混乱を防ぐための仕組みです。

🏠 たとえ話：災害対策本部

大きな地震が起きた時、自衛隊・消防・警察がバラバラに動いたら大混乱です。
災害対策本部が設置され、本部長が全体を指揮し、各部隊に役割を割り振ることで効率的な救助が可能になります。
ITインシデントでも同じ。インシデントコマンダーが全体を指揮します。

インシデント対応の主要ロール

ロール 役割 主な責任
インシデントコマンダー（IC） 全体指揮 意思決定、リソース配分、エスカレーション判断
コミュニケーションリード 社内外への情報発信 ステータスページ更新、経営層への報告、顧客対応
オペレーションリード 技術的な対応の指揮 障害調査の指示、復旧作業の実行と監督
スクライブ（記録係） タイムラインの記録 発言・判断・アクションを時系列で記録
サブジェクトマターエキスパート（SME） 専門知識の提供 該当システムの技術的知見を提供

インシデントコマンダーの心得

# インシデントコマンダー行動指針

## やるべきこと
- 全体の状況を把握し続ける（鳥の目）
- 定期的に状況を要約して共有する（5〜10分ごと）
- 判断に迷ったらエスカレーションする
- 各担当者に明確なタスクを割り振る
- 「次の報告は○分後」とタイムボックスを設定する

## やってはいけないこと
- 自分で手を動かして調査・修復する（指揮に専念）
- 一人で判断を抱え込む
- 声の大きい人の意見に流される
- 犯人探しを始める

War Roomの運営

War Roomとは、重大インシデント発生時に関係者が集まる場所（物理的な会議室またはオンライン通話）です。

項目 内容
参加者 IC、各リード、必要なSME（必要最小限のメンバー）
コミュニケーション 専用のSlackチャンネルまたはビデオ通話
更新頻度 重大インシデントは15分ごとにステータス更新
終了条件 ICが「インシデント終了」を宣言するまで継続
⚠️ インシデント指揮の失敗パターン
  • インシデントコマンダーが自ら技術調査を始めてしまい、指揮がおろそかになる
  • 全員がWar Roomに集まり、実際に手を動かす人がいなくなる
  • 情報共有が口頭のみで、後から何が起きたか分からなくなる
  • エスカレーション基準が曖昧で、判断が遅れる
❌ 指揮系統のアンチパターン
  • 「一番声が大きい人」がなし崩し的にICになる
  • 経営層がWar Roomに入って技術的な指示を出す
  • 誰がICか分からない状態で対応が始まる
  • ICが交代なしで何時間も対応を続ける

Post-mortemとは

Post-mortem（ポストモーテム）とは、インシデント発生後に行う振り返りのことです。 「なぜ起きたのか」「どうすれば防げたか」「何を学んだか」を整理し、同じ障害を二度と起こさないための仕組みです。

最も重要なのはブレームレス（Blameless）であること。 「誰が悪いか」ではなく「仕組みのどこに問題があったか」にフォーカスします。

🏠 たとえ話：航空事故調査

航空業界では事故が起きると、パイロットを処罰するのではなく、なぜ事故が起きたかを徹底的に調査します。
「パイロットがボタンを押し間違えた」で終わらず、「なぜ押し間違えやすいデザインだったのか」「訓練は十分だったか」「疲労管理は適切だったか」まで掘り下げます。
この文化があるからこそ、航空業界は極めて高い安全性を実現しています。

ブレームレス文化の本質

ブレームレスな対応
  • 「なぜこの変更がレビューで見逃されたのか？」
  • 「テストカバレッジが不足していた部分はどこか？」
  • 「アラートが遅れた原因は監視設定のどこにあるか？」
  • 「同様の事故を仕組みで防ぐには何が必要か？」
ブレームフルな対応（NG）
  • 「誰がこのコードを書いた？」
  • 「なぜ確認しなかったのか？」
  • 「もっと注意すべきだった」
  • 「二度とこんなミスをしないように」

5 Whys（なぜなぜ分析）

根本原因を掘り下げるために、「なぜ？」を5回繰り返す手法です。 表面的な原因ではなく、構造的・仕組みの問題にたどり着くことが目的です。 

# 5 Whys 分析例：本番DBのデータが消えた

Why 1: なぜデータが消えた？
→ 開発者がDELETE文を本番DBで実行した

Why 2: なぜ本番DBで実行できた？
→ 開発者が本番DBの接続情報を持っていた

Why 3: なぜ開発者が本番の接続情報を持っていた？
→ アクセス権限の分離ができていなかった

Why 4: なぜ権限分離ができていなかった？
→ 環境分離のポリシーが未整備だった

Why 5: なぜポリシーが未整備だった？
→ 初期開発のまま運用が成長し、ガバナンスが追いつかなかった

## 根本原因
環境分離とアクセス制御のポリシーが未整備

## 対策
1. 本番DB接続をBastion経由の承認制に変更
2. 開発・ステージング・本番の接続情報を完全分離
3. 破壊的SQLの実行にダブルチェック機構を導入

On-call運用

📚 このページで学ぶこと
  • On-callローテーションの設計と運用
  • エスカレーションパスの設計方法
  • On-callエンジニアの燃え尽き防止策

On-callとは

On-callとは、サービスに障害が発生した際に、勤務時間外でも対応できるエンジニアを常に確保する仕組みです。 24時間365日稼働するサービスでは不可欠な体制です。

🏠 たとえ話：病院の当直医

病院では夜間でも患者を受け入れるために、当直医がいます。
当直医は全ての病気を治すのではなく、緊急対応（応急処置）を行い、翌日の専門医に引き継ぎます。
同様に、On-callエンジニアはサービスの復旧（応急処置）を行い、根本対応は翌営業日のチームに引き継ぎます。

ローテーション設計

項目 推奨値 理由
シフト期間 1週間交代 2週間以上は燃え尽きリスクが高い
最小チーム人数 最低6人 6人で6週に1回の担当。これ以下は過負荷
プライマリ/セカンダリ 2名体制 プライマリが対応不能時のバックアップ
応答時間SLO 5〜15分 アラート受信からアクション開始まで
引き継ぎ 週明けの朝 対面/オンラインで未解決事項を共有

エスカレーションパス

# エスカレーションパス例

Level 1: On-callプライマリ（5分以内に応答）
  ↓ 対応不能 or 15分経過
Level 2: On-callセカンダリ（5分以内に応答）
  ↓ 対応不能 or 重大インシデント判定
Level 3: チームリード/テックリード（判断・追加リソース投入）
  ↓ Sev1判定
Level 4: エンジニアリングマネージャー（組織横断の対応）
  ↓ ビジネスクリティカル
Level 5: VP/CTO（経営判断が必要な場合）

## エスカレーション基準
- Sev1: 全ユーザー影響 → 即座にLevel 3以上
- Sev2: 一部ユーザー影響 → 30分で解決しない場合Level 3
- Sev3: 軽微な影響 → 翌営業日対応でもOK

燃え尽き防止策

対策 内容
代休の保証 深夜対応があった場合は翌日休暇を取得可能
On-call手当 On-call担当期間中の追加手当を支給
ノイズアラートの削減 対応不要なアラートを継続的に減らす
ランブック整備 対応手順を文書化し、誰でも対応可能にする
振り返り On-call中のアラート数・深夜対応数をトラッキング
⚠️ On-callの危険信号
  • On-call中に毎晩アラートで起こされる → アラート設計を見直す
  • 対応不要な（ノイジーな）アラートが多すぎる → アラート疲れの原因
  • 特定の人だけがOn-callを担当している → チーム全体で分担する
  • ランブックがなく、属人的な知識が必要 → 手順書を整備する
❌ On-callアンチパターン
  • On-callを「新人の修行」として押し付ける
  • 深夜対応後も通常勤務を強要する
  • アラート疲れを「根性論」で乗り越えさせる
  • On-callの負荷を測定・可視化しない
❓ 確認クイズ

障害レベル分類

📚 このページで学ぶこと
  • Severity（重要度）レベルの定義と分類基準
  • 各レベルに応じた対応SLAとエスカレーション基準
  • 正確なSeverity判定のためのフレームワーク

なぜ障害レベル分類が必要か

全ての障害に同じ対応をしていては、リソースが足りません。 影響度に応じて対応のレベルを変えることで、効率的かつ適切な障害対応が可能になります。 「障害レベル＝どれだけ真剣に対応するか」の基準です。

🏠 たとえ話：病院のトリアージ

救急外来では、患者の重症度によって優先順位をつけます。
心臓が止まっている人（Sev1）と、指を切った人（Sev4）では対応が全く違います。
ITシステムも同じ。全面ダウンとUI崩れでは、対応の緊急度が全く異なります。

Severityレベル定義

レベル 名称 定義 例
Sev1 Critical サービス全体のダウン、データ損失 全ユーザーがログインできない、決済不能
Sev2 Major 主要機能の障害、多数ユーザーに影響 検索機能が動かない、特定地域でアクセス不能
Sev3 Minor 一部機能の障害、限定的な影響 レポート出力が遅い、画像が表示されない
Sev4 Low 軽微な問題、ユーザー影響なし 管理画面のUI崩れ、ログの警告メッセージ

各レベルの対応SLA

レベル 初動開始 ステータス更新 目標復旧時間 Post-mortem
Sev1 5分以内 15分ごと 1時間以内 必須（48時間以内）
Sev2 15分以内 30分ごと 4時間以内 必須（1週間以内）
Sev3 1時間以内 1日ごと 翌営業日 推奨
Sev4 翌営業日 完了時 次スプリント 不要

Severity判定フレームワーク

# Severity判定フローチャート

1. ユーザーへの影響は？
   ├── 全ユーザー影響 → Sev1候補
   ├── 多数ユーザー影響 → Sev2候補
   ├── 一部ユーザー影響 → Sev3候補
   └── ユーザー影響なし → Sev4候補

2. ビジネスへの影響は？
   ├── 売上/収益に直結 → 1レベル上げる
   ├── ブランド/信頼に影響 → 1レベル上げる
   └── 影響軽微 → そのまま

3. データへの影響は？
   ├── データ損失あり → Sev1
   ├── データ不整合あり → 最低Sev2
   └── データ影響なし → そのまま

4. 代替手段は？
   ├── なし → 1レベル上げる
   └── あり → そのまま

最終判定: 上記を総合してSeverityを決定
迷ったら1つ上のレベルを選択する

エスカレーション基準

レベル 通知先 エスカレーション条件
Sev1 On-call全員、マネージャー、VP 発生と同時に全レベルにエスカレーション
Sev2 On-call、チームリード 30分で解決しない場合マネージャーへ
Sev3 On-call 翌営業日までに解決しない場合チームリードへ
Sev4 チームチャンネル 通常のバグとして処理
⚠️ Severity判定の注意点
  • 迷ったら高いレベルを選ぶ（過小評価は過大評価より危険）
  • 対応中にSeverityが変わることがある（状況に応じて再判定する）
  • 「いつも全部Sev1」にしない（オオカミ少年になる）
  • Sev1判定を恐れて低く見積もらない
❌ 障害レベル分類のアンチパターン
  • Severityの定義が曖昧で、判定者によってバラバラになる
  • 政治的な理由でSeverityを操作する（Sev1を避けたい等）
  • Sev1なのにエスカレーションせず、一人で対応しようとする
  • Severity定義を作ったが、誰も知らない・覚えていない
❓ 確認クイズ

障害のSeverity判定で迷った場合、最も適切な行動はどれですか？

DR/BCP

📚 このページで学ぶこと
  • 災害復旧計画（DR）と事業継続計画（BCP）の違い
  • RPO（目標復旧時点）とRTO（目標復旧時間）の設計
  • DR/BCPの策定と訓練の実践方法

DR/BCPとは

DR（Disaster Recovery：災害復旧）は、災害時にITシステムを復旧するための計画です。 BCP（Business Continuity Plan：事業継続計画）は、災害時にも事業を継続するための包括的な計画です。 DRはBCPの一部であり、IT面に特化しています。

🏠 たとえ話：家の防災計画

DR = 「家が地震で壊れた時に、どこに避難してどう生活を再建するか」
BCP = 「地震で家が壊れても、仕事を続けて収入を維持する計画」
RPO = 「家族のアルバムをどこまで遡って保存しているか（バックアップの頻度）」
RTO = 「避難してから通常の生活に戻るまでの目標時間」

RPOとRTO

指標 正式名称 意味 例
RPO Recovery Point Objective 「どの時点まで」のデータを復旧するか RPO=1時間 → 最大1時間分のデータ損失を許容
RTO Recovery Time Objective 「どのくらいの時間で」復旧するか RTO=4時間 → 4時間以内にサービス復旧

DRの戦略パターン

戦略 RTO コスト 説明
バックアップ&リストア 数時間〜数日 低 バックアップからデータを復元する
パイロットライト 数十分〜数時間 中低 最小構成のシステムを常時稼働
ウォームスタンバイ 数分〜数十分 中高 縮小版のシステムを別リージョンで稼働
マルチサイトアクティブ ほぼゼロ 高 複数リージョンで同時に稼働（Active-Active）

DR/BCP計画テンプレート

# DR/BCP計画書

## 1. 基本情報
対象システム: ユーザー向けWebアプリケーション
RPO: 1時間
RTO: 4時間
DR戦略: ウォームスタンバイ

## 2. 前提条件
- プライマリ: ap-northeast-1（東京）
- セカンダリ: ap-northeast-3（大阪）
- データベース: クロスリージョンレプリカ設定済み

## 3. 発動条件
- プライマリリージョン全体の障害
- データセンター火災/自然災害
- 長時間（2時間以上）の復旧見込みなし

## 4. 復旧手順
Step 1: DR発動の判断（CTO承認）
Step 2: DNSフェイルオーバー実行
Step 3: セカンダリリージョンのスケールアップ
Step 4: データ整合性の確認
Step 5: サービス復旧確認

## 5. 連絡体制
- 一次連絡: インシデントコマンダー → SREチーム
- 二次連絡: SREチーム → 開発チーム・CS
- 三次連絡: 経営層 → 広報・顧客

## 6. 訓練計画
- 机上訓練: 四半期に1回
- 実地訓練: 半年に1回（実際にフェイルオーバー実行）
効果的なDR/BCP
  • 定期的にDR訓練を実施し、手順を検証済み
  • RPO/RTOが実際に達成可能な値に設定されている
  • バックアップからの復旧を定期的にテスト済み
  • DR計画が最新の状態に保たれている
形骸化したDR/BCP
  • 計画書を作ったが、一度も訓練していない
  • RPO/RTOが根拠なく設定され、達成不可能
  • バックアップは取っているが、復元テストをしていない
  • 2年前に作った計画書がそのまま放置されている
⚠️ バックアップの落とし穴
  • バックアップを取っていたが、復元できなかった（復元テスト未実施）
  • バックアップの暗号化キーが失われた
  • バックアップ先が本番と同じリージョンにあり、同時に被災した
  • バックアップの頻度が不十分で、RPOを満たせなかった
❌ DR/BCPのアンチパターン
  • 「うちには災害なんて来ない」と計画を立てない
  • 計画は立てたが訓練をしない（いざという時に動けない）
  • DR環境のメンテナンスを怠り、本番との差異が広がる
  • RPO/RTOを「ゼロ」に設定し、コストが青天井になる
❓ 確認クイズ

カオスエンジニアリング

📚 このページで学ぶこと
  • カオスエンジニアリングの概念と目的
  • Chaos Monkey・Game Dayなどの実践手法
  • 安全に障害注入テストを行うための原則

カオスエンジニアリングとは

カオスエンジニアリングとは、本番環境で意図的に障害を起こし、システムの耐障害性を検証する手法です。 Netflixが2010年にChaos Monkeyを開発したことで広く知られるようになりました。

「障害は必ず起きる」という前提に立ち、予期せぬ障害が起きる前に、計画的に障害を起こして弱点を見つけるというアプローチです。

🏠 たとえ話：避難訓練

学校で行う避難訓練は「実際に地震が起きたとき、パニックにならずに避難できるか」を確認するためのものです。
カオスエンジニアリングも同じ。「実際に障害が起きたとき、システムは正しく動くか」を事前に確認します。
避難訓練で「非常口が開かない」と分かれば、本番前に修理できます。

カオスエンジニアリングの原則

原則 内容
仮説を立てる 「サーバー1台が落ちても、ユーザーには影響しないはず」等
本番環境で実験する ステージング環境だけでは本当の耐障害性は分からない
影響範囲を限定する いきなり全体に影響する実験はしない（ブラストラディウスを制御）
自動化する 定期的に実行し、継続的に耐障害性を検証する
すぐに止められるようにする 実験が予想外の結果を生んだら即座に中断

代表的なカオスエンジニアリングツール

ツール/手法 開発元 内容
Chaos Monkey Netflix ランダムにサーバーインスタンスを停止
Chaos Kong Netflix リージョン全体を無効化
Litmus CNCF Kubernetes環境向けのカオス実験フレームワーク
Gremlin Gremlin Inc. 商用カオスエンジニアリングプラットフォーム
AWS Fault Injection Simulator AWS AWS環境での障害注入サービス

Game Day（障害訓練）

Game Dayは、チーム全体で障害シナリオを実行し、対応力を検証する訓練です。 避難訓練のIT版であり、定期的に実施することが重要です。 

# Game Day 実施テンプレート

## 基本情報
実施日: 2024-XX-XX
参加者: SREチーム、バックエンドチーム
シナリオ: データベースのプライマリがダウンした場合

## 準備
1. 仮説を立てる
   - 「フェイルオーバーが自動で完了し、30秒以内に復旧するはず」
2. ロールバック手順を確認
   - 実験が失敗した場合の復旧手順を用意
3. 影響範囲を限定
   - カナリア環境のみで実施 or トラフィックの5%で実施
4. 監視体制を強化
   - 追加のダッシュボード、リアルタイム監視の準備

## 実施
1. 障害注入の実行
2. システムの挙動を観察
3. 仮説との差異を記録
4. 問題があれば即座に中止

## 振り返り
- 仮説は正しかったか？
- 予想外の挙動はあったか？
- 改善すべき点は何か？
- 次回のGame Dayテーマは？

段階的な導入ステップ

段階 内容 リスク
Level 1 開発環境で障害注入テスト リスクなし
Level 2 ステージング環境でGame Day 低リスク
Level 3 本番の一部トラフィックで実験 中リスク（制御下）
Level 4 本番で自動的にChaos実験を実行 中〜高リスク（成熟したチーム向け）
⚠️ カオスエンジニアリングの前提条件
  • 十分な監視・可観測性が整っていること（何が起きたか把握できる）
  • 障害を即座に止められる仕組みがあること（キルスイッチ）
  • チームがインシデント対応に慣れていること（基本ができていないのに応用は危険）
  • 経営層やステークホルダーの理解と承認があること
❌ カオスエンジニアリングのアンチパターン
  • 監視体制が不十分なのに本番で障害注入する
  • 仮説なしに「とりあえずサーバーを落としてみる」
  • 影響範囲を制御せず、全ユーザーに影響を与える
  • Game Dayの結果を放置し、発見した弱点を修正しない
  • 「カオスエンジニアリングやってます」とアピールするが、実態は雑な障害テスト
❓ 確認クイズ

カオスエンジニアリングを安全に実施するために最も重要なのはどれですか？
