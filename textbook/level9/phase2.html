なぜブランチ戦略が必要か

チーム開発では、複数人が同時にコードを変更します。 ブランチ戦略は「誰が・いつ・どこで変更を加え・どうやって統合するか」のルールを定めることで、混乱を防ぎます。

🏠 たとえ話：交通ルール

ブランチ戦略は道路の交通ルールに似ています。ルールがなければ車（開発者）は好き勝手に走り、衝突（コンフリクト）が頻発します。 交通ルール（ブランチ戦略）を決めることで、全員が安全に目的地（リリース）に到達できます。

Git Flow

Git Flowは、Vincent Driessen が提唱した古典的なブランチモデルです。 main、develop、feature、release、hotfix の5種類のブランチを使います。

ブランチ 役割 寿命
main 本番リリース済みコード 永続
develop 次回リリースの開発統合 永続
feature/* 個別機能の開発 一時的
release/* リリース準備（QA・バグ修正） 一時的
hotfix/* 本番の緊急修正 一時的 
# Git Flow の基本操作
git checkout develop
git checkout -b feature/user-auth

# 開発完了後
git checkout develop
git merge --no-ff feature/user-auth
git branch -d feature/user-auth

# リリース準備
git checkout -b release/1.2.0 develop
# QA・修正後
git checkout main
git merge --no-ff release/1.2.0
git tag -a v1.2.0 -m "Release 1.2.0"
git checkout develop
git merge --no-ff release/1.2.0

GitHub Flow

GitHub Flowはシンプルさを重視した戦略です。 main ブランチと短命な feature ブランチだけで運用します。

✓ GitHub Flow のルール
  1. main は常にデプロイ可能な状態を保つ
  2. 作業は main から分岐したブランチで行う
  3. こまめにプッシュしてPRを作成する
  4. レビュー・承認後に main へマージ
  5. マージ後すぐにデプロイ
# GitHub Flow の基本操作
git checkout main
git pull origin main
git checkout -b feature/add-search

# 開発＆プッシュ
git add .
git commit -m "feat: 検索機能を追加"
git push -u origin feature/add-search

# GitHub上でPR作成 → レビュー → マージ → デプロイ

Trunk-based Development

Trunk-based Developmentは、全員が main（trunk）に直接・または極めて短命なブランチで統合する戦略です。 CI/CDが成熟したチームで採用されます。

特徴 Git Flow GitHub Flow Trunk-based
ブランチ数 多い（5種類） 少ない（2種類） 最小（1〜2種類）
マージ頻度 低い 中程度 高い（1日複数回）
リリースサイクル 計画的リリース 継続的デプロイ 継続的デプロイ
向いている規模 大規模・計画的 中小規模・Web CI/CD成熟チーム
学習コスト 高い 低い 中程度
⚠️ アンチパターン：戦略なしの開発

ブランチ戦略を決めずに開発を始めると、長寿命ブランチが乱立し、マージが困難になります。 プロジェクト開始時に必ずチームで合意しましょう。

PRサイズの重要性

PRのサイズはレビューの質に直結します。 小さなPRはレビューしやすく、バグの発見率が高くなります。

🏠 たとえ話：引っ越しの荷物

巨大なPRは、引っ越し時にすべてを1つの段ボールに詰め込むようなもの。重すぎて運べず、中身の確認も困難です。 適切なサイズに分けることで、効率的に運び・確認できます。

PRサイズ 変更行数目安 レビュー品質 マージまでの時間
XS 〜50行 非常に高い 数時間
S 50〜200行 高い 半日〜1日
M 200〜400行 中程度 1〜2日
L 400行〜 低下しがち 数日以上
❌ 巨大PRのリスク
  • レビュアーが疲弊し「LGTM」で通してしまう
  • バグの見落としが増える
  • コンフリクトの発生確率が上がる
  • ロールバックが困難になる

コードレビューの目的

📚 このページで学ぶこと
  • コードレビューが品質向上に果たす役割
  • 知識共有・チーム力向上への貢献
  • 設計改善のきっかけとしてのレビュー

コードレビューとは何か

コードレビューは、他の開発者が書いたコードを確認し、問題点の指摘や改善提案を行うプロセスです。 単なるバグ探しではなく、チーム全体の成長に直結する重要な活動です。

🏠 たとえ話：原稿の校正

コードレビューは本の校正に似ています。著者（開発者）は自分の文章（コード）の誤りに気づきにくいものです。 第三者の目（レビュアー）が入ることで、誤字脱字（バグ）だけでなく、文章の分かりやすさ（可読性）や論理の一貫性（設計）も改善されます。

目的1：品質向上

品質の側面 レビューで検出できること
正確性 ロジックの誤り、エッジケースの見落とし
安全性 セキュリティ脆弱性、権限チェック漏れ
効率性 N+1クエリ、不要なループ
可読性 命名の不統一、複雑すぎるロジック

目的2：知識共有

レビューを通じて、チームメンバーは担当外の領域のコードに触れる機会を得ます。 これによりバス係数（特定の人が抜けた時のリスク）が改善されます。

✓ 知識共有の効果
  • 特定の人に依存しない体制が構築される
  • チーム全体のスキルレベルが底上げされる
  • 新メンバーのオンボーディングが加速する
  • コーディングスタイルがチーム内で統一される

目的3：設計改善

実装前のレビュー（設計レビュー）だけでなく、コードレビューの段階でも設計の問題を発見できます。 「この責務は別クラスに分けるべきでは？」「この処理はもっとシンプルにできるのでは？」といった視点がコード品質を高めます。

⚠️ アンチパターン：形骸化したレビュー
  • 中身を見ずに「LGTM」を出す
  • スタイルの指摘ばかりで本質的な問題を見ない
  • 「忙しいから」とレビューを後回しにし続ける
  • レビューを「承認のための儀式」として扱う

レビュー観点の体系化

📚 このページで学ぶこと
  • セキュリティ観点でのレビューポイント
  • パフォーマンス観点でのレビューポイント
  • 保守性・可読性の観点でのレビューポイント

なぜ観点を体系化するか

レビューの観点を明確にしないと、レビュアーの経験や気分に依存した場当たり的なレビューになります。 チェックリスト化することで、品質のばらつきを減らせます。

セキュリティ観点

❌ 見逃しやすいセキュリティ問題
  • SQLインジェクション：ユーザー入力を直接クエリに埋め込んでいないか
  • XSS：ユーザー入力を無害化せずにHTMLに出力していないか
  • 認証・認可：適切な権限チェックがあるか
  • 機密情報：APIキーやパスワードがハードコードされていないか
  • 依存関係：脆弱性のあるライブラリを使っていないか
// セキュリティ：SQLインジェクションの例

// ❌ 危険：文字列結合でクエリを組み立て
const query = `SELECT * FROM users WHERE name = '${userInput}'`;

// ✅ 安全：パラメータ化クエリを使用
const query = 'SELECT * FROM users WHERE name = $1';
const result = await db.query(query, [userInput]);

パフォーマンス観点

観点 チェック内容
N+1クエリ ループ内でDBクエリを発行していないか
不要な再レンダリング React等でメモ化が必要な箇所はないか
大量データ処理 ページネーションやストリーミングを使っているか
キャッシュ 頻繁にアクセスされるデータをキャッシュしているか
インデックス 検索条件のカラムにインデックスがあるか

保守性・可読性観点

観点 チェック内容
命名 変数名・関数名が意図を正確に表しているか
関数サイズ 1つの関数が大きすぎないか（目安：30行以内）
単一責任 クラスや関数が1つのことだけを担当しているか
コメント 「なぜ」を説明するコメントがあるか
テスト 変更に対応するテストが追加・更新されているか
体系的なレビュー
レビューチェックリスト:
☐ セキュリティ: 入力検証あり
☐ パフォーマンス: N+1なし
☐ 可読性: 命名が適切
☐ テスト: カバレッジ維持
☐ エラー処理: 例外を適切に処理
場当たり的なレビュー
「なんとなくコードを眺めて...」
「見た感じ問題なさそう...」
「スタイルが気になるな...」
→ 重大な問題を見逃すリスク大

建設的なフィードバック

📚 このページで学ぶこと

  • 具体性のあるフィードバックの書き方
  • 代替案を添えた提案型レビューの実践

建設的なフィードバックとは

レビューは人ではなくコードに対して行うものです。 建設的なフィードバックとは、問題を指摘するだけでなく、なぜ問題なのかを説明し、改善の方向性を示すことです。

🏠 たとえ話：料理のアドバイス

「まずい」と言われても何を直せばいいか分かりません。 「塩が少し足りないので、小さじ1/2追加するとバランスが良くなるかも」と言われれば、具体的に改善できます。 コードレビューも同様に、「何が」「なぜ」問題で「どうすれば」良くなるかを伝えましょう。

指摘のレベル分け

プレフィックス 意味 対応
[must] 修正必須（バグ・セキュリティ問題） マージ前に対応が必要
[should] 強く推奨する改善 理由があればスキップ可
[nit] 細かい指摘（スタイル等） 対応は任意
[question] 理解のための質問 回答のみでOK
[praise] 良い実装への称賛 対応不要

具体的なフィードバックの書き方

建設的なフィードバック
[must] この箇所でSQLインジェクションの
リスクがあります。ユーザー入力を直接
クエリに埋め込んでいるため、
パラメータ化クエリを使用しましょう:

const result = await db.query(
  'SELECT * FROM users WHERE id = $1',
  [userId]
);

[nit] 変数名 `d` だと意味が分かり
にくいので `deliveryDate` はどうで
しょう？

[praise] このエラーハンドリングの
パターン、とても分かりやすいです！
非建設的なフィードバック
「ここ間違ってます」
→ 何が間違いかわからない

「こんなコード書かないでください」
→ 人格否定に近い

「なんでこうしたの？」
→ 詰問調で萎縮させる

「LGTM」（中身を見ていない）
→ レビューの意味がない

レビューを受ける側の心構え

✓ レビューを受けるときのポイント
  • 指摘はコードに対するもので、自分への攻撃ではない
  • なぜそう書いたかの理由を説明する
  • 「確かにそうですね」と素直に受け入れる柔軟さを持つ
  • 不明点は「もう少し詳しく教えてください」と聞く
⚠️ 避けるべきレビューの伝え方
  • 「普通はこうする」「常識でしょ」など相手を見下す表現
  • 疑問形での間接的な否定（「これで本当に動くの？」）
  • 代替案なしの否定だけの指摘
  • 大量の nit 指摘で本質的な問題を埋もれさせること

3つのマージ戦略

PRをマージする際、Git/GitHub では主に3つの方法を選べます。 それぞれ履歴の残り方が異なります。

🏠 たとえ話：日記の書き方

Mergeは日記に「今日○○ブランチの内容を取り込んだ」と記録を残す方法。 Squashは細かい下書きをまとめて清書する方法。 Rebaseは最初からこの順番で書いていたかのように並べ直す方法です。

Merge Commit（--no-ff）

# マージコミットを作成
git checkout main
git merge --no-ff feature/user-auth

# 履歴イメージ：
#   *   Merge branch 'feature/user-auth'  ← マージコミット
#   |\
#   | * feat: バリデーション追加
#   | * feat: ログイン画面実装
#   |/
#   * 前のコミット

Squash Merge

# 全コミットを1つにまとめてマージ
git checkout main
git merge --squash feature/user-auth
git commit -m "feat: ユーザー認証機能を追加"

# 履歴イメージ：
#   * feat: ユーザー認証機能を追加  ← 1つにまとまる
#   * 前のコミット

Rebase Merge

# ブランチのコミットをmainの先頭に付け替え
git checkout feature/user-auth
git rebase main
git checkout main
git merge feature/user-auth

# 履歴イメージ：
#   * feat: バリデーション追加     ← 直線的な履歴
#   * feat: ログイン画面実装
#   * 前のコミット

比較表

特徴 Merge Squash Rebase
履歴の詳細度 全コミット保持 1コミットに集約 全コミット保持
履歴の形 分岐あり 直線的 直線的
マージ元の追跡 容易 困難 困難
git bisect 詳細に追跡可 粒度が粗い 詳細に追跡可
推奨シーン 大規模・厳密な追跡 小PR・クリーンな履歴 直線的な履歴を好む
⚠️ Rebase の注意点

共有ブランチ（mainやdevelop）をrebaseしてはいけません。 他の人が参照しているコミットの履歴が書き換わり、チーム全体に影響します。 Rebaseは自分のfeatureブランチに対してのみ使いましょう。

コンフリクト解決

📚 このページで学ぶこと
  • マージコンフリクトの仕組みと読み方
  • コンフリクト解決の手順とコツ
  • 意味的コンフリクトの概念と予防策

マージコンフリクトとは

マージコンフリクトは、同じファイルの同じ箇所を複数の人が異なる方法で変更した場合に発生します。 Gitが自動でマージできないため、人間が判断して解決する必要があります。

🏠 たとえ話：共同編集の衝突

2人が同じ文書の同じ段落を同時に書き換えた場合、どちらの版を採用すべきか自動では判断できません。 2人で話し合い「Aさんの表現を採用しつつ、Bさんの追記も含める」のように解決するのがコンフリクト解消です。

コンフリクトマーカーの読み方

# コンフリクトが発生したファイルの内容
<<<<<<< HEAD
const MAX_RETRIES = 5;
=======
const MAX_RETRIES = 10;
>>>>>>> feature/increase-retry

# 読み方：
# <<<<<<< HEAD      → 現在のブランチ（マージ先）の内容
# =======          → 区切り
# >>>>>>> feature/  → マージ元ブランチの内容

コンフリクト解決の手順

# 1. コンフリクトの確認
git status
# → both modified: src/config.ts

# 2. ファイルを編集してコンフリクトを解決
#    マーカーを削除し、正しいコードに修正する
const MAX_RETRIES = 10;  # 適切な方を選択

# 3. 解決済みとしてマーク
git add src/config.ts

# 4. マージを完了
git commit -m "merge: feature/increase-retry のコンフリクトを解決"
✓ コンフリクト解決のコツ
  • 解決前に両方の変更の意図を理解する（git log で経緯を確認）
  • 変更者本人に確認を取る（判断に迷った場合）
  • 解決後に必ずテストを実行する
  • エディタやツール（VS Code等）のコンフリクト解決UIを活用する

意味的コンフリクト

意味的コンフリクトは、Gitが検出できないコンフリクトです。 ファイルの異なる箇所を変更した場合、Git上はコンフリクトになりませんが、論理的に矛盾が生じることがあります。

❌ 意味的コンフリクトの例 
// Aさん: 関数名を変更（utils.ts）
// getUserName → fetchUserName に変更

// Bさん: 同じ関数を呼び出すコードを追加（page.ts）
// const name = getUserName(id);  ← 古い名前で呼んでいる

// → Gitではコンフリクトにならないが、
//   マージ後にランタイムエラーが発生する
⚠️ 意味的コンフリクトの予防策
  • マージ後に必ずCI（テスト・ビルド）を実行する
  • TypeScriptなどの型チェックで早期に検出する
  • 短命なブランチを使い、こまめにマージする
  • 関連する変更は同じPRにまとめる
❓ 確認クイズ

意味的コンフリクトについて正しい説明はどれ？

PRとCIの関係

CI（継続的インテグレーション）をPRと連携させることで、 人間がレビューする前に自動的にコードの品質をチェックできます。 これにより、レビュアーはロジックや設計に集中できます。

🏠 たとえ話：入場ゲート

CIは空港のセキュリティゲートのようなものです。 乗客（コード）が搭乗（マージ）する前に、自動的にチェック（テスト・リント・ビルド）を行います。 ゲートを通過できないコードはマージできません。

GitHub Actions でのCI設定

# .github/workflows/ci.yml

ステータスチェックとブランチ保護

GitHub のブランチ保護ルールを使うと、CIが成功しない限りマージできないように制御できます。

保護ルール 効果
Require status checks to pass 指定したCIジョブが成功しないとマージ不可
Require branches to be up to date ベースブランチの最新をマージしてからでないとマージ不可
Require pull request reviews 指定人数のApproveがないとマージ不可
Require conversation resolution レビューコメントが全て解決済みでないとマージ不可 
# gh CLI でブランチ保護を確認
gh api repos/{owner}/{repo}/branches/main/protection

# ステータスチェックの結果を確認
gh pr checks <PR番号>

CI連携のベストプラクティス

✓ 効果的なCI構成
  • 高速なチェック（lint、型チェック）を先に実行する
  • テストの並列実行でCI時間を短縮する
  • キャッシュ（node_modules等）を活用する
  • PRごとにプレビュー環境をデプロイする
❌ やってはいけないCI運用
  • CIが失敗してもマージを許可する設定
  • 不安定なテスト（Flaky Test）を放置する
  • CIの実行時間が長すぎて開発者が待てない（目安：10分以内）
  • ブランチ保護なしでmainへの直接プッシュを許可する

自動レビューツール

📚 このページで学ぶこと

  • reviewdog によるリント結果のPRコメント化
  • GitHub Actions を使った自動レビューの構築

自動レビューツールとは

自動レビューツールは、人間のレビュアーに代わって機械的にチェック可能な項目を自動で指摘するツールです。 スタイルの統一やルール違反の検出を自動化することで、レビュアーが本質的な問題に集中できるようになります。

🏠 たとえ話：スペルチェッカー

文章を書く時、スペルチェッカーが自動で誤字を指摘してくれます。 校正者（レビュアー）はスペルミスを探す手間が省け、文章の内容や論理構成に集中できます。 自動レビューツールはコードにおけるスペルチェッカーです。

Danger.js

Danger.jsは、PRのメタ情報（変更行数、変更ファイル、説明文など）を元にルールベースのチェックを行うツールです。 

// dangerfile.ts
import { danger, warn, fail, message } from 'danger';

// PRの説明が空の場合に警告
if (!danger.github.pr.body || danger.github.pr.body.length < 10) {
  warn('PRの説明を記載してください。');
}

// PRが大きすぎる場合に警告
const bigPRThreshold = 500;
if (danger.github.pr.additions + danger.github.pr.deletions > bigPRThreshold) {
  warn('PRの変更が500行を超えています。分割を検討してください。');
}

// テストファイルの追加を確認
const hasTestChanges = danger.git.modified_files
  .some(f => f.includes('.test.') || f.includes('.spec.'));
const hasSrcChanges = danger.git.modified_files
  .some(f => f.includes('src/'));

if (hasSrcChanges && !hasTestChanges) {
  warn('ソースコードの変更がありますが、テストが更新されていません。');
}

// package.json の変更時にlockfileも更新されているか
const packageChanged = danger.git.modified_files.includes('package.json');
const lockfileChanged = danger.git.modified_files.includes('package-lock.json');

if (packageChanged && !lockfileChanged) {
  fail('package.json が変更されていますが、package-lock.json が更新されていません。');
}

reviewdog

reviewdogは、リンターやフォーマッターの出力をPRのインラインコメントとして投稿するツールです。 

# .github/workflows/reviewdog.yml
name: reviewdog

on:
  pull_request:

jobs:
  eslint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: '20'

      - run: npm ci

      - uses: reviewdog/action-eslint@v1
        with:
          reporter: github-pr-review
          eslint_flags: 'src/'

  actionlint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: reviewdog/action-actionlint@v1
        with:
          reporter: github-pr-review

ペアプロ / モブプロ

📚 このページで学ぶこと
  • ペアプログラミングとモブプログラミングの違い
  • リアルタイムレビューとしての効果
  • 知識共有を加速させる実践方法

ペアプログラミングとは

ペアプログラミングは、2人の開発者が1つの画面で一緒にコードを書く手法です。 1人が「ドライバー」（キーボードを操作）、もう1人が「ナビゲーター」（方向性を指示・レビュー）を担当します。

🏠 たとえ話：ラリーのドライバーとコドライバー

ラリー競技では、ドライバーが運転し、コドライバーが地図を読んでコースを指示します。 2人が協力することで、1人では辿り着けない速さと正確さで目的地に到達できます。 ペアプロも同様に、2人の力を合わせてより良いコードをより速く書きます。

モブプログラミングとは

モブプログラミングは、チーム全員（3人以上）が1つの画面で一緒にコードを書く手法です。 ドライバーが交代しながら進めます。

特徴 ペアプロ モブプロ
参加人数 2人 3人以上（チーム全員）
役割 ドライバー＋ナビゲーター ドライバー＋残り全員がナビゲーター
適したシーン 通常の開発タスク、メンタリング 設計判断、複雑な問題、オンボーディング
コスト感 2人分の時間 チーム全員の時間
知識共有の範囲 2人間 チーム全体

リアルタイムレビューとしての効果

ペアプロ/モブプロはリアルタイムのコードレビューです。 コードを書いている瞬間にフィードバックを受けるため、後からPRレビューで大幅な修正が必要になることが減ります。

✓ ペアプロ/モブプロのメリット
  • 品質向上：2つ以上の目でリアルタイムにチェック
  • 知識共有：暗黙知が自然に伝播する
  • 集中力：1人で作業するより集中を維持しやすい
  • 設計の合意：その場で議論・合意できる
  • オンボーディング：新メンバーが実践的に学べる

効果的な実践方法

プラクティス 説明
ポモドーロ 25分作業 + 5分休憩のリズムで進める
ドライバー交代 15〜30分ごとにドライバーを交代する
Ping-Pong テスト→実装を交互に担当する（TDDと組み合わせ）
Strong-style 「アイデアはナビゲーターの口を通り、ドライバーの手を通る」

⚠️ ペアプロ/モブプロの注意点
  • 全ての作業にペアプロが必要なわけではない（ルーチンタスクは1人で可）
  • ドライバーが一方的に進めず、ナビゲーターに考える時間を与える
  • 疲労を考慮し、長時間の連続セッションは避ける
  • 性格や好みを尊重し、強制しない
ペアプロに適した場面
  • 複雑なバグの調査・修正
  • 新しい技術・アーキテクチャの導入
  • 新メンバーのオンボーディング
  • 重要な設計判断を伴う実装
  • セキュリティに関わるコード
ペアプロに不向きな場面
  • 単純なリファクタリング作業
  • ドキュメントの更新
  • 依存関係のアップデート
  • 個人の調査・プロトタイピング
  • 定型的なCRUD実装
