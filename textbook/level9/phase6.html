監視（Monitoring）とオブザーバビリティの違い

監視（Monitoring）は「既知の問題を検知する」仕組みです。 CPUが90%を超えたらアラート、ディスクが満杯になったらアラート—— あらかじめ何を見るか決めておく必要があります。

一方、オブザーバビリティ（Observability）は 「未知の問題を調査・解明できる能力」です。 システムの外部出力（ログ・メトリクス・トレース）から、 内部状態を推測し、今まで見たことのない問題にも対処できます。

🏠 たとえ話：車のダッシュボード

監視は「エンジン警告灯が点灯したら異常」というアプローチ。 オブザーバビリティは「速度計・回転数・燃料計・油温計など あらゆる計器を見て、なぜエンジンの調子が悪いのかを 自分で分析できる」アプローチです。

観点 監視（Monitoring） オブザーバビリティ
目的 既知の問題を検知する 未知の問題も調査・解明できる
アプローチ 何を見るか事前に決める 任意の質問をデータに投げられる
データ 定義済みのメトリクス ログ・メトリクス・トレースの組合せ
対象 単一サービス向き 分散システム・マイクロサービス向き
問いかけ 「この値は正常か？」 「なぜこの問題が起きたのか？」

オブザーバビリティの3本柱

オブザーバビリティは3種類のテレメトリデータで構成されます。 これらを組み合わせることで、システムの内部状態を包括的に把握できます。

柱 内容 具体例
ログ（Logs） 個別のイベント記録。いつ何が起きたか エラーメッセージ、リクエスト内容、処理結果
メトリクス（Metrics） 数値の時系列データ。傾向を把握 レスポンスタイム、エラー率、CPU使用率
トレース（Traces） リクエストの処理経路。どこで時間がかかったか API→DB→キャッシュの処理フロー 
// 3本柱の活用例：「APIが遅い」という問題の調査

// 1. メトリクスで傾向を確認
//    → レスポンスタイムのp99が3秒を超えている

// 2. トレースで遅い箇所を特定
//    → データベースクエリに2.5秒かかっている

// 3. ログで根本原因を調査
//    → 「Full table scan on users table」が記録されている
//    → インデックスが欠落していた！
⚠️ アンチパターン：1つの柱だけに頼る
  • ログだけ → 全体の傾向やパフォーマンスの変化が見えない
  • メトリクスだけ → 「何が起きたか」の詳細がわからない
  • トレースだけ → 全リクエストを記録するとコストが膨大に
  • 3つを組み合わせて初めてオブザーバビリティが実現する

テキストログの限界

従来のテキストログは人間が読むには便利ですが、 機械的な解析やフィルタリングが困難です。 構造化ログはJSON形式でデータを記録し、検索・集計を容易にします。

テキストログ
2024-01-15 10:30:45 ERROR
  Failed to process order
  #12345 for user john_doe:
  payment timeout
構造化ログ（JSON）
{
  "timestamp": "2024-01-15T10:30:45Z",
  "level": "error",
  "message": "Failed to process order",
  "order_id": "12345",
  "user_id": "john_doe",
  "error_type": "payment_timeout",
  "duration_ms": 30000,
  "service": "order-service"
}

ログレベルの使い分け

レベル 用途 例
FATAL アプリケーションが停止するレベルの致命的エラー データベース接続不能で起動失敗
ERROR 処理が失敗した。対応が必要 決済処理のタイムアウト
WARN 想定外だが処理は継続できる リトライで成功、非推奨APIの利用
INFO 正常な処理の記録 ユーザーログイン、注文完了
DEBUG 開発・調査時の詳細情報 SQLクエリの内容、変数の値

コンテキスト付与のベストプラクティス

// Node.js + pino による構造化ログの実装例
const pino = require('pino');
const logger = pino({
  level: process.env.LOG_LEVEL || 'info',
  formatters: {
    level: (label) => ({ level: label }),
  },
  timestamp: pino.stdTimeFunctions.isoTime,
});

// リクエストごとにコンテキストを付与
function createRequestLogger(req) {
  return logger.child({
    request_id: req.headers['x-request-id'],
    user_id: req.user?.id,
    method: req.method,
    path: req.url,
    ip: req.ip,
  });
}

// 使用例
app.post('/orders', (req, res) => {
  const log = createRequestLogger(req);

  log.info({ order_data: req.body }, 'Order creation started');

  try {
    const order = createOrder(req.body);
    log.info({ order_id: order.id }, 'Order created successfully');
    res.json(order);
  } catch (err) {
    log.error({
      error_type: err.constructor.name,
      error_message: err.message,
      stack: err.stack,
    }, 'Order creation failed');
    res.status(500).json({ error: 'Internal error' });
  }
});
❌ アンチパターン：ログの落とし穴
  • 個人情報をログに出力：パスワード、クレジットカード番号をそのまま記録
  • ログレベルが全部INFO：重要度が分からず、エラーが埋もれる
  • メッセージだけで文脈なし：「エラーが発生しました」だけでは調査不能
  • 大量のDEBUGログを本番で有効化：パフォーマンス低下とコスト増大
✓ 良い構造化ログの条件
  • 一貫したフィールド名：userId vs user_id のばらつきをなくす
  • リクエストIDの伝播：分散システム全体で同一リクエストを追跡
  • 機密情報のマスキング：個人情報は自動的に除去・マスク
  • 適切な粒度：必要な情報を過不足なく記録

REDメソッドとUSEメソッド

メトリクスを「何でも計測する」のではなく、 フレームワークに従って設計することで、 重要な指標を漏れなくカバーできます。

メソッド 対象 指標 説明
RED サービス（リクエスト駆動型） Rate（レート） 1秒あたりのリクエスト数
Errors（エラー） 失敗したリクエストの割合
Duration（所要時間） リクエストの処理にかかった時間
USE リソース（CPU、メモリ、ディスク等） Utilization（使用率） リソースがどの程度使用されているか
Saturation（飽和度） リソースがどの程度逼迫しているか
Errors（エラー） リソース関連のエラー数

Prometheusのメトリクスタイプ

タイプ 用途 例
Counter 単調増加する累積値 リクエスト総数、エラー総数
Gauge 増減する現在値 CPU使用率、メモリ使用量、接続数
Histogram 値の分布（バケット） レスポンスタイムの分布
Summary 値の分布（分位数） p50, p90, p99レスポンスタイム 
# Prometheus メトリクス定義の例（prometheus.yml + アプリケーション側）

# --- prometheus.yml ---
global:
  scrape_interval: 15s
  evaluation_interval: 15s

scrape_configs:
  - job_name: 'api-server'
    static_configs:
      - targets: ['api-server:9090']
    metrics_path: '/metrics'

  - job_name: 'node-exporter'
    static_configs:
      - targets: ['node-exporter:9100']

# --- アプリケーション側（Node.js + prom-client）---
const client = require('prom-client');

// REDメソッドに基づくメトリクス定義

// Rate: リクエスト数（Counter）
const httpRequestsTotal = new client.Counter({
  name: 'http_requests_total',
  help: 'Total number of HTTP requests',
  labelNames: ['method', 'path', 'status_code'],
});

// Errors: エラー数（Counter）
const httpErrorsTotal = new client.Counter({
  name: 'http_errors_total',
  help: 'Total number of HTTP errors',
  labelNames: ['method', 'path', 'error_type'],
});

// Duration: レスポンス時間（Histogram）
const httpRequestDuration = new client.Histogram({
  name: 'http_request_duration_seconds',
  help: 'HTTP request duration in seconds',
  labelNames: ['method', 'path'],
  buckets: [0.01, 0.05, 0.1, 0.5, 1, 2, 5, 10],
});
⚠️ アンチパターン：カーディナリティ爆発

ラベルにユーザーIDやリクエストIDのような高カーディナリティ値を 使うと、時系列データが爆発的に増加し、ストレージとクエリ性能に深刻な影響を与えます。

  • 悪い例：labelNames: ['user_id']（ユーザー数だけ時系列が増える）
  • 良い例：labelNames: ['method', 'status_code']（有限な組み合わせ）
  • ラベルの組み合わせが1000を超えないかを常に意識する

なぜ分散トレーシングが必要か

マイクロサービスアーキテクチャでは、1つのリクエストが 複数のサービスをまたいで処理されます。 問題が発生したとき、どのサービスのどの処理で遅延やエラーが起きたのかを 追跡するのが分散トレーシングの役割です。

🏠 たとえ話：宅配便の追跡番号

荷物を送るとき、追跡番号を使えば「今どこにあるか」「どの中継地点を通ったか」が分かります。 分散トレーシングのトレースIDはまさにこの追跡番号。 リクエストがどのサービスを通り、各地点でどれだけ時間がかかったかを記録します。

トレースの構成要素

用語 説明 例
Trace 1つのリクエストの全体的な処理の流れ ユーザーが注文を完了するまでの一連の処理
Span Trace内の1つの処理単位 API呼び出し、DBクエリ、キャッシュ参照
Trace ID Trace全体を一意に識別するID abc123def456
Span ID 個別のSpanを識別するID span-001, span-002
Parent Span あるSpanの呼び出し元のSpan APIハンドラ → DBクエリの親子関係 
// トレースの視覚的なイメージ
// Trace ID: abc-123
//
// [API Gateway]──────────────────────────── 250ms
//   └─[Order Service]────────────────────── 200ms
//       ├─[User Service]─────── 30ms
//       ├─[Inventory Service]── 50ms
//       └─[Payment Service]──────────────── 120ms
//           └─[DB Query]──────── 80ms  ← ボトルネック！

OpenTelemetryの設定

// OpenTelemetry SDK の設定例（Node.js）
// tracing.js - アプリケーション起動前にロードする

const { NodeTracerProvider } = require('@opentelemetry/sdk-trace-node');
const { SimpleSpanProcessor } = require('@opentelemetry/sdk-trace-base');
const { OTLPTraceExporter } = require('@opentelemetry/exporter-trace-otlp-http');
const { Resource } = require('@opentelemetry/resources');
const { SemanticResourceAttributes }
  = require('@opentelemetry/semantic-conventions');
const { HttpInstrumentation }
  = require('@opentelemetry/instrumentation-http');
const { ExpressInstrumentation }
  = require('@opentelemetry/instrumentation-express');
const { registerInstrumentations }
  = require('@opentelemetry/instrumentation');

// プロバイダー設定
const provider = new NodeTracerProvider({
  resource: new Resource({
    [SemanticResourceAttributes.SERVICE_NAME]: 'order-service',
    [SemanticResourceAttributes.SERVICE_VERSION]: '1.0.0',
    environment: process.env.NODE_ENV,
  }),
});

// エクスポーター設定（Jaeger/Zipkin/OTLPコレクターへ送信）
const exporter = new OTLPTraceExporter({
  url: 'http://otel-collector:4318/v1/traces',
});

provider.addSpanProcessor(new SimpleSpanProcessor(exporter));
provider.register();

// 自動計装の有効化
registerInstrumentations({
  instrumentations: [
    new HttpInstrumentation(),
    new ExpressInstrumentation(),
  ],
});
❌ アンチパターン：トレーシングの落とし穴
  • 全リクエストをトレース：サンプリングなしだとコストとパフォーマンスに影響
  • コンテキスト伝播の漏れ：非同期処理やメッセージキューでトレースが途切れる
  • Spanの粒度が粗すぎる：サービス単位だけでは問題箇所が特定できない
  • トレースデータの保持期間が短すぎる：過去の問題を調査できない

アラート設計

  • アラート疲れ（Alert Fatigue）の原因と対策

症状ベース vs 原因ベース

アラートの設計で最も重要なのは、「何に対してアラートを出すか」です。 Google SREの原則では、症状ベース（Symptom-based）のアラートが推奨されています。

原因ベース（非推奨）
  • CPU使用率が90%超えたら
  • メモリ使用量が80%超えたら
  • 特定のプロセスが停止したら
  • → ユーザーに影響がない場合でも通知される
症状ベース（推奨）
  • エラー率が1%を超えたら
  • レスポンスタイムp99が2秒超えたら
  • 注文成功率が99%を下回ったら
  • → ユーザーに影響がある問題だけ通知

アラート疲れ（Alert Fatigue）

アラート疲れとは、アラートが多すぎて重要な通知が埋もれてしまう状態です。 「オオカミ少年」効果で、本当に重要なアラートも無視されるようになります。

原因 問題 対策
閾値が低すぎる 正常な変動でもアラート発生 過去データに基づく適切な閾値設定
同一障害で複数アラート 1つの問題で大量通知 アラートのグルーピング・抑制
対処不要なアラート 自動復旧する問題でも通知 アクション不要ならアラートにしない
未分類のアラート 重要度が不明で全部同じに見える 重要度レベルの分類（P1〜P4）

良いアラートの条件

# Prometheus Alerting Rules の設定例

groups:
  - name: api-alerts
    rules:
      # 症状ベース：エラー率が高い
      - alert: HighErrorRate
        expr: |
          sum(rate(http_requests_total{status_code=~"5.."}[5m]))
          /
          sum(rate(http_requests_total[5m]))
          > 0.01
        for: 5m  # 5分間持続した場合のみ発火
        labels:
          severity: critical
        annotations:
          summary: "API error rate is above 1%"
          description: "Error rate: {{ $value | humanizePercentage }}"
          runbook_url: "https://wiki.example.com/runbooks/high-error-rate"

      # 症状ベース：レスポンスが遅い
      - alert: HighLatency
        expr: |
          histogram_quantile(0.99,
            rate(http_request_duration_seconds_bucket[5m])
          ) > 2
        for: 10m
        labels:
          severity: warning
        annotations:
          summary: "API p99 latency is above 2 seconds"
          runbook_url: "https://wiki.example.com/runbooks/high-latency"
✓ 良いアラートのチェックリスト
  • アクション可能：受け取った人が何をすべきか明確
  • Runbook付き：対処手順のドキュメントへのリンクがある
  • 適切な宛先：対処できるチームに通知される
  • 重複排除：同じ問題で何度もアラートを出さない
  • 持続条件あり：一瞬のスパイクでは発火しない（for句）
⚠️ アンチパターン：アラート設計のNG
  • 「とりあえず全部アラート」→ 対処すべきものが分からない
  • Runbook（対処手順書）がない → 夜中に起こされても何もできない
  • アラートの見直しをしない → 誰も見ないアラートが放置される
  • 重要度の区別がない → 全部がcriticalで本当の緊急事態が埋もれる

4つのゴールデンシグナル

Google SREが提唱する4つのゴールデンシグナルは、 あらゆるサービスの健全性を測る基本的な指標です。 ダッシュボードは、まずこの4つを表示することから始めましょう。

シグナル 内容 表示例
レイテンシ リクエストの処理にかかる時間 p50/p90/p99のレスポンスタイム推移グラフ
トラフィック システムへの需要量 RPM（リクエスト/分）の時系列グラフ
エラー 失敗したリクエストの割合 HTTP 5xxの割合、ステータスコード分布
サチュレーション リソースの逼迫度合い CPU/メモリ/ディスク使用率、キュー長

ダッシュボードのターゲットと構成

ダッシュボードは見る人によって最適なデザインが異なります。 1つのダッシュボードにすべてを詰め込むのではなく、 用途別に分けることが重要です。

種類 対象者 目的 表示内容
概要 マネージャー、ステークホルダー 全体の健全性を一目で把握 SLI/SLO、全体エラー率、可用性
サービス別 開発チーム 担当サービスの詳細状態 4ゴールデンシグナル、デプロイ履歴
インフラ SRE / インフラチーム 基盤リソースの監視 CPU/メモリ/ディスク/ネットワーク
障害対応 オンコール担当 問題の迅速な特定 直近のエラー、異常メトリクス、関連ログ

❌ アンチパターン：ダッシュボード設計のNG
  • 情報過多：1画面に50個のグラフを詰め込んで何も読み取れない
  • 文脈なしの数値：「85%」が良いのか悪いのか判断できない（閾値の明示が必要）
  • 作って放置：古いメトリクスが残り、現状と合わないダッシュボード
  • 誰向けか不明：技術者用と経営層用を同一ダッシュボードに混在
✓ 良いダッシュボードの原則
  • 5秒ルール：5秒で「正常か異常か」が判断できる
  • ドリルダウン可能：概要→詳細へ掘り下げられる構造
  • アノテーション：デプロイや障害のタイムスタンプを表示
  • 閾値の可視化：正常範囲と異常範囲を色分け

APM（Application Performance Management）

📚 このページで学ぶこと
  • APMの役割と主要な機能
  • Datadog / New Relic などの主要APMツールの特徴
  • APMを使ったパフォーマンス問題の特定と改善

APMとは何か

APM（Application Performance Management）は、 アプリケーションのパフォーマンスをリアルタイムで監視・分析するツールです。 ログ・メトリクス・トレースを統合的に扱い、 コード レベルでのボトルネックを特定できます。

🏠 たとえ話：人間ドック

健康診断が「血圧・体重・血液検査」など複数の検査を組み合わせて 健康状態を総合的に判断するように、APMはアプリケーションの 「レスポンスタイム・エラー率・リソース使用量・依存関係」など を総合的に分析します。

APMの主要機能

機能 説明 活用場面
サービスマップ サービス間の依存関係と通信状態を可視化 影響範囲の把握、依存関係の整理
トランザクション分析 個別リクエストの処理内容を詳細に表示 遅いAPIの原因調査
エラー追跡 エラーの発生パターン、スタックトレースを集約 バグの優先順位付け
データベース分析 遅いクエリ、N+1問題の検出 DB起因のパフォーマンス改善
デプロイ追跡 デプロイ前後のパフォーマンス比較 リグレッションの早期発見

New Relic 使いやすいUI、フルスタック可視化 ユーザーあたり＋データ量課金 無料枠あり、初心者に親切
Grafana + Tempo OSS、カスタマイズ自由 インフラ費のみ（セルフホスト） Prometheus/Lokiと統合

ログ集約

なぜログ集約が必要か

複数のサーバーやコンテナで動くシステムでは、 ログが各ノードに分散しています。 問題が発生したとき、各サーバーにSSHしてログを確認するのは非効率で不可能に近い。 ログ集約は、すべてのログを1箇所に集めて検索・分析できるようにします。

🏠 たとえ話：図書館の蔵書管理

本が教室ごとにバラバラに置かれていたら、特定の本を探すのは大変です。 図書館のように1箇所に集め、分類・索引を付ければすぐに見つかります。 ログ集約は「ログの図書館」を作ることです。

監視コスト管理

📚 このページで学ぶこと
  • オブザーバビリティにかかるコストの構造と要因
  • ログ量削減・サンプリング・保持期間の最適化手法
  • コストと可観測性のバランスの取り方

監視コストが膨らむ理由

オブザーバビリティツールの費用は、主にデータ量に比例します。 マイクロサービス化・トラフィック増加に伴い、 ログ・メトリクス・トレースのデータ量は爆発的に増加しがちです。

コスト要因 内容 対策
ログ量 DEBUGログ、冗長なアクセスログ ログレベル管理、不要ログの除外
メトリクスの カーディナリティ ラベルの組み合わせが多すぎる 高カーディナリティラベルの排除
トレースの全量収集 全リクエストのトレースを保存 サンプリング戦略の導入
保持期間 古いデータを無期限に保持 段階的な保持ポリシー設定

サンプリング戦略

全データを収集・保存する必要はありません。 サンプリングを使って、コストを管理しながら必要な可観測性を維持します。

戦略 内容 適用場面
ヘッドサンプリング リクエストの開始時に収集するか決定（例：10%） シンプルなコスト削減
テールサンプリング 処理完了後に結果を見て収集するか決定 エラーや遅いリクエストは100%収集したい場合
優先度サンプリング 重要なエンドポイントは高い率で収集 決済系は100%、ヘルスチェックは0% 
# OpenTelemetry Collector のサンプリング設定例

# otel-collector-config.yaml
processors:
  # テールサンプリング：エラーや遅いリクエストは必ず収集
  tail_sampling:
    decision_wait: 10s
    policies:
      # エラーは100%収集
      - name: errors-policy
        type: status_code
        status_code:
          status_codes: [ERROR]

      # 2秒以上かかったリクエストは100%収集
      - name: latency-policy
        type: latency
        latency:
          threshold_ms: 2000

      # それ以外は10%サンプリング
      - name: default-policy
        type: probabilistic
        probabilistic:
          sampling_percentage: 10

  # ログのフィルタリング
  filter:
    logs:
      exclude:
        match_type: strict
        bodies:
          - "health check"  # ヘルスチェックログを除外

service:
  pipelines:
    traces:
      processors: [tail_sampling]
    logs:
      processors: [filter]

データ種別 ホット（高速） ウォーム（通常） コールド（低速） 削除
ログ 7日 30日 90日 90日超
メトリクス 30日（生データ） 90日（1分集約） 1年（1時間集約） 1年超
トレース 7日 30日 - 30日超
⚠️ アンチパターン：コスト管理の失敗
  • 「全部取っておけばいい」思考：データ量に比例してコストが増大し続ける
  • コスト可視化をしない：月末の請求書で初めてコスト増に気づく
  • サンプリングなしの全量収集：トラフィック増加でコストが線形に増加
  • コスト削減で必要なデータまで削除：障害時に調査できなくなる

可観測性文化

📚 このページで学ぶこと
  • チーム全体でオブザーバビリティを実践する文化の構築
  • SRE（Site Reliability Engineering）との連携方法
  • オブザーバビリティ成熟度モデルと段階的な導入

ツールだけでは不十分

最先端のAPMやログ集約基盤を導入しても、 チームがそれを日常的に活用しなければ意味がありません。 オブザーバビリティは「ツール」ではなく「文化」です。

🏠 たとえ話：健康管理の習慣

高性能な体組成計を買っても、毎日乗って記録し、 食事や運動を見直さなければ健康にはなりません。 オブザーバビリティも同じで、ツールを入れるだけでなく、 データを見て行動を変える習慣がなければ効果は出ません。

オブザーバビリティ成熟度モデル

レベル 段階 状態 次のステップ
Level 1 反応型 問題が起きてからサーバーにSSHしてログを見る ログ集約基盤の導入
Level 2 基本監視 基本的なメトリクス監視とアラートがある 構造化ログ、ダッシュボード整備
Level 3 統合型 ログ・メトリクス・トレースが統合されている SLI/SLO定義、チーム横断の活用
Level 4 予測型 データに基づいて問題を予防できる 自動対応、カオスエンジニアリング
Level 5 最適化型 全チームが自律的にオブザーバビリティを活用 継続的な改善と文化の深化

SRE連携のベストプラクティス

SRE（Site Reliability Engineering）チームは オブザーバビリティの推進役として重要な役割を果たします。 開発チームとSREが協力することで、信頼性の高いサービスを実現できます。

プラクティス 内容 効果
SLI/SLO の共同定義 開発チームとSREが一緒にサービスレベル目標を決める 品質基準の共通認識
ポストモーテム 障害後に全員で振り返り、再発防止策を立てる 組織学習、blame-free 文化
On-call ローテーション 開発者もオンコールに参加する 運用の理解促進、品質意識向上
エラーバジェット SLO未達時は新機能開発を止めて改善に集中 信頼性と開発速度のバランス
トイル削減 手作業の運用を自動化する 創造的な作業への時間確保

チームへの定着方法

// オブザーバビリティ文化を定着させるための具体的なアクション

// 1. 開発プロセスへの組み込み
//    - PR レビューにオブザーバビリティ観点を含める
//    - 新機能のDesign Docに「どう監視するか」のセクションを追加
//    - Definition of Done に「ダッシュボード更新」を含める

// 2. チーム習慣の確立
//    - 毎朝のスタンドアップでダッシュボードを確認
//    - 週次でSLI/SLOレビューを実施
//    - 月次でアラートの棚卸し（不要アラートの削除）

// 3. 知識共有
//    - 障害対応のRunbookを整備・更新
//    - ポストモーテムを全社に共有
//    - 新メンバーのオンボーディングに監視ツール研修を含める

// 4. 計測と改善
//    - MTTD（検知までの時間）を計測
//    - MTTR（復旧までの時間）を計測
//    - アラートの精度（偽陽性率）を追跡
❌ アンチパターン：文化構築の失敗
  • 「SREチームの仕事」と丸投げ：開発者が自分のサービスの監視に関心を持たない
  • ポストモーテムが犯人探し：blame-free でないと次回からインシデントが隠蔽される
  • トップダウンの押し付け：現場の課題に合わないツールや方針を強制する
  • 一度きりの取り組み：最初だけ盛り上がってすぐに形骸化する
✓ オブザーバビリティ文化の成功指標
  • 開発者がダッシュボードを日常的に見ている（「使われるダッシュボード」が存在する）
  • 新機能リリース時にログ・メトリクス・アラートがセットで実装される
  • 障害時にデータから問題を特定できる（「ログを見て分かりました」）
  • MTTD/MTTRが継続的に改善されている
  • チーム全員がSLI/SLOを理解し、説明できる
